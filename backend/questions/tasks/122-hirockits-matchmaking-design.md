## Что проверяем

Интервьюер ожидает кандидата, который сможет **челленджить его в архитектуре**. Задача уже спроектирована — важно понять, насколько кандидат думает в ту же сторону и может ли он предложить альтернативы или улучшения. Из 20+ кандидатов только один смог на уровне пообщаться по архитектуре.

Проверяется:
- Умение декомпозировать систему на микросервисы с чёткими зонами ответственности
- Понимание stateless vs stateful и влияния на масштабируемость
- Умение оставаться в рамках контекста своего сервиса, не лезть в чужие bounded context
- Обоснованный выбор технологий (почему Redis, а не Memcached/Cassandra — через понимание структур данных)

## Условие

Спроектировать систему матчмейкинга для платформы онлайн-шахмат (русский аналог chess.com). Полный жизненный цикл: от момента, когда пользователь нажимает кнопку "Играть", до завершения партии.

Клиент, шлюз, авторизация — всё это абстракции. Из абстракции на вход приходит `user_id`. Нужно спроектировать кусочек системы: подбор пары, создание и проведение матча.

## Функциональные требования

- Пользователь нажимает "Играть" — сообщение с `user_id` приходит в сервис матчмейкинга
- Подбор пары по **Elo-рейтингу**: игроки с примерно одинаковым рейтингом должны быть в паре (профессионал не должен играть с новичком)
- Если точного совпадения нет — постепенно расширять диапазон поиска
- Возможность **отмены** — пользователь нажимает "Отмена", его убирают из очереди
- После нахождения пары — создать матч (`match_id`), сгенерировать ссылку для обоих игроков
- Игроки подключаются к конкретному **игровому серверу** по **WebSocket**
- Игровой сервер репортит события в **менеджер матчей** по ходу игры
- **Reconnect**: если игрок отключился (браузер упал, компьютер выключился) — должен иметь возможность вернуться в игру, всё состояние загружается
- По завершении матча: очистить кэш, сохранить PGN (последовательность ходов), записать финальное состояние в БД, изменить статус матча на "завершён"
- Все события отправляются в **Kafka** для дальнейшей обработки (аналитика и т.д.)

## Дополнительные требования и аналитика

- **Зарегистрированных пользователей**: ~1 000 000
- **DAU**: ~50 000
- **Одновременных игр в моменте**: ~2 000
- Микросервисная архитектура
- Каждый сервис отвечает за свою масштабируемость и throughput
- Сервис матчмейкинга должен быть **stateless** (stateful сервис невозможно масштабировать)

## Подсказки интервьюера

- **"Клиент, шлюз — это абстракция. Из абстракции тебе на вход приходит user_id."** — не тратить время на auth, API gateway
- **"Рейтинг, а не ранг. Рейтинг нужен для Elo — чтобы у игроков примерно одинаковый Elo был."** — корректная терминология
- **"Должен быть сервис профилей, в который ходишь за рейтингом по user_id. Сам сервис профилей отвечает за свою масштабируемость — ты за это не отвечаешь."** — каждый микросервис владеет своим scaling
- **"Тогда у тебя получается stateful сервис, ты его не сможешь масштабировать."** — ключевой архитектурный хинт
- **"Ты пытаешься за пределы контекста выйти."** — оставаться в рамках своего bounded context

## Приемлемый вариант решения

### Компоненты

1. **Facade (API Gateway)** — внешний сервис, принимает запрос "хочу играть" из интернета

2. **Queue Service** — внутренний сервис с единственной ответственностью: принять запрос на постановку в очередь и принять запрос на отмену (удаление из очереди). Больше ничего не делает

3. **Redis (Sorted Sets)** — хранилище очереди. Игроки раскладываются в **бакеты по рейтингу**. Через sorted sets можно делать range-запрос: указать диапазон рейтинга и получить подходящую пару. Начинаем с узкого диапазона, расширяем пока не найдём совпадение

4. **Worker** — опрашивает кэш примерно **раз в секунду**, ищет пары. Когда пара найдена — уведомляет следующий сервис

5. **Match Manager** — создаёт матч (`match_id`), генерирует **ссылку на конкретный game server** (game server-ов много), сохраняет мета-информацию в **БД**, хранит текущее состояние игры в **кэше** (для reconnect). Получает события от game server-а по ходу партии. При завершении матча: очищает кэш, сохраняет PGN в **object storage (S3)**, обновляет статус в БД, отправляет все события в **Kafka**

6. **Game Server** — игроки подключаются по **WebSocket**. Каждое событие репортится в Match Manager

7. **Player Profile Service** — отдельный домен/bounded context. Имеет свой кэш (**80% cache hit rate**), свою БД. Обновления профилей приходят через **Kafka** и обрабатываются **consumer-ом асинхронно** — чтобы размазать нагрузку по времени и не создавать thundering herd

### Почему именно Redis

> "Когда тебя спрашивают 'а почему тут Redis, а не Memcached?', тебе нужно понимать, что в Redis есть разные структуры данных (set, sorted set и т.д.). Когда ты понимаешь, для чего нужны эти структуры, ты будешь понимать, для чего их можно применить — и это будет ответом на вопрос."

Redis Sorted Set — идеальная структура для матчмейкинга по рейтингу:
- `ZADD queue <elo_rating> <user_id>` — добавить в очередь
- `ZRANGEBYSCORE queue <min_elo> <max_elo> LIMIT 0 2` — найти пару в диапазоне рейтинга
- `ZREM queue <user_id>` — удалить (отмена)
- O(log N) на все операции

Memcached не подходит: нет sorted sets, нет range-запросов — только key-value.
