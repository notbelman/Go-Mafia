## Что проверяем

Кандидат понимает как построить распределенную масштабируемую систему и как ее мониторить.

## Условие

Проектируем Messenger Avito. Представим себе, что его сейчас нет, и нужно спроектировать Backend-часть.

Frontend/mobile часть не рассматриваем в деталях, но стоит держать в голове типичные юзкейсы (кнопка "Написать" на странице объявления, список чатов пользователя).

## Функциональные требования

- Отправить сообщение
- Принять и прочитать сообщение
- Чаты связаны с объявлениями пользователей, инициализация чата происходит при переходе с конкретного объявления по кнопке "Написать"
- Чаты являются peer-to-peer — для общения покупателя с продавцом
- Просмотр списка чатов (вскользь без проектирования самого API — обсуждаем в контексте шардирования, ключ шардирования не должен конфликтовать с требованием собрать список чатов)
- "Realtime" — сообщения должны доставляться от отправителя к получателю с задержкой до 3 секунд
- Дополнительно: пуш-уведомления
- Дополнительно: добавление картинок

## Дополнительные вводные от бизнеса

> Сразу не выкладывать, дать возможность соискателю самому спросить про это.

- 30 млн уникальных пользователей в месяц
- DAU 3 млн юзеров
- Активных объявлений — 100 млн
- Один юзер в среднем пишет по 3 чатам 10 сообщений в день
- В чате в среднем всего 10 сообщений, время активной переписки в чате — в среднем 7 дней
- На одно объявление в среднем приходится 10 чатов
- Средняя длина сообщения 50 символов, максимальная длина сообщения — 10 КБ
- В системе могут быть пользователи с большим количеством чатов (популярные продавцы, у которых много товаров и им пишут тысячи пользователей)

## Приемлемый вариант решения

### БД
- Обоснованный выбор СУБД
- Посчитана нагрузка на БД и объем хранимых данных
- Шардированная и реплицированная БД — все сообщения одного чата должны лежать в одном шарде для оптимального доступа. Соответственно сообщения можно шардировать либо по ID чата, либо подойдёт по связанному ID объявления (т.к. мы его знаем на старте чата при связке). Обсуждаемо — шардирование по пользователям, но с ним много подводных камней (отправитель/получатель, дублировать ли данные). Важно, чтобы кандидат аргументировал тот или иной вариант (на каких операциях поможет), и какие есть трейд-оффы. Шардирование по ID сообщения должно считаться однозначно плохим решением, увеличивающим нагрузку на систему
- Есть понимание, как делать решардинг

### Архитектура
- Обоснован выбор монолит/микросервисы, система декомпозирована на сервисы
- Сервисы развернуты в облаке, межсервисная балансировка запросов
- Желательно несколько ДЦ, пользователь направляется к ближайшему ДЦ
- Должно быть разделение, какие запросы можно делать "синхронными" через REST-like API (например, получение истории чата), а какие через websocket (отправка/получение сообщений для обеспечения realtime)
- Не должно быть необоснованных кэшей (в случае мессенджера они почти бесполезны)

### Метрики
- Какие метрики будет собирать
- Есть понимание, что такое перцентили
- Выбрано 5 метрик, позволяющих понимать состояние системы (ok/prefail/fail)
- Круто, если успели обсудить алертинг — по техническим и продуктовым метрикам, их просадка относительно "предыдущего" периода
