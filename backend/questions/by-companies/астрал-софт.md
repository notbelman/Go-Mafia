## Вопросы

### Docker / Helm / Nginx

#### 1. Приходилось ли вам самостоятельно настраивать Docker-образы и Helm-чарты?

Docker-образы — да, писал и правил Dockerfile для своих сервисов (multi-stage сборка, финальный образ на scratch). Helm-чарты — трогал по минимуму: мог поправить env-переменную или resource limits на стейдже, но владели чартами DevOps. Понимаю структуру чарта (templates, values.yaml, Chart.yaml), как работает `helm upgrade --install` и rollback.

**Теория — Helm:**
Helm — пакетный менеджер для Kubernetes. **Chart** — это набор шаблонов (Go templates) + values.yaml с параметрами. При `helm install` Helm рендерит шаблоны, подставляя значения из values, и отправляет готовые манифесты в K8s API. Helm хранит **release** — версионированный снапшот того, что задеплоено. Это позволяет делать `helm rollback` к предыдущей версии. Ключевые файлы: `Chart.yaml` (метаданные, зависимости), `values.yaml` (дефолтные параметры), `templates/` (шаблоны deployment, service, ingress и т.д.).

---

#### 2. Какие подходы вы использовали при сборке Docker-образов?

Multi-stage build. Первый стейдж — `golang:1.22-alpine`, собираем бинарник с `CGO_ENABLED=0 GOOS=linux`. Второй стейдж — `FROM scratch`, копируем только бинарник и TLS-сертификаты (`ca-certificates`). Итоговый образ ~20 МБ. `.dockerignore` чтобы не тащить `vendor`, `*.md`, `_test.go` в контекст сборки.

**Теория — Multi-stage build:**
Каждая инструкция `FROM` в Dockerfile начинает новый стейдж. Финальный образ содержит только то, что скопировано в последний стейдж — промежуточные стейджи (компиляторы, зависимости сборки) не попадают в итоговый образ. Это решает главную проблему: образ для сборки (нужен Go SDK, git, make) и образ для запуска (нужен только бинарник) — разные вещи.

`scratch` — пустой базовый образ, буквально 0 байт. Нет shell, нет libc, нет утилит. Подходит для статически слинкованных бинарников (Go с `CGO_ENABLED=0`). Минимальная attack surface — нечего эксплуатировать если контейнер скомпрометирован.

---

#### 3. Углублялись ли вы во внутренности Docker (например, слои, оптимизация образов)?

Понимаю механику слоёв и использую на практике для оптимизации кеша.

**Теория — слои Docker:**
Каждая инструкция в Dockerfile (`RUN`, `COPY`, `ADD`) создаёт отдельный **слой** — read-only файловую дельту. Слои кешируются: если инструкция и её контекст не изменились — слой берётся из кеша. Поэтому важен порядок инструкций: то что меняется редко — наверх, то что часто — вниз. Классический паттерн для Go:

```dockerfile
COPY go.mod go.sum ./       # меняется редко — зависимости закешируются
RUN go mod download
COPY . .                    # меняется часто — только этот слой пересобирается
RUN go build -o /app
```

Под капотом Docker использует **union filesystem** (overlay2 на Linux). Контейнер при запуске добавляет поверх read-only слоёв один writable слой. Все записи идут туда (copy-on-write). При удалении контейнера writable слой удаляется — образ не меняется.

#### 4. Как в Nginx настроить маршрутизацию между несколькими сервисами (контейнерами)?

**Теория — Nginx как reverse proxy:**
Nginx принимает входящие запросы и проксирует их на backend-сервисы по правилам маршрутизации. Ключевые директивы:

- **`upstream`** — определяет группу backend-серверов (с балансировкой: round-robin по умолчанию, `least_conn`, `ip_hash`)
- **`server`** — виртуальный хост, слушает порт, матчит домен через `server_name`
- **`location`** — правило маршрутизации по URL-пути
- **`proxy_pass`** — проксирует запрос в upstream

```nginx
upstream orders_backend {
    server orders-service:8080;
}
upstream tracking_backend {
    server tracking-service:8080;
}

server {
    listen 80;
    location /api/orders {
        proxy_pass http://orders_backend;
    }
    location /api/tracking {
        proxy_pass http://tracking_backend;
    }
}
```

В Kubernetes обычно используется **Ingress** (nginx ingress controller) — декларативное описание маршрутов через K8s-манифесты, без ручного редактирования nginx.conf. Ingress controller сам генерирует конфиг nginx из Ingress-ресурсов.

### Kubernetes / Observability

#### 5. Какие инструменты вы использовали для логирования?

На уровне приложения — **zap** (uber-go/zap). В hot path (Kafka consumer-ы, обработка телематических событий) — `Logger` без аллокаций. В менее нагруженных местах — `SugaredLogger`. Формат — JSON. Каждая строка содержит `trace_id`, `service`, `level`, `msg`. Инфраструктура — ELK стек: Fluent Bit → Elasticsearch → Kibana.

**Теория — zap и структурированное логирование:**
zap — высокопроизводительный логгер для Go. Два режима:
- **`Logger`** — строго типизированный, zero-allocation. Поля передаются через `zap.String("key", val)`, `zap.Int("count", n)`. Никаких `fmt.Sprintf` — всё пишется напрямую в буфер. Подходит для hot path где каждая аллокация = нагрузка на GC
- **`SugaredLogger`** — удобный API как у `fmt.Printf`, но с аллокациями. Для init-кода, обработки ошибок — где производительность некритична

Структурированные логи (JSON) вместо plain text — чтобы агрегатор (ELK, Loki) мог парсить поля, индексировать и фильтровать без регулярок.

---

#### 6. Как организован сбор логов в Kubernetes: как логи из контейнеров попадают в централизованное хранилище?

**Теория — pipeline логирования в K8s:**

1. **Контейнер** пишет в stdout/stderr — стандарт в K8s. Не в файлы, не в сокеты — просто stdout
2. **Container runtime** (containerd) перехватывает stdout и пишет JSON-логи на ноду в `/var/log/containers/`
3. **Fluent Bit** (или Fluentd) задеплоен как **DaemonSet** — по одному поду на каждой ноде. Читает логи с ноды, парсит JSON, добавляет K8s-метаданные (имя пода, namespace, контейнер, лейблы) через Kubernetes API
4. **Elasticsearch** принимает и индексирует логи
5. **Kibana** — UI для поиска и визуализации

Почему DaemonSet: лог-агент должен быть на каждой ноде, потому что логи контейнеров лежат локально на ноде. DaemonSet гарантирует ровно один под на ноду.

Альтернатива ELK — **Loki + Grafana** (от Grafana Labs). Loki не индексирует содержимое логов (только лейблы), поэтому дешевле по storage.

#### 7. Работали ли вы с метриками? Какие инструменты использовали?

Да. **Prometheus + Grafana**. В каждом сервисе подключал `prometheus/client_golang`, поднимал эндпоинт `/metrics`. Добавлял метрики в код: счётчики обработанных событий, гистограммы латенций, гейджи (размер буфера, количество WS-подключений). Alertmanager рассылал алерты в Telegram.

**Теория — Prometheus:**
Prometheus работает по **pull-модели**: сам ходит на эндпоинты сервисов (`/metrics`) по расписанию (scrape interval, обычно 15-30 сек) и забирает метрики. Это отличает его от push-систем (StatsD, Graphite) где сервис сам отправляет метрики.

Типы метрик:
- **Counter** — монотонно растущее число (total requests, total errors). Только `Inc()`. Для rate используешь `rate(counter[5m])` в PromQL
- **Gauge** — текущее значение, может расти и падать (температура, количество горутин, consumer lag)
- **Histogram** — распределение значений по bucket-ам. Позволяет считать перцентили (P50, P95, P99). Каждый bucket — отдельный counter
- **Summary** — похож на histogram, но перцентили считаются на клиенте. Нельзя агрегировать между инстансами — поэтому histogram обычно предпочтительнее

**Grafana** визуализирует данные из Prometheus через **PromQL** — язык запросов. Пример: `histogram_quantile(0.95, rate(http_duration_seconds_bucket[5m]))` — P95 латенции за последние 5 минут.

#### 8. Использовали ли бизнес-метрики (например, upstream, SLA и т.д.)?

Да. Помимо технических (latency, error rate) были бизнесовые: `telematics_events_processed_total{provider="..."}` — обработано событий по провайдеру, `carrier_errors_total` — ошибки по каждому перевозчику, `tracking_position_age_seconds` — "свежесть" позиции на карте (SLA — не старше 5 сек). По `carrier_errors_total` был алерт: > 50 ошибок за 5 мин → warning.

**Теория — бизнес-метрики vs технические:**
Технические метрики (CPU, memory, latency) говорят **как** работает система. Бизнес-метрики говорят **что** система делает с точки зрения пользователя. Примеры: процент доставок в срок, количество активных ТС на карте, время от события до отображения диспетчеру.

Бизнес-метрики ценнее для алертинга: CPU 90% — может быть нормой при пиковой нагрузке. А вот "0 обновлений позиций за 2 минуты" — однозначно инцидент. Реализуются теми же инструментами (Prometheus counter/gauge), но семантика привязана к домену.

#### 9. Создавали ли вы дашборды (например, в Grafana)? Что именно отображали?

Да. Основные дашборды:
- **Service Overview** — RPS, латенции (P50/P95/P99), error rate по сервисам
- **Kafka Pipeline** — consumer lag по топикам, throughput (events/sec), размер буфера COPY
- **Provider Health** — доступность и латенсии запросов к каждому телематическому провайдеру, drop rate по причинам (невалидные координаты, мало спутников)

**Теория — принципы хороших дашбордов:**
**USE-метод** (для ресурсов): Utilization (загрузка), Saturation (очереди), Errors. Применяется к CPU, диску, сети, пулам соединений.

**RED-метод** (для сервисов): Rate (RPS), Errors (error rate), Duration (latency). Показывает здоровье сервиса с точки зрения запросов.

Практика: наверху дашборда — общая картина (всё зелёное / есть проблема). Ниже — drill-down по компонентам. Алерты настраиваются не на дашборде, а в Alertmanager — дашборд для людей, алерты для автоматики.

### Архитектура / Коммуникация

#### 10. Как сервисы взаимодействовали между собой?

Два способа:
- **gRPC (protobuf)** — синхронное взаимодействие, когда нужен ответ здесь и сейчас. Строгий типизированный контракт, низкая латентность
- **Kafka** — асинхронное, event-driven. Сервис публикует событие и не ждёт обработки. Развязка по времени и отказоустойчивость — если consumer лежит, сообщения копятся в Kafka

**Теория — синхронное vs асинхронное:**

**Синхронное (gRPC, HTTP):** вызывающий блокируется до получения ответа. Плюсы: простая ментальная модель, сразу знаешь результат. Минусы: temporal coupling (оба сервиса должны быть доступны одновременно), каскадные отказы (downstream лёг → upstream тоже), нужен circuit breaker.

**Асинхронное (Kafka, RabbitMQ):** producer отправил сообщение и пошёл дальше. Плюсы: развязка — producer и consumer не знают друг о друге, буферизация при пиках, один event → много consumer-ов (fan-out). Минусы: eventual consistency, сложнее отлаживать (нет стека вызовов, нужен distributed tracing), сложнее гарантировать порядок.

**gRPC** работает поверх HTTP/2: мультиплексирование запросов в одном TCP-соединении, бинарный фрейминг, поддержка streaming (server-side, client-side, bidirectional). Контракт описывается в `.proto` файле, из которого генерируется код для клиента и сервера.

---

#### 11. Как устроен контракт (protobuf)?

В `.proto`-файле описываешь `message` (структуры данных) и `service` (RPC-методы). Запускаешь `protoc` с плагином (`protoc-gen-go` + `protoc-gen-go-grpc` для Go) — получаешь клиент и серверный интерфейс.

**Теория — protobuf wire format и совместимость:**

Protobuf — бинарный формат сериализации. Каждое поле кодируется как `(field_number << 3 | wire_type)` + значение. Именно поэтому **номер поля** — главный идентификатор, не имя. Имена нужны только при кодогенерации.

Правила совместимости:
- **Можно** добавлять новые поля с новыми номерами — старый код их проигнорирует (forward compatible)
- **Можно** удалить поле из `.proto` — старые данные с этим полем десериализуются, поле просто игнорируется (backward compatible)
- **Нельзя** менять номер поля — это сломает десериализацию
- **Нельзя** менять тип поля на несовместимый (int32 → string)
- Удалённые номера стоит помечать `reserved` чтобы никто случайно не переиспользовал

Дефолтные значения (0, "", false) **не сериализуются** — экономия байтов. Следствие: невозможно отличить "поле не задано" от "поле равно дефолту" без использования `optional` (proto3) или wrapper types.

---

#### 12. Как в protobuf реализовать повторяющиеся поля (repeated)?

**Теория:**

`repeated` — ключевое слово перед типом поля: `repeated string tags = 1;`. В Go компилируется в слайс: `Tags []string`.

Ключевые свойства:
- **Порядок сохраняется** — это list, не set
- Применяется к любому типу, включая `message`: `repeated Event events = 2;` → `[]*Event`
- **Пустой repeated = отсутствует в wire-формате** (0 байт). При десериализации получишь `nil` слайс (в Go), не пустой слайс
- Для map-подобных структур есть `map<K, V>` — синтаксический сахар поверх `repeated` с вложенным message

Wire format: элементы repeated-поля кодируются последовательно с одинаковым field number. Скалярные типы (int32, float и т.д.) по умолчанию **packed** — все элементы в одном length-delimited блоке, экономит байты.

### Базы данных

#### 14. Как удалять данные в ClickHouse?

**Теория:**

ClickHouse оптимизирован под append-only: данные записываются батчами и хранятся в immutable **партах** (отсортированных блоках). Классический `DELETE` как в PostgreSQL здесь не работает — нельзя удалить строку из отсортированного immutable файла без перезаписи.

Три механизма удаления:

1. **Lightweight DELETE** (`DELETE FROM t WHERE ...`) — появился в последних версиях. Помечает строки маской, физически удаляются при следующем merge. Для единичных удалений подходит, но на больших объёмах может тормозить

2. **Мутации** (`ALTER TABLE t DELETE WHERE ...`) — тяжёлая операция. ClickHouse перезаписывает все затронутые парты. Выполняется асинхронно в фоне, может занять минуты. Не подходит для частых удалений — каждая мутация порождает перезапись данных

3. **TTL** — самый ClickHouse-way подход. Указывается прямо в DDL:
   ```sql
   CREATE TABLE events (...) ENGINE = MergeTree()
   ORDER BY (event_date, event_id)
   TTL event_date + INTERVAL 90 DAY DELETE;
   ```
   Данные удаляются автоматически при merge партов по истечении срока. Никакого ручного вмешательства.

4. **ReplacingMergeTree** — для логического удаления. Пишешь строку с `is_deleted=1`, при `SELECT ... FINAL` дубли схлопываются и удалённые отфильтровываются. Merge не гарантирован сразу — до merge `FINAL` нужен обязательно.

#### 16. Приходилось ли оптимизировать SQL-запросы?

Да. Основные приёмы: `EXPLAIN ANALYZE` для анализа плана, составные индексы по полям в WHERE, партиционирование по дате.

**Теория — оптимизация SQL:**

1. **Индексы.** B-tree индекс — основная структура в PostgreSQL. Составной индекс `(a, b)` эффективен для `WHERE a = X AND b = Y`, для `WHERE a = X`, но **не** для `WHERE b = Y` (leftmost prefix rule). Порядок полей в индексе важен.

2. **Seq Scan vs Index Scan.** Seq Scan читает всю таблицу последовательно — O(N). Index Scan ищет по B-tree дереву — O(log N). Но если запрос возвращает >5-10% таблицы, планировщик может выбрать Seq Scan — потому что sequential I/O быстрее random I/O при чтении большой доли данных.

3. **Коррелированный подзапрос vs JOIN.** Коррелированный подзапрос (`WHERE x IN (SELECT ... WHERE outer.id = inner.id)`) выполняется по разу на каждую строку внешнего запроса — O(N×M). JOIN позволяет планировщику выбрать Hash Join или Merge Join — обычно значительно быстрее.

4. **Партиционирование.** Таблица разбивается на физические части (партиции) по ключу (обычно дата). Запрос с ключом партиции в WHERE сканирует только нужные партиции (**partition pruning**). Без ключа — сканирует все.

#### 17. Объясните разницу между: EXPLAIN, EXPLAIN ANALYZE, COST

**Теория:**

**`EXPLAIN`** — показывает план выполнения запроса **без его выполнения**. Планировщик анализирует статистику таблиц и выбирает оптимальный план (Seq Scan, Index Scan, Hash Join, Nested Loop и т.д.). Видишь оценочные значения: estimated rows, estimated cost. Безопасен — ничего не читает и не меняет.

**`EXPLAIN ANALYZE`** — **реально выполняет** запрос и показывает фактические значения рядом с оценочными: actual time, actual rows, loops. Позволяет увидеть где планировщик ошибся в оценке. Если estimated rows = 100, а actual = 1 000 000 — статистика устарела, нужно запустить `ANALYZE` для обновления. Важно: DML-запросы (`UPDATE`, `DELETE`) реально выполнятся — оборачивай в `BEGIN` / `ROLLBACK`.

**COST** — не команда, а поле в выводе EXPLAIN. Два числа: `cost=0.00..123.45`.
- **Startup cost** (первое число) — стоимость до выдачи первой строки. У Index Scan обычно > 0 (нужно спуститься по дереву), у Seq Scan обычно 0
- **Total cost** (второе число) — стоимость получения всех строк
- Единицы условные, не миллисекунды. Базируются на настройках: `seq_page_cost` (по умолчанию 1.0), `random_page_cost` (по умолчанию 4.0). Планировщик выбирает план с минимальным total cost

#### 18. Что такое транзакция? Как она реализована в PostgreSQL? Какие механизмы используются (MVCC и т.д.)?

**Теория:**

**Транзакция** — атомарная единица работы с БД. Свойства ACID:
- **Atomicity** — либо все операции выполнились, либо ни одна (rollback через WAL)
- **Consistency** — данные переходят из одного валидного состояния в другое (constraints, FK)
- **Isolation** — параллельные транзакции не видят промежуточных состояний друг друга
- **Durability** — после COMMIT данные на диске, даже при падении (WAL — Write-Ahead Log)

**MVCC (Multi-Version Concurrency Control)** — механизм изоляции в PostgreSQL. Вместо блокировки строк при чтении, PG хранит **несколько версий** каждой строки:
- `xmin` — ID транзакции, которая создала эту версию
- `xmax` — ID транзакции, которая удалила/обновила (0 если строка актуальна)

При `UPDATE` PG не меняет строку in-place, а создаёт новую версию (новая строка с новым xmin) и помечает старую (xmax = ID текущей транзакции).

**Видимость строки** определяется снапшотом — списком активных транзакций на момент начала чтения. Строка видима если:
- `xmin` закоммичен И не в снапшоте активных (т.е. завершился до начала нашего чтения)
- `xmax` равен 0 ИЛИ не закоммичен ИЛИ в снапшоте активных

Главное преимущество: **читатели не блокируют писателей и наоборот**. Недостаток: dead tuples (старые версии строк) накапливаются, нужен **VACUUM** для их очистки.

**Уровни изоляции в PG:**
- **Read Committed** (дефолт) — новый снапшот на каждый SQL-statement. Может видеть изменения других транзакций между своими statements (non-repeatable read)
- **Repeatable Read** — один снапшот на всю транзакцию. Не видит изменений, закоммиченных после начала транзакции
- **Serializable** — полная сериализация. Использует предикатные блокировки (SSI — Serializable Snapshot Isolation). Может выкинуть `serialization_failure` при конфликте — приложение должно ретраить

#### 19. Если таблица партиционирована (например, по времени), и запрос не содержит ключ партиции — как будет выполняться запрос?

**Теория:**

**Partition pruning** — оптимизация планировщика, которая исключает из сканирования партиции, не содержащие нужных данных. Работает **только** если ключ партиции присутствует в `WHERE`.

Если ключа нет — pruning не срабатывает. PostgreSQL сгенерирует план **Append** — последовательное сканирование **всех** партиций. Если партиций 12 (по месяцам за год) — будет 12 отдельных Index Scan (или Seq Scan). Если 365 (по дням) — 365 сканов. Каждая партиция — отдельная физическая таблица со своими индексами.

Это может быть дороже, чем обычная непартиционированная таблица:
- Overhead на планирование (больше узлов в плане)
- Каждая партиция имеет свой индекс — больше random I/O
- Append-узел собирает результаты из всех партиций

Правило: запросы к партиционированным таблицам **всегда** должны включать ключ партиции в WHERE. На код-ревью отсутствие ключа — блокер.

### Брокеры сообщений (Kafka)

#### 20. Почему нельзя просто использовать один топик для всех типов сообщений?

**Теория:**

1. **Связность consumer-ов.** Consumer должен десериализовать каждое сообщение, определить тип и по-разному обрабатывать. Код усложняется, появляются зависимости от всех типов событий. Каждое изменение схемы одного типа затрагивает всех consumer-ов.

2. **Разная скорость обработки.** Notification Service обрабатывает за 100 мс (HTTP-вызов), Billing Service — за 5 мс. В общем топике они в одной consumer group — медленный consumer тормозит общий throughput. В отдельных топиках каждая группа потребляет независимо.

3. **Невозможность независимого масштабирования.** GPS-события идут в 15 000/sec, driver events — 30/sec. В общем топике нельзя добавить партиций только для GPS — партиции общие.

4. **Разный retention.** GPS жрёт 95% storage. Хочешь retention 7 дней для GPS и 90 дней для driver events — в одном топике это невозможно.

5. **Schema evolution.** В отдельном топике одна схема — Schema Registry проверяет совместимость при деплое. В общем топике несколько схем — сложнее контролировать.

Правило: **один топик — одна семантика события, одна схема.**

---

#### 21. Как определяется, в какую партицию попадет сообщение?

**Теория:**

Kafka producer определяет партицию через **partitioner** (стратегия разделения):

1. **С ключом:** `hash(key) % num_partitions`. В Java-клиенте — murmur2, в Go (sarama, confluent-kafka-go) — аналогичный алгоритм. Гарантия: все сообщения с одинаковым ключом **всегда** попадают в одну партицию → гарантия порядка для одного ключа. У нас ключом был `vehicle_id` — все события одного ТС в одной партиции.

2. **Без ключа:** **sticky partitioning** (Kafka 2.4+). Producer накапливает батч сообщений и отправляет весь батч в одну партицию, затем переключается на следующую. До 2.4 — round-robin (каждое сообщение в следующую партицию).

3. **Кастомный partitioner:** можно реализовать свою логику (например, по региону, по приоритету).

Важно: если количество партиций изменилось (`num_partitions` выросло) — `hash(key) % N` даёт другой результат. Сообщения с тем же ключом начнут попадать в другую партицию. Поэтому изменение количества партиций в продакшне — деструктивная операция.

---

#### 22. Может ли в одной партиции быть несколько типов событий?

**Теория:**

Технически — да. Kafka не знает ничего о содержимом сообщения — для неё это просто байты (`byte[]`). В одну партицию могут попасть сообщения с разными типами событий:
- Если они в одном топике и разные ключи хэшируются в одну партицию
- Если producer намеренно не разделяет типы по топикам

Но это **антипаттерн**:
- Consumer должен десериализовать каждое сообщение, определять тип (switch/case по полю type), по-разному обрабатывать
- Schema evolution усложняется: изменение одного типа может сломать десериализацию другого
- Мониторинг сложнее: lag одного consumer group отражает обработку всех типов разом

Исключение: один топик с разными типами допустим когда события семантически связаны и всегда обрабатываются вместе (например, events одного агрегата в event sourcing).

---

#### 23. Есть ли гарантия, что определённый тип события попадёт в конкретную партицию?

**Теория:**

Только если **ключ детерминирован и количество партиций не меняется**.

`hash(key) % N` — детерминистическая функция. Если всегда передавать один ключ (например, `"order-123"`) и N не меняется — сообщение всегда попадает в одну и ту же партицию.

Когда гарантия ломается:
- **N изменилось** (добавили партиции): `hash("order-123") % 12` ≠ `hash("order-123") % 15`. Сообщения с тем же ключом начнут попадать в другую партицию
- **Ключ не задан**: round-robin / sticky, никакой гарантии
- **Кастомный partitioner** изменён

Именно поэтому **количество партиций не меняют** после создания топика в продакшне, если важен порядок обработки по ключу. Если нужно больше throughput — лучше заранее создать топик с запасом партиций (12, 24, 36).

#### 25. Как передать файл между машинами в Linux?

**Теория — основные способы:**

- **`scp`** — копирование через SSH. `scp file.txt user@host:/path`. Простой, но устаревший (OpenSSH рекомендует `sftp`)
- **`rsync`** — умная синхронизация. `rsync -avz file.txt user@host:/path`. Передаёт только дельту (изменённые блоки), поддерживает compression (`-z`), показывает прогресс (`--progress`). Идеален для больших файлов и повторных передач
- **`sftp`** — интерактивный FTP поверх SSH. Можно ходить по директориям удалённой машины
- **Через объектное хранилище** — `aws s3 cp` / `mc cp` (MinIO). Подходит когда нет прямого SSH между машинами

Под капотом `scp` и `rsync` используют SSH для шифрования. `rsync` эффективнее при повторных передачах: разбивает файл на блоки, вычисляет rolling checksum, передаёт только изменившиеся блоки.

#### 26. Что такое Load Average? Как его интерпретировать?

**Теория:**

**Load Average** — среднее количество процессов в двух состояниях за 1, 5 и 15 минут:
- **Runnable (R)** — готовы к выполнению или выполняются на CPU
- **Uninterruptible sleep (D)** — ждут I/O (чтение с диска, сетевой ввод/вывод)

Видно в `uptime`, `top`, `/proc/loadavg`.

Интерпретация:
- Load Average нужно сравнивать с **количеством CPU** (`nproc`)
- LA = 1.0 на 1-ядерной машине → CPU загружен на 100%
- LA = 4.0 на 8-ядерной → 50% загрузки, всё хорошо
- LA = 12.0 на 8-ядерной → очередь из 4 процессов, задержки

Три значения (1, 5, 15 мин) показывают тренд:
- 1 мин > 5 мин > 15 мин → нагрузка растёт
- 1 мин < 5 мин < 15 мин → нагрузка падает

Подвох: высокий LA при низком CPU usage → проблема не в CPU, а в **I/O** (процессы в состоянии D). Смотри `wa` (iowait) в `top` или `iostat`.

#### 27. Как работает fork() в Linux?

**Теория:**

`fork()` — системный вызов, создаёт **дочерний процесс** как копию родительского. Копируется:
- Адресное пространство (виртуальная память)
- Таблица файловых дескрипторов
- Переменные окружения
- Маски сигналов, PID группы

Ключевая оптимизация — **Copy-on-Write (CoW)**:
- При `fork()` физические страницы памяти **не копируются**
- Обе процесса разделяют одни и те же физические страницы, помеченные как read-only
- При первой попытке записи (любым из процессов) — ядро копирует только **эту страницу** (4 КБ), снимает read-only
- Результат: `fork()` выполняется за микросекунды даже для процесса с гигабайтами памяти

Типичный паттерн: `fork()` + `exec()`:
1. `fork()` создаёт копию процесса (дёшево благодаря CoW)
2. `exec()` заменяет адресное пространство дочернего процесса новой программой
3. Страницы родителя не были скопированы — потому что `exec()` сразу их выбросил

---

#### 28. Как процесс может определить, является ли он родительским или дочерним после fork()?

**Теория:**

По возвращаемому значению `fork()`:
- **Родитель** получает PID дочернего процесса (> 0)
- **Дочерний** получает 0
- При ошибке возвращается -1 (только родителю, дочерний не создаётся)

```c
pid_t pid = fork();
if (pid == 0) {
    // дочерний процесс
} else if (pid > 0) {
    // родитель, pid — PID дочернего
} else {
    // ошибка: ENOMEM, EAGAIN (превышен лимит процессов)
}
```

Почему дочерний получает 0, а не PID родителя? Потому что дочерний может узнать PID родителя через `getppid()`, а вот parent не может узнать PID ребёнка иначе как из возвращаемого значения `fork()` (у родителя может быть много детей).

#### 29. Почему при удалении открытого файла место на диске не освобождается?

**Теория:**

В Linux файловая система разделяет **имя файла** и **данные файла**:

- **Inode** — структура, хранящая метаданные файла (размер, права, указатели на блоки данных на диске). У каждого файла свой inode
- **Имя файла (directory entry)** — запись в директории, связывающая имя с номером inode. Это **hard link** (жёсткая ссылка)

`rm` (системный вызов `unlink()`) удаляет **directory entry** — имя файла из директории. Inode имеет **счётчик ссылок** (link count). `unlink` уменьшает его на 1.

Данные на диске освобождаются когда **оба условия** выполнены:
1. Счётчик ссылок = 0 (нет ни одного имени, указывающего на inode)
2. Нет открытых файловых дескрипторов на этот inode

Если процесс держит файл открытым (`fd` = ссылка на inode на уровне ядра) — inode жив, данные на диске целы. Процесс продолжает читать/писать через свой `fd`. Новые процессы файл уже не найдут (имя удалено), но старые работают. Место освободится когда процесс закроет `fd` (или умрёт).

Практическое следствие: лог-файл удалён, но `du` показывает что диск занят. `lsof +L1` покажет процессы, держащие удалённые файлы открытыми. Решение: рестарт процесса или `logrotate` с `copytruncate`.

### Go / Concurrency

#### 30. Что такое race condition?

**Теория:**

**Race condition (гонка данных)** — ситуация когда корректность результата зависит от порядка выполнения конкурентных операций над общими данными без синхронизации.

Классический пример:
```go
var counter int

// Горутина 1          // Горутина 2
counter++              counter++
// read → 0            // read → 0
// modify → 1          // modify → 1
// write → 1           // write → 1
// Итог: 1, а не 2
```

`counter++` — это **три** операции: read, modify, write. Между ними другая горутина может вклиниться.

**Go Memory Model** формально определяет: без явной синхронизации (mutex, channel, atomic) **нет гарантий видимости** записей между горутинами. Даже чтение `bool` или `int` без синхронизации — это data race, если другая горутина пишет. Компилятор и процессор могут:
- Переупорядочивать инструкции (instruction reordering)
- Кешировать значения в регистрах (не перечитывать из памяти)
- Оптимизировать "лишние" чтения

Средства защиты:
- `sync.Mutex` / `sync.RWMutex` — взаимное исключение
- `chan` — каналы, синхронизация через коммуникацию
- `sync/atomic` — атомарные операции на уровне процессора
- `sync.Once`, `sync.WaitGroup` — специализированные примитивы

#### 31. Как работает проверка -race в Go?

**Теория:**

`-race` флаг (`go build -race`, `go test -race`) подключает **ThreadSanitizer (TSan)** — runtime-инструментацию от Google.

Как работает:
1. Компилятор вставляет вызов к TSan **перед каждой операцией чтения/записи** в память
2. TSan поддерживает **shadow memory** — параллельную структуру данных. Для каждого слова памяти хранится: ID горутины, тип операции (read/write), логическое время (vector clock)
3. При каждом доступе TSan проверяет: было ли **параллельное** обращение из другой горутины? Если да, и между ними нет happens-before отношения (mutex, channel, atomic) — это race
4. При обнаружении race — **паника** с двумя стектрейсами: текущий доступ + предыдущий конфликтующий

Оверхед:
- CPU: ×2-20 (каждая операция с памятью проверяется)
- RAM: ×5-10 (shadow memory)
- Поэтому только в тестах и CI, никогда в проде

В проекте `go test -race ./...` был обязательным шагом CI — PR не мержился без прохождения.

#### 32. Что произойдёт, если несколько goroutine одновременно пишут в одну переменную без синхронизации?

**Теория:**

**Undefined behavior** по Go Memory Model. Конкретно может произойти:

1. **Torn read/write** — для типов больше размера машинного слова (string — 16 байт на 64-bit: pointer + length; interface — 16 байт: type pointer + data pointer; slice — 24 байта). Одна горутина записала pointer, но ещё не записала length — другая горутина читает невалидную комбинацию. Результат: паника, segfault, чтение мусора

2. **Lost update** — обе горутины читают одно значение, модифицируют, записывают. Одно из изменений потеряно (как с `counter++`)

3. **Stale read** — компилятор закешировал значение в регистре. Горутина читает старое значение, хотя другая давно записала новое. Без memory barrier (который обеспечивают mutex/atomic/channel) нет гарантии видимости

4. **Compiler reordering** — компилятор переставил инструкции для оптимизации. Без happens-before порядок виден другой горутине иначе, чем написано в коде

Race detector (`-race`) поймает это в тестах. В проде без детектора — тихая порча данных, рандомные паники, трудновоспроизводимые баги. Чинить data race в проде по логам — кошмар, поэтому `-race` в CI обязателен.
