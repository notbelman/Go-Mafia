# Вопросы

## Go

### Типы данных

#### 1. Какие встроенные типы данных в Go?

**Числовые целочисленные:**
- `int`, `int8`, `int16`, `int32`, `int64` — знаковые
- `uint`, `uint8`, `uint16`, `uint32`, `uint64` — беззнаковые
- `byte` — алиас для `uint8`
- `rune` — алиас для `int32`, представляет Unicode code point
- `uintptr` — целое число, достаточное для хранения указателя

**Числовые с плавающей точкой:**
- `float32`, `float64`
- `complex64`, `complex128`

**Логический:**
- `bool` — `true` / `false`

**Строковый:**
- `string` — неизменяемая последовательность байт

**Составные (composite) типы:**
- `array` — массив фиксированной длины
- `slice` — динамический срез
- `map` — хеш-таблица
- `struct` — структура
- `chan` — канал

**Ссылочные / специальные:**
- `pointer` (`*T`)
- `function` — функции являются first-class citizen
- `interface` — набор методов

### Строки

#### 2. Что из себя представляет строка?

Строка в Go — это **неизменяемая (immutable) последовательность байт**. Внутри runtime строка представлена структурой `StringHeader`:

```go
type StringHeader struct {
    Data uintptr // указатель на массив байт
    Len  int     // длина в байтах
}
```

Ключевые свойства:
- **Immutable** — нельзя изменить отдельный байт строки. Любая "модификация" создаёт новую строку
- **UTF-8 по умолчанию** — строки хранят байты в кодировке UTF-8, но это не гарантируется — можно положить любые байты
- `len(s)` возвращает количество **байт**, а не символов
- Индексация `s[i]` возвращает **байт** (`byte`), а не символ
- Итерация `for i, r := range s` декодирует **руны** (Unicode code points)
- Конвертация `[]byte(s)` создаёт копию (кроме оптимизаций компилятора)

#### 3. Как правильно посчитать количество символов в Unicode-строке?

Использовать `utf8.RuneCountInString(s)` из пакета `unicode/utf8`:

```go
import "unicode/utf8"

s := "Привет, 世界!"
fmt.Println(len(s))                        // 21 (байт)
fmt.Println(utf8.RuneCountInString(s))     // 10 (рун/символов)
```

Альтернативный способ — конвертация в `[]rune`:

```go
fmt.Println(len([]rune(s))) // 10
```

Разница: `utf8.RuneCountInString` **не аллоцирует** новый слайс, а просто считает руны, поэтому предпочтительнее.

> **Важно:** одна руна — это один Unicode code point, но не всегда один "видимый символ" (grapheme cluster). Например, эмодзи `👨‍👩‍👧` — это несколько рун. Для подсчёта grapheme clusters нужна библиотека вроде `rivo/uniseg`.

### Слайсы и массивы

#### 4. Что такое слайсы?

Слайс (slice) — это **динамическая обёртка над массивом**. Внутри runtime представлен структурой `SliceHeader`:

```go
type SliceHeader struct {
    Data uintptr // указатель на underlying array
    Len  int     // текущая длина (количество элементов)
    Cap  int     // ёмкость (сколько элементов вмещает underlying array от Data)
}
```

Ключевые свойства:
- **Reference-семантика** — слайс содержит указатель на массив, поэтому несколько слайсов могут разделять один underlying array
- **Нулевое значение** — `nil`, при этом `len(nil) == 0` и `cap(nil) == 0`
- Создание: литерал `[]int{1, 2, 3}`, `make([]int, len, cap)`, срез от массива `arr[1:3]`

#### 5. Как добавить элемент в слайс?

Через встроенную функцию `append`:

```go
s := []int{1, 2, 3}
s = append(s, 4)       // один элемент
s = append(s, 5, 6, 7) // несколько
s = append(s, other...) // другой слайс
```

**Механизм работы `append`:**
1. Если `len < cap` — элемент записывается в существующий underlying array, `len` увеличивается
2. Если `len == cap` — аллоцируется **новый** underlying array с увеличенной ёмкостью, данные копируются, старый массив остаётся для GC

**Стратегия роста (Go 1.18+):**
- При `cap < 256` — удваивается
- При `cap >= 256` — растёт по формуле `newcap += (newcap + 3*256) / 4` (~25% прирост), с выравниванием по классам размеров аллокатора

> **Важно:** `append` может вернуть новый слайс с другим `Data`, поэтому **всегда** присваивай результат: `s = append(s, ...)`.

#### 6. Чем слайс отличается от массива?

| Свойство               | Массив `[N]T`                                         | Слайс `[]T`                                                    |
| ---------------------- | ----------------------------------------------------- | -------------------------------------------------------------- |
| **Размер**             | Фиксированный, часть типа                             | Динамический                                                   |
| **Тип**                | `[3]int ≠ [4]int`                                     | `[]int` — один тип независимо от длины                         |
| **Передача в функцию** | **Копируется** целиком (value type)                   | Копируется только заголовок (3 слова), данные разделяются      |
| **Использование**      | Редко, в основном для фиксированных данных (хеши, IP) | Повсеместно                                                    |
| **Нулевое значение**   | Массив нулевых элементов                              | `nil`                                                          |
| **Сравнение**          | == сравнивает поэлементно                             | == только с `nil`; для содержимого — `slices.Equal` (Go 1.21+) |

### Мапы

#### 7. Что такое мапа?

Map в Go — это **неупорядоченная хеш-таблица** вида `map[K]V`, связывающая ключи с значениями.

```go
m := map[string]int{
    "alice": 30,
    "bob":   25,
}
m["charlie"] = 35       // вставка
val, ok := m["alice"]   // чтение с проверкой наличия
delete(m, "bob")         // удаление
```

Ключевые свойства:
- **Нулевое значение** — `nil`. Чтение из nil-мапы возвращает zero value, но **запись в nil-мапу** — это `panic`
- **Ключ** должен быть **comparable** (поддерживать ==): числа, строки, указатели, структуры из comparable полей. Слайсы, мапы и функции — **нельзя** использовать как ключи
- **Порядок итерации** — **рандомизирован** runtime-ом намеренно, чтобы код не зависел от порядка
- **Не потокобезопасна** — конкурентные чтение и запись без синхронизации → `fatal error: concurrent map read and map write`
- Передаётся по ссылке (map — это указатель на `runtime.hmap`)

**Устройство (до Go 1.24):** Массив бакетов, в каждом бакете до 8 пар ключ-значение. При заполнении > 6.5 элементов на бакет происходит **инкрементальный рехеш** (growing).

#### 8. Что такое Swiss Table (Go 1.24)?

**Swiss Table** — новая реализация хеш-таблицы в Go 1.24, заменившая старую на основе бакетов. Разработана изначально в Google для C++ (Abseil).

**Принцип работы:**
- Таблица разделена на **группы по 8 или 16 слотов**
- Каждая группа имеет **control byte array** — массив метаданных (по 1 байту на слот), хранящий 7 бит от хеша + 1 бит состояния (пустой/занятый/удалённый)
- Поиск: вычисляется хеш → определяется группа → **SIMD-подобное сравнение** control bytes за одну операцию → точное сравнение ключа только для совпавших слотов

**Преимущества по сравнению со старой реализацией:**
- **Быстрее** — меньше cache misses, поиск по control bytes помещается в одну кэш-линию
- **Меньше памяти** — более компактное хранение метаданных
- **Быстрее удаление** — tombstone в control byte вместо overflow chains
- В бенчмарках: **~15-30% ускорение** на типичных операциях

> Переход прозрачен для пользователя — API `map` не изменился.

#### 9. Можно ли взять указатель на мапу?

**На саму переменную-мапу** — да, `&m` вернёт `*map[K]V`. Но это редко нужно, потому что `map` уже является ссылочным типом (внутри — указатель на `runtime.hmap`).

**На элемент мапы** — **нельзя**:

```go
m := map[string]int{"a": 1}
p := &m["a"] // ошибка компиляции: cannot take address of m["a"]
```

**Причина:** при вставке новых элементов хеш-таблица может переаллоцировать бакеты, и все адреса элементов станут невалидными. Компилятор запрещает это на уровне спецификации.

**Обходной путь** — хранить указатели как значения: `map[string]*MyStruct`.

### Интерфейсы

#### 10. Что такое интерфейсы?

Интерфейс в Go — это **именованный набор сигнатур методов**. Тип реализует интерфейс **неявно** (implicit satisfaction) — достаточно иметь все нужные методы, `implements` не нужен.

```go
type Writer interface {
    Write(p []byte) (n int, err error)
}
```

**Внутреннее представление:**

Непустой интерфейс — структура `iface`:
```go
type iface struct {
    tab  *itab          // указатель на таблицу методов + метаинформация о типе
    data unsafe.Pointer // указатель на конкретное значение
}
```

Пустой интерфейс `any` (`interface{}`) — структура `eface`:
```go
type eface struct {
    _type *_type         // информация о типе
    data  unsafe.Pointer // указатель на значение
}
```

**Ловушка nil-интерфейса:**
```go
var w io.Writer       // w == nil (tab == nil, data == nil)
var buf *bytes.Buffer // buf == nil
w = buf               // w != nil! (tab != nil, data == nil)
```

Интерфейс `nil` только если **оба** поля (tab/type и data) равны nil.

#### 11. Используешь ли интерфейсы в работе и как?

Да, постоянно. Основные паттерны:

1. **Dependency Injection** — зависимости сервисного слоя определяются через интерфейсы:
```go
type OrderService struct {
    repo  OrderRepository  // интерфейс, а не конкретная реализация
    queue EventPublisher
}
```

2. **Тестирование** — подмена зависимостей моками/стабами. Интерфейс определяется **на стороне потребителя**, а не провайдера:
```go
// В пакете service, а не в пакете postgres
type UserRepository interface {
    GetByID(ctx context.Context, id int64) (*User, error)
}
```

3. **Абстракция инфраструктуры** — storage, message broker, cache скрыты за интерфейсом, можно менять реализацию без правок бизнес-логики

4. **Полиморфизм** — обработка разнородных объектов через единый интерфейс (например, разные типы нотификаций)

#### 12. Зачем нужны интерфейсы, можно же без них написать?

Можно, но код станет **жёстко связанным** (tightly coupled). Интерфейсы решают:

1. **Инверсия зависимостей (DIP)** — бизнес-логика не зависит от конкретной базы данных, брокера, HTTP-клиента. Зависимости направлены от инфраструктуры к домену, а не наоборот

2. **Тестируемость** — без интерфейсов нельзя подменить PostgreSQL на in-memory стаб в unit-тестах. Придётся поднимать реальную БД для каждого теста

3. **Заменяемость** — переход с RabbitMQ на Kafka, с PostgreSQL на ClickHouse — меняется только реализация интерфейса, бизнес-код не трогается

4. **Контракт** — интерфейс явно документирует, **что** нужно от зависимости. Компилятор проверяет, что реализация корректна

5. **Принцип разделения интерфейсов (ISP)** — потребитель зависит только от методов, которые реально использует, а не от всего "толстого" объекта

> **Правило Go:** "Accept interfaces, return structs" — принимай интерфейсы, возвращай конкретные типы. Определяй интерфейс **на стороне потребителя**, а не рядом с реализацией.

### Горутины

#### 13. Как работают горутины?

Горутина — это **легковесный поток выполнения**, управляемый Go runtime, а не ОС.

```go
go func() {
    // выполняется конкурентно
}()
```

**Характеристики:**
- **Малый стек** — начальный размер ~2-4 КБ (vs ~1-8 МБ у OS-потока), растёт динамически до гигабайт
- **Дешёвое создание** — можно запускать сотни тысяч горутин в одном процессе
- **Кооперативно-вытесняющий планировщик** — горутины переключаются в safe points (вызовы функций, операции с каналами, системные вызовы), а с Go 1.14 добавлена **асинхронная preemption** через сигналы ОС
- **Мультиплексируются** на OS-потоки — M горутин на N потоков (M:N scheduling)

**Как горутина "умирает":**
- Возврат из функции горутины
- `runtime.Goexit()` (выполняет deferred-функции перед выходом)
- Завершение программы (main goroutine завершилась)

#### 14. Как горутины работают под капотом?

Go использует **модель GMP** (Goroutine, Machine, Processor):

- **G (Goroutine)** — структура `runtime.g`, содержит стек, program counter, статус, ссылку на текущий M
- **M (Machine)** — OS-поток. Один M выполняет одну G в каждый момент времени
- **P (Processor)** — логический процессор. Содержит **локальную очередь горутин** (run queue). Количество P = `GOMAXPROCS` (по умолчанию = числу CPU)

**Как работает планировщик:**

1. Каждый P имеет локальную очередь (до 256 горутин) + есть глобальная очередь
2. M берёт P, достаёт G из локальной очереди P и выполняет
3. Если локальная очередь пуста — **work stealing**: M крадёт половину горутин из очереди другого P
4. Если красть нечего — берёт из глобальной очереди
5. При блокирующем syscall — M отсоединяется от P, P передаётся другому M (или создаётся новый). Когда syscall завершается, горутина возвращается в очередь

**Preemption:**
- **Кооперативная** — при вызове функций runtime проверяет preemption flag (stackguard)
- **Асинхронная (Go 1.14+)** — sysmon-поток шлёт сигнал `SIGURG` горутине, которая выполняется > 10ms без yield-точек

#### 15. Как завершить все горутины если в сервисе что-то пошло не так?

**Основной подход — `context.Context` с отменой:**

```go
ctx, cancel := context.WithCancel(context.Background())
defer cancel()

// передаём ctx во все горутины
for i := 0; i < n; i++ {
    go worker(ctx)
}

// при ошибке — отменяем контекст
cancel() // все горутины получат сигнал через ctx.Done()
```

**С errgroup (рекомендуемый способ):**

```go
g, ctx := errgroup.WithContext(context.Background())

g.Go(func() error {
    return worker1(ctx)
})
g.Go(func() error {
    return worker2(ctx)
})

if err := g.Wait(); err != nil {
    // первая ошибка отменяет ctx → все горутины получают сигнал
    log.Fatal(err)
}
```

`errgroup.WithContext` создаёт контекст, который **автоматически отменяется** при первой ошибке из любой горутины. `Wait()` ждёт завершения всех горутин и возвращает первую ошибку.

**Для graceful shutdown сервиса:**

```go
ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGINT, syscall.SIGTERM)
defer stop()

// запускаем сервер с этим контекстом
// при получении сигнала ctx отменяется → все горутины начинают завершение
```

### Контекст

#### 16. Какие контексты есть?

Все контексты реализуют интерфейс `context.Context`:
```go
type Context interface {
    Deadline() (deadline time.Time, ok bool)
    Done() <-chan struct{}
    Err() error
    Value(key any) any
}
```

**Корневые контексты (не отменяемые):**
- `context.Background()` — основной корень, используется в `main`, инициализации, тестах
- `context.TODO()` — заглушка, когда контекст нужен, но непонятно какой передать

**Производные контексты:**

| Функция | Описание |
|---|---|
| `WithCancel(parent)` | Возвращает `ctx` + `cancel()`. Вызов `cancel()` отменяет ctx и всех детей |
| `WithTimeout(parent, d)` | Автоматическая отмена через duration `d`. Синтаксический сахар над `WithDeadline` |
| `WithDeadline(parent, t)` | Автоматическая отмена в момент времени `t` |
| `WithValue(parent, k, v)` | Привязывает пару ключ-значение. Для передачи request-scoped данных (trace ID, user ID), **не** для передачи зависимостей |
| `WithCancelCause(parent)` | (Go 1.20+) Как `WithCancel`, но `cancel(err)` принимает причину отмены |
| `WithoutCancel(parent)` | (Go 1.21+) Создаёт контекст, который **не отменяется** при отмене родителя, но сохраняет values |
| `AfterFunc(ctx, f)` | (Go 1.21+) Вызывает `f` в отдельной горутине после отмены `ctx` |

**Правило вложенности:** если у parent deadline 5s, а у child — 10s, то child всё равно отменится через 5s (побеждает более строгий deadline).

#### 17. Какие случаи для использования таймаута?

1. **HTTP-запросы к внешним сервисам** — защита от зависания при недоступности downstream:
```go
ctx, cancel := context.WithTimeout(ctx, 3*time.Second)
defer cancel()
req, _ := http.NewRequestWithContext(ctx, "GET", url, nil)
```

2. **Запросы к БД** — ограничение времени выполнения тяжёлых запросов:
```go
ctx, cancel := context.WithTimeout(ctx, 5*time.Second)
defer cancel()
rows, err := db.QueryContext(ctx, "SELECT ...")
```

3. **gRPC-вызовы** — таймаут на inter-service communication

4. **Graceful shutdown** — даём сервису N секунд на завершение текущих запросов:
```go
ctx, cancel := context.WithTimeout(context.Background(), 15*time.Second)
defer cancel()
server.Shutdown(ctx)
```

5. **Ожидание внешних ресурсов** — подключение к Redis, Kafka, получение лока

6. **Бизнес-SLA** — если запрос клиента не может обрабатываться дольше X секунд по требованиям SLA

### Каналы

#### 18. Что такое каналы?

Канал (`chan`) — это **типизированный примитив для коммуникации между горутинами**. Реализует принцип CSP (Communicating Sequential Processes): "Don't communicate by sharing memory; share memory by communicating."

```go
ch := make(chan int)    // небуферизированный
ch := make(chan int, 5) // буферизированный на 5 элементов
```

**Небуферизированный** (`make(chan T)`):
- Отправка блокируется, пока кто-то не прочитает (и наоборот)
- Обеспечивает **синхронизацию** — happens-before гарантия между отправителем и получателем

**Буферизированный** (`make(chan T, N)`):
- Отправка блокируется только когда буфер **полон**
- Чтение блокируется когда буфер **пуст**
- Семантически похож на очередь (FIFO)

**Внутри runtime:** канал — это структура `runtime.hchan`, содержащая кольцевой буфер, mutex, и очереди ожидающих горутин (sendq, recvq).

#### 19. Что будет если писать в буферизированный канал и никто не читает?

Горутина будет успешно отправлять сообщения **до заполнения буфера**. Как только буфер заполнится, следующая отправка **заблокирует горутину навсегда**.

```go
ch := make(chan int, 2)
ch <- 1 // ОК, буфер: [1]
ch <- 2 // ОК, буфер: [1, 2]
ch <- 3 // БЛОКИРОВКА — буфер полон, никто не читает
```

Если заблокированная горутина — единственная (или все остальные тоже заблокированы), runtime обнаружит **deadlock** и завершит программу:
```
fatal error: all goroutines are asleep - deadlock!
```

> В продакшене это обычно приводит к **goroutine leak** — горутина висит вечно, потребляя память. Поэтому всегда используй `select` с `ctx.Done()` или таймаутом.

#### 20. Что будет если закрыть канал с непрочитанными сообщениями?

**Данные не теряются.** Все непрочитанные сообщения остаются в буфере и могут быть прочитаны:

```go
ch := make(chan int, 3)
ch <- 10
ch <- 20
ch <- 30
close(ch)

fmt.Println(<-ch) // 10
fmt.Println(<-ch) // 20
fmt.Println(<-ch) // 30
fmt.Println(<-ch) // 0 (zero value, канал пуст и закрыт)
```

После `close`:
- **Чтение** — сначала вернёт все оставшиеся сообщения, затем zero value без блокировки
- **Запись** — `panic: send on closed channel`
- **Повторный close** — `panic: close of closed channel`
- `for v := range ch` — корректно прочитает все сообщения и завершит цикл

#### 21. Что такое направленность каналов?

Направленность (directionality) — ограничение канала на **только отправку** или **только чтение** на уровне типа:

```go
chan T     // двунаправленный (send + receive)
chan<- T   // только отправка (send-only)
<-chan T   // только чтение (receive-only)
```

**Неявная конвертация:** двунаправленный канал автоматически приводится к однонаправленному, но **не наоборот**:

```go
func producer(out chan<- int) { // может только отправлять
    out <- 42
}

func consumer(in <-chan int) { // может только читать
    val := <-in
}

ch := make(chan int)
go producer(ch) // chan int → chan<- int — OK
go consumer(ch) // chan int → <-chan int — OK
```

**Зачем:**
- **Контракт на уровне компилятора** — функция не может случайно закрыть канал, из которого должна только читать
- **Документация** — сигнатура функции явно показывает роль канала
- Попытка записи в `<-chan` или чтения из `chan<-` — **ошибка компиляции**

#### 22. Что будет если писать в закрытый канал?

**`panic: send on closed channel`** — runtime паника, которая крашит горутину (и всю программу, если не перехвачена через `recover`).

```go
ch := make(chan int, 1)
close(ch)
ch <- 1 // panic: send on closed channel
```

**Правило:** закрывать канал должен **только отправитель** (или координатор), и **только один раз**. Получатель не должен закрывать канал — он не знает, собирается ли отправитель ещё писать.

**Паттерн безопасного закрытия при нескольких отправителях:**
```go
// Координатор закрывает "done" канал, отправители проверяют:
select {
case out <- value:
case <-done:
    return
}
```

### Примитивы синхронизации

#### 23. Какие примитивы синхронизации есть?

Пакет `sync` и `sync/atomic`:

| Примитив | Назначение |
|---|---|
| **`sync.Mutex`** | Взаимное исключение. `Lock()` / `Unlock()`. Только одна горутина в критической секции |
| **`sync.RWMutex`** | Readers-writer lock. Много параллельных читателей **или** один писатель |
| **`sync.WaitGroup`** | Ожидание завершения группы горутин. `Add(n)`, `Done()`, `Wait()` |
| **`sync.Once`** | Гарантия однократного выполнения функции (потокобезопасная инициализация) |
| **`sync.Map`** | Потокобезопасная мапа. Оптимальна при read-heavy нагрузке с редкими записями и стабильным набором ключей |
| **`sync.Pool`** | Пул переиспользуемых объектов для снижения нагрузки на GC |
| **`sync.Cond`** | Condition variable — горутины ждут наступления условия. `Wait()`, `Signal()`, `Broadcast()` |
| **`sync/atomic`** | Атомарные операции над числами и указателями без блокировок: `Add`, `Load`, `Store`, `Swap`, `CompareAndSwap` |
| **`atomic.Value`** | Атомарное хранение/чтение произвольного значения |

Дополнительно из `golang.org/x/sync`:
- **`errgroup.Group`** — WaitGroup + контекст + первая ошибка
- **`semaphore.Weighted`** — семафор с весами
- **`singleflight.Group`** — дедупликация одновременных вызовов с одинаковым ключом

#### 24. Какой самый популярный кейс для atomic?

**Счётчики и метрики** — самый частый кейс:

```go
var requestCount atomic.Int64 // Go 1.19+

func handler(w http.ResponseWriter, r *http.Request) {
    requestCount.Add(1)
    // ...
}

func metricsHandler(w http.ResponseWriter, r *http.Request) {
    fmt.Fprintf(w, "requests: %d", requestCount.Load())
}
```

Другие популярные кейсы:
- **Флаги состояния** — `atomic.Bool` для graceful shutdown (`isShutdown.Store(true)`)
- **Конфигурация hot-reload** — `atomic.Value` для атомарной подмены структуры конфига
- **Lock-free структуры данных** — `CompareAndSwap` (CAS) для реализации lock-free стека, очереди

**Когда atomic vs mutex:**
- `atomic` — для одной переменной, простые операции (read/write/increment)
- `mutex` — для защиты нескольких связанных переменных или сложной логики

#### 25. Mutex vs RWMutex?

**`sync.Mutex`** — эксклюзивная блокировка:
- `Lock()` — захватить. Если занят — горутина блокируется
- `Unlock()` — отпустить
- В каждый момент времени — **ровно одна** горутина в критической секции

**`sync.RWMutex`** — разделяемая блокировка на чтение/запись:
- `RLock()` / `RUnlock()` — блокировка на чтение (shared). Множество горутин могут держать RLock одновременно
- `Lock()` / `Unlock()` — блокировка на запись (exclusive). Ждёт завершения **всех** читателей, блокирует новых
- При ожидающем `Lock()` новые `RLock()` тоже блокируются (защита от starvation писателя)

**Когда что использовать:**

| Сценарий | Выбор |
|---|---|
| Чтений >> записей (read-heavy, например кеш) | `RWMutex` — читатели не блокируют друг друга |
| Чтений ≈ записей | `Mutex` — проще, меньше overhead |
| Критическая секция очень короткая | `Mutex` — overhead RWMutex не окупится |
| Одна переменная, без сложной логики | `atomic` — быстрее обоих |

**Важно:** `RWMutex` внутри дороже `Mutex` (больше атомарных операций), поэтому выигрыш есть **только** при существенном преобладании чтений и достаточно длинной критической секции.

## PostgreSQL

### Индексы

#### 26. Какие индексы есть в PostgreSQL, какими пользовался?

| Тип индекса | Структура | Когда использовать |
|---|---|---|
| **B-tree** (default) | Сбалансированное дерево | Операции `=`, `<`, `>`, `<=`, `>=`, `BETWEEN`, `IN`, `LIKE 'prefix%'`. **90% случаев** |
| **Hash** | Хеш-таблица | Только `=`. Компактнее B-tree, но менее универсален. С PG 10 WAL-safe |
| **GiST** | Обобщённое поисковое дерево | Геоданные (`PostGIS`), полнотекстовый поиск, range-типы, `@>`, `&&` |
| **GIN** (Generalized Inverted Index) | Инвертированный индекс | `jsonb`-поля (`@>`, `?`, `?&`), массивы, полнотекстовый поиск (`tsvector`) |
| **BRIN** (Block Range Index) | Хранит min/max на блок | Естественно упорядоченные данные (timestamp лога, serial ID). Очень компактный |
| **SP-GiST** | Space-partitioned GiST | Телефонные номера, IP-адреса, неравномерно распределённые данные |

**Варианты:**
- **Partial index** — `CREATE INDEX ... WHERE status = 'active'` — индексирует только подмножество строк
- **Composite index** — `CREATE INDEX ... ON t(a, b, c)` — работает для запросов по prefix (a), (a,b), (a,b,c)
- **Covering index** — `CREATE INDEX ... INCLUDE (col)` — добавляет столбцы в листовые страницы, позволяет Index-Only Scan
- **Unique index** — гарантирует уникальность + используется для поиска
- **Expression index** — `CREATE INDEX ... ON t(lower(email))` — индекс по выражению

В работе чаще всего: **B-tree** (по PK, FK, фильтрам), **GIN** (по jsonb-полям и массивам), **Partial** (для "горячих" подмножеств).

#### 27. Что такое индекс и зачем он нужен?

**Индекс** — это дополнительная структура данных, которая хранит **упорядоченное** (или структурированное) отображение значений столбца → ссылки на строки таблицы (ctid — указатель на heap tuple).

**Аналогия:** предметный указатель в книге — вместо чтения всей книги, находишь термин в алфавитном указателе и переходишь на нужную страницу.

**Зачем:**
- **Ускорение поиска** — вместо Sequential Scan (O(n) — чтение всей таблицы) выполняется Index Scan (O(log n) для B-tree)
- **Ускорение сортировки** — `ORDER BY` по индексированному столбцу не требует дополнительной сортировки
- **Ускорение JOIN** — Nested Loop Join по индексу внутренней таблицы
- **Обеспечение уникальности** — `UNIQUE INDEX` проверяется при вставке/обновлении

**Без индекса:** PostgreSQL выполняет **Seq Scan** — читает каждую строку таблицы и проверяет условие. На таблице в 10М строк это может занимать секунды.

**С индексом (B-tree):** Спускается по дереву за O(log n) шагов, находит нужные ctid, читает только конкретные страницы heap. На 10М строк — миллисекунды.

#### 28. Как понять на что добавить индексы?

**1. `EXPLAIN ANALYZE` — главный инструмент:**
```sql
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT * FROM orders WHERE user_id = 123 AND status = 'pending';
```
Смотрим:
- **Seq Scan** с высокой стоимостью → кандидат на индекс
- **Filter** с большим `Rows Removed by Filter` → фильтр неэффективен, нужен индекс
- **Sort** с `Sort Method: external merge` → сортировка не в памяти, индекс поможет

**2. `pg_stat_user_tables` — статистика использования:**
```sql
SELECT relname, seq_scan, seq_tup_read, idx_scan
FROM pg_stat_user_tables
ORDER BY seq_tup_read DESC;
```
Таблицы с высоким `seq_scan` и `seq_tup_read` — кандидаты.

**3. `pg_stat_statements` — самые тяжёлые запросы:**
```sql
SELECT query, calls, mean_exec_time, total_exec_time
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 20;
```

**4. Эвристики:**
- Столбцы в `WHERE` с высокой **селективностью** (возвращают малый % строк) — хорошие кандидаты
- `JOIN ON` столбцы — FK без индекса = медленный Nested Loop
- `ORDER BY` / `GROUP BY` на больших таблицах
- Столбцы с `UNIQUE` constraint — автоматически создаётся индекс

#### 29. Почему нельзя навесить индексы на всю таблицу?

**1. Замедление записи.** Каждый `INSERT`, `UPDATE`, `DELETE` должен обновить **все** индексы таблицы. Каждый индекс — это отдельная структура данных, которую нужно модифицировать. На таблице с 10 индексами вставка может быть в 5-10 раз медленнее, чем с одним.

**2. Расход дискового пространства.** Индекс хранит копию индексируемых столбцов + ctid. Суммарный размер индексов может **превышать** размер самой таблицы. Это увеличивает объём хранилища и бэкапов.

**3. Расход RAM.** PostgreSQL кэширует горячие страницы индексов в shared_buffers. Больше индексов → больше конкуренция за кэш → горячие данные вытесняются → больше дискового I/O.

**4. Замедление VACUUM.** VACUUM должен очистить dead tuples во **всех** индексах. Больше индексов → дольше vacuum → больше bloat пока vacuum не завершится.

**5. Планировщик может не использовать.** Если селективность низкая (запрос возвращает >5-15% таблицы), планировщик выберет Seq Scan как более эффективный. Индекс существует, потребляет ресурсы, но не используется.

> **Правило:** индекс оправдан, когда ускорение чтения перевешивает замедление записи. Добавляй индексы на основе реальных запросов и `EXPLAIN ANALYZE`, а не "на всякий случай".

### Работа с данными

#### 30. Таблица с 1М записей, нужно сохранить только 1К строк, остальное удалить — как?

`DELETE` 999К строк — плохая идея: огромная транзакция, массивный WAL, долгий VACUUM, блокировки.

**Лучший подход — "пересоздание":**

```sql
-- 1. Создаём новую таблицу с той же структурой
CREATE TABLE orders_new (LIKE orders INCLUDING ALL);

-- 2. Копируем только нужные 1К строк
INSERT INTO orders_new
SELECT * FROM orders WHERE <условие_отбора>;

-- 3. В одной транзакции меняем местами
BEGIN;
ALTER TABLE orders RENAME TO orders_old;
ALTER TABLE orders_new RENAME TO orders;
COMMIT;

-- 4. Удаляем старую таблицу
DROP TABLE orders_old;
```

`INCLUDING ALL` копирует индексы, constraints, defaults, sequences.

**Преимущества:**
- Новая таблица **компактна** — нет dead tuples, не нужен VACUUM
- `RENAME` — мгновенная операция (меняет имя в каталоге), **не копирует данные**
- Минимальный downtime — только на момент `BEGIN...COMMIT`
- WAL-нагрузка — только на 1К вставок вместо 999К удалений

**Альтернатива через TRUNCATE + INSERT (если допустим кратковременный лок):**
```sql
-- сохраняем нужное во временную
CREATE TABLE orders_keep AS
SELECT * FROM orders WHERE status = 'active' LIMIT 1000;

-- truncate быстрее чем delete — не пишет строки в WAL
TRUNCATE orders; -- мгновенно, но берёт ACCESS EXCLUSIVE lock

-- возвращаем нужное
INSERT INTO orders SELECT * FROM orders_keep;
DROP TABLE orders_keep;
```

#### 31. Усложнение: во время очистки могут прийти нужные записи, как не потерять?

Проблема: между копированием нужных строк и переименованием могут прийти новые `INSERT`-ы в старую таблицу, которые мы потеряем.

**Решение 1 — Транзакция с блокировкой:**
```sql
BEGIN;

-- блокируем таблицу от записи на время операции
LOCK TABLE orders IN SHARE ROW EXCLUSIVE MODE;

-- сохраняем нужное
CREATE TEMP TABLE orders_keep AS
SELECT * FROM orders WHERE status = 'active';

-- чистим
TRUNCATE orders;

-- возвращаем
INSERT INTO orders SELECT * FROM orders_keep;

COMMIT;
-- после коммита новые записи снова идут в таблицу
```
`EXCLUSIVE MODE` блокирует `INSERT/UPDATE/DELETE`, но разрешает `SELECT`. Новые записи подождут в очереди и после `COMMIT` попадут уже в новую таблицу `orders`.

**Решение 2 — Партиционирование (если задача регулярная):**
Разделить таблицу по времени. "Очистка" = detach/drop старой партиции. Новые записи всегда идут в актуальную партицию.

**Решение 3 — Мягкое удаление батчами (если downtime недопустим):**
```sql
-- Удаляем батчами по 10К, не блокируя таблицу надолго
DELETE FROM orders
WHERE id IN (
    SELECT id FROM orders
    WHERE NOT <условие_сохранения>
    LIMIT 10000
);
-- Повторяем в цикле, пока есть что удалять
-- Между батчами — пауза для снижения нагрузки
```
Новые записи не теряются, так как таблица никогда не блокируется эксклюзивно.

## Архитектура и инфраструктура

#### 32. Что такое gRPC?

**gRPC** (Google Remote Procedure Call) — высокопроизводительный RPC-фреймворк от Google, работающий поверх **HTTP/2**.

**Ключевые компоненты:**
- **Protocol Buffers (protobuf)** — язык описания интерфейсов (IDL) и бинарный формат сериализации. Контракт описывается в `.proto`-файле
- **HTTP/2** — мультиплексирование (несколько запросов в одном TCP-соединении), сжатие заголовков (HPACK), server push
- **Кодогенерация** — из `.proto` генерируются клиент и сервер для 10+ языков

```protobuf
service OrderService {
    rpc CreateOrder (CreateOrderRequest) returns (CreateOrderResponse);
    rpc StreamUpdates (OrderFilter) returns (stream OrderUpdate); // server streaming
}
```

**Типы взаимодействия:**
1. **Unary** — один запрос → один ответ (как обычный HTTP)
2. **Server streaming** — один запрос → поток ответов
3. **Client streaming** — поток запросов → один ответ
4. **Bidirectional streaming** — поток ↔ поток

**Встроенные возможности:** дедлайны/таймауты, отмена (propagation), interceptors (middleware), балансировка нагрузки, TLS, health checks.

#### 33. Чем gRPC отличается от REST?

| Свойство | gRPC | REST |
|---|---|---|
| **Протокол** | HTTP/2 | HTTP/1.1 (чаще) или HTTP/2 |
| **Формат данных** | Protobuf (бинарный) | JSON (текстовый), реже XML |
| **Контракт** | `.proto`-файл (строгий, кодогенерация) | OpenAPI/Swagger (опциональный) |
| **Модель взаимодействия** | Unary + 3 вида streaming | Request-Response |
| **Производительность** | Высокая (бинарная сериализация, мультиплексирование, сжатие) | Ниже (текстовый JSON, один запрос на соединение в HTTP/1.1) |
| **Человекочитаемость** | Нет (бинарный формат) | Да (JSON в браузере/curl) |
| **Браузерная поддержка** | Нужен grpc-web прокси | Нативная |
| **Связность** | Тесная (клиент и сервер должны знать .proto) | Слабая (REST — архитектурный стиль, свобода) |
| **Когда выбирать** | Межсервисная коммуникация (внутренний трафик), streaming, low-latency | Публичные API, веб-клиенты, простые CRUD |

#### 34. Что такое REST?

**REST** (Representational State Transfer) — **архитектурный стиль** проектирования распределённых систем, описанный Роем Филдингом в 2000 году.

**6 ограничений (constraints) REST:**

1. **Client-Server** — разделение ответственности между клиентом (UI) и сервером (данные/логика)
2. **Stateless** — каждый запрос содержит **всю** информацию для обработки. Сервер не хранит сессию клиента между запросами
3. **Cacheable** — ответы должны явно указывать, можно ли их кэшировать
4. **Uniform Interface** — единообразный интерфейс:
   - Идентификация ресурсов через URI (`/api/orders/123`)
   - Манипуляция ресурсами через представления (JSON, XML)
   - Самоописательные сообщения (Content-Type, методы HTTP)
   - HATEOAS — гипермедиа как движок состояния (ссылки в ответах)
5. **Layered System** — клиент не знает, общается ли он с конечным сервером или промежуточным (proxy, load balancer)
6. **Code on Demand** (опционально) — сервер может передавать исполняемый код (JavaScript)

**RESTful API на практике:**
- Ресурсы = существительные: `/users`, `/orders/42`
- HTTP-методы = действия: `GET` (чтение), `POST` (создание), `PUT` (полное обновление), `PATCH` (частичное), `DELETE` (удаление)
- HTTP-коды = результат: `200 OK`, `201 Created`, `404 Not Found`, `409 Conflict`

> Большинство "REST API" в реальности — **HTTP API**, не соблюдающие все 6 constraints (особенно HATEOAS). Это нормально и даже ожидаемо.

#### 35. Kafka vs RabbitMQ?

| Свойство | Apache Kafka | RabbitMQ |
|---|---|---|
| **Модель** | **Distributed commit log** — append-only лог, consumer читает по offset | **Message broker** (AMQP) — очередь сообщений с routing |
| **Хранение** | Сообщения **сохраняются** на диск (retention по времени/размеру). Можно перечитать | Сообщения **удаляются** после подтверждения (ack). По умолчанию — очередь |
| **Доставка** | Pull-модель — consumer сам тянет | Push-модель — broker пушит consumer-у |
| **Пропускная способность** | Очень высокая (миллионы msg/sec). Батчинг, zero-copy, sequential I/O | Средняя (десятки тысяч msg/sec). Каждое сообщение обрабатывается индивидуально |
| **Гарантии доставки** | At-least-once, at-most-once, exactly-once (transactional API) | At-least-once, at-most-once (manual ack/nack) |
| **Ordering** | **Гарантирован внутри партиции** | Гарантирован в пределах одной очереди |
| **Routing** | Простой — по topic + partition key | Гибкий — exchange types: direct, topic, fanout, headers |
| **Consumer groups** | Встроенные — горизонтальное масштабирование consumers | Competing consumers на одной очереди |
| **Масштабирование** | Горизонтальное (партиции по брокерам) | Вертикальное + кластер (менее тривиально) |
| **Latency** | Выше (батчинг ради throughput) | Ниже (отдельные сообщения) |

**Когда Kafka:**
- Event sourcing, event-driven architecture
- Высокий throughput (логи, метрики, аналитика)
- Нужна повторная обработка (replay) сообщений
- Stream processing (Kafka Streams, Flink, ksqlDB)
- Несколько независимых consumer-ов одного потока данных

**Когда RabbitMQ:**
- Классические task queues (обработка задач воркерами)
- Нужна гибкая маршрутизация (routing по заголовкам, паттернам)
- Важна низкая latency отдельных сообщений
- Request-reply паттерн
- Простое развёртывание для небольших нагрузок
