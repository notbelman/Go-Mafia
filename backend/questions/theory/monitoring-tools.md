## Ответы исходя из МОЕЙ легенды

**1. Какими средствами мониторинга и логирования пользуетесь?**

Prometheus для метрик, Grafana для дашбордов и алертов, Loki для централизованных логов. На Bitfinex ещё Elasticsearch + Kibana и Sentry для ошибок. Логируем через zap в JSON с request ID для трассировки. Алерты летят в Telegram.

---

**2. Какие задачи решают метрики и какие — логи?**

Метрики — это числа для ответа на вопрос "что происходит сейчас": RPS, латенси, размер очереди, лаг Kafka, hit rate кеша. По ним строишь дашборды и алерты. Логи — это контекст для ответа на вопрос "почему это произошло": конкретный запрос, конкретная ошибка, stack trace, request ID. Метрики говорят что сломалось, логи — почему.

---

**3. Как подключить Prometheus к Go-сервису? Писал ли кастомные метрики?**

Подключаешь `promhttp.Handler()` на `/metrics`, регистрируешь метрики через `prometheus.NewCounterVec`, `NewHistogramVec` и т.д. Да, писал кастомные: `document_queue_size` — размер очереди документов, `exchange_request_duration_seconds` — латенси бирж, `kafka_consumer_lag` — отставание консьюмеров, `balance_below_threshold_total` — алерт на низкий баланс, `algorithm_decisions_total` — сколько решений принял алгоритм. Все метрики с лейблами: биржа, токен, тип алгоритма.

---

**4. Откуда берутся данные для Grafana?**

Grafana сама не собирает данные, она только визуализирует. Источники: Prometheus для метрик, Loki для логов, ClickHouse для аналитики (на Bitfinex — история ордеров, сделок, свечей). Настраиваешь data source, пишешь PromQL или LogQL запросы, строишь панели.

---

**5. Что такое pprof, для чего и как его использовать?**

pprof — встроенный профилировщик Go. Подключаешь `net/http/pprof`, он даёт эндпоинты: `/debug/pprof/heap` для памяти, `/debug/pprof/profile` для CPU, `/debug/pprof/goroutine` для горутин. Смотришь flame graph — видишь какие функции жрут CPU или выделяют память. На Bitfinex использовал когда cex-ws-api начал потреблять много памяти — через heap profile нашёл что не освобождались буферы WebSocket при реконнектах.

---

**6. Сервис потребляет много памяти и падает по OOM — как решать?**

Сначала снимаю heap profile через pprof, смотрю какие объекты занимают память и кто их аллоцирует. Проверяю горутины — не утекают ли (goroutine profile). Смотрю метрики: растёт ли потребление линейно или скачками. На TMS-проекте document-service падал по OOM при генерации тяжёлых отчётов — каждый отчёт держал все данные в памяти. Решили батчингом: обрабатываем данные порциями, а не грузим всё сразу. Плюс ограничили параллельные воркеры до 10.

---

**7. Как наблюдать утечку памяти или 100% CPU?**

Метрики в Grafana: `process_resident_memory_bytes`, `go_memstats_heap_inuse_bytes`, CPU usage. Если растёт монотонно — утечка. Дальше pprof: heap profile покажет где аллокации, CPU profile покажет какие функции жрут процессор. Goroutine profile — не утекают ли горутины (частая причина утечек). На Bitfinex отслеживал через дашборд "Биржи и соединения" — если WebSocket-соединения отваливались и не чистились, горутины копились.

---

**8. Можно ли понять, на какую часть логики сервис тратит память?**

Да, через pprof heap profile. Он показывает дерево аллокаций: какая функция → какой вызов → сколько байт. Можно отфильтровать по конкретному пакету. Например, видишь что 80% памяти в `document-service` уходит на `generateMonthlyReport` → `loadAllTrips` — значит проблема в том что грузишь все рейсы за месяц в память разом.

---

**9. Как находил узкие места в продакшене?**

Начинаю с метрик и алертов — они показывают где проблема. Дальше логи с request ID для конкретного запроса. На Bitfinex: `exchange_request_duration_seconds` показал что одна биржа тормозит → временно отключили алгоритмы. `kafka_consumer_lag` вырос на cex-candles → добавили воркеров. На TMS: `pg_query_duration_seconds` показал медленные JOIN-ы → добавили индекс по `driver_id` и `trip_date`. На marketplace: после релиза аукциона `api_error_total` показал рост 500-х → нашли баг в валидации ставок.

---

**10. Что такое трейсинг и за счёт чего он работает?**

Трейсинг — отслеживание пути запроса через цепочку сервисов. Каждый запрос получает trace ID, каждый сервис добавляет свой span с таймингами. Видишь всю цепочку: откуда пришёл запрос, сколько времени провёл в каждом сервисе, где задержка. У нас использовали Loki + Grafana с request ID через zap-логирование — не полноценный distributed tracing как Jaeger, но по request ID можно собрать весь путь запроса через логи. На Bitfinex трейсил путь ордера: cex-algo → cex-ws-api → биржа → cex-orders — видно где задержка.

---

**11. 500-ка за фасадом 500 микросервисов — как разобраться?**

У нас было 7-11 сервисов, не 500, но принцип тот же. Сначала алерт показывает какой сервис отдаёт 500. Дальше по request ID иду в логи — вижу цепочку вызовов. Метрики сужают область: если `pg_query_duration_seconds` взлетел — проблема в базе, если `exchange_request_duration_seconds` — проблема на бирже. Если ошибка межсервисная — иду по trace: видно какой сервис вернул ошибку первым.

---

**12. Есть ли способ превентивно узнать о проблемах? Работал ли с алёртами?**

Да, настраивал алерты на всех проектах. Примеры: `document_queue_size > 50` — очередь растёт, скоро коллапс. `kafka_consumer_lag > 60 сек` — консьюмер не успевает. `websocket_connections_active < expected` — отвалилось соединение. `balance_below_threshold` — кончаются деньги на бирже. `pg_query_duration p99 > 1.5 сек` — база перегружена. `algorithm_decisions_total = 0 за 30 мин` — алгоритм остановился. Алерты летят в Telegram, дежурный реагирует. На TMS алерт по очереди сработал и мы успели среагировать до того как пользователи начали жаловаться.

---

**13. Что конкретно ищешь в логах среди огромного потока?**

Фильтрую по: request ID конкретного запроса, уровню ошибки (error/fatal), имени сервиса, временному окну. Ищу первую ошибку в цепочке — часто каскад начинается с одной. Смотрю контекст: какой пользователь, какой эндпоинт, какие параметры. На Bitfinex: по request ID находил почему ордер не исполнился — видел всю цепочку от решения алгоритма до ответа биржи. Через Loki в Grafana удобно: фильтр по лейблам сервиса + grep по тексту ошибки.

---

**14. Какие инструменты нужны чтобы понять что происходит с консьюмером?**

`kafka_consumer_lag` в Prometheus — растёт ли отставание. Логи консьюмера — есть ли ошибки обработки. Метрики throughput — сколько сообщений в секунду обрабатывает. На Bitfinex: лаг на cex-candles вырос до 30 секунд при высокой волатильности — увидели в дашборде Kafka, добавили воркеров, лаг упал.

---

**15. Настройки мониторинга были общие или у каждого департамента свои?**

У нас была одна команда на продукт, поэтому мониторинг общий — один Prometheus, одна Grafana. Но дашборды разделены по зонам ответственности: дашборд по биржам и соединениям, по алгоритмам, по Kafka, по базе. На TMS аналогично: отдельный дашборд по документам, по рейсам, по ошибкам API. Каждый смотрит свою зону, но инфраструктура общая.

---

**16. Что помогало в решении инцидентов и как сократить время поиска?**

Три вещи: алерты (узнаёшь о проблеме раньше пользователей), структурированные логи с request ID (быстро находишь конкретный запрос), дашборды с ключевыми метриками (сразу видишь картину). На Bitfinex время обнаружения сбоев сократилось с 15 минут до 2 после настройки мониторинга. На TMS после инцидента с генерацией документов добавили алерт на размер очереди — следующий раз увидели проблему до того как она стала критичной.
