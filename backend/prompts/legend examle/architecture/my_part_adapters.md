# Моя часть — Телематический Pipeline

## Контекст

Телематический pipeline TMS ЛАНИТ. Моя зона ответственности — весь hot path от провайдеров до нормализованных событий в Kafka:

**5 адаптеров → Kafka (telematics.raw) → Telematics Service → Kafka (3 топика) → downstream сервисы**

Детальный разбор каждого адаптера (edge cases, failure modes, протоколы): [[Менторство/резюме/старые/белман/созанов алексей/Ланит/architecture/adapters_deep_dive]]

## Провайдеры и адаптеры

### Решение: 1 провайдер = 1 отдельный сервис-адаптер

Причина: у каждого провайдера свой протокол с разной моделью соединения — WebSocket-клиент, HTTP-сервер для webhook, TCP-сервер, REST-поллер, SOAP-клиент. Объединять = смешивать разные failure-режимы в одном процессе. Один адаптер упал — остальные четыре работают.

| Адаптер | Провайдер | Протокол | Модель | Как работает |
|---|---|---|---|---|
| Navixy Adapter | Navixy | **WebSocket** | Push | Persistent WS соединение, event-driven. Провайдер стримит события |
| СКАУТ Adapter | СКАУТ | **REST JSON** | Pull (батч) | `GET /events?from=last_ts` раз в 1 сек. Один запрос = пачка событий от всех ТС провайдера |
| Omnicomm Adapter | Omnicomm | **Webhook** | Push | Провайдер POST-ит на наш HTTP endpoint при каждом событии |
| Wialon Adapter | Wialon | **TCP binary** (Wialon IPS) | Push | Persistent TCP-соединение, открытый бинарный протокол, парсим фреймы |
| АвтоГРАФ Adapter | АвтоГРАФ | **SOAP XML** | Pull (батч) | Legacy провайдер. Забираем батч по расписанию, кастомный маршалинг XML в Go |

### Все адаптеры stateless

- Без PG, без Redis, без кеша
- Задача: принял пакет от провайдера → распарсил → смаппил в protobuf → отправил в Kafka
- При рестарте: push-адаптеры (WS, Webhook, TCP) — провайдер переподключается или досылает. Pull-адаптеры (СКАУТ, АвтоГРАФ) — запрашивают с небольшим overlap, дубли ловит Telematics Service

### Pull vs Push — trade-offs

| | Push (WS, Webhook, TCP) | Pull (REST, SOAP) |
|---|---|---|
| Задержка | Минимальная — событие приходит сразу | До 1 сек (интервал поллинга) |
| Контроль нагрузки | Провайдер контролирует — может заспамить | Мы контролируем — забираем когда готовы |
| Reconnect | Наша ответственность — нужен reconnect с backoff | Не нужен — каждый запрос независимый |
| Дубли | Провайдер может дослать при реконнекте (2-3 сек окно) | При ретрае тот же батч (5-10 сек окно) |
| Потеря данных | Если мы лежим — провайдер может копить или терять | Данные копятся на стороне провайдера, заберём позже |

## Разделение ответственности

| Слой | Что делает | Чего НЕ делает |
|---|---|---|
| **Адаптер** | Парсит формат провайдера, маппит в protobuf, разбивает один пакет трекера на 1-3 события по типу (GPS/ENGINE/DRIVER_EVENT) | Не валидирует бизнес-правила |
| **Telematics Service** | Валидация, роутинг в нужный топик по типу события | Не знает ничего про формат провайдеров, ничего не хранит |

**Адаптер = структурная нормализация** (из формата провайдера → единый protobuf).
**Telematics Service = бизнес-валидация + роутинг** (валидно? куда роутить?).

Adapter Pattern в чистом виде: если завтра добавится шестой провайдер — пишем один адаптер, Telematics Service не трогаем.

### Один пакет от трекера → несколько событий

Трекер на машине шлёт всё в одном пакете: GPS + engine + alerts. Адаптер разбирает и генерит 1-3 события:

```
Пакет от Wialon (бинарный):
  lat: 55.7, lon: 37.6, speed: 80, fuel: 45%, rpm: 2100, ignition: true

Адаптер генерит:
  → RawTelematicsEvent{type: GPS, lat: 55.7, lon: 37.6, speed: 80, ...}
  → RawTelematicsEvent{type: ENGINE, fuel_level: 45, rpm: 2100, ignition: true, ...}
```

Driver events — по триггеру (резкое торможение, превышение скорости). Если в пакете есть alert-флаг → адаптер генерит третье событие.

## Формат данных — Protobuf

### Почему Protobuf, а не JSON

| | Protobuf | JSON |
|---|---|---|
| Размер | ~300 байт на событие | ~500-700 байт |
| Типизация | Из коробки (.proto файл = контракт) | Нет, строки везде |
| Скорость сериализации | Быстрее (бинарный) | Медленнее (текстовый парсинг) |
| Читаемость | Нечитаемый (бинарный) | Читаемый |
| Совместимость с gRPC | Нативная (gRPC в стеке) | Нужна конвертация |
| Версионирование | Backward/forward compatible (новые поля = новые номера) | Ломается при изменении структуры |

При ~2K events/sec разница 200-400 байт на событие = **400-800 КБ/с экономии трафика** в Kafka. На пиках (массовый утренний старт, burst от провайдеров) разница ещё заметнее.

### Как Kafka работает с Protobuf

Kafka хранит **просто байты** — ей безразлично что внутри: JSON, protobuf, avro, картинка.

```
Producer (адаптер):
  event := &RawTelematicsEvent{...}
  bytes, _ := proto.Marshal(event)     // Go: google.golang.org/protobuf
  producer.Send("telematics.raw", bytes)  // Kafka получает []byte

Consumer (Telematics Service):
  bytes := consumer.Read("telematics.raw")
  event := &RawTelematicsEvent{}
  proto.Unmarshal(bytes, event)         // обратно в структуру
```

**Schema Registry (Confluent)** — опционально. Хранит .proto-схемы, проверяет совместимость при деплое нового producer-а. Мы использовали: producer регистрирует схему, consumer валидирует — защита от случайного слома контракта при деплое.

**Процесс schema evolution (как обновляем .proto без downtime):**

- **Все поля `optional`** (proto3 default). Никогда не добавляем `required` — это ломает forward compatibility.
- **Новое поле = новый номер** (`field_number`). Номера **никогда не переиспользуем**, даже если поле удалено — помечаем `reserved 28;` / `reserved "old_name";`. Переиспользование = catastrophic: старый consumer прочитает новое значение по старой семантике.
- **Переименование поля** — ок. Wire format идёт по номеру, не по имени. Но нужно согласовать с downstream — код генерируется из .proto и в нём используется имя поля.
- **Смена типа поля** — breaking change. Делаем в два шага: (1) добавляем новое поле с новым номером и новым типом, producer пишет оба поля в течение grace period, consumer читает приоритетно новое, (2) через N релизов удаляем старое поле (помечаем `reserved`).
- **CI проверка:** Schema Registry в CI-пайплайне. При PR с изменением .proto запускается `buf breaking` (или аналог) против `main` — breaking changes блокируют merge. Non-breaking auto-register при деплое.
- **Порядок релиза:** сначала деплоим consumer-ы (они готовы читать новые поля, игнорируют неизвестные), потом producer-ы (начинают писать новые поля). Обратный порядок = consumer получает новое поле, не знает что с ним делать, игнорирует — тоже ок для protobuf.

### Незаполненные поля = 0 байт

Protobuf не сериализует дефолтные значения. Событие типа GPS с 7 заполненными полями из 25 возможных → в проводе только эти 7. Это ключевое: одна структура на все типы событий, но каждое событие компактное.

### .proto файл

```protobuf
syntax = "proto3";
package telematics;

message RawTelematicsEvent {
  // === Общее (всегда заполнено) ===
  string    event_id    = 1;   // UUID, генерит адаптер
  string    vehicle_id  = 2;   // ID транспортного средства у нас в системе
  string    provider    = 3;   // "navixy", "scout", "omnicomm", "wialon", "avtograf"
  EventType type        = 4;   // тип события — определяет какие поля заполнены
  int64     timestamp   = 5;   // unix ms, время от трекера (его часы)
  int64     received_at = 6;   // unix ms, когда адаптер получил (наши часы)

  enum EventType {
    GPS          = 0;
    ENGINE       = 1;
    DRIVER_EVENT = 2;
  }

  // === GPS (заполнено при type = GPS) ===
  double lat         = 10;   // широта
  double lon         = 11;   // долгота
  double speed       = 12;   // км/ч
  double heading     = 13;   // 0-360 градусов, направление движения
  double altitude    = 14;   // метры над уровнем моря
  int32  satellites  = 15;   // кол-во спутников (качество GPS-сигнала)
  double hdop        = 16;   // horizontal dilution of precision (чем меньше — тем точнее)

  // === Engine (заполнено при type = ENGINE) ===
  double fuel_level      = 20;  // % (0-100), текущий уровень топлива
  double fuel_consumed   = 21;  // литры, абсолютное значение с начала поездки
  int32  engine_rpm      = 22;  // обороты двигателя
  double odometer        = 23;  // км, пробег
  bool   ignition        = 24;  // зажигание вкл/выкл
  double coolant_temp    = 25;  // °C, температура охлаждающей жидкости
  double battery_voltage = 26;  // вольты, напряжение бортовой сети
  int32  engine_hours    = 27;  // моточасы (для расчёта ТО)

  // === Driver events (заполнено при type = DRIVER_EVENT) ===
  string driver_event_code = 30;  // код события:
                                   // "harsh_brake"    — резкое торможение
                                   // "harsh_accel"    — резкое ускорение
                                   // "speeding"       — превышение скорости
                                   // "geofence_exit"  — выход из геозоны
                                   // "geofence_enter" — вход в геозону
                                   // "idle_start"     — начало простоя
                                   // "idle_end"       — конец простоя
                                   // "sos"            — тревожная кнопка
  double event_value       = 31;  // контекст: скорость при превышении, G-force при торможении
  double event_lat         = 32;  // широта в момент события
  double event_lon         = 33;  // долгота в момент события
}
```

**Нумерация с пропусками (1-6, 10-16, 20-27, 30-33):** protobuf best practice. Оставляет место для новых полей в каждой секции. Например, добавить `tire_pressure = 28` в Engine — без конфликтов и без слома обратной совместимости.

**`received_at` vs `timestamp`:** разница между ними = лаг доставки. Мониторили: если `received_at - timestamp > 30 сек` → алерт, провайдер тормозит или сеть между нами деградирует.

## Kafka

### Кластер

Kafka — общая шина на весь проект TMS. Один кластер, не отдельная инсталляция для телематики.

| Параметр | Значение |
|---|---|
| Брокеров | 3 (стандартный минимум) |
| Replication factor | 3 (каждое сообщение на всех брокерах) |
| min.insync.replicas | 2 (запись успешна когда подтвердили 2 из 3) |
| Деплой | K8s, Strimzi оператор (управляет брокерами как CRD) |

**Зачем 3 брокера:** минимум для отказоустойчивости. Один упал → два оставшихся держат все данные (replication factor = 3), запись продолжается (min.insync.replicas = 2). На нашей нагрузке (~2K/sec, 610 КБ/с) — 3 брокера с огромным запасом, Kafka держит сотни тысяч msg/sec на кластер.

### Как работает Consumer Group

Kafka не "отправляет" сообщения сервисам. **Сервисы сами тянут** (poll).

```
Топик: telematics.raw (8 партиций)
Ключ партиционирования: vehicle_id
  → hash("truck-42") % 8 = 5 → партиция 5
  → ВСЕ события truck-42 ВСЕГДА в партиции 5

Consumer group: "telematics-service" (2 инстанса в норме)

Kafka-координатор распределяет:
  Инстанс 1 ← партиции [0, 1, 2, 3]    → ~7 500 ТС × ~250 events/sec
  Инстанс 2 ← партиции [4, 5, 6, 7]    → ~7 500 ТС × ~250 events/sec

Правило: одну партицию читает СТРОГО ОДИН consumer в группе.
→ нет гонок, нет дублей между инстансами
→ порядок событий для конкретного ТС гарантирован
```

Каждый инстанс при старте говорит Kafka: "я в группе `telematics-service`". Координатор (один из брокеров) распределяет партиции. Инстансы **сами** вычитывают сообщения из своих партиций.

### Топики

#### Сырые данные (вход)

| Топик | Кто пишет | RPS | Партиций |
|---|---|---|---|
| `telematics.raw` | Все 5 адаптеров | ~2 030/sec | 8 |

**Почему 8 партиций:** 2-4 инстанса Telematics Service в consumer group. 8 × 250 events/sec на партицию = 2000/sec с запасом на пики. 8 делится на 2 и 4 — ровное распределение. Запас партиций в 2-4× от текущих инстансов позволяет вертикально наращивать consumer group до 8 без перепартиционирования (а перепартиционирование онлайн ломает гарантию порядка по `vehicle_id` — лучше сразу с запасом).

**Ключ партиционирования: `vehicle_id`.** Все события одного ТС в одной партиции → один consumer → порядок событий для конкретного ТС гарантирован (downstream Tracking/Analytics видит их в правильной последовательности, это важно для построения маршрутов и вычисления скоростей).

#### Нормализованные данные (выход Telematics Service)

| Топик | Что внутри | RPS | Кто читает |
|---|---|---|---|
| `telematics.gps` | Координаты, скорость, heading | ~1 500/sec | Tracking, Routing |
| `telematics.engine` | RPM, топливо, одометр, зажигание | ~500/sec | Analytics |
| `telematics.driver-events` | Резкое торможение, превышение, геозоны | ~30/sec | Notification, Analytics |

**Почему 3 топика, а не один:**
- **Разный RPS** — GPS 1.5K/sec, engine 500/sec, driver events 30/sec. В одном топике GPS забивает consumer-ов которым нужно только engine/driver-events
- **Разные consumer-ы** — Routing-у не нужно топливо, Notification-у не нужны все координаты (только driver events). Если один топик — каждый consumer читает всё и дропает ненужное впустую
- **Разный retention** — GPS жрёт ~75% storage (1.5K × 300 байт vs 500 × 300 байт vs 30 × 300 байт). Можно поставить retention 7 дней на `.gps` и 30-90 дней на `.driver-events`
- **Независимое масштабирование** — `.gps` нужно 8 партиций, `.driver-events` хватит 2

## Telematics Service

### Зачем он вообще нужен — почему не делать всё в адаптерах

Закономерный вопрос: адаптер уже парсит формат провайдера и кладёт в Kafka. Почему бы ему сразу не провалидировать и не разложить по нужным топикам? Зачем отдельный сервис в середине?

**Альтернатива, которую я рассматривал:**

```
Вариант A (выбранный): Адаптер → telematics.raw → Telematics Service → .gps/.engine/.driver-events
Вариант B (отклонённый): Адаптер (парсинг + валидация + роутинг) → .gps/.engine/.driver-events
```

**Сравнение:**

| Аспект | A (отдельный Telematics) | B (всё в адаптерах) |
|---|---|---|
| Код валидации | В одном месте | Копипаста в 5 адаптерах или общая Go-библиотека |
| Знание про downstream топики | Только у Telematics | **У всех 5 адаптеров** — утечка знаний вниз по pipeline |
| Изменить правило валидации (`satellites >= 5`) | 1 PR → 1 деплой | 5 PR → 5 деплоев (или 1 PR в библиотеку + 5 передеплоев) |
| Добавить новый тип события (`.maintenance`) | 1 PR в Telematics | 5 адаптеров должны узнать о новом топике |
| Добавить нового провайдера | Новый адаптер, Telematics не трогаем | Новый адаптер повторяет всю валидацию/роутинг |
| Рассинхрон поведения между провайдерами | Невозможен | **Возможен** — забыли обновить библиотеку в одном адаптере |
| Latency | +1 Kafka hop (~5-10 мс) | Минус этот hop |
| Количество сервисов | 5 адаптеров + Telematics = 6 | 5 адаптеров |

**Почему выбрали A — два ключевых аргумента:**

**1. Разделение ответственности.** Адаптер отвечает за "**внешний мир** → наш формат". Его боль — протоколы провайдеров: WS reconnect, бинарные TCP-фреймы, SOAP маршалинг, 5 моделей авторизации. Это грязная, специфичная для провайдера работа. Telematics Service отвечает за "наш сырой формат → **наша внутренняя бизнес-модель**". Его боль — бизнес-правила (что считаем валидным GPS, куда роутим какой тип). Это два разных слоя, смешивать их = каждый адаптер превращается в полу-бизнес-сервис.

**2. Изоляция скорости изменений.** Бизнес-правила валидации меняются часто (продакт приносит: "добавьте фильтр `speed > 200`", "добавьте новый driver event `tailgating`"). Протоколы провайдеров меняются редко (Wialon не меняет TCP несколько лет). Если всё в адаптере — каждое изменение бизнес-логики требует трогать редко-меняющийся код парсеров провайдеров. Риск сломать то, к чему не должен был прикасаться. Разделение сервисов = разделение скоростей изменений.

**Trade-off, который мы осознанно приняли:** +1 Kafka hop (~5-10 мс latency), +1 сервис в операции. Для GPS телеметрии с периодичностью ~1 сек эта latency некритична, а центральная точка изменений бизнес-логики стоит того.

**Когда B был бы правильным выбором:** 1-2 адаптера (копипаста минимальна), критичная latency (торговый pipeline), тривиальная валидация. У нас все три условия против: 5 адаптеров, latency не критична, валидация нетривиальна и растёт.

**Почему не общая Go-библиотека `telematics-common` вместо сервиса.** Библиотека решает дублирование кода, но не решает главное: (а) рассинхрон поведения при обновлении — если в одном адаптере версия библиотеки отстала, он валидирует по-старому; (б) утечку знаний про downstream топики во все адаптеры; (в) обновление валидации всё равно требует передеплоя всех 5 адаптеров. Библиотека — валидная альтернатива, но сервис даёт центральную точку изменений без риска рассинхрона.

### Почему один сервис (не разделять Validation и Router)

Все операции — один pipeline над одним событием:
1. Десериализация protobuf (наносекунды)
2. Валидация (in-memory, микросекунды)
3. Роутинг в топик по `type` (один `producer.Send`)

Разделять на 2 сервиса (Validation → Router) = лишний сетевой хоп через Kafka, второй деплой, вторая consumer group. Latency вырастет, операционная сложность — тоже. Выигрыша ноль: логика простая, bottleneck — Kafka I/O, не CPU.

### PG — нет. Redis — нет.

Telematics Service **ничего не хранит**, ни персистентно, ни в памяти. Он чистый pipe: прочитал из Kafka → провалидировал → записал в нужный топик Kafka по типу события. База данных не нужна, кеш не нужен.

**Почему нет дедупликации на этом уровне.** Kafka работает по модели at-least-once: при падении consumer-а / ребалансе / рестарте — перечитываются незакоммиченные сообщения, возможны дубли. Обрабатывать дубли на уровне Telematics Service через in-memory кеш бессмысленно: кеш теряется при рестарте / ребалансе, и дубли всё равно проскакивают в downstream. Раз downstream должен быть идемпотентен в любом случае — отдельный слой дедупа избыточен. Дубли штатно обрабатываются consumer-ами ниже: Tracking Service через `INSERT ... ON CONFLICT (vehicle_id, timestamp) DO NOTHING`, Redis через перезапись `HSET` тем же значением, Analytics через `ReplacingMergeTree` в ClickHouse, Notification Service через `event_id` как idempotency key.

### Stateless

**Полностью stateless.** Нет кеша, нет локального состояния, нет PVC. Инстансы взаимозаменяемы — K8s может убивать, масштабировать, ребалансить без последствий. Нет миграций, нет бэкапов, нет warm-up периода после старта.

Для сравнения, **stateful** — это когда потеря данных = проблема: PG с заказами, Redis с текущими позициями в Tracking Service. Там нужны реплики, бэкапы, PVC. У Telematics Service ничего этого нет.

### Graceful shutdown

K8s при остановке пода: `SIGTERM` → grace period (`terminationGracePeriodSeconds: 30`) → `SIGKILL`. За это окно Telematics Service выполняет последовательность:

1. **preStop hook** от K8s делает HTTP POST на `/admin/shutdown` сервиса — это сигнал начать graceful shutdown до прихода SIGTERM (K8s сначала вызывает preStop, потом SIGTERM).
2. **Pause Kafka consumer** — перестаём читать новые сообщения из `telematics.raw`.
3. **Дообработка in-flight** — текущие события в pipeline (десериализация, валидация, роутинг) доделываются.
4. **Flush Kafka producer** — гарантируем что все отправленные в downstream топики сообщения получили ACK от Kafka. Async producer в норме батчит — на shutdown явный flush.
5. **Commit offset** — последние обработанные offset-ы закоммичены в `__consumer_offsets`.
6. **Close consumer group membership** — координатор Kafka узнаёт о уходе и начинает ребаланс **сразу**, не ждёт heartbeat timeout 6 сек.
7. **Exit 0** — под уходит.

Если не успели за 30 сек → SIGKILL → ребаланс по heartbeat timeout (6 сек) + ~20-50 дублей в окне незакоммиченного. Downstream обрабатывает штатно (идемпотентность — см. раздел про дедупликацию).

### Валидация

| Правило | Действие | Зачем |
|---|---|---|
| lat/lon == 0,0 | Drop | Баг провайдеров — трекер потерял GPS, шлёт нули |
| satellites < 4 | Drop | Минимум 4 спутника для 3D-позиции. Меньше = мусор |
| hdop > 5 | Drop | Точность хуже 5 метров — для логистики бесполезно |
| timestamp > now() + 1 мин | Drop | Часы трекера сбились вперёд (clock skew) |
| GPS с timestamp < now() - 24h | Drop | Старые данные — повторная отправка после долгого офлайна, смысла сохранять нет (всё равно в историю не поставишь в порядке) |
| driver_event с timestamp < now() - 5 мин | Drop | Реакция на событие (резкое торможение, SOS, геозона) имеет смысл только near-real-time — стейл бесполезен для Notification Service, запись в историю пусть идёт через GPS-поток |
| vehicle_id пустой | Drop | Невалидное событие |

Каждый дроп — метрика `telematics_dropped_total{reason="...", provider="..."}`. Видно на дашборде: если у Wialon внезапно 30% дропов — проблема на стороне провайдера, эскалируем.

## Масштабирование Telematics Service

### HPA (Horizontal Pod Autoscaler)

```yaml
min replicas: 2      # минимум для отказоустойчивости
max replicas: 6      # потолок (8 партиций, но с запасом под scaling)

Метрики:
  primary:   kafka_consumer_lag > 200   → scale up
  secondary: CPU > 70%                  → scale up (подстраховка)

Cooldown: 5 мин (не дёргать реплики туда-сюда)
```

**Почему lag, а не RPS:**
- RPS — входящая нагрузка, мы её не контролируем
- Lag — "насколько мы отстаём". Lag = 0 → всё ок даже при 5K RPS. Lag растёт при 3K → проблема в обработке
- Consumer lag экспортируется в Prometheus через кастомную метрику `kafka_consumer_lag`, HPA читает через Prometheus Adapter

**Потолок:** максимум 8 инстансов = количество партиций `telematics.raw`. Больше инстансов чем партиций → лишние idle. Нужно больше 8 → сначала добавляем партиции (а это ломает гарантию порядка по `vehicle_id`, так что лучше заранее overprovision).

### Как работает масштабирование

```
Нормальный режим (2 инстанса):
  Инстанс 1 ← [0,1,2,3]     4 партиции × ~250 events/sec = ~1 000/sec
  Инстанс 2 ← [4,5,6,7]     4 партиции × ~250 events/sec = ~1 000/sec

Burst от провайдера (lag > 200):
  HPA поднимает 3-й инстанс
  Kafka ребаланс (секунды):
  Инстанс 1 ← [0,1,2]       3 партиции
  Инстанс 2 ← [3,4,5]       3 партиции
  Инстанс 3 ← [6,7]         2 партиции
  → нагрузка размазалась, lag падает

Lag упал (cooldown 5 мин):
  HPA убирает 3-й инстанс → обратно 2 инстанса
```

## Сценарии отказа

### Инстанс Telematics Service упал — пошаговый разбор

```
Исходное состояние:
  Инстанс 1 ← партиции [0,1,2,3]
  Инстанс 2 ← партиции [4,5,6,7]
  (2 инстанса в норме)
```

**t=0 — Инстанс 2 умер (OOM / segfault / нода K8s упала)**

Сообщения для партиций [4,5,6,7] перестают обрабатываться — копятся в Kafka. Поскольку Telematics Service stateless, терять нечего — нет ни кеша, ни локального состояния.

**t=0...6 сек — Kafka ждёт heartbeat**

Consumer шлёт heartbeat координатору каждые `heartbeat.interval.ms` (3 сек). Координатор ждёт `session.timeout.ms` (у нас 6 сек). Не дождался → считает consumer мёртвым.

В это окно сообщения для партиций [4,5,6,7] **не обрабатываются**, lag растёт: 6 сек × ~1 000 events/sec (половина потока) = ~6 000 необработанных сообщений.

**t=6...10 сек — Ребаланс**

Координатор перераспределяет партиции мёртвого consumer-а на оставшегося:

```
  Инстанс 1 ← [0,1,2,3,4,5,6,7]   все 8 партиций
  (нагрузка ×2 от нормы — до scale up)
```

**t=10 сек — Consumer-ы начинают читать новые партиции**

Инстанс 1 получает партицию 5. Но с какого offset?

```
Партиция 5 (была у инстанса 2):
  offset 1000 — последний committed offset (инстанс 2 подтвердил)
  offset 1001-1020 — инстанс 2 прочитал и обработал, но НЕ закоммитил
  offset 1021-1150 — накопились за 6 сек простоя

Инстанс 1 начинает с offset 1001 (первый после committed)
→ сообщения 1001-1020 будут обработаны ПОВТОРНО (at-least-once)
```

**t=10...12 сек — Часть сообщений обрабатывается повторно**

Сообщения 1001-1020 (~20 штук) инстанс 2 уже отправил в `telematics.gps`, но не успел закоммитить offset. Инстанс 1 перечитывает и отправляет в `telematics.gps` снова. Это штатный at-least-once Kafka.

**t=10...12 сек — Downstream обрабатывает дубли идемпотентно**

```
Tracking Service получает дубль из telematics.gps:

  PostgreSQL:
    INSERT INTO position_history (vehicle_id, timestamp, lat, lon, speed, heading)
    VALUES ('truck-42', 1704067200000, 55.7, 37.6, 80, 45)
    ON CONFLICT (vehicle_id, timestamp) DO NOTHING;
    → affected rows = 0
    → запись уже есть, ничего не произошло

  Redis (текущая позиция):
    HSET vehicle:truck-42 lat 55.7 lon 37.6 speed 80
    → перезапись тем же значением = noop

Дубль безопасен. Ни PG ни Redis не пострадали.

Analytics Service (ClickHouse): ReplacingMergeTree по (vehicle_id, timestamp) — дубль схлопывается при merge.
Notification Service: хранит отправленные event_id, дубль не вызовет повторной отправки.
```

**t=12+ — Полная работоспособность**

```
Инстанс 1: обрабатывает все 8 партиций (нагрузка ×2 от нормы)
→ HPA видит рост CPU/lag → через cooldown поднимет 2-й инстанс взамен упавшего
→ Kafka ребалансит обратно на 2 → нагрузка выровнялась
```

**Итого: timeline**

```
t=0       Инстанс 2 упал
t=0-6     Kafka ждёт heartbeat timeout. Партиции [4-7] не обрабатываются
t=6-10    Ребаланс. Все 8 партиций переезжают на инстанс 1
t=10-12   Перечитывание незакоммиченных сообщений → ~20-50 дублей в downstream
t=12+     Обработка возобновлена, HPA поднимает новый 2-й инстанс
```

**Критично ли?**

| Вопрос | Ответ |
|---|---|
| Данные потеряны? | **Нет.** Kafka хранит всё. Незакоммиченные — перечитаны |
| Сколько дублей пройдёт? | ~20-50 (незакоммиченное окно). Не тысячи |
| Дубли опасны? | **Нет.** PG: `ON CONFLICT DO NOTHING`. Redis: idempotent `HSET`. ClickHouse: `ReplacingMergeTree`. Notification: `event_id` idempotency key |
| Диспетчер заметит? | **Нет.** Разрыв 6-10 сек. GPS обновляется каждую секунду — на карте точка "подвисает" на 10 сек, потом догоняет |
| Алерт сработает? | **Да.** `consumer_lag > 1000` через ~2 сек. Но к моменту реакции дежурного (15 мин SLA) — уже всё восстановилось |
| Нужно ли ручное вмешательство? | **Нет.** Kafka ребаланс + HPA — полностью автоматическое восстановление |

**На интервью:** "Telematics Service stateless — при падении инстанса терять нечего. At-least-once Kafka даёт ~20-50 дублей в окне перечитывания незакоммиченных сообщений, но downstream consumer-ы идемпотентны по построению (ON CONFLICT, HSET overwrite, ReplacingMergeTree, event_id key) — это штатный паттерн at-least-once pipeline, отдельный слой дедупа не нужен."

### Добавился новый инстанс (scale up)

```
Было: 2 инстанса
HPA добавил 3-й (lag > 200 или CPU > 70%)

t=0     Новый инстанс стартует
t=0-5   Kafka ребаланс:
          Инстанс 1 ← [0,1,2]       3 партиции
          Инстанс 2 ← [3,4,5]       3 партиции
          Инстанс 3 ← [6,7]         2 партиции   ← новый

t=5+    Инстанс 3 читает партиции [6,7] с последнего committed offset.
        Поскольку он stateless — нет warm-up, нет прогрева кеша.
        Читает → валидирует → роутит. Сразу в рабочем режиме.
```

Инстанс готов к работе мгновенно после ребаланса. Никакого прогрева не требуется.

### Kafka брокер упал

```
Один брокер из 3 упал:
  - Replication factor = 3 → данные есть на 2 оставшихся
  - min.insync.replicas = 2 → запись продолжается (2 из 3 живы)
  - Leader партиций с упавшего брокера → Kafka автоматически выбирает нового лидера среди реплик
  - Consumer-ы переключаются на нового лидера
  - Простой: секунды (время выбора лидера)

Два брокера из 3 упали:
  - min.insync.replicas = 2, живых = 1 → запись НЕВОЗМОЖНА
  - Адаптеры получают ошибку записи → буферизуют в памяти / ретраят
  - Consumer-ы не могут читать → lag копится
  - Критический инцидент → DevOps поднимает брокеры
  - После восстановления: адаптеры дошлют, consumer-ы догонят

Все 3 брокера упали:
  - Полная недоступность Kafka
  - Push-адаптеры (WS, TCP): копят в памяти, при переполнении — дропают старые (ring buffer)
  - Pull-адаптеры (REST, SOAP): перестают поллить, данные копятся у провайдера
  - После восстановления Kafka: адаптеры дошлют, pull-адаптеры заберут накопленное
  - GPS-данные за период простоя от push-адаптеров могут быть потеряны
```
