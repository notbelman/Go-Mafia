- **Шардирование** — разбиение данных между несколькими независимыми серверами БД. Каждый шард = полноценная БД со своими индексами, транзакциями, бэкапами
- **Shard key** — столбец, по которому определяется шард. Должен быть высокой кардинальности, не меняться, использоваться в запросах. Плохой ключ = один шард перегружен или scatter-gather на все
- **4 стратегии роутинга:** Hash (равномерно, но resharding больно), Range (диапазоны, но hotspots), Directory (lookup-таблица, полный контроль), [[Consistent Hashing и Virtual Buckets|Consistent Hashing]] (добавление шарда = ~1/N перемещается)
- **Cross-shard:** JOIN не работает → денормализация. Транзакции ACID только внутри шарда → [[Распределённые транзакции|2PC]] или eventual. Запросы без shard key → scatter-gather на все шарды
- **Роутинг запросов:** клиентский (мин. latency, но логика в коде), прокси (приложение не знает о шардах, +1 хоп), координатор (умная прокси, JOIN cross-shard)
- **Перебалансировка** — штатная операция, но трудная: данные продолжают читаться/писаться. 4 способа: read-only (даунтайм), immutable (INSERT вместо UPDATE), репликация (самый популярный), смешанный
- **Генерация ID:** auto-increment пересекается между шардами. Решения: UUID (без координации, но 16 байт), Snowflake (timestamp+machine_id+seq), выделенный генератор, диапазоны
- **Золотое правило:** если можно не шардировать — не шардируй. PG инструменты: Citus, postgres_fdw, ручной роутинг
- ID генерируется **до** записи → по нему хеш → определяем шард → пишем. Если ID генерирует БД (auto-increment) — мы не знаем шард заранее

## Стратегии роутинга

| Стратегия | Как работает | Плюсы | Минусы | Когда |
|---|---|---|---|---|
| **Hash** | hash(key) % N | Равномерное распределение | Resharding = почти всё переезжает | Нет естественного диапазона |
| **Range** | key в [A, B) → шард | Диапазонные запросы на 1 шард | Hotspots (все пишут в последний) | Time-series, естественный порядок |
| **Directory** | Lookup-таблица key→shard | Полный контроль | Lookup = SPOF, +1 запрос | VIP-клиенты на отдельных шардах |
| **Consistent Hashing** | Кольцо, ближайший шард по часовой | Добавление = ~1/N переезжает | Сложнее, без virtual nodes неравномерно | Динамическое кол-во шардов, кэши |

## Под капотом

- Shard key — столбец, по которому определяется на какой шард попадает строка
- Приложение или прокси вычисляет шард по ключу и отправляет запрос на нужный сервер
- Каждый шард — полноценная БД со своими индексами, транзакциями, бэкапами

### Когда нужно
- Данные не влезают на один сервер
- Нужно масштабировать запись (репликация не помогает)
- Нагрузка естественно делится по ключу (user_id, tenant_id)

### Когда не нужно
- Данные влезают на один сервер — overhead не оправдан
- Read-heavy нагрузка — [[Репликация|репликация]] проще
- Много cross-shard запросов — убьёт перформанс

## Грабли

### Выбор shard key

| Ошибка | Последствие |
|---|---|
| Низкая кардинальность | Один шард перегружен |
| Часто меняется | Строка переезжает между шардами |
| Не используется в запросах | Scatter-gather на все шарды |

### Cross-shard операции

| Операция | Проблема | Решение |
|---|---|---|
| Запросы | Опросить все шарды, смержить — медленно | Colocation: связанные данные на одном шарде |
| JOIN | Не работает между шардами | Денормализация или на стороне приложения |
| Транзакции | ACID только внутри шарда | [[Распределённые транзакции|2PC]] (медленно) или eventual consistency |
| Resharding | Даунтайм или сложная миграция | [[Consistent Hashing и Virtual Buckets|Consistent hashing]], планировать заранее |

## Роутинг запросов к шардам

Кто решает, на какой шард отправить запрос?

### 1. Клиентский роутинг
Приложение само знает адреса всех шардов и вычисляет, куда идти.

**Плюс:** нет лишних сетевых хопов — минимальная [[Производительность|latency]].
**Минус:** логика шардирования в коде. Добавили/удалили шард — обновлять клиент.

### 2. Прокси (тупая)
Между приложением и шардами стоит прокси. Приложение шлёт обычные запросы, прокси роутит.

**Плюс:** приложение не знает о шардировании.
**Минус:** +1 хоп, единая точка отказа, не умеет сложные запросы (JOIN из двух шардов).

### 3. Координатор (умная прокси)
Как прокси, но умеет собирать данные из нескольких шардов: JOIN, GROUP BY, агрегации.

**Плюс:** приложение не знает о шардировании + сложные запросы.
**Минус:** +1 хоп, единая точка отказа, бутылочное горлышко при росте.

**Масштабирование координатора:** stateless → просто добавляем инстансы. Stateful → репликация, [[Консенсус и координация|выбор лидера]].

| | Клиент | Прокси | Координатор |
|---|---|---|---|
| Latency | Минимум | +1 хоп | +1 хоп |
| Сложные запросы | Мёржит сам | Нет | Да |
| Логика в приложении | Да | Нет | Нет |
| Точка отказа | Нет | Да | Да |

## Перебалансировка шардов (переналивка)

Перенос данных с одного шарда на другой. Штатная операция — происходит когда шард **живой**, не когда упал.

### Зачем
- Данные распределились неравномерно — один шард перегружен
- Добавляем новый шард — нужно перенести часть данных
- Выводим шард из эксплуатации

### Почему это трудно
Во время переналивки данные продолжают читаться и писаться. UPDATE на запись, которая уже переехала — куда его применять?

### 4 способа

| Способ | Суть | Плюс | Минус |
|---|---|---|---|
| **Read-only** | Запрещаем запись, переливаем | Просто | Даунтайм на запись |
| **Immutable** | UPDATE = INSERT новой версии | Нет проблемы "апдейт не туда" | Нужен merge при чтении |
| **Репликация** | Реплика source→target, потом переключение | Минимальный даунтайм | Сложнее настроить |
| **Смешанный** | Лочим конкретного юзера на время миграции | Гибко | Нужна кастомная логика |

### Золотое правило
Если можно не шардировать — **не шардируй**. Перебалансировка — одна из главных причин, почему шардирование откладывают как можно дольше.

## Генерация ID в шардированных системах

Auto-increment на каждом шарде → ID пересекаются. ID генерируется **до** записи → по нему хеш → определяем шард → пишем.

| Подход | Как работает | Плюс | Минус |
|---|---|---|---|
| **UUID** | Случайный 128 бит | Без координации | 16 байт, плохо в B-tree (page splits) |
| **Snowflake** | timestamp + machine_id + sequence | Уникальный + упорядоченный | Зависимость от синхронизации часов |
| **Выделенный генератор** | Отдельный сервис выдаёт ID | Гарантия уникальности, монотонные | SPOF, +1 хоп |
| **Диапазоны** | Шард 1 → 1–1M, шард 2 → 1M–2M | Нет координации при записи | Могут закончиться, неравномерно |

## Инструменты (PostgreSQL)

- **Citus** — расширение, автоматический шардинг + distributed queries
- **postgres_fdw** — foreign data wrappers, ручной шардинг через foreign tables
- **Вручную** — роутинг на уровне приложения
