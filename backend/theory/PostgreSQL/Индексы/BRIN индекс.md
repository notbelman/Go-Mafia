- **BRIN** — минималистичный индекс: хранит только **min/max** для блоков страниц. Размер **~0.1%** от таблицы (vs 30% у B-tree)
- Работает только если данные **физически упорядочены** (append-only: логи, события, time-series)
- Поиск: проверить min/max каждого блока → пропустить неподходящие → Bitmap Heap Scan подходящих

---

## Структура

```
┌─────────────────────────────────────────┐
│ Block Range 0 (pages 0-127):            │
│   min = '2024-01-01', max = '2024-01-05'│
├─────────────────────────────────────────┤
│ Block Range 1 (pages 128-255):          │
│   min = '2024-01-06', max = '2024-01-10'│
├─────────────────────────────────────────┤
│ Block Range 2 (pages 256-383):          │
│   min = '2024-01-11', max = '2024-01-15'│
└─────────────────────────────────────────┘
```

По дефолту один блок = 128 страниц = 1 МБ данных. Настраивается через `pages_per_range`.

## Как работает поиск

```sql
WHERE created_at = '2024-01-08'

1. Block 0: '01-08' в [01-01, 01-05]? Нет → skip
2. Block 1: '01-08' в [01-06, 01-10]? Да  → scan pages 128-255
3. Block 2: '01-08' в [01-11, 01-15]? Нет → skip

→ Bitmap Heap Scan: читаем ВСЕ строки страниц 128-255, фильтруем
```

BRIN не даёт точного адреса строки — даёт диапазон страниц. Внутри диапазона PG читает всё и фильтрует.

## Когда использовать

- **Append-only** таблицы (логи, события, метрики) — данные физически упорядочены
- **Огромные таблицы** (100M+ строк) с range-запросами
- Когда B-tree слишком большой (BRIN ~0.1% vs B-tree ~30%)

## Когда НЕ использовать

- Данные часто UPDATE или INSERT в случайном порядке (min/max будут перекрываться)
- Нужен точечный поиск по `=` (B-tree точнее)
- Таблица небольшая

```sql
CREATE INDEX idx_logs_created ON logs USING BRIN(created_at);

-- С настройкой размера блока:
CREATE INDEX idx_logs ON logs USING BRIN(created_at) WITH (pages_per_range = 64);
```
