- **Write amplification** — одна логическая запись приводит к **нескольким физическим** записям на диск. В PG: UPDATE одной строки → запись в heap + запись в **каждый индекс** + запись в **WAL** (и heap и индексы)
- PG **хуже** многих СУБД: UPDATE = DELETE + INSERT (MVCC) → **две** версии строки + обновление всех индексов. Один UPDATE = **2 + N×2** записей (N = количество индексов)
- Снижение: **HOT updates** (если изменяемая колонка не в индексе), **меньше индексов**, **fillfactor**, **TOAST** для больших значений
- **B-tree vs LSM-Tree**: B-tree = высокий WA (перезапись целой страницы 8KB ради 1 строки), LSM = ниже WA при записи, но compaction добавляет свой WA

---

## Откуда берётся

Один `UPDATE users SET name = 'Alice' WHERE id = 1`:

```
1. WAL: записать old tuple (для ROLLBACK)          ← запись
2. Heap: пометить старую строку мёртвой (xmax)      ← запись
3. Heap: вставить новую строку (новый TID)           ← запись
4. WAL: записать новую строку                        ← запись
5. Index 1 (name): добавить указатель на новый TID   ← запись
6. WAL: записать изменение Index 1                   ← запись
7. Index 2 (email): добавить указатель               ← запись (даже если email не менялся!)
8. WAL: записать изменение Index 2                   ← запись
```

**1 логический UPDATE → 8+ физических записей.** С 5 индексами → 14+ записей.

## Почему PG особенно подвержен

| Фактор | Почему увеличивает WA |
|:--|:--|
| MVCC: UPDATE = DELETE + INSERT | 2 версии строки вместо 1 |
| Все индексы обновляются | даже если колонка **не в этом индексе** |
| WAL | **каждое** изменение heap и индекса пишется в WAL |
| Страница 8KB | изменил 100 байт → PG пишет **full page image** (8KB) при первом изменении страницы после checkpoint |

**Full page writes** (FPW): при первом изменении страницы после checkpoint PG пишет **целую страницу 8KB** в WAL (защита от torn page). Изменил 1 байт → 8KB в WAL.

## Как снизить

### HOT updates
Если изменяемая колонка **не в индексе** + есть место на странице → индексы **не обновляются**:
```sql
-- 5 индексов, но name не в них → HOT update, 0 записей в индексы
UPDATE users SET name = 'Alice' WHERE id = 1;
```

### Меньше индексов
Каждый лишний индекс = +2 записи на UPDATE (индекс + WAL). Удали неиспользуемые: `pg_stat_user_indexes WHERE idx_scan = 0`.

### Fillfactor
```sql
ALTER TABLE users SET (fillfactor = 70);
-- 30% страницы свободно → HOT updates вероятнее
```

### TOAST
Большие значения (>2KB) выносятся в TOAST-таблицу. UPDATE маленького поля не трогает TOAST → меньше I/O.

## B-tree vs LSM-Tree: write amplification

| | B-tree (PG) | LSM-Tree (RocksDB) |
|:--|:--|:--|
| Запись | Random I/O, перезапись страницы 8KB | Sequential I/O, append в memtable |
| WA | Высокий (FPW + индексы) | Ниже при записи, но compaction добавляет |
| Compaction WA | Нет | Данные перезаписываются при merge (2-10x) |
| Итого | Стабильно высокий | Ниже на запись, выше на compaction |

## Мониторинг

-- WAL генерация
SELECT pg_wal_lsn_diff(pg_current_wal_lsn(), '0/0') AS total_wal_bytes;

-- Размер WAL за время
