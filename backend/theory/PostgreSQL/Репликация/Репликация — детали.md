- **WAL (Write-Ahead Log)** — журнал всех изменений. Сначала пишем в лог (append-only, быстро), потом применяем к данным (случайная запись, медленно). Crash recovery + репликация
- **Physical репликация** — передаёт байты WAL (страницы диска). Реплика = точная копия. Быстрее, но вся база целиком, read-only, одинаковые версии PG
- **Logical репликация** — передаёт изменения сущностей (INSERT/UPDATE/DELETE). Можно выбранные таблицы, разные версии PG, реплика writable. Медленнее (декодирование)
- **SBR** (Statement-Based) — передаём SQL-запросы. Читаемо, но `NOW()/RANDOM()` сломают данные. **RBR** (Row-Based) — передаём изменённые строки в бинарном виде. Компактнее, нет проблем с недетерминизмом
- **3 аномалии replication lag:** Read Your Own Writes (написал → не видишь), Монотонное чтение (данные "моргают" между репликами), Согласованное префиксное чтение (ответ без контекста)
- **CDC** — захват изменений из БД → Kafka → Elasticsearch/ClickHouse. **libslave** — приложение прикидывается репликой, держит данные в RAM (пример: Тинькофф, рекламный движок за 100мс)
- PG: WAL в `pg_wal/`, сегменты по 16MB. LSN = позиция в WAL. Checkpoint = сброс грязных страниц. `wal_level`: minimal → replica → logical
- Replication lag: мастер `SELECT replay_lag FROM pg_stat_replication`, реплика `SELECT now() - pg_last_xact_replay_timestamp()`. <100ms ок, >1s проблема

## Physical vs Logical репликация

| | Physical | Logical |
|---|---|---|
| Что передаётся | Байты WAL (страницы диска) | Изменения сущностей |
| Что реплицируется | Вся база целиком | Можно выбранные таблицы |
| Реплика read-only? | Да (hot standby) | Нет, можно писать |
| Версии БД | Одинаковые | Могут отличаться |
| Архитектура | Одинаковая (x86 → x86) | Любая |
| Скорость | Быстрее | Медленнее (декодирование) |
| Кейс | HA, failover, read scaling | Миграции, частичная репликация, multi-master |

## WAL (Write-Ahead Log)

Журнал всех изменений. Сначала пишем в лог, потом применяем к данным на диске.

### Зачем
- **Crash recovery** — после падения воспроизводим WAL, данные не теряются
- **Репликация** — отправляем WAL на реплики, они воспроизводят изменения

### Как работает

```
1. BEGIN; INSERT INTO users(name) VALUES('Alex');
2. Изменения → WAL buffer (память) + shared buffers (память)
3. COMMIT → WAL buffer сбрасывается на диск (fsync)
4. Ответ клиенту "ok"
5. Позже (checkpoint) → грязные страницы из shared buffers на диск
```

### Почему сначала WAL
- Последовательная запись в лог — быстро (append-only)
- Случайная запись в таблицы — медленно (seek time)
- Упали до checkpoint? При старте воспроизводим WAL — данные не потеряны
- По сути два хранилища: WAL (быстрая запись) + движок (медленная перестройка)

### PostgreSQL: детали

| Вопрос | Ответ |
|---|---|
| LSN | Log Sequence Number — позиция в WAL (формат: 0/3A8B2C0) |
| Checkpoint | Сброс грязных страниц на диск, после него старый WAL можно удалить |
| Где лежат | `pg_wal/`, сегменты по 16MB |
| wal_level | minimal (crash recovery), replica (physical, default), logical |

## SBR vs RBR (Statement vs Row Based)

Два формата внутри **логической** репликации.

### SBR (Statement-Based)
Передаются SQL-запросы: `INSERT INTO users VALUES('Vova', 25)`.

**Плюс:** читаемость, удобно для дебага.
**Минус:** `NOW()`, `RANDOM()`, `UUID()` вернут разные значения на разных узлах → данные разъедутся.

### RBR (Row-Based)
Передаются изменённые строки в бинарном виде — дельта сущности.

**Плюс:** компактнее, быстрее, нет проблем с недетерминизмом.
**Минус:** менее читаемый, труднее дебажить.

**Режимы:** full (вся строка) или minimal (только изменённые поля).

### Mixed
Некоторые БД автоматически переключаются: видит `RANDOM()` → RBR, простой INSERT → SBR.

### Аналогия
SBR vs RBR — как REST vs gRPC. REST (SBR) — текстовый, читаемый. gRPC (RBR) — бинарный, компактный.

## Replication Lag и 3 аномалии

Отставание реплики от мастера. Причины: медленная сеть, реплика нагружена read-запросами, слабое железо.

### 1. Read Your Own Writes
**Проблема:** Вова опубликовал твит, обновил страницу — твита нет. Запись на мастер, чтение с реплики, где данные не доехали.

**Решение:** после записи какое-то время читать из мастера (отслеживать, когда пользователь последний раз писал).

### 2. Монотонное чтение
**Проблема:** пост Роналду появился → обновил → пропал → обновил → снова. Запросы на разные реплики с разным лагом, данные "моргают".

**Решение:** привязать пользователя к одной реплике (хэш user_id). Данные не откатываются назад.

### 3. Согласованное префиксное чтение
**Проблема:** А опубликовал фото, Б ответил комплиментом. Третий видит ответ Б, но не видит фото А — посты на разных партициях с разным лагом.

**Решение:** причинно-связанные записи писать в одну партицию.

### Измерение (PostgreSQL)
```sql
-- на мастере
SELECT replay_lag FROM pg_stat_replication;

-- на реплике
SELECT now() - pg_last_xact_replay_timestamp();
```

Допустимый lag зависит от бизнеса. <100ms ок, >1s проблема.

### Важно
Все три аномалии **трудно кодятся, трудно дебажатся, трудно поддерживаются**. Не все компании их решают. Но знать нужно.

## CDC и libslave

### CDC (Change Data Capture)
Захват изменений из БД → автоматическая отправка в другие системы.

```
PostgreSQL → CDC (слушает WAL) → Kafka → Elasticsearch (поиск)
                                       → ClickHouse (аналитика)
```

Коннекторы подключаются к replication log и перенаправляют изменения. В Kafka есть готовые коннекторы. Бывают медленные — часто пишут свои.

### libslave (приложение-реплика)
Приложение прикидывается репликой БД и слушает replication log. Данные в RAM — не нужно ходить в сеть.

**Пример Тинькофф:** рекламный движок на C++, отвечает за 100мс. libslave подключается к MySQL, приложение хранит данные в RAM, отвечает мгновенно.

**Ограничение:** данные должны помещаться в RAM.

**Инициализация:** при старте — начальная наливка (SELECT), дальше обновления через replication stream.
