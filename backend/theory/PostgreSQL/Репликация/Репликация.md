- **Репликация** — копирование данных с одного сервера БД на другие в реальном времени. Зачем: HA/failover, read scaling, disaster recovery, offloading аналитики
- **Синхронная** → strong consistency: COMMIT ждёт подтверждения реплик. Потеря данных невозможна, но медленно. Одна реплика зафейлилась → откат всей операции
- **Асинхронная** → eventual consistency: COMMIT → ответ клиенту → потом отправка на реплики. Быстро, но replication lag, stale reads, потеря последних транзакций при падении мастера
- **Single-Leader** (master-slave) — самая распространённая. Пишем в мастер, читаем из реплик. Failover: promote реплику с наименьшим лагом. Split brain решается через generation
- **Multi-Leader** (master-master) — пишем в несколько мастеров. Главная проблема — **конфликты**: LWW, ранг реплик, CRDT (дельта вместо абсолютного значения)
- **Masterless** — все узлы равны. W + R > N → strong consistency. W=N, R=1 = оптимизация чтения. Редко на практике (Cassandra, DynamoDB)
- **Репликация ≠ бэкап**: DROP TABLE разлетится по всем репликам. Бэкап защищает от человеческой ошибки, репликация — от падения сервера
- PG: `synchronous_commit` = off/local/remote_write/on/remote_apply. Hot Standby = заранее определённая синхронная реплика для быстрого failover

## Сравнение топологий

| | Single-Leader | Multi-Leader | Masterless |
|---|---|---|---|
| Запись | Только мастер | Несколько мастеров | Любой узел |
| Конфликты | Нет | Да (LWW, CRDT) | Да |
| Failover | Нужен (promote реплику) | Проще (другой мастер жив) | Не нужен |
| Сложность | Низкая | Высокая | Высокая |
| Примеры | PostgreSQL, MySQL | BDR, CockroachDB | Cassandra, DynamoDB |

## Синхронная vs Асинхронная

| | Синхронная | Асинхронная | Полусинхронная |
|---|---|---|---|
| Когда ответ клиенту | После подтверждения реплик | Сразу после локального COMMIT | После получения репликой (не применения) |
| Консистентность | Strong | Eventual | Между ними |
| Потеря данных | Невозможна | Последние транзакции | Маловероятна |
| Скорость | Медленнее | Быстрее | Между ними |

### Синхронная → Strong Consistency

```
COMMIT → WAL на диск → отправка на реплики → ждём подтверждения ВСЕХ → ответ клиенту
```

**Плюс:** данные консистентны, потеря невозможна.
**Минус:** медленно. Одна реплика зафейлилась → откат, клиент получает ошибку.

### Асинхронная → Eventual Consistency

```
COMMIT → WAL на диск → ответ клиенту → потом асинхронно на реплики
```

**Плюс:** быстро. Для пользователя как будто репликации нет.
**Минус:** replication lag. Чтение с реплики может вернуть устаревшее. При падении мастера — потеря последних транзакций.

### Полусинхронная (Semi-Sync)

```
COMMIT → WAL на диск → отправка → ждём что реплики ПОЛУЧИЛИ (не применили) → ответ клиенту
```

Компромисс: не ждём применения, только подтверждение доставки. На практике редко.

### PostgreSQL: synchronous_commit

| Значение | Что ждём |
|---|---|
| off | Ничего (даже локальный flush не ждём) |
| local | Flush на мастере (default) |
| remote_write | Получение репликой (в память) — полусинхронная |
| on / remote_apply | Применение на реплике — синхронная |

**Когда что:** потеря данных недопустима (деньги) → синхронная. Важна скорость → асинхронная.

## Single-Leader (Master-Slave)

Пишем только в мастер. Читаем из мастера или слейвов. Самая распространённая топология.

### Failover
Мастер упал → выбираем реплику с наименьшим лагом → promote. Ручной (минуты-часы) или автоматический (Patroni, pg_auto_failover).

### Hot Standby
Заранее определённая синхронная реплика, которая станет мастером при сбое. Остальные могут быть асинхронными. Даунтайм минимален — следующий мастер уже известен.

### Split Brain
Мастер не упал, а потерял связь. Кластер выбрал нового мастера. Старый вернулся — два мастера. Решение: **generation** (поколение) у каждого мастера. Запросы от старого поколения отклоняются.

## Multi-Leader (Master-Master)

Пишем в несколько мастеров. Нет даунтайма на запись при падении одного.

**Когда:** два датацентра с async репликацией внутри, между ними master-master.

### Конфликты — главная проблема

```
EU мастер: UPDATE users SET balance = 100 WHERE id = 1
US мастер: UPDATE users SET balance = 200 WHERE id = 1
```

| Подход | Как работает | Минус |
|---|---|---|
| **LWW** (Last Write Wins) | По времени | Ретраи могут нарушить порядок |
| **Ранг реплик** | Выигрывает мастер с большим рангом | Жёсткий приоритет |
| **Решение на клиенте** | Как мёрж в git | Сложнее |
| **CRDT** | Дельта (+500 вместо SET 500), любой порядок | Ограниченные типы данных |

## Masterless (без ведущих узлов)

Все узлы равны. Пишем в W узлов, читаем из R узлов.

**Формула:** W + R > N → strong consistency.

| Оптимизация | Параметры | Эффект |
|---|---|---|
| Чтения | W = N, R = 1 | Пишем во все, читаем из одной |
| Записи | W = 1, R = N | Пишем в одну, читаем из всех |

На практике редко. Ближе к P2P (Cassandra, DynamoDB).

## Репликация vs бэкапы

Репликация — живая копия, failover за секунды. Бэкап — снимок на момент времени.

**Зачем бэкапы при наличии репликации?** DROP TABLE разлетится по всем репликам. Бэкап защищает от человеческой ошибки, репликация — от падения сервера.
