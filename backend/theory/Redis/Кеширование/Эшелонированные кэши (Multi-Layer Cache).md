## Уровни
```
Запрос → L1 (in-memory, в процессе) → L2 (Redis) → L3 (БД)
              ~1 нс, 0 сети              ~1 мс          ~5-50 мс
```

| Уровень | Где               | Скорость | Размер       | Shared между подами |
| :------ | :---------------- | :------- | :----------- | :------------------ |
| L1      | В памяти процесса | ~1 нс    | Ограничен RAM процесса | ❌ Нет, у каждого пода свой |
| L2      | Redis             | ~1 мс    | Большой      | ✅ Да, общий        |
| L3      | PostgreSQL        | ~5-50 мс | Неограничен  | ✅ Да               |

## Зачем L1 если есть Redis

Запрос в Redis — это сеть: сериализация → TCP round-trip → десериализация. Даже при ~1 мс, на 10 000 RPS это 10 секунд CPU на одну только сериализацию. L1 — обращение к памяти процесса, сети нет вообще.
```
Без L1:  10 000 RPS × 1 мс = 10 сек/сек на сетевые вызовы Redis
С L1:    9 500 попаданий в L1 (0 мс) + 500 промахов → Redis
```
## Проблема L1: консистентность между подами

У каждого пода свой L1. Один под обновил данные — другие не знают.
```
Pod 1: L1 = {user:123: "Alice"}    ← устарело
Pod 2: L1 = {user:123: "Alice"}    ← устарело
БД:          {user:123: "Bob"}     ← актуальное
```

**Решения:**
```
1. Короткий TTL на L1 (5-10 сек)
   Просто, допускаем stale в пределах TTL

2. Pub/Sub инвалидация через Redis/Kafka
   При обновлении → publish("invalidate:user:123")
   Все поды подписаны → удаляют из L1

3. Только для иммутабельных данных
   Справочники, конфиги, статика — не меняются, проблемы нет
```

## Когда использовать

| Сценарий                                 | Нужен L1?         |
| :--------------------------------------- | :----------------- |
| Высокий RPS, горячие ключи              | ✅ Да              |
| Данные редко меняются (справочники)      | ✅ Да              |
| Данные часто меняются, важна актуальность | ❌ Только Redis    |
| Низкий RPS, простой сервис              | ❌ Избыточно       |

## Что использовать для L1 в Go

| Вариант                   | Особенности                              |
| :------------------------ | :--------------------------------------- |
| `sync.Map`                | Встроенный, нет TTL, нет eviction        |
| `patrickmn/go-cache`      | TTL из коробки, простой API              |
| `dgraph-io/ristretto`     | TTL, LRU eviction, контроль памяти       |
| `allegro/bigcache`        | Для больших объёмов, минимальный GC pressure |

## Реализация в Go
```go
import "sync"

type MultiCache struct {
    l1  sync.Map              // L1: in-memory
    l2  *redis.Client         // L2: Redis
    db  *pgx.Pool             // L3: PostgreSQL
}

func (c *MultiCache) Get(key string) (*Item, error) {
    // L1: in-memory
    if val, ok := c.l1.Load(key); ok {
        return val.(*Item), nil
    }

    // L2: Redis
    cached, err := c.l2.Get(ctx, key).Result()
    if err == nil {
        item := unmarshal(cached)
        c.l1.Store(key, item) // промоутим в L1
        return item, nil
    }

    // L3: БД
    item, err := c.db.GetItem(key)
    if err != nil {
        return nil, err
    }

    c.l2.Set(ctx, key, marshal(item), 5*time.Minute) // кладём в L2
    c.l1.Store(key, item)                              // кладём в L1
    return item, nil
}
```
