- **Data intensive (IO bound)** — нагрузка на ввод/вывод (диск, сеть, БД). CPU простаивает, ждёт ответа. Масштабируем: диски, сеть, RAM
- **Compute intensive (CPU bound)** — нагрузка на процессор (ML, графы, математика). Масштабируем: ядра, тактовая частота
- **Read heavy** — читают >> пишут (соцсети). Кэширование эффективно, реплики на чтение, CDN
- **Write heavy** — пишут >> читают (логи). Батчинг, append-only, кэширование менее эффективно
- **High throughput** — максимальный объём данных через систему. Можно очереди, батчинг, compaction, сжатие. [[Производительность|Latency]] вторичен. Архитектура: [[Архитектура бэкенда#Микросервисы|микросервисы]] ок — лишний хоп не критичен
- **Low latency** — минимальное время отклика. **Нельзя**: очереди, лишние сетевые хопы, батчинг. Архитектура: [[Архитектура бэкенда#Монолит|монолит]]. Пример: HFT — каждая миллисекунда = потеря денег
- High throughput и low latency — **противоположные подходы**. То, что запрещено в low latency (очереди, батчи) — основной инструмент high throughput
- **Read/Write ratio — один из первых вопросов** при проектировании. От ответа зависит выбор БД, стратегия кэширования, способ хранения

## Сравнение подходов

| | High throughput | Low latency |
|---|---|---|
| Цель | Максимум данных через систему | Минимальное время отклика |
| Очереди, батчи | Основной инструмент | Запрещено |
| Сетевые хопы | Ок | Каждый хоп = боль |
| Архитектура | [[Архитектура бэкенда#Микросервисы|Микросервисы]] | [[Архитектура бэкенда#Монолит|Монолит]] |
| Масштабирование | [[Масштабирование|Горизонтальное]] | [[Масштабирование|Вертикальное]] |
| Кэширование | [[Кэширование — основы|Внешнее]] | [[Кэширование — основы|Внутреннее (in-process)]] |
| Пример | Система трейсинга (11 GB/s) | HFT (биржа) |

## Data intensive vs Compute intensive

| | Data intensive (IO bound) | Compute intensive (CPU bound) |
|---|---|---|
| Нагрузка на | Ввод/вывод: диск, сеть, БД | Процессор: вычисления |
| CPU | Простаивает, ждёт | Загружен на максимум |
| Примеры | Поход в сторонние сервисы, сбор данных | ML-инференс, алгоритмы на графах |
| Масштабируем | Больше дисков, быстрее сеть, больше RAM | Больше ядер, выше тактовая частота |

**Зачем различать:** от типа нагрузки зависит, что масштабировать. IO bound → [[Производительность|железо по latency/throughput]]. CPU bound → железо по CPU.

## Read/Write ratio

При проектировании системы важно понять — будут больше читать или больше писать.

**Read heavy** (больше чтения):
- Пример: соцсети — посты пишут редко, читают постоянно
- [[Кэширование — основы|Кэширование]] эффективно (высокий hit rate), реплики на чтение, CDN

**Write heavy** (больше записи):
- Пример: система логов — пишут постоянно, читают редко
- Оптимизация записи: батчинг, последовательная запись, append-only
- Кэширование менее эффективно — данные быстро устаревают

## High throughput приложения

Заточены на максимальный объём данных/запросов через систему. [[Производительность|Latency]] вторичен.

**Пример:** система трейсинга в Яндексе — 11 GB/s. Важно не как быстро один запрос, а сколько суммарно пропустим.

**Инструменты:**
- очереди — накапливаем, обрабатываем пачками
- батчинг — собираем N записей, пишем разом
- compaction — дубли отбрасываем, пишем только последнее значение
- последовательная запись, сжатие, группировка
- [[Кэширование — основы|внешнее кэширование]]

**Архитектура:** [[Архитектура бэкенда#Микросервисы|микросервисы]] подходят — лишний хоп не критичен, зато можно [[Масштабирование|масштабировать]] отдельные части.

## Low latency приложения

Заточены на минимальное время отклика. Запрос пришёл — **сразу** обработал.

**Пример:** HFT (High Frequency Trading) — роботы торгуют на бирже, каждая миллисекунда = потеря денег. Плюсовики допиливают вплоть до ядра ОС.

**Ключевое:** нельзя написать "как-нибудь" и потом оптимизировать. Нужно **сразу** проектировать под low latency.

**Чего нельзя:**
- очереди — это дополнительный latency
- лишние сетевые хопы — каждый хоп = задержка
- батчинг, группировка, ожидание — всё это latency

**Архитектура:** как правило, [[Архитектура бэкенда#Монолит|монолит]]. Никаких дополнительных сетевых походов.

## Связь
- [[Производительность]] — latency, throughput, response time как метрики
- [[Масштабирование]] — high throughput → горизонтальное, low latency → вертикальное
- [[Архитектура бэкенда]] — выбор монолит/микросервисы зависит от типа нагрузки
- [[Кэширование — основы]] — read heavy → высокий hit rate → кэш полезен
