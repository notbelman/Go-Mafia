- **Cache Hit** — данные в кэше есть. **Cache Miss** — нет, идём в БД. **Hit Rate** = hits / total запросов в кэш
- **Формула эффективности:** `avg = hit_rate × cache_time + miss_rate × (cache_time + db_time)`. Если miss rate > 80% → кэш скорее **вреден** — добавляет хоп, а ускорения нет
- **Внутреннее** (in-process, map, BoltDB) — максимальная скорость, но сервис становится [[Stateless vs Stateful сервисы|stateful]] → нужны [[Балансировка — алгоритмы|sticky sessions]], кэш вымывается при рестарте
- **Внешнее** (Redis, Memcached, Tarantool) — +сетевой хоп, но сервис остаётся [[Stateless vs Stateful сервисы|stateless]], кэш переживает рестарт, инвалидация в одном месте
- **Hot Key** — ключ с непропорционально большой долей запросов (Роналду, 600M подписчиков). Один инстанс кэша перегружается
- **Cache Miss Attack** — запросы несуществующих ключей пробивают кэш → вся нагрузка на БД. Защита: **negative caching** (кэшируем отсутствие) + rate limiting на [[Проксирование|reverse proxy]]
- **Прогрев (Warmup)** — после рестарта кэш пуст → все запросы в БД → БД может не выдержать. Blue-green деплой помогает с постепенным прогревом
- **Инвалидация** — удаление/обновление устаревших данных. Без инвалидации кэш врёт. Подробнее в [[Кэширование — стратегии]] и [[Кэширование — инвалидация]]
- Кэш должен **ускорять**, а не **держать** нагрузку. В идеале БД справляется и без кэша

## Внутреннее vs Внешнее

| | Внутреннее (in-process) | Внешнее |
|---|---|---|
| Скорость | Максимальная (данные в RAM) | + сетевой хоп |
| Сериализация | Не нужна | Нужна |
| Масштабирование | Больно ([[Stateless vs Stateful сервисы|stateful]]) | Просто |
| Падение сервиса | Кэш потерян | Кэш на месте |
| Инвалидация | В N инстансах | В одном месте |
| Пример | map, BoltDB | Redis, Memcached, Tarantool |

## Cache Hit, Cache Miss, Hit Rate

- **Cache Hit** — пошёл в кэш → данные есть → забрал. Успех
- **Cache Miss** — пошёл в кэш → данных нет → промах. Идём в БД
- **Hit Rate** = количество hit / общее количество запросов в кэш

Hit rate зависит от [[Алгоритмы вытеснения — основные|алгоритма вытеснения]] (LRU, LFU) и характера данных ([[Свойства и типы нагрузки|read heavy]] → выше hit rate).

## Формула эффективности кэша

Не всегда кэширование ускоряет систему.

```
Среднее время доступа = hit_rate × cache_time + miss_rate × (cache_time + db_time)
```

### Пример
- DB access time = 100 мс, Cache access time = 20 мс, Miss rate = 80%

```
Среднее = 0.2 × 20 + 0.8 × (20 + 100) = 4 + 96 = 100 мс
```

100 мс — столько же, сколько просто ходить в БД без кэша. **Кэш бесполезен.**

**Правило:** miss rate > 80% → кэш скорее вреден — добавляет лишний хоп, а ускорения нет.

## Внутреннее vs Внешнее кэширование

| | Внутреннее (in-process) | Внешнее |
|---|---|---|
| Скорость | Максимальная (данные в RAM) | + сетевой хоп |
| Сериализация | Не нужна | Нужна |
| Масштабирование | Больно ([[Stateless vs Stateful сервисы|stateful]]) | Просто |
| Падение сервиса | Кэш потерян | Кэш на месте |
| Инвалидация | В N инстансах | В одном месте |
| Пример | map, BoltDB | Redis, Memcached, Tarantool |

### Внутреннее (in-process)
Кэш живёт внутри сервиса — в памяти (map, дерево) или в файле (BoltDB). Максимальная скорость, но сервис становится [[Stateless vs Stateful сервисы|stateful]] → нужны [[Балансировка — алгоритмы|sticky sessions]], кэш вымывается при рестарте/деплое/OOM.

Подходит для [[Свойства и типы нагрузки|low latency]] приложений.

### Внешнее
Кэш — отдельный сервис (Redis, Memcached). Приложение ходит в него по сети. Сервис остаётся [[Stateless vs Stateful сервисы|stateless]] → [[Масштабирование|горизонтальное масштабирование]] просто.


## Hot Key (горячий ключ)

Ключ, на который приходится непропорционально большая часть запросов.

**Пример:** Криштиану Роналду — 600 млн подписчиков. Ключ `user:ronaldo` — горячий. Один инстанс кэша перегружается, если горячий ключ попал на него.

При [[Балансировка — алгоритмы|sticky sessions]] все запросы к этому ключу идут на один сервер.

## Cache Miss Attack

Атака: злоумышленник запрашивает данные, которых **гарантированно нет** в кэше (несуществующие ID). Каждый запрос — miss → летит в БД → БД ложится.

### Защита — negative caching
Запросили user 5 → его нет в БД → кэшируем **отсутствие** ("user 5 не существует"). Следующий запрос → кэш отвечает "не существует", в БД не идём.

Плюс rate limiting на [[Проксирование|reverse proxy]] — ещё одна линия защиты.


## Прогрев кэша (Cache Warmup)

Когда кэш только поднялся — он пустой. Все запросы идут мимо кэша прямо в БД → БД может не выдержать.

### Как прогревать
- наполнить реальными данными заранее
- постепенно пускать трафик, чтобы кэш заполнялся естественно
- blue-green деплой: новый инстанс прогревается, пока старый держит нагрузку

### Когда кэш вымывается
- сервис рестартнулся / передеплоился / заООМился
- внутреннее кэширование → прогрев после каждого рестарта
- внешнее → прогрев только при падении самого кэша

## Инвалидация кэша

Удаление или обновление устаревших данных. Без инвалидации кэш врёт — отдаёт старые данные.

**Пример:** баланс 500₽ в БД и в кэше. Потратил 200₽, в БД → 300₽. А в кэше по-прежнему 500₽.

Паттерны инвалидации: [[Кэширование — стратегии|стратегии кэширования]] и [[Кэширование — инвалидация|версионирование/теги]].
