- **Latency** — время от отправки запроса до **начала** обработки. Считается в одну сторону. Не включает прогрев
- **Response time** — полный путь туда-обратно: отправка → обработка → ответ. Включает все latency на пути. Это то, что чувствует пользователь
- **Throughput** — сколько запросов система обрабатывает за единицу времени (RPS). Узкое место определяет итоговую пропускную способность
- Latency и throughput **связаны, но не взаимозаменяемы** — рост throughput часто чуть ухудшает latency (очереди, батчинг). Можно закидывать железом — тогда latency не пострадает
- Типичный сценарий: заказчик задаёт потолок по latency ("не больше секунды"), дальше выжимаем максимальный throughput
- **RAM** ~0.25 мс (чтение 1 МБ), **SSD** ~1 мс, **HDD** ~20 мс. Throughput: RAM ~20 ГБ/с, NVMe ~1 ГБ/с, HDD ~200 МБ/с
- Требование "ответ за 5 мс" → HDD не подходит. "5 ГБ/с throughput" → считаем сколько дисков/плашек нужно

## Latency (задержка)

Время от отправки запроса до момента, когда принимающая сторона **начинает** его обрабатывать. Всё, что происходит пока запрос ждёт — это latency.

**Из чего складывается:** TCP-очередь, очередь в приложении, ожидание свободного потока, снятие с ядра планировщиком — куча задержек до начала обработки.

**Можно мерить между любыми точками:**
- клиент → сервер
- сервер → база данных
- клиент → база данных (через несколько узлов)

**Как считать:** клиент кладёт timestamp в запрос, сервер берёт diff когда начинает обрабатывать.

**Нюансы:**
- считается в одну сторону (не туда-обратно как ping)
- не включает bootstrap/прогрев приложения — меряем только когда сервис прогрет
- проблема синхронизации часов между узлами — решается через NTP, но расхождения возможны

## Response time (время ответа)

Полное время от отправки запроса клиентом до получения ответа. Включает все latency на пути.

```
Response time = T1 + T2 + T3 + T4 + T5 + T6 + T7

T1: клиент → сервер (по сети)
T2: сервер обрабатывает запрос
T3: сервер → БД (по сети)
T4: БД читает с диска
T5: БД → сервер (ответ)
T6: сервер десериализует, собирает ответ
T7: сервер → клиент (по сети)
```

| | Latency | Response time |
|---|---|---|
| Что меряет | Задержка до начала обработки | Полный путь туда-обратно |
| Масштаб | Между двумя точками | Весь маршрут запроса |

**На практике:** чаще всего [[Observability#Метрики (Monitoring)|метрики]] строят по response time — это то, что чувствует пользователь.

## Throughput (пропускная способность)

Сколько запросов система может обработать за единицу времени. Измеряется в **RPS** (requests per second).

**Как считать:** клиент включает таймер на секунду: отправил 200 запросов → сервер переадресовал 120 в БД → БД обработала 100 → обратно вернулось 95. Throughput = 95 RPS. Узкое место определяет итоговый throughput.

**Как добиваться высокого throughput:**
- очереди, батчинг, compaction
- последовательная запись
- [[Масштабирование|горизонтальное масштабирование]]

## Latency и throughput железа

Когда бизнес задаёт требование "запрос за 5 мс", сразу понимаем, какое железо подходит.

**Latency (чтение 1 МБ):**

| Железо | Latency |
|---|---|
| RAM | ~0.25 мс |
| SSD | ~1 мс |
| HDD | ~20 мс |

**Throughput:**

| Железо | Пропускная способность |
|---|---|
| HDD | ~200 МБ/с |
| SSD (SATA) | ~500 МБ/с |
| SSD (NVMe) | ~1000 МБ/с |
| DDR3 RAM | ~20 000 МБ/с |

**Как применять:**
- Требование "ответ за 5 мс" → HDD (20 мс) не подходит → SSD или RAM
- Требование "пропускать 5 ГБ/с" → считаем, сколько дисков/плашек нужно
- Сеть тоже добавляет latency — если по сети не успеваем, остаётся только RAM
