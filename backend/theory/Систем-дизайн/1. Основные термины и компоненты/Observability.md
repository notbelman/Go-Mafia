- **Логирование** — текстовые записи о событиях. Централизованно: демон на каждой машине → ELK Stack (Elasticsearch + Logstash + Kibana). Без этого — SSH на 200 машин и грепать
- **Метрики** — переменные в коде (счётчики), которые инкрементируются при событиях → Prometheus → дашборды → алерты. Базовые: RPS, [[Производительность|response time/latency]], error rate, CPU, RAM
- **Трейсинг** — путь **одного запроса** через все сервисы. Trace = граф операций, Span = одна операция. Trace ID пробрасывается через headers. Инструменты: Jaeger, Zipkin
- **Error Tracking** — централизованный сбор ошибок со stack trace + контекст. SDK автоматически отправляет exception. Пример: Sentry → алерт в Slack
- **Continuous Profiling** — периодическое снятие профилей (CPU, память) в проде. Flame graph, сравнение до/после релиза. Overhead ~10%. Пример: Pyroscope
- Логирование — **поток всех событий**. Error tracking — **только ошибки**, но с полным контекстом. Трейсинг — **граф одного запроса**. Дополняют друг друга
- Без [[Observability#Метрики (Monitoring)|метрик]] узнаёшь о проблемах **от пользователей**, а не от алертов. Без [[#Трейсинг|трейсинга]] [[Архитектура бэкенда|микросервисы]] не отладить

## Логирование

### Проблема
В распределённой системе логи лежат на каждой машине отдельно. 200 инстансов = 200 мест, куда нужно зайти по SSH и грепать.

### Решение — централизованная система
1. На каждой машине стоит **демон** (агент), который собирает логи
2. Демон отправляет логи в центральную систему
3. В UI — поиск, фильтрация, агрегация по всем сервисам сразу

### ELK Stack
- **E**lasticsearch — хранит и индексирует логи
- **L**ogstash — собирает и обрабатывает логи
- **K**ibana — UI для поиска и визуализации

### Отличие от трейсинга
- Трейсинг — путь одного запроса через сервисы (граф)
- Логирование — текстовые записи о событиях (поток)
- Дополняют друг друга: в логе можно искать по trace ID

## Метрики (Monitoring)

Переменные внутри приложения, которые инкрементируются при событиях. Периодически отправляются в систему мониторинга → дашборды → алерты.

### Как работает
1. В коде заводим счётчик (например, `requests_total`)
2. При каждом запросе инкрементируем
3. Раз в N секунд метрика уходит в систему мониторинга (Prometheus, Graphite)
4. На дашборде видим графики
5. Настраиваем алерт: если `error_rate > 5%` → звонок дежурному

### Базовые метрики
- RPS / TPS / QPS — запросов в секунду
- [[Производительность|Response time / Latency]]
- Success rate / Error rate
- CPU, RAM, Disk, Network, I/O
- Uptime / Downtime
- Размеры очередей, буферов
- Количество процессов, потоков

### Overhead
Метрики — дополнительная нагрузка (отправка, хранение), но без них в продакшне нельзя.

## Трейсинг

Отслеживание пути **одного запроса** через все сервисы в распределённой системе.

### Зачем
Запрос прошёл через 20 [[Архитектура бэкенда|микросервисов]]. Где-то сломалось. Логи на каждом сервисе отдельно — искать вручную нереально. Трейсинг собирает всю цепочку в одну картинку.

### Ключевые понятия
- **Trace** — граф всех операций одного запроса (от входа до ответа клиенту)
- **Span** — одна операция внутри trace (вызов сервиса, запрос в БД, обращение в кэш)
- **Trace ID** — уникальный идентификатор, пробрасывается через все сервисы в headers

### Как работает
1. На входе генерируется trace ID
2. Каждый сервис создаёт span с этим trace ID
3. Span содержит: имя операции, время начала/конца, статус, метаданные
4. Всё собирается в систему трейсинга (Jaeger, Zipkin)
5. В UI видим граф: какой сервис вызвал какой, сколько времени заняло

### Что даёт
- найти, где именно ошибка или тормоз
- граф зависимостей сервисов (кто кого вызывает)
- понять полный [[Производительность|response time]] и из чего он складывается

## Error Tracking

Централизованный сбор ошибок и крашей со всех сервисов в одном месте.

### Как работает
1. В приложении происходит exception / panic
2. SDK автоматически отправляет stack trace + контекст
3. В UI — список ошибок, группировка, частота, первое/последнее появление

### Что отправляется
- Stack trace
- Контекст запроса (URL, параметры, headers)
- Информация о пользователе
- Версия приложения, окружение (prod, staging)

### Отличие от логирования
| | Логирование | Error Tracking |
|---|---|---|
| Что собирает | Все события (info, warning, error) | Только ошибки |
| Контекст | Текстовая строка | Stack trace + переменные + user ID + версия |
| Пример | ELK Stack | Sentry |

## Непрерывное профилирование (Continuous Profiling)

Периодическое снятие профилей приложения (CPU, память, горутины) **в продакшне**.

### Как работает
1. Агент периодически снимает профиль (какие функции сколько CPU едят, где выделяется память)
2. Профили отправляются в центральную систему (Pyroscope, Parca)
3. В UI — flame graph, сравнение профилей до/после релиза

### Зачем
- понять, почему приложение тормозит / ест память
- сравнить профили до и после релиза — что изменилось
- найти утечки памяти, CPU-bottleneck

### Отличие от обычного профилирования
Обычное — разработчик запускает профилировщик локально. Непрерывное — крутится в продакшне постоянно, можно посмотреть профиль за любой момент в прошлом. Overhead ~10%.

- [[Производительность]] — response time, latency как базовые метрики
