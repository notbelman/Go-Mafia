- **Round Robin** — по кругу: 1→2→3→1→2→3. Покрывает **80–90% задач** балансировки. По умолчанию на собесе
- **Weighted Round Robin** — Round Robin с весами. Сеньор-сервер (weight=5) получает больше запросов. На практике редко — обычно однотипные узлы
- **Random** — случайным образом. Просто, но неравномерно. Иногда это самое простое решение — про него часто забывают
- **Least Connections / Least Response Time** — направляем туда, где меньше соединений / быстрее ответ. Умнее Round Robin, но балансировщик должен отслеживать состояние инстансов
- **Power of Two Choices** — случайно выбираем 2 инстанса, из них берём лучший. Компромисс random vs least connections. Больше теоретический
- **Sticky Sessions** — хэшируем ключ (user ID) → остаток от деления → номер инстанса. Один ключ всегда на одном инстансе. Нужны для [[Stateless vs Stateful сервисы|stateful]] сервисов с [[Кэширование — основы|in-process кэшем]]
- **Клиентская балансировка** — нет отдельного LB, клиент сам знает обо всех инстансах. Нет лишнего хопа, но клиент усложняется
- Проблема sticky sessions: изменилось количество узлов → все перемешаются. Решается **consistent hashing** (тема шардирования)

## Round Robin, Weighted Round Robin

### Round Robin

Запросы распределяются по кругу: 1 → 2 → 3 → 1 → 2 → 3.

**Аналогия:** менеджер раздаёт задачи трём программистам по очереди — Васе, Пете, Коле, снова Васе. Не знает, насколько задачи сложные — просто раздаёт по кругу.

**Покрывает 80–90% задач балансировки.**

### Weighted Round Robin

То же самое, но инстансам назначается вес. Более мощный сервер получает больше запросов.

```nginx
upstream backend {
    server 192.168.1.1 weight=5;   # сеньор — 5 задач за круг
    server 192.168.1.2 weight=1;   # джун — 1 задача
    server 192.168.1.3 weight=1;
}
```

**Когда нужен:** серверы разных характеристик (разные CPU, RAM). На практике редко — обычно однотипные узлы.

## Random

Запросы распределяются случайным образом.

### Когда подходит
- тестирование
- когда не важна эффективность распределения
- когда просто нужно размазать по разным тачкам

### Минусы
- неравномерное распределение
- нет учёта нагрузки на инстансы

## Least Connections, Least Response Time

Балансировщик смотрит на **реальную нагрузку** инстансов и направляет запрос туда, где легче.

| Алгоритм | Критерий |
|---|---|
| Least Connections | Меньше всего открытых соединений |
| Least Response Time | Самое маленькое время ответа |
| Least Bandwidth | Меньше пропускная способность (редко — можно попасть на больной инстанс) |

Умнее Round Robin, но сложнее в реализации — балансировщик должен отслеживать состояние каждого инстанса.

## Power of Two Choices

Случайно выбираем **2 инстанса** из списка. Из этих двух выбираем лучший по метрике (least connections, least response time).

**Зачем:** компромисс между random (быстро, но глупо) и least connections (умно, но дорого).

На практике редкий, больше теоретический.

## Sticky Sessions (привязка к инстансу)

### Зачем
В инстансах хранится [[Кэширование — основы|кэш/сессия]] пользователя. Вова попал на инстанс 2, там его кэш. При Round Robin следующий запрос может попасть на инстанс 1 или 3, где кэша нет.

### Решение — хэширование
1. Берём ключ пользователя (user ID, session ID)
2. Считаем хэш (например, CRC32)
3. Остаток от деления на количество узлов → номер инстанса

Один и тот же ключ всегда даёт один и тот же инстанс.

### Почему не хэш-таблица на балансировщике
Можно хранить маппинг "пользователь → инстанс", но это съедает память балансировщика. Хэширование не требует хранения.

### Коллизии
Два пользователя могут попасть на один инстанс — чуть неравномерное распределение, но всё работает. Бороться не нужно.

### Проблема
Количество узлов изменилось (добавили/убрали инстанс) → остаток от деления изменится → **все перемешаются**. Решается consistent hashing (тема шардирования).

## Клиентская балансировка

Нет отдельного балансировщика. Клиентский код сам знает обо всех инстансах и сам решает, куда отправить запрос.

### Плюсы
- нет лишнего сетевого хопа → ниже [[Производительность|latency]]
- нет единой точки отказа (балансировщик не может упасть, его нет)

### Минусы
- клиент усложняется логикой балансировки
- при добавлении/удалении инстанса нужно доносить конфигурацию до всех клиентов
- плохо с эксплуатацией

**Итог:** хорошо по перформансу, плохо по удобству. Поэтому чаще ставят отдельный балансировщик.
