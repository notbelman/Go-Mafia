- **Cache Aside (Lazy)** — приложение само координирует кэш и БД. Miss → идёт в БД → кладёт в кэш. Самая популярная. Кэш упал → сервис работает, просто медленнее
- **Cache Through** — приложение общается **только с кэшом**. Кэш сам ходит в БД при промахе. Кэш упал → **сервис недоступен** (критическая зависимость)
- **Cache Ahead** — приложение читает **только из кэша**. Фоновый воркер периодически загружает данные из БД. Минимальный [[Производительность|latency]], но данные могут отставать
- Cache Aside — "lazy": данные попадают в кэш **только когда их запросили**. Первый запрос всегда miss (cold start)
- Cache Through — кто координирует = ключевое отличие. Aside → приложение. Through → кэш. Through нужен **умный кэш** (не просто Redis из коробки)
- Cache Ahead — подходит для данных, которые **меняются редко** (конфигурации, справочники). Не подходит для часто меняющихся (баланс пользователя)

## Сравнение

| | Cache Aside | Cache Through | Cache Ahead |
|---|---|---|---|
| Кто координирует | Приложение | Кэш | Воркер |
| Ходит ли приложение в БД | Да, при miss | Нет | Нет |
| Кэш упал → | Работает (медленнее) | **Не работает** | **Не работает** |
| Актуальность данных | Высокая | Высокая | Может отставать |
| Сложность инфраструктуры | Низкая | Высокая (умный кэш) | Средняя (воркер) |

## Cache Aside (Lazy Caching)

Приложение само координирует кэш и БД. Кэш ничего не знает про БД, БД ничего не знает про кэш.

### Чтение
1. Приложение идёт в кэш
2. Hit → возвращает данные
3. Miss → идёт в БД → получает → кладёт в кэш → возвращает

### Запись
1. Приложение пишет в БД
2. БД подтверждает
3. Приложение кладёт новое значение в кэш (или нет — зависит от требований к консистентности)

### Почему "lazy"
Данные попадают в кэш только когда их кто-то запросил. Никто не запрашивал → в кэше нет.

### Плюсы
- простая реализация — логика в коде приложения
- кэш упал → сервис работает, просто медленнее (ходит в БД)
- самая распространённая стратегия

### Минусы
- первый запрос всегда miss (cold start)
- приложение усложняется логикой "проверь кэш → сходи в БД → положи в кэш"

## Cache Through (сквозное кэширование)

Приложение общается **только с кэшом**. Кэш сам ходит в БД при промахе.

### Чтение
1. Приложение идёт в кэш
2. Hit → возвращает данные
3. Miss → **кэш сам** идёт в БД → сохраняет у себя → возвращает

### Запись
1. Приложение пишет в кэш
2. **Кэш сам** пишет в БД
3. Кэш подтверждает приложению

### Плюсы
- простая логика приложения — одна точка обращения
- консистентность: кэш и БД всегда синхронны

### Минусы
- сложная инфраструктура — кэш должен уметь ходить в БД
- кэш упал → **сервис недоступен** (критическая зависимость)
- нужен умный кэш (не просто Redis из коробки)

### Ключевое отличие от Cache Aside
Кто координирует. Cache Aside → приложение. Cache Through → кэш.

## Cache Ahead (опережающее кэширование)

Приложение читает **только из кэша**. Фоновый воркер периодически загружает данные из БД.

### Чтение
Приложение идёт в кэш → получает данные. В БД **не ходит никогда**.

### Наполнение кэша
Фоновый процесс (воркер, крон) периодически читает из БД → кладёт в кэш.

### Плюсы
- минимальный [[Производительность|latency]] на чтение — только кэш
- приложение максимально простое

### Минусы
- данные могут быть неактуальны (воркер ещё не обновил)
- нужен фоновый процесс для синхронизации
- часто меняющиеся данные — кэш постоянно устаревает

### Compaction при записи
Если пишем асинхронно батчами, можно использовать compaction — из нескольких записей одного ключа оставляем только последнюю.

### Когда подходит
- данные, которые меняются редко (конфигурации, справочники)
- **не подходит** для часто меняющихся (баланс пользователя)
