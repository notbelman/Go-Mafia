- **Репликация PG:** синхронная (нельзя потерять бронирование); ES — асинхронная (поиск не критичен)
- **Шардирование:** hotels по гео (latitude/longitude), orders по user_id
- **Сезонность:** лето — курорты (Сочи, Крым), зима — горнолыжные (Красная Поляна, Шерегеш)
- **Подготовка к сезону:** нагрузочное тестирование, ресурсы x2, точечное усиление гео-шардов
- **Graceful degradation:** ES упал — поиск не работает, бронирования продолжают; резервная платёжка

---

Strong consistency определяет всё: синхронная репликация, шардирование по гео, подготовка к сезону.

## Репликация PostgreSQL (hotels, orders): синхронная

**Почему синхронная?** Strong consistency. Нельзя потерять бронирование. Нельзя показать "2 свободных номера", когда на самом деле 0 (мастер обновил, реплика не успела).

Балун: "Strong consistency — даже думать не надо. Синхронная репликация."

**Проблема асинхронной:** записали заказ → пошли на реплику → заказа ещё нет. Клиент: "Я же только что забронировал, где мой заказ?" Решения (если бы была асинхронная): sticky sessions к мастеру, read-after-write с мастера. Но проще — синхронная.

## Репликация ElasticSearch: асинхронная

Поиск — не критичная операция. Задержка на секунду — пользователь не заметит. Strong consistency для поиска не нужна. Если ElasticSearch упал — поиск не работает, но бронирования продолжают.

## Stateless сервисы

**LB, API Gateway (оба), Hotel Service, Order Service** — скейлятся горизонтально без проблем.

## Шардирование hotels: по гео (latitude/longitude)

**Почему по гео, а не по hotel_id?** Пользователь ищет отели в Сочи, не в Сочи+Новосибирск+Москва. По гео — все отели региона на одном шарде, один запрос.

**Дополнительный бонус для сезонности:** летом нагрузка на курортные шарды, зимой — на горнолыжные. Можно точечно усилить нужные шарды, не трогая остальные.

**Минус:** если искать по всей стране — мультишардовый запрос. Но это редкий кейс.

## Шардирование orders: по user_id

Пользователю нужны только **свои** заказы. Нет доступа к заказам других. По user_id — все заказы на одном шарде, один запрос.

processing_order — локальная в каждом шарде, воркер проходит мультисканом.

## Сезонность

**Лето:** курортные регионы (Сочи, Крым, Турция) — всплеск нагрузки.
**Зима:** горнолыжные (Красная Поляна, Шерегеш) — всплеск.

**Подготовка:**
1. Определить сезонные регионы (по историческим данным)
2. Нагрузочное тестирование за несколько месяцев до сезона
3. Закладывать ресурсы ×2 минимум
4. Гео-шардирование позволяет точечно усилить нужные шарды
5. После сезона — сдуваем ресурсы или оставляем (если сервис растёт)

Балун: "В Ozon с конца весны начинали к сезону готовиться."

**Точно посчитать на старте — нельзя.** Нет исторических данных. После первого сезона — есть метрики для прогноза.

## Финальная архитектура

```
Client → LB → API GW (client) ──┬──→ Hotel Service → PostgreSQL (sync replica)
                                │         │
Admin  → LB → API GW (admin) ───┘         └──→ ElasticSearch (async replica)
								 │
								 ├──→ Order Service → PostgreSQL (sync replica)
								 │         │
								 │         ├──→ Kafka (saga)
								 │         │
								 │         └──→ Payment Service (внешний)
								 │
								 └──→ Воркер таймаутов → processing_order
```

## Итоговые решения и почему

| Решение | Почему |
|---|---|
| Реляционка (PostgreSQL) | Транзакции, strong consistency, деньги |
| Синхронная репликация | Нельзя потерять бронирования |
| Saga (не 2PC) | Нет single point of failure |
| room_type вместо room | Отели работают по категориям, не по номерам |
| available по дням | Проще, чем интервалы (пересечения, минимумы) |
| ElasticSearch | Полнотекстовый поиск с морфологией |
| Шардирование по гео | Пользователь ищет локально + бонус для сезонности |
| processing_order | Контроль зависших заказов, таймауты |
| Резервная платёжка | Если основная недоступна — не теряем клиента |
