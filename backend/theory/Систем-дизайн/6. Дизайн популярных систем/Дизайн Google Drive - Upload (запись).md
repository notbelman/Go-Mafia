- **Chunking на клиенте:** файл бьётся на чанки ~1 МБ, нумеруются (index), отправляются параллельно
- **CAS дедупликация:** хэш чанка уже в S3 → не записываем повторно, только добавляем в chunk_per_file
- **Сжатие на сервере:** CPU bound, но не греем клиентские устройства
- **Порядок записи:** сначала S3, потом PostgreSQL — безопаснее при сбоях (бесхозный чанк лучше потерянных метаданных)
- **CQRS:** Uploader (mutable: загрузка, удаление) и Downloader (immutable: чтение) — скейлятся независимо

---

Как файл попадает в систему. Клиент → балансер → Uploader → S3 + PostgreSQL.

## Архитектура записи

```
Client → Nginx (LB) → Uploader Service → S3 (чанки)
                                        → PostgreSQL (метаданные)
```

**Uploader Service** — отдельный сервис для записи. Принимает чанки, сжимает, кладёт в S3, пишет метаданные в PostgreSQL.

## Порядок действий при загрузке файла

**1. Клиент разбивает файл на чанки** (~1 МБ каждый), нумерует их (index = 0, 1, 2...).

**2. Клиент отправляет чанки** — можно параллельно (несколько воркеров/потоков). Параллельно — потому что загрузка это I/O bound нагрузка, нужно максимально использовать пропускную способность.

**3. Uploader получает чанк →** сжимает его (CPU bound, но на сервере) → считает хэш.

**4. Проверка дедупликации.** Хэш уже есть в S3? Если да и контент совпадает — не записываем в S3, только добавляем запись в chunk_per_file. Если нет — записываем в S3.

**5. Запись в PostgreSQL.** Добавляем запись в chunk_per_file (file_id, chunk_hash, index).

**6. Все чанки загружены →** ставим `ready = true` на файле.

## Порядок: сначала S3, потом PostgreSQL

Почему не наоборот? Если записали в PostgreSQL, но не в S3 — метаданные есть, а данных нет. Хуже. Если записали в S3, но не в PostgreSQL — чанк лежит "бесхозный", но при повторной попытке дедупликация его найдёт и не запишет повторно. Безопаснее.

## Восстановление загрузки

Загрузили 2 из 10 чанков, сеть моргнула. Как восстановить?

1. Клиент повторяет запрос
2. Сервер смотрит chunk_per_file — видит 2 записи
3. Понимает, каких чанков не хватает (по index)
4. Клиент догружает только недостающие

Альтернативы: хранить прогресс загрузки в отдельной KV-базе, или клиент помнит локально, какие чанки отправил.

## Параллельная загрузка и sticky sessions

Файл из 10 чанков. Три инстанса Uploader. Чанки могут приходить на разные инстансы. Это ОК — индекс проставлен клиентом, в PostgreSQL запишется правильно.

Но: если один сервис создаёт запись file в PostgreSQL, а другой пытается вставить chunk_per_file — может быть race condition. Решение: **sticky sessions** — все чанки одного файла идут на один инстанс. Или: файл создаётся заранее (отдельным запросом), а потом чанки грузятся на любой инстанс.

## CQRS: Uploader + Downloader

Балун разделил на два сервиса:
- **Uploader (mutable)** — загрузка, удаление, создание каталогов
- **Downloader (immutable)** — только чтение

Почему: разная нагрузка (сжатие vs разжатие), разные паттерны масштабирования. Можно скейлить независимо.
