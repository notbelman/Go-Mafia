- **FR:** upload, download, delete файлов; создание каталогов (без шаринга, версионирования)
- **NFR:** DAU 50 млн, availability 99.95%, read/write 1:1, макс. файл 100 ГБ
- **На пользователя:** ~100 файлов, средний размер ~1 МБ, 6 обращений/день
- **ASR:** система про хранение — огромные объёмы данных и трафик
- **API:** uploadFile, downloadFile, removeFile, createDirectory

---

Система хранения файлов. Ключевая особенность — работа с большими объёмами данных и трафика.

## Функциональные требования

- Сохранение и загрузка файлов
- Удаление файлов
- Создание каталогов (структуризация файлов как в файловой системе)

Что **не** поддерживаем: редактирование файлов, шаринг, совместный доступ, версионирование.

## Нефункциональные требования

- DAU 50 млн
- Availability стандартная (99.95%)
- Read/write соотношение ≈ 1:1 (сколько загружают, столько и скачивают)
- Максимальный размер файла: 100 ГБ
- У каждого пользователя ~100 файлов, средний размер ~1 МБ
- Пользователь обращается к файлам 6 раз в день (3 загрузки + 3 скачивания)
- Геораспределённости нет, сезонности нет

## ASR (ключевое требование)

Здесь нет явного read-intensive или write-intensive — соотношение 1:1. Но это **система про хранение.** Огромные объёмы данных, большой трафик. ASR = как эффективно хранить и передавать файлы. Балун: "Нам важно подумать, как это всё будет храниться. Не где, а сам подход."

## API

```
uploadFile(file)         — загрузка файла (по чанкам)
downloadFile(file_id)    — скачивание файла
removeFile(file_id)      — удаление файла
createDirectory(name, parent_id) — создание каталога
```

## Ключевые решения до начала проектирования

Прежде чем рисовать компоненты, Балун проговорил **три фундаментальных решения**:

1. **Чанкинг** — бьём файлы на куски по ~1 МБ (по размеру среднего файла)
2. **Сжатие** — жмём чанки на сервере (не на клиенте, чтобы не греть мобилки)
3. **Дедупликация через CAS** — одинаковые чанки храним один раз, адресуем по хэшу

Эти три решения определяют всю дальнейшую архитектуру.
