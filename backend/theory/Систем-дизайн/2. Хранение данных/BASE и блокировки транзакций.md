- **BASE** — антипод ACID для распределённых систем. **BA** (Basically Available) — всегда отвечает, даже устаревшими данными. **S** (Soft state) — состояние меняется фоново. **E** (Eventually consistent) — узлы когда-нибудь сойдутся
- **2PL (Two-Phase Locking)** — изоляция транзакций через мьютекс на каждую строку. Фаза расширения (захват блокировок) → фаза сужения (отпускание). Проблема: **deadlock**
- **Deadlock:** A лочит строку 1, хочет 2. B лочит строку 2, хочет 1. Обе ждут. Решение БД: по таймауту убить одну (rollback). Предотвращение: захватывать блокировки **в одном порядке**
- **MVCC** (Multi-Version Concurrency Control) — альтернатива 2PL без блокировок. UPDATE = пометить старую строку + вставить новую. Поэтому INSERT дешевле UPDATE в PostgreSQL
- **2PL ≠ 2PC** — 2PL про изоляцию транзакций (блокировки), 2PC про распределённые транзакции (коммит)
- ACID в NoSQL: MongoDB — multi-doc с 4.0 (медленнее). Cassandra — Paxos (дорогие). Redis — MULTI/EXEC (атомарный батч). DynamoDB — TransactWriteItems (до 100 items)

## BASE vs ACID

| | ACID | BASE |
|---|---|---|
| Консистентность | Strong (строгая) | Eventual (когда-нибудь) |
| Доступность | Может отказать | Всегда отвечает |
| Подход | Корректность важнее | Доступность важнее |
| Где | Реляционки (PostgreSQL) | Распределённые NoSQL (Cassandra) |

### BASE расшифровка
- **BA — Basically Available:** система всегда отвечает, даже если часть узлов упала. Может вернуть устаревшие данные, но не ошибку
- **S — Soft state:** состояние может меняться со временем без новых записей — фоновая синхронизация
- **E — Eventually consistent:** после записи все узлы _когда-нибудь_ придут к одному состоянию

### ACID в NoSQL

| БД | ACID | Детали |
|---|---|---|
| MongoDB | Да (с 4.0) | Multi-document, но медленнее single-doc |
| Cassandra | Частично | Lightweight transactions через Paxos, дорогие |
| Redis | Частично | MULTI/EXEC — атомарный батч, не полноценные транзакции |
| DynamoDB | Частично | TransactWriteItems (до 100 items), eventual по умолчанию |

## 2PL (Two-Phase Locking)

Механизм изоляции транзакций через мелкогранулярные блокировки (мьютекс на каждую строку).

### Две фазы
1. **Фаза расширения** — транзакция захватывает блокировки на нужные строки
2. **Фаза сужения** — отпускает блокировки в обратном порядке

### Проблема: deadlock
```
Транзакция A: лочит строку 1 → хочет строку 2
Транзакция B: лочит строку 2 → хочет строку 1
→ обе ждут друг друга → пробка на перекрёстке
```

### Как БД решает
Менеджер транзакций по таймауту убивает одну (rollback), вторая проходит.

### Как предотвратить самим
Захватывать блокировки **в одном и том же порядке** во всех транзакциях. Все лочат сначала строку 1, потом 2 → deadlock невозможен.

## MVCC (альтернатива 2PL)

Multi-Version Concurrency Control — версионный подход **без блокировок**. Используется в PostgreSQL.

UPDATE = пометить старую строку (TX Max) + вставить новую. Поэтому INSERT дешевле UPDATE в MVCC-базах.

### 2PL ≠ 2PC
- **2PL** (Two-Phase Locking) — изоляция транзакций, про блокировки
- **2PC** (Two-Phase Commit) — распределённые транзакции, про коммит
