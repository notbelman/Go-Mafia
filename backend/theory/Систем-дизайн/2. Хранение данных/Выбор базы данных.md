- **SQL**: таблицы, строгая схема, ACID, нативный JOIN, вертикальное масштабирование. **NoSQL**: документы/KV/графы, гибкая схема, BASE, горизонтальное масштабирование
- **6 критериев выбора:** транзакции → реляционка. Формат данных (время/граф/файлы). Навык команды. Характер обращения (мелкие/аналитика/KV). Сообщество. Частота изменения схемы
- **Персистентные** (PostgreSQL) — данные на диске, переживают рестарт. **In-Memory** (Redis, Tarantool) — данные в RAM, быстрее, но рестарт = потеря. Решение: снапшоты + WAL + репликация
- **Embedded** (BoltDB, RocksDB) — библиотека в коде, нет сетевых запросов, пишет на диск "под ноги". **Single File** (SQLite) — вся БД = один файл
- **MongoDB vs PostgreSQL:** MongoDB = гибкая схема + embedded documents + горизонтальное масштабирование. PostgreSQL = строгая схема + JOIN + полный ACID
- MongoDB: multi-document ACID с 4.0, но медленнее — проектировался под **single-document atomicity**. `$lookup` вместо JOIN — дороже, правильнее embedded documents
- Не обязательно одна БД: посты → реляционка, аналитика → ClickHouse, поиск → ES, кэш → Redis. Но не городить звездолёт для двух таблиц
- Деньги = **всегда транзакции** = реляционка

## SQL vs NoSQL

| | SQL | NoSQL |
|---|---|---|
| Модель данных | Таблицы, строки, колонки | Документы, KV, графы, column-family |
| Схема | Строгая, определена заранее | Гибкая, можно менять на лету |
| Язык запросов | SQL (стандарт) | У каждой БД свой (MQL, CQL, API) |
| JOIN | Нативный, быстрый | Нет или дорогой (`$lookup`) |
| Транзакции | ACID из коробки | BASE по умолчанию, ACID частично |
| Масштабирование | [[Масштабирование\|Вертикальное]] (горизонтальное сложно) | [[Масштабирование\|Горизонтальное]] из коробки |
| Консистентность | Strong по умолчанию | Eventual по умолчанию (tunable) |
| Связи | FK, нормализация | Embedded documents, денормализация |

## MongoDB vs PostgreSQL

| | PostgreSQL | MongoDB |
|---|---|---|
| Модель | Строки в таблицах, FK, нормализация | BSON-документы, embedded data |
| Схема | Строгая (ALTER TABLE) | Гибкая (документы могут отличаться) |
| Транзакции | Полный ACID из коробки | Multi-document ACID с 4.0 (медленнее) |
| JOIN | Нативный, оптимизатор (nested loop, hash, merge) | `$lookup` — дороже, нет оптимизатора |
| Когда | Сложные связи, транзакции, аналитика с JOIN | Гибкая схема, вложенные данные, rapid prototyping |

## 6 критериев выбора БД

### 1. Транзакции
Нужны транзакции → реляционка. Деньги = всегда транзакции.

### 2. Формат данных
Временные события → time series. Отношения/графы → графовая. Сырые файлы → blob storage. Документы без связей → документная.

### 3. Навык работы с технологией
Нет опыта с графовой БД, а время поджимает → реляционка закроет задачу.

### 4. Характер обращения к данным
Много маленьких запросов → реляционка. Миллионы строк по паре колонок → колоночная. Ключ-значение → KV.

### 5. Сообщество и зрелость
Непонятная БД от Васи → риск. Популярное решение → быстрее решишь проблемы.

### 6. Частота изменяемости формата данных
Бизнес постоянно меняет структуру → документная. Стабильный формат → реляционка.

### Не обязательно одна БД
Посты → реляционка. Аналитика → ClickHouse. Поиск → Elasticsearch. Кэш → Redis/Tarantool. Данные дублируются, но нагрузка размазывается. **Но:** не городить звездолёт для двух таблиц.

## Персистентные vs In-Memory

| | Персистентные | In-Memory |
|---|---|---|
| Хранение | Диск (HDD/SSD) | RAM |
| Рестарт | Данные на месте | Данные потеряны (без доп. мер) |
| Скорость | Медленнее | Быстрее ([[Производительность\|RAM на порядки быстрее диска]]) |
| Пример | PostgreSQL, MySQL, ClickHouse | Redis, Memcached, Tarantool |

### Как in-memory решают проблему рестарта
1. **Снапшоты** — периодически записывать состояние на диск. Минус: данные между снапшотами теряются
2. **WAL (Write-Ahead Log)** — журнал изменений на диск перед каждой операцией. Потеря минимальна
3. **Репликация** — копия на другом инстансе

**На практике:** комбинируют всё. Tarantool = снапшоты + WAL + репликация.

## Embedded и Single File базы данных

### Embedded (встраиваемые)
Код БД встраивается в приложение как библиотека. Нет сетевых запросов — пишет "под ноги" на диск.

**Зачем:** структурированно писать на диск, строить индексы, конкурентный доступ — без отдельного сервера БД.

**Примеры:** BoltDB (Go), RocksDB, LevelDB.

### Single File Database
Вся БД = один файл. Можно скопировать, передать, поднять.

**Пример:** SQLite. Где используется: мобильные приложения, локальные конфигурации, прототипы.

**Отличие:** single file — про формат (один файл). Embedded — про архитектуру (библиотека). SQLite — и то, и другое.
