- **Chunking** — разбиение больших файлов на куски фиксированного размера (~1 МБ). Восстановление загрузки (догрузить недошедшие), равномерное распределение, дедупликация, параллельная загрузка
- **CAS (Content Addressable Storage)** — адрес файла = хэш содержимого. Одинаковый контент → одинаковый ключ → храним один раз
- **Дедупликация:** мем "котик" сохранён 10K пользователями → без CAS = 10K копий, с CAS = один чанк + 10K ссылок
- Разбиение **на клиенте** (клиент знает какие чанки загружены), сжатие **на сервере** (не греть CPU мобилки)
- **Коллизии хэшей:** при совпадении хэша — сравниваем побайтово. Решение: double hashing (второй хэш другой функцией)
- Нет модифицирующих операций — файлы неизменяемые. Иначе нужен copy-on-write
- Подсчёт ссылок через таблицу `chunk_per_file` — когда ссылок ноль, чанк можно удалить

## Chunking (разбиение файлов на чанки)

### Зачем
1. **Восстановление загрузки.** 100 ГБ, на 50 ГБ сеть моргнула → догрузить только недошедшие чанки
2. **Равномерное распределение.** Файлы одинакового размера ложатся ровно на хранилище
3. **Дедупликация.** Одинаковые куски разных файлов хранятся один раз
4. **Параллельная загрузка.** Несколько воркеров грузят разные чанки одновременно

### Размер чанка
Зависит от среднего размера файла. ~1 МБ — хороший компромисс. Балун: "Мегабайт нормально пишется, мегабайт нормально читается."

Слишком маленький (100 байт) — слишком много записей в метабазе. Слишком большой (1 ГБ) — теряем преимущества восстановления.

### Где разбивать
**На клиенте.** Клиент разбивает файл, нумерует чанки, отправляет по одному (или параллельно). Клиент знает, какие чанки уже загружены → можно догрузить.

### Где сжимать
**На сервере.** Сжатие на клиенте экономит трафик, но греет CPU (мобилки). Сжатие на сервере — клиенту легче.

### Где встречается
Google Drive, Dropbox, S3 (multipart upload), видеостриминг (HLS/DASH), торренты.

## CAS (Content Addressable Storage) + дедупликация

Хранилище, где ключ = хэш содержимого.

### Как работает

**Запись:** чанк → считаем хэш → есть чанк с таким хэшем и контент совпадает? → **не записываем**, ссылаемся → нет? → записываем.

**Чтение:** знаем хэш → достаём по хэшу.

### Дедупликация

Мем "котик" сохранён 10K пользователями:
- Без CAS: 10K копий одного файла
- С CAS: один чанк в S3, 10K ссылок в метабазе

Подсчёт ссылок через таблицу `chunk_per_file`. Ссылок ноль → можно удалить.

### Коллизии хэшей
Два разных чанка → одинаковый хэш. Редко, но возможно.

**Обнаружение:** при совпадении хэша — побайтовое сравнение содержимого.

**Решение:** double hashing — второй хэш другой функцией.

Балун: "Это те же самые алгоритмы и структуры данных. В system design не придумано отдельных решений."

### Важно
Нет модифицирующих операций. Файлы неизменяемые. Если бы нужно было редактировать — copy-on-write (при изменении создаём копию).

### Где встречается
Git (SHA-1), Docker (слои образов), системы дедупликации бэкапов, IPFS.
