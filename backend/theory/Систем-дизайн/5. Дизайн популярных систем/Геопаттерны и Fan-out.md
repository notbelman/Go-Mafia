- **Fan-out on Write (push)** — пост создан → сразу обновляем ленты всех друзей. Чтение мгновенное (лента готова). Минус: 1 запись = N операций по числу друзей
- **Fan-out on Read (pull)** — лента собирается в момент чтения. Запись дешёвая, но чтение медленное (обход всех друзей)
- **Celebrity Problem** — знаменитость с 1M подписчиков → 1 пост = 1M операций записи. Решение: гибрид — обычные → push, звёзды (>5–10K подписчиков) → pull, подмёрживаем при чтении
- **Geohash** — координаты как строка. Чем длиннее строка, тем меньше квадратик. 5 символов ≈ 4.9×4.9 км — достаточно для такси/доставки
- Geohash быстрее квадродеревьев на высоком RPS записи (3000+) — обновление = просто перезапись значения, нет перестроения дерева
- Поиск ближайших: вычисляем geohash точки → достаём всех из этого квадратика. Нет водителей → смотрим соседние
- Гибрид push/pull — золотая середина. Порог (5–10K) определяется эксплуатацией

## Fan-out on Write vs Fan-out on Read

| | Fan-out on Write (push) | Fan-out on Read (pull) |
|---|---|---|
| Когда формируем ленту | При создании поста | При чтении ленты |
| Запись | Дорогая (1 → N операций) | Дешёвая (просто сохранили) |
| Чтение | Мгновенное (лента готова) | Медленное (собираем на лету) |
| Подходит для | Read-intensive, обычные пользователи | Write-intensive, знаменитости |

### Fan-out on Write (push)

Пост создан → **сразу** обновляем ленты всех друзей/подписчиков.

```
Post Service → Kafka (transaction outbox) → Feed Service
  → Relation Service ("с кем дружит автор?")
  → обновляет home feed каждого друга в Tarantool/Redis
```

**Структура кэша:** дека (deque). Новый пост → в начало, переполнение → выкидываем с конца.

### Fan-out on Read (pull)

Пользователь открывает ленту → **в момент чтения** собираем посты от всех друзей, сортируем, отдаём.

### На практике — гибрид

Обычные (< 5–10K друзей) → push. Звёзды (> 5–10K) → pull, подмёрживаем при чтении.

## Celebrity Problem (проблема знаменитостей)

Павел Дуров написал пост → нужно обновить 1M home feeds. Одна запись = миллион операций.

### Решение — гибридный подход

**Обычный пользователь** → fan-out on write, пушим в ленты друзей. Друзей мало — ок.

**Знаменитость** → **не пушим** в ленты. Просто обновляем user feed самой знаменитости.

**При чтении:** Feed Service достаёт home feed → смотрит дату первого поста → проверяет user feed всех знаменитостей, на которых подписан → если есть свежее — **подмёрживает на лету**.

### Компромисс
Чтение чуть дороже (подмёрж). Зато запись не порождает миллион операций.

### Где встречается
Twitter, Instagram, YouTube, новостные агрегаторы — везде, где один автор может иметь непропорционально много подписчиков.

## Geohash

Географические координаты как строка фиксированной длины. Пространство делится на квадратики.

### Разрядность

| Символов | Размер квадрата |
|---|---|
| 2 | 1200 × 625 км |
| 3 | 156 × 156 км |
| 4 | 39 × 19.5 км |
| **5** | **4.9 × 4.9 км** (такси/доставка) |
| 6 | 1.2 × 0.6 км |

### Зачем вместо квадродеревьев
5M водителей обновляют координаты каждые 5 сек = 3300+ RPS на запись. Квадродеревья требуют перестроения — медленно. Geohash = просто перезапись строки.

### Хранение позиций
```
driver_position:
  geohash (PK) | driver_id | latitude | longitude
```

Вторичный хэш-индекс на `driver_id` — при обновлении позиции проверяем, не сменился ли квадратик.

### Поиск ближайших
Пассажир в точке → вычисляем geohash → достаём всех из квадратика. Нет водителей → смотрим соседние.

### Ограничение
Пользователь на границе квадратика — ближайший может быть в соседнем квадрате. Для такси не критично, для точных задач — проверять соседей.

### Где встречается
Tinder, Delivery Club, Яндекс.Еда, 2ГИС — любой гео-поиск с высоким RPS.
