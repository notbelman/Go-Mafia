Сервис для трекинга водителей. Отвечает на вопрос: "Где сейчас находятся водители?"

## Почему отдельный Geo Service

Задача "трекать позиции водителей" сильно отделена от всего остального (заказы, матчинг, поездки). Можно оторвать от всей системы и проектировать отдельно. Начинаем с неё — Балун: "Я привык начинать кушать слона по кусочкам. Что простого?"

## Почему in-memory (Tarantool)

~3300 RPS на обновление позиций. Каждый апдейт — перезапись координат. Дисковая БД не потянет такой поток случайных записей. Поэтому сразу in-memory.

## Почему Geohash, а не дерево

**Квадродерево (Quadtree) или R-tree:** при каждом обновлении позиции — перестроение части дерева. На 3300 RPS перестроение будет медленным. Конкурентный доступ к дереву — ещё сложнее.

**Geohash:** просто строка. Обновление = перезапись значения (или перемещение между ячейками). Никакого перестроения. Поиск ближайших = достать всех из одной ячейки по ключу.

Выбрана **5-символьная** разрядность ≈ 5 км × 5 км. Достаточно для поиска ближайшего такси.

## Data model

```
driver_position:
  geohash     (PK часть)
  driver_id   (PK часть)
  latitude
  longitude
```

**Вторичный хэш-индекс на driver_id.** Зачем: при обновлении позиции нужно найти водителя, проверить, сменился ли квадратик.

## Алгоритм обновления позиции

1. Водитель шлёт новые координаты (lat, lng)
2. Вычисляем новый geohash из координат
3. По driver_id (через вторичный индекс) находим текущую запись
4. Сравниваем старый geohash с новым:
   - **Совпадает** → просто обновляем lat/lng
   - **Не совпадает** → удаляем из старого geohash, вставляем в новый

## Поиск ближайших водителей

1. Пассажир в точке (lat, lng) → вычисляем geohash
2. Достаём всех водителей в этом geohash
3. Нет водителей? → Сканим соседние geohash-ячейки
4. Нет нигде → "Нет таксистов поблизости"

**Ограничение:** пассажир на границе квадратика — ближайший может быть в соседнем. Для такси не критично (подождёт пару минут).

## Две структуры: base и active

```
base_driver_position    — свободные водители (для Matching)
active_driver_position  — занятые водители (для Ride Service)
```

**Зачем разделили:** без разделения Matching Service ищет водителей → получает 10 штук → все уже везут пассажиров. Бесполезный результат. Matching смотрит **только** base, Ride Service обновляет **только** active.

**Переход между структурами:**
- Водитель начал смену → добавляется в base
- Водитель взял заказ → перемещается из base в active
- Водитель завершил поездку → обратно в base
- Водитель закончил смену → удаляется из base
