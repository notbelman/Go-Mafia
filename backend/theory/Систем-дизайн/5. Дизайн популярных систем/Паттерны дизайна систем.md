- **ASR (Architecture Significant Requirement)** — ключевое требование, которое определяет всю архитектуру. Лента = read-intensive, такси = real-time обновление координат, мессенджер = доставка + надёжность
- **C4 Model** — 4 уровня масштаба: C1 (системы) → C2 (сервисы, БД, очереди) → C3 (компоненты) → C4 (код). На SD-интервью достаточно C1 + C2
- **Architecture as Code** (PlantUML) — архитектура в Git, ревью через PR, версионирование. Miro-доски забрасывают через неделю, код в репозитории — обновляется
- **Staging Bucket** — промежуточное хранилище для файлов, не привязанных к сущности. Загрузил фото → staging → создал пост → перекладываем в основной bucket. Воркер чистит staging по TTL
- **Масштабирование Stateful** — 3 подхода: **fan-out** (шлём всем инстансам), **Service Discovery** (регистрация user→инстанс), **адрес в метаинформации** (IP в стейте пользователя)
- **Сезонность** — предсказуемые всплески (лето = море, зима = горы, Чёрная пятница). Закладывать ×2, шардирование по гео, готовиться заранее (Ozon — с конца весны к сезону)
- Выделить ASR и проговорить вслух на интервью — сразу плюс. Показывает понимание, что движет архитектурой

## ASR (Architecture Significant Requirement)

Ключевое требование, без учёта которого архитектуру можно выбросить.

### Как найти
Смотрим на требования и спрашиваем: "От чего зависит, как я буду строить систему?"

| Система | ASR | Почему |
|---|---|---|
| Лента соцсети | Read-intensive (read/write = 50:1) | Всё затачиваем на чтение: pre-built feeds, in-memory кэш |
| Яндекс.Такси | Real-time обновление (3300 RPS координат) | Архитектура вокруг потока координат |
| Мессенджер | Доставка в реальном времени + надёжность | Сообщение должно дойти за секунды, не потеряться |

### На интервью
Балун: "Если вы это ключевое не учтёте, вашу архитектуру можно взять и выбросить в помойку".

## C4 Model, Architecture as Code

### Четыре уровня масштаба
Аналогия с картой: материки → страны → города → улицы.

| Уровень | Что показывает | Пример |
|---|---|---|
| **C1 — System Context** | Системы целиком и связи | "Есть система аналитики, сообщений, постов" |
| **C2 — Container** | Сервисы, БД, очереди внутри системы | "Post Service, Feed Service, Kafka, PostgreSQL" |
| **C3 — Component** | Компоненты внутри сервиса | Редко рисуют |
| **C4 — Code** | Классы | На практике почти не используется |

### Зачем кодом, а не в Miro
- **Версионирование:** архитектура в Git, видно кто/когда/что изменил
- **Ревью:** добавляешь микросервис → PR → архитектор смотрит
- **Актуализация:** Miro забрасывают, код обновляется вместе с проектом

### PlantUML — синтаксис
```
Person(user, "Пользователь")
Container(post_svc, "Post Service", "Go")
ContainerDb(postgres, "PostgreSQL", "Posts DB")
Rel(user, post_svc, "создаёт пост")
Rel(post_svc, postgres, "пишет/читает")
```

## Staging Bucket (отстойник для медиа)

Промежуточное хранилище для загруженных файлов, которые ещё не привязаны к сущности.

### Проблема
Пользователь загрузил картинку в пост, начал писать текст... и передумал. Картинка уже в S3, а поста нет. Накапливается мусор.

### Решение — двухэтапная загрузка
1. Пользователь грузит картинку → Media Service кладёт в **staging bucket** → возвращает URL
2. Пользователь создаёт пост → Post Service получает URL → воркер перекладывает из staging в **основной bucket**

### Очистка
Воркер периодически проходит по staging и удаляет всё старше N часов. Можно сегментировать по часам — дропаем пачкой.

### Где встречается
Мессенджеры, маркетплейсы, CMS — везде, где загрузка медиа до привязки к сущности.

## Масштабирование Stateful-сервисов

Как масштабировать сервис с persistent connections (WebSocket). Нельзя раундробином — нужно попасть в инстанс, где живёт соединение.

### Три подхода

| Подход | Как работает | Плюс | Минус |
|---|---|---|---|
| **Fan-out** | Шлём во все инстансы, нужный доставляет | Просто | Лишний трафик (N-1 мусор) |
| **Service Discovery** | Регистрация user→инстанс в SD | Точечная доставка | SD под нагрузкой |
| **Адрес в метаинфо** | IP инстанса в стейте пользователя | Нет отдельного сервиса | Нужен механизм обновления |

### При падении инстанса
Клиент теряет WebSocket → переподключается → попадает на другой инстанс → регистрируется заново.

## Сезонность

Подготовка к предсказуемым всплескам нагрузки.

### Что делать
1. **Выделить сезонность в требованиях** — проговорить на интервью
2. **Шардирование по гео** — точечно усилить шарды для курортных регионов
3. **Закладывать ×2** под сезон. После — сдуваем или оставляем

### Когда готовиться
Не за месяц. Балун: "В Ozon мы с конца весны начинали к сезону готовиться." Нагрузочное тестирование, подготовка железа, прогноз по прошлым сезонам.

**На старте** точно посчитать нельзя — нет исторических данных. Берём ×2. После первого сезона — есть метрики.
