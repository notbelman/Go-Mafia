- Сервис сокращения URL: длинный URL → короткий (tinyurl.com/y7keocwj), клик по короткому → redirect на длинный
- **100M URL/день**, read/write = 10:1 → write 1160 RPS, read 11 600 RPS. Storage: 365 ТБ за 10 лет
- Два API: `POST /api/v1/data/shorten {longUrl}` → shortURL, `GET /api/v1/{shortUrl}` → redirect
- **base62** от уникального ID → 7-символьный shortURL. 62^7 = 3.5 трлн > 365 млрд записей. Конфликтов нет (ID уникальный)
- **301 redirect** = браузер кэширует (меньше нагрузки, нет аналитики). **302 redirect** = каждый клик через нас (аналитика, больше нагрузки)
- БД: таблица `url (id BIGINT PK, shortURL VARCHAR(7), longURL TEXT)`. Реляционная, не хеш-таблица — 365 ТБ не поместится в RAM
- Кэш (Redis) для read-heavy нагрузки. Cache Aside: проверяем кэш → miss → БД → кладём в кэш
- Масштабирование: веб-серверы stateless → горизонтально, БД → репликация + шардирование, rate limiting от спама

## Функциональные требования

1. **Сокращение:** длинный URL → короткий URL
2. **Перенаправление:** короткий URL → redirect на длинный
3. Без удаления и обновления
4. Высокая доступность, масштабируемость, устойчивость к сбоям

## Нефункциональные требования + расчёт

### Расчёт

```
Запись: 100M URL/день / 86400 = 1 160 RPS write
Чтение: read/write = 10:1 → 11 600 RPS read
Storage: 100M × 365 × 10 лет = 365 млрд записей
         365 млрд × 100 байт (средний URL) = 365 ТБ за 10 лет
hashValue: 7 символов (62^7 = 3.5 трлн > 365 млрд)
```

### Read/Write ratio
10:1 → **read-heavy** → нужен кэш для ускорения чтения.

## API

```
POST api/v1/data/shorten
  параметр: {longUrl: longURLString}
  возвращает: shortURL

GET api/v1/{shortUrl}
  возвращает: longURL для HTTP-перенаправления
```

## 301 vs 302 redirect

| | 301 (permanent) | 302 (temporary) |
|---|---|---|
| Браузер кэширует? | **Да** — повторные запросы не идут к нам | **Нет** — каждый клик через нас |
| Нагрузка на сервер | Меньше (только первый запрос) | Больше (каждый клик) |
| Аналитика кликов | **Нет** — мы не видим повторные | **Да** — можно считать переходы |
| Когда выбирать | Нужна скорость, не нужна аналитика | Нужна аналитика кликов |

## Модель данных (БД)

Реляционная БД (не хеш-таблица в памяти — 365 ТБ не поместится в RAM).

```
Таблица: url
  id        BIGINT      PK  (от генератора уникальных ID)
  shortURL  VARCHAR(7)      (base62 от id)
  longURL   TEXT            (исходный URL)
```

Пример записи:

| id | shortURL | longURL |
|---|---|---|
| 2009215674938 | zn9edcu | https://en.wikipedia.org/wiki/Systems_design |

## Функция хеширования — почему base62

### Проблема с хеш-функциями (CRC32, MD5, SHA-1)

| Хеш-функция | Результат | Длина |
|---|---|---|
| CRC32 | 5cb54054 | 8 символов |
| MD5 | 5a62509a84df9ee03fe... | 32 символа |
| SHA-1 | 0eeae7916c0685390... | 40 символов |

Даже самый короткий (CRC32) > 7 символов. Обрезать до 7 → **коллизии**. Алгоритм разрешения: берём первые 7 символов хеша → проверяем в БД → если конфликт, рекурсивно добавляем заданную строку к longURL и хешируем заново, пока результат не станет уникальным. Минус: обращение к БД при каждом запросе (дорого). Можно использовать **фильтр Блума** для оптимизации проверки — вероятностная структура, которая позволяет быстро проверить, входит ли элемент в множество, без обращения к БД.

### base62 — выбранное решение

base62: кодирование с 62 символами [0–9, a–z, A–Z].

```
Уникальный ID → base62 → shortURL (7 символов)

Пример: 11157 → 2 × 62² + 55 × 62¹ + 59 × 62⁰ = [2, T, X] → "2TX"
Пример: 2009215674938 → base62 → "zn9edcu"
```

### Сравнение двух подходов

| | Хеш + разрешение конфликтов | base62 |
|---|---|---|
| Длина shortURL | Фиксированная | Переменная (растёт с ID) |
| Генератор ID | Не нужен | **Нужен** |
| Конфликты | Возможны, нужно разрешать | **Исключены** (ID уникальные) |
| Предсказуемость | Нет (хеш не зависит от ID) | Да — можно угадать следующий (угроза безопасности) |

## Флоу записи (сокращение URL)

1. longURL подаётся на вход
2. Проверяем: есть ли longURL в БД?
3. **Да** → возвращаем существующий shortURL
4. **Нет** → генерируем новый уникальный ID (распределённый генератор)
5. Преобразуем ID в shortURL методом base62
6. Сохраняем (id, shortURL, longURL) в БД

### Распределённый генератор ID
Нужен для получения ID, которые не повторяются в рамках всей системы. Решения: Snowflake, выделенный генератор, диапазоны (подробнее — глава 7 книги).

## Флоу чтения (перенаправление URL)

1. Пользователь кликает по короткой ссылке
2. Балансировщик нагрузки направляет запрос к веб-серверу
3. shortURL **есть в кэше**? → сразу возвращаем longURL (redirect)
4. **Нет в кэше** → ищем в БД → кладём в кэш → redirect
5. **Нет в БД** → пользователь ввёл неправильный URL

### Почему кэш
Read/write = 10:1 → read-heavy. Пара `<shortURL, longURL>` хранится в кэше для ускорения. Стратегия: **Cache Aside** (проверяем кэш → miss → БД → пишем в кэш).

## Масштабирование и дополнительные вопросы

| Аспект | Решение |
|---|---|
| **Веб-серверы** | Stateless → горизонтальное масштабирование |
| **БД** | Репликация (read scaling) + хеш-шардирование по shortURL (равномерное распределение, прямой lookup при чтении; range-based по id создаст hotspot на последнем шарде) |
| **Кэш** | Redis, Cache Aside |
| **Rate limiting** | Защита от спама коротких URL |
| **Аналитика** | Отслеживание кликов, времени перехода |
| **Доступность** | Репликация, несколько ДЦ |
