ФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ:

1. Сокращение: длинный URL -> короткий URL
2. Перенаправление: короткий URL -> redirect на длинный
3. Без удаления и обновления
4. Высокая доступность, масштабируемость, устойчивость к сбоям ^n_fr

НЕФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ + РАСЧЁТ:

Запись: 100M URL/день -> 100M / 86400 = 1160 RPS write
Чтение: read/write = 10:1 -> 11 600 RPS read
Storage: 100M x 365 x 10 лет = 365 млрд записей
365 млрд x 100 байт (средний URL) = 365 ТБ за 10 лет
hashValue: 7 символов (62^7 = 3.5 трлн > 365 млрд) ^n_nfr

ФЛОУ ЗАПИСИ (сокращение URL):

API: POST api/v1/data/shorten {longUrl: string}
Возвращает: shortURL

1. longURL подаётся на вход
2. Проверяем: есть ли longURL в БД?
3. Да -> возвращаем существующий shortURL
4. Нет -> генерируем новый уникальный ID
5. Преобразуем ID в shortURL методом base62
6. Сохраняем (id, shortURL, longURL) в БД

Пример: ID 2009215674938 -> base62 -> zn9edcu
https://tinyurl.com/zn9edcu ^n_write

ФЛОУ ЧТЕНИЯ (перенаправление):

API: GET api/v1/{shortUrl}
Возвращает: longURL для HTTP-перенаправления

1. Пользователь кликает по короткой ссылке
2. Балансировщик направляет к веб-серверу
3. shortURL есть в кэше? -> сразу возвращаем longURL
4. Нет в кэше -> ищем в БД -> кладём в кэш
5. Возвращаем longURL пользователю

Почему кэш: read/write = 10:1, read-heavy
-> пара <shortURL, longURL> хранится в кэше ^n_read

301 vs 302 REDIRECT:

301 (permanent): браузер КЭШИРУЕТ ответ.
Повторные запросы не идут к нашему сервису.
+ Меньше нагрузки на сервер
- Нет аналитики (не видим повторные клики)

302 (temporary): каждый клик проходит через нас.
Браузер НЕ кэширует.
+ Можно считать переходы, аналитика
- Больше нагрузки

ВЫБОР: нужна аналитика -> 302. Нужна скорость -> 301 ^n_301

ПОЧЕМУ base62, А НЕ ХЕШ-ФУНКЦИЯ:

CRC32 -> 5cb54054 (8 символов, слишком длинный)
MD5   -> 5a62509a84df... (32 символа)
SHA-1 -> 0eeae7916c06... (40 символов)

Обрезать до 7 -> коллизии! Нужно проверять
в БД при каждом запросе (дорого). Фильтр Блума
может помочь, но сложнее.

base62: уникальный ID -> строка из [0-9, a-z, A-Z]
Конфликтов нет (ID всегда уникальный)

НО: если ID инкрементируется на 1, можно
угадать следующий URL -> угроза безопасности.
Решение: распределённый генератор ID (Snowflake) ^n_hash

МОДЕЛЬ ДАННЫХ (БД):

Таблица url:
  id        BIGINT   PK  (от генератора ID)
  shortURL  VARCHAR(7)   (base62 от id)
  longURL   TEXT         (исходный URL)

Почему реляционная БД, а не хеш-таблица в памяти:
ресурсы памяти ограничены и дороги для 365 ТБ данных ^n_db

МАСШТАБИРОВАНИЕ И ДОП. ВОПРОСЫ:

- Rate limiting: защита от спама коротких URL
- Веб-серверы: stateless -> добавляем инстансы
- БД: репликация (read scaling) + шардирование
- Кэш: Redis, Cache Aside
- Аналитика: интеграция для отслеживания кликов
- Доступность, согласованность, надёжность ^n_scale
