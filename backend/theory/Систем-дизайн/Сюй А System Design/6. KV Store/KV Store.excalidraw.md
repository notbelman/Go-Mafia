## Text Elements
ОБРАБОТКА БЕССРОЧНЫХ СБОЕВ — ДЕРЕВО МЕРКЛА:

Реплика пропала навсегда → синхронизация.
1. Делим ключи на бакеты
2. Хешируем ключи в каждом бакете
3. Строим дерево хешей снизу вверх
4. Сравниваем корни → совпадают → данные ОК
5. Не совпадают → спускаемся → находим только
   несогласованные бакеты → синхронизируем их

Плюс: объём синхронизации пропорционален
ОТЛИЧИЯМ, а не размеру всех данных.

ЗАПИСЬ: commit log → memory cache → SSTable
ЧТЕНИЕ: memory cache → Bloom Filter → SSTable ^n_merkle

ИТОГОВАЯ ТАБЛИЦА РЕШЕНИЙ:

Хранение объёмных данных        → Consistent hashing (распределение по серверам)
Высокая доступность чтения     → Репликация + несколько ДЦ
Высокая доступность записи     → Версионирование + векторные часы
Секционирование данных         → Consistent hashing
Регулируемая согласованность   → Кворум (W, R, N)
Гетерогенность серверов        → Virtual nodes
Временные сбои                 → Нестрогий кворум + hinted handoff
Бессрочные сбои                → Дерево Меркла
Обнаружение сбоев              → Gossip protocol
Сбои уровня ДЦ                 → Репликация между ДЦ
Запись на узле                 → Commit log → memory cache → SSTable
Чтение на узле                 → Memory cache → Bloom Filter → SSTable ^WsApnMfn

ОБНАРУЖЕНИЕ СБОЕВ — GOSSIP PROTOCOL:

1. Каждый узел хранит список (ID + счётчик пульсации + время)
2. Периодически инкрементирует свой счётчик
3. Шлёт пульс СЛУЧАЙНЫМ узлам
4. Получатели обновляют свои списки
5. Счётчик не растёт долго → узел МЁРТВ

Почему не "все ко всем":
При 100+ серверах мультивещание неэффективно.
Gossip = O(log N) распространение информации.

ОБРАБОТКА ВРЕМЕННЫХ СБОЕВ:
Нестрогий кворум + Hinted Handoff:
Недоступный s2 → запросы идут на s3.
s2 вернулся → s3 передаёт изменения. ^TKeltRDz

ВЕРСИОНИРОВАНИЕ — ВЕКТОРНЫЕ ЧАСЫ:

D1([Sx,1]) → D2([Sx,2]) → ответвление:
  D3([Sx,2],[Sy,1])  ← сервер Sy
  D4([Sx,2],[Sz,1])  ← сервер Sz
→ D3 и D4 конфликтуют!
D5([Sx,3],[Sy,1],[Sz,1]) ← клиент разрешил

Все версии Y >= X → потомок → нет конфликта
Хоть одна версия Y < X → конфликт → клиент решает

NFR:
- Малый размер пар: < 10 КБ
- Высокая доступность, автомасштабирование
- Tunable consistency (W, R, N)
- Низкая латентность ^rpxErGYY

KV Store (хранилище ключ-значение) — конспект ^title

CAP-ТЕОРЕМА → выбираем AP:

CP: блокируем запись при partition (банки)
AP: продолжаем отвечать, eventual consistency
CA: не существует (сеть рвётся всегда)

КВОРУМ (N, W, R):
N = кол-во реплик, W = кворум записи, R = кворум чтения
W + R > N → строгая согласованность (обычно N=3, W=R=2)
R=1, W=N → быстрое чтение
W=1, R=N → быстрая запись

Координатор = прокси между клиентом и репликами.
Отправляет запросы, собирает подтверждения. ^n_cap
