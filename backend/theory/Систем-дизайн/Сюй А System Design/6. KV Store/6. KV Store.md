- **KV Store** — нереляционная БД: `put(key, value)` и `get(key)`. Ключ уникальный, значение — непрозрачный объект. Примеры: Amazon Dynamo, Cassandra, Redis, Memcached
- Один сервер: хеш-таблица в памяти, но ресурсы ограничены. Для крупных данных → **распределённое** хранилище (distributed hash table)
- **CAP-теорема** определяет архитектуру: CP (банки — согласованность важнее) или AP (соцсети — доступность важнее). CA не существует в реальности — сетевые сбои неизбежны
- **Секционирование:** consistent hashing — ключ на кольце → ближайший сервер по часовой. Virtual nodes для равномерности. Добавление/удаление серверов → перемещается ~1/N данных
- **Репликация:** N реплик по часовой стрелке от ключа. Реплики в **разных ДЦ** для надёжности. Кворум: W + R > N → строгая согласованность
- **Версионирование:** векторные часы `D([S1,v1],[S2,v2])` для обнаружения конфликтов. Конфликт разрешает **клиент** (как merge в git)
- **Обнаружение сбоев:** gossip protocol (протокол сплетен) — каждый узел шлёт пульс случайным, счётчик пульсации не растёт → узел мёртв
- **Хранение на узле:** запись → commit log → memory cache → при заполнении сбрасывается на диск в SSTable. Чтение → memory cache → фильтр Блума → SSTable

## Требования (из книги)

### Вопросы к интервьюеру
Явного диалога в книге нет, но требования сформулированы:

### Функциональные требования
1. `put(key, value)` — вставить пару
2. `get(key)` — получить значение по ключу
3. Малый размер пар: < 10 КБ

### Нефункциональные требования
- Возможность хранения **объёмных данных** (не влезает на один сервер)
- **Высокая доступность** — быстрые ответы даже при сбоях
- **Хорошая масштабируемость** — поддержка крупных наборов данных
- **Автоматическое масштабирование** — серверы добавляются/удаляются автоматически
- **Регулируемая согласованность** (tunable consistency)
- **Низкая латентность**

## CAP-теорема — выбор архитектуры

Распределённая система может обеспечить **не больше двух** из трёх:
- **C (Consistency)** — все клиенты видят одни и те же данные
- **A (Availability)** — любой клиент получает ответ, даже если узлы недоступны
- **P (Partition Tolerance)** — система работает при нарушении связи

**P — неизбежен** в распределённой системе → реальный выбор: **CP или AP**.

| Тип | Поведение при partition | Пример |
|---|---|---|
| **CP** | Блокирует запись, ждёт восстановления | Банковские системы |
| **AP** | Продолжает отвечать, возможны устаревшие данные | Соцсети, кэши |
| CA | Не существует в реальности | — |

**В этой главе:** проектируем **AP-систему** (Dynamo/Cassandra) с eventual consistency.

## Секционирование данных — Consistent Hashing

Данные не помещаются на один сервер → делим на секции.

### Как работает
1. Серверы наносятся на **кольцо хеширования**
2. Ключ хешируется → ставится на кольцо
3. Ключ сохраняется на **ближайшем сервере по часовой стрелке**

### Преимущества
- **Автоматическое масштабирование:** добавление/удаление серверов → перемещается ~1/N данных
- **Гетерогенность:** серверу с большей ёмкостью → больше virtual nodes

## Репликация данных

Для высокой доступности и надёжности данные реплицируются по **N серверам**.

### Как выбираются реплики
От позиции ключа на кольце двигаемся по часовой → выбираем **N ближайших уникальных** серверов. Реплики размещаются в **разных ДЦ**.

### Кворум (W, R, N)
- **N** = количество реплик
- **W** = кворум записи (сколько реплик должны подтвердить запись)
- **R** = кворум чтения (от скольких реплик ждём ответ)

| Конфигурация | Эффект |
|---|---|
| R = 1, W = N | Оптимизировано для быстрого **чтения** |
| W = 1, R = N | Оптимизировано для быстрой **записи** |
| **W + R > N** | **Строгая согласованность** (обычно N=3, W=R=2) |
| W + R ≤ N | Строгая согласованность **не гарантирована** |

**Координатор** — узел-прокси между клиентом и репликами. Отправляет запросы, собирает подтверждения.

## Модели согласованности

| Модель | Описание |
|---|---|
| **Строгая** | Любое чтение = последняя запись. Все реплики подтвердили |
| **Слабая** | Чтение может вернуть не последнее значение |
| **Eventual** | Рано или поздно все реплики согласуются |

**Выбор для Dynamo/Cassandra:** eventual consistency + версионирование для разрешения конфликтов.

## Версионирование — Векторные часы

### Проблема
Два сервера одновременно обновляют одно значение → конфликт.

```
Сервер 1: put("name", "johnSanFrancisco") → v1
Сервер 2: put("name", "johnNewYork")      → v2
→ Конфликт! Какая версия правильная?
```

### Решение — Векторные часы
Пара `[сервер, версия]` для каждого элемента данных.

```
D1([Sx, 1])                         ← первая запись
D2([Sx, 2])                         ← обновление на том же сервере
D3([Sx, 2], [Sy, 1])                ← ответвление на Sy
D4([Sx, 2], [Sz, 1])                ← ответвление на Sz
→ D3 и D4 конфликтуют! (Sy и Sz не знают друг о друге)
D5([Sx, 3], [Sy, 1], [Sz, 1])      ← клиент разрешил конфликт
```

### Как обнаружить конфликт
- Если **все** версии Y ≥ версий X → Y является потомком X → **нет конфликта**
- Если **хоть одна** версия Y < версии X → **конфликт** → клиент разрешает

### Недостатки
- Усложняет клиент (логика разрешения конфликтов)
- Пары `[сервер, версия]` накапливаются → нужен лимит длины (Amazon не сталкивались с проблемой)

## Обнаружение сбоев — Gossip Protocol

### Проблема
Нельзя судить о поломке сервера по сигналу только от одного другого сервера. Мультивещание "все ко всем" — неэффективно при большом количестве серверов.

### Gossip Protocol (протокол сплетен)
1. Каждый узел хранит **список участников** (ID + счётчик пульсации + время)
2. Каждый узел периодически **инкрементирует** свой счётчик
3. Каждый узел шлёт пульс **случайным** узлам
4. При получении пульса — обновляют список
5. Счётчик не растёт долго → **узел мёртв**

## Обработка сбоев

### Временные сбои — Нестрогий кворум + Прозрачная передача (Hinted Handoff)
Сервер s2 недоступен → вместо него запросы обрабатывает **s3**. Когда s2 вернётся → s3 передаст ему изменения.

### Бессрочные сбои — Дерево Меркла
Реплика пропала навсегда → нужно синхронизировать данные.

**Дерево Меркла:**
1. Делим ключи на бакеты
2. Хешируем ключи в каждом бакете
3. Строим дерево хешей снизу вверх
4. Сравниваем корни двух деревьев → совпадают → данные одинаковые
5. Не совпадают → спускаемся по дереву → находим **только несогласованные бакеты**

**Плюс:** синхронизируем только отличия, а не всё подряд.

### Сбои уровня ДЦ
Реплики в **разных ДЦ**. Один ДЦ целиком недоступен → данные доступны из других.

## Архитектура системы

```
                    Кольцо (consistent hashing)
                  ┌──── n0 ────┐
              n7  │            │  n1
                  │   Клиент   │
              n6  │  ↕ запрос  │  n2
                  │            │
              n5  └──── n4 ────┘  n3
                    координатор
```

### Особенности
- Клиент общается через **координатор** (любой узел на кольце)
- Полностью **децентрализовано** — нет единой точки отказа
- Каждый узел выполняет: клиентский API, обнаружение сбоев, разрешение конфликтов, репликация, хранение

## Маршрут записи (Write Path)

```
Клиент → Запись
    1. Записываем в commit log (на диске, для crash recovery)
    2. Записываем в memory cache (в памяти, быстро)
    3. Когда cache полон → сбрасываем на диск в SSTable
```

**SSTable** (Sorted String Table) — упорядоченный список `<key, value>` на диске.

## Маршрут чтения (Read Path)

```
Клиент → Чтение
    1. Проверяем memory cache → есть → возвращаем
    2. Нет в памяти → проверяем фильтр Блума
    3. Фильтр Блума определяет, в какой SSTable может быть ключ
    4. Читаем из SSTable → возвращаем
```

**Фильтр Блума** — вероятностная структура данных: "ключ точно НЕ здесь" или "ключ ВОЗМОЖНО здесь". Позволяет не сканировать все SSTable.
