- **Rate Limiter** — ограничивает количество запросов за промежуток времени. Защита от DoS, экономия бюджета (платные API), снижение нагрузки от ботов
- Размещение: **middleware** между клиентом и API (или API Gateway, если микросервисы). Не на клиенте — легко подделать
- **5 алгоритмов:** Token Bucket (Amazon, Stripe), Leaking Bucket (Shopify), Fixed Window Counter, Sliding Window Log, Sliding Window Counter
- Счётчики в **Redis** (in-memory): `INCR` — атомарный инкремент, `EXPIRE` — автоудаление по TTL. Не в БД — слишком медленно
- Правила хранятся в **YAML на диске** → рабочие узлы загружают в кэш. Пример Lyft: `domain: auth, rate_limit: 5/minute`
- При отклонении: **HTTP 429** + заголовки `X-Ratelimit-Remaining`, `X-Ratelimit-Limit`, `X-Ratelimit-Retry-After`. Отклонённые можно сбросить в очередь
- **Race condition:** два запроса параллельно читают счётчик=3, оба пишут 4 вместо 5. Решение: Lua-скрипт в Redis (атомарно). НЕ блокировки
- **Синхронизация:** несколько серверов RL → централизованный Redis. НЕ sticky sessions (немасштабируемо). Eventual consistency между ДЦ

## Функциональные требования

1. Точная фильтрация избыточных запросов
2. Уведомление пользователя при блокировке (HTTP 429)
3. Возможность отложить отклонённые запросы в очередь для обработки позже

## Нефункциональные требования

- **Низкая латентность** — ограничитель не должен замедлять HTTP-ответы
- **Минимальное потребление памяти**
- **Распределённое ограничение** — доступен разным серверам/процессам
- **Высокая отказоустойчивость** — проблема с RL не должна сломать всю систему
- **Обработка исключений** — понятное сообщение об ошибке

## Где размещать ограничитель

| Вариант | Описание | Проблемы |
|---|---|---|
| **На клиенте** | Клиент сам ограничивает | Ненадёжно — запросы легко подделать |
| **На сервере** | Логика внутри API | Полный контроль, но нужно писать самим |
| **Middleware** | Промежуточный слой перед API | **Рекомендуется** — фильтрует до серверов |
| **API Gateway** | Если уже есть микросервисы | Поддерживает: rate limiting, SSL, auth, белые списки IP |

Если уже есть API Gateway → добавить rate limiting туда. Если нет ресурсов на своё решение → коммерческий gateway.

## 5 алгоритмов ограничения трафика

### 1. Маркерная корзина (Token Bucket)

Корзина с маркерами, пополняется с постоянной скоростью. Каждый запрос = 1 маркер. Нет маркеров → отклоняем.

**Параметры:** размер корзины (max маркеров) + частота пополнения (маркеров/сек).

**Сколько корзин:**
- Разные endpoints → разные корзины (публикация, лайки, добавление друзей)
- Фильтрация по IP → корзина на каждый IP
- Глобальный лимит → одна общая корзина

**Плюсы:** простой, справляется со **всплесками** (пока маркеры есть — пропускаем).
**Минусы:** подобрать размер и частоту непросто.
**Кто использует:** Amazon, Stripe.

### 2. Дырявое ведро (Leaking Bucket)

Очередь FIFO фиксированного размера. Запросы обрабатываются с **постоянной скоростью**. Очередь полна → отклоняем.

**Параметры:** размер очереди + скорость утечки (запросов/сек).

**Плюсы:** стабильная скорость обработки, экономит память.
**Минусы:** всплеск забивает очередь **старыми** запросами → новые отклоняются.
**Кто использует:** Shopify.

### 3. Счётчик фиксированных интервалов (Fixed Window Counter)

Время делится на равные интервалы (1 сек, 1 мин), у каждого счётчик. Счётчик ≥ лимит → отклоняем. В начале нового интервала сбрасывается.

**Плюсы:** простой, экономит память, сброс в конце интервала.
**Минусы:** **всплеск на границе** двух интервалов → 2× лимита. Пример: 5 запросов в конце минуты + 5 в начале следующей = 10 за 1 минуту при лимите 5.

### 4. Журнал скользящих интервалов (Sliding Window Log)

Храним **временные метки** каждого запроса в Redis sorted set. При новом запросе: удаляем просроченные, считаем оставшиеся. Больше лимита → отклоняем.

**Плюсы:** **очень точный** — на любом скользящем интервале запросы не превышают лимит.
**Минусы:** **много памяти** — метка записывается даже для отклонённых запросов.

### 5. Счётчик скользящих интервалов (Sliding Window Counter)

Гибрид Fixed Window + Sliding Window Log.

```
Формула: запросы_текущего + запросы_предыдущего × % перекрытия

Пример (лимит 7/мин):
  Предыдущая минута: 5 запросов
  Текущая минута: 3 запроса
  Мы на отметке 30% текущей минуты → 70% перекрытия
  Результат: 3 + 5 × 0.7 = 6.5 ≈ 6 < 7 → пропускаем
```

**Плюсы:** сглаживает всплески, экономит память.
**Минусы:** приблизительный (предполагает равномерное распределение). По данным Cloudflare: ошибка **~0.003%** из 400 млн запросов.

## Архитектура (подробная)

```
                    Правила (YAML на диске)
                           ↓
                    Рабочие узлы → Кэш правил
                           ↓
Клиент → Промежуточный RL → Redis (счётчики + TTL)
               │
          ┌────┴────┐
          ↓         ↓
      Серверы API   HTTP 429 (или → Очередь сообщений)
```

### Как работает
1. Клиент шлёт запрос → промежуточный RL
2. RL загружает правила из кэша
3. RL извлекает счётчик из Redis, проверяет лимит
4. **Не достигнут** → запрос проходит к серверам API
5. **Достигнут** → HTTP 429 клиенту. Запрос либо сбрасывается, либо → очередь

### Почему Redis
- **In-memory** → быстро (не диск)
- `INCR` — атомарный инкремент счётчика
- `EXPIRE` — автоудаление по TTL (счётчик сбрасывается после интервала)
- **Централизованный** → все серверы RL ходят в один Redis

## HTTP-заголовки ответа

| Заголовок | Что содержит |
|---|---|
| `X-Ratelimit-Remaining` | Сколько запросов осталось в текущем интервале |
| `X-Ratelimit-Limit` | Лимит вызовов в каждом интервале |
| `X-Ratelimit-Retry-After` | Через сколько секунд можно повторить |

При превышении: **HTTP 429** + заголовок `X-Ratelimit-Retry-After`.

## Распределённое окружение — две проблемы

### 1. Состояние гонки (Race Condition)

```
Начальное значение счётчика: 3

Запрос 1: читает 3 → инкрементирует → пишет 4
Запрос 2: читает 3 → инкрементирует → пишет 4

Результат: 4 (но должно быть 5!)
```

**Решение:** Lua-скрипт в Redis — атомарная операция "прочитать + проверить + инкрементировать". Или Redis sorted sets.
**НЕ использовать блокировки** — замедлят систему.

### 2. Синхронизация между серверами

Несколько серверов RL → клиент может попасть на разные. Каждый RL не знает о запросах других.

**Решение:** централизованный Redis. Все серверы RL ходят в один Redis.
**НЕ использовать sticky sessions** — немасштабируемо.

Данные между ДЦ синхронизируются через **eventual consistency**.

## Мониторинг и оптимизация

- Проверить эффективность алгоритма и правил после запуска
- Слишком строгие правила → теряем корректные запросы → ослабить
- Всплески (распродажи) → **token bucket** лучше чем fixed window
- Распределение по нескольким ДЦ → ниже латентность (Cloudflare — 194 пограничных сервера)

## Дополнительные вопросы на собесе

- **Жёсткое vs гибкое ограничение:**
  - Жёсткое — не превышаем лимит никогда
  - Гибкое — можно ненадолго превысить

- **Уровни OSI:**
  - L7 (HTTP) — в этой главе
  - L3 (IP) — через iptables

- **Рекомендации для клиента:**
  - Кэш на клиенте — не делать API-вызовы слишком часто
  - Backoff между повторами
  - Код для обработки 429
  - Не отправлять слишком много за короткий промежуток
