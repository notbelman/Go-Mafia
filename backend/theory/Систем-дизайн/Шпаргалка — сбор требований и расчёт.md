## 2. Нефункциональные требования

Как хорошо система работает.

| Что спросить | Зачем |
|---|---|
| **DAU** | Из него считаем RPS |
| **Read/Write ratio** | Определяет архитектуру (кэш, репликация, fan-out) |
| **Availability** | 99.9%? 99.99%? |
| **Response time** | На ключевые операции (отправка: 1с, чтение: 200мс) |
| **Retention** | Сколько хранить (навсегда, 2 года, 30 дней) |
| **Лимиты** | Макс. размер сообщения, юзеров в чате, файла |
| **География** | Один регион или весь мир? |
| **Сезонность** | Есть ли предсказуемые пики? |

**ASR** — ключевое требование, от которого зависит вся архитектура. Лента = read-intensive. Такси = real-time координаты. Мессенджер = доставка + надёжность.

## 3. Расчёт нагрузки

### RPS

```
RPS = DAU × действий_на_юзера_в_день / 86400
```

Пример: 100M DAU × 10 чтений / 86400 ≈ **11 574 RPS read**
Если read/write = 5:1 → RPS write ≈ 2 315

### Трафик

```
Трафик/сек = RPS write × размер_запроса
```

Пример: 2315 × 2 КБ ≈ **4.6 МБ/с**
В день: × 86400 ≈ **400 ГБ/день**
В год: × 365 ≈ **150 ТБ/год**

### Storage

```
Storage = трафик/год × retention × replication_factor
```

Пример: 150 ТБ × 2 года × 2 (реплика) = **600 ТБ**
600 ТБ / 6 ТБ (HDD) = **100 дисков** → нужно шардирование

### Нужен ли SSD?

Суммарный трафик (read+write) < 200 МБ/с → HDD хватит.
Больше → SSD. Или hot на SSD, cold на HDD.

## 4. API

По умолчанию REST. Для сервис↔сервис — gRPC.

```
POST   /resource        — создать
GET    /resource/{id}   — получить
GET    /resource?...    — список (пагинация: offset/cursor)
PUT    /resource/{id}   — обновить целиком
PATCH  /resource/{id}   — обновить частично
DELETE /resource/{id}   — удалить
```

Если real-time (чат, уведомления, координаты) → добавляем **WebSocket** канал.

Для каждой фичи из FR — один endpoint. Записать явно.
