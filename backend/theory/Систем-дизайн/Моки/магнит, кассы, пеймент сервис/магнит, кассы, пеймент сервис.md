- Система оплаты покупок на кассе/КСО через мобильное приложение магазина. Оплата НЕ через СБП — через банковское приложение клиента (deeplink)
- **DAU 500K** (1000 юзеров × 500 магазинов), 5 касс на магазин (2500 касс всего). **RPS 6**, пик ×5 = 30 RPS — копейки
- Трафик ~70 КБ/с, storage 146 ГБ за 2 года с репликой — один PG, шардирование не нужно
- **ASR: strong consistency + идемпотентность** — деньги, нельзя списать дважды, нельзя потерять оплату
- Финальная архитектура: **3 микросервиса** (Session Service, Payment Processor, Status Updater) + Bank Adapter + Kafka + PG + Redis
- **Эволюция от простого к сложному**: один сервис → + идемпотентность → + Kafka/outbox → + Redis → декомпозиция на микросервисы

## CJM (Customer Journey Map)

1. Кассир/клиент сканирует товары
2. Переходит к оплате
3. Идентифицируется на кассе/КСО
4. Выбирает "оплатить в приложении магазина"
5. Переходит в приложение магазина
6. Выбирает банк, с которого происходит оплата
7. В приложении банка оплачивает покупку (deeplink)
8. Возвращается на экран результата в приложении магазина
9. На кассе/КСО получает сообщение об успешной оплате

## Функциональные требования

1. **Создание платёжной сессии** — касса формирует чек (товары + сумма) и инициирует запрос на оплату
2. **Выбор банка в приложении** — пользователь выбирает банковское приложение для оплаты
3. **Переход в банковское приложение (deeplink)** — редирект для подтверждения
4. **Подтверждение оплаты** — банк проводит платёж, возвращает статус
5. **Отображение результата** — приложение и касса получают подтверждение

**Исключено из scope:** возвраты, частичные отмены, программа лояльности, СБП, сканирование товаров

### ASR: strong consistency + идемпотентность

Деньги = транзакционная система. Один платёж = один чек. Никаких гонок, дублей, потерь.

### Где eventual допустима

- **История покупок** — задержка 2-3 сек некритична
- **Аналитика/отчёты** — задержка в минуты ок

### Где strong обязательна

- **Платёжная сессия** — статус, подтверждение на кассу
- **Идентификация клиента** — касса должна точно знать кто перед ней

## Расчёт нагрузки

### RPS

```
RPS = 500 000 × 1 / 86 400 ≈ 6 RPS
Пик ×5 = 30 RPS
```

### Трафик (сеть)

```
Средний запрос ≈ 2 КБ (JSON, без медиа)
Read (поллинг статуса):
  Активных сессий одновременно ≈ 6 × 30 сек = ~180
  Каждая поллится 2 раза (касса + мобилка) = 360 RPS
  360 × 0.1 КБ = 36 КБ/с

Write: 6 × 2 КБ = 12 КБ/с
Итого: ~50 КБ/с, пик ~186 КБ/с — ничто
```

### Storage

```
1 транзакция ≈ 0.2 КБ
В день = 500 000 × 0.2 КБ = 100 МБ
В год = 36.5 ГБ
За 2 года × 2 (реплика) = 146 ГБ — один диск
```

**Итог:** шардирование не нужно. Один PG с синхронной репликой. Главный вызов — не нагрузка, а надёжность платёжного флоу.

## API Design

REST для клиент → backend.

```
POST   /api/v1/payment/identify
       Body: { qr_code, pos_id }
       → Идентификация клиента на кассе

POST   /api/v1/payment/session
       Body: { user_id, pos_id, items[], total_amount }
       → Создание платёжной сессии

POST   /api/v1/payment/session/{session_id}/pay
       Body: { bank_id }
       → Инициация оплаты

GET    /api/v1/payment/session/{session_id}/status
       → Поллинг статуса (приложение + касса)
       Response: { status: "pending|processing|success|failed|expired" }
```

## Эволюция архитектуры (от простого к сложному)

### Стадия 1: Базовая архитектура

**Один Payment Service + PG (master + sync replica).**

```
Касса/Мобилка → LB → API GW → Payment Service → PG (sync replica)
                                               → Bank Adapter → Банк
```

30 RPS — один сервис закрывает задачу. Начинаем с простого.

### Стадия 2: + Идемпотентность

**Вопрос:** "А если POST /pay придёт дважды?"

Статусная машина в PG: `UPDATE ... WHERE status = 'pending'` — второй запрос не пройдёт условие.

```sql
UPDATE payment_session
SET status = 'processing'
WHERE session_id = 123 AND status = 'pending'
RETURNING *;
-- affected rows = 0 → дубль → отбиваем
```

Плюс `idempotency_key` в банк — банк тоже не спишет дважды.

### Стадия 3: + Kafka + Outbox

**Вопрос:** "А если сеть моргнёт и ответ банка потеряется?"

Bank Adapter пишет результат в Kafka (топик: `payment.result`). Payment Service читает из Kafka → PG → commit offset.

Outbox-паттерн в Bank Adapter: сначала пишет в свою таблицу, потом в Kafka. При падении — перечитает неотправленные.

```sql
outbox:
  id              UUID PK
  event_type      VARCHAR     -- payment.success, payment.failed
  payload         JSONB
  sent            BOOLEAN     -- false → true после отправки в Kafka
  created_at      TIMESTAMP
```

**Порядок коммита consumer-а:**
1. Пишем в PG ✓
2. Пишем в Redis ✓
3. Коммитим offset Kafka ✓ ← только после PG!

### Стадия 4: + Redis

**Вопрос:** "Можно ли снять нагрузку поллинга с PG?"

Redis как кэш статусов. Касса/мобилка поллят → Payment Service → Redis (hit) → ответ.

При обновлении: PG (источник правды) + Redis (кэш).

### Стадия 5: Декомпозиция на 3 микросервиса

**Вопрос:** "Что если Payment Service полностью упал?"

```
┌────────────────────┐
│  Session Service   │  — POST /session, GET /status → PG, Redis
├────────────────────┤
│  Payment Processor │  — POST /pay → Bank Adapter
├────────────────────┤
│  Status Updater    │  — Kafka consumer → PG + Redis
└────────────────────┘
```

Каждый падает независимо:
- Status Updater упал → Kafka копит, при подъёме догонит
- Payment Processor упал → сессии создаются, fallback на карту/наличные
- Session Service упал → нет новых сессий, но активные оплаты дойдут

## Финальная архитектура

```
Касса/Мобилка → LB → API GW ──→ Session Service → PG + Redis
                             ──→ Payment Processor → Bank Adapter → Банки
                                                                  → Kafka
                                 Status Updater ← Kafka → PG + Redis
```
![[магнит, пеймет сервис.png]]
### Три сценария получения ответа от банка

**1. Банк ответил SUCCESS:**
```
Банк → Bank Adapter → Kafka → Status Updater → PG (status=success) + Redis
Касса поллит → Redis → "success" → закрывает чек
```

**2. Банк ответил FAIL:**
```
Банк → Bank Adapter → Kafka → Status Updater → PG (status=failed) + Redis
Касса поллит → Redis → "failed" → "Попробуйте снова"
```

**3. Банк не ответил (таймаут 2 мин):**
```
Воркер (cron): SELECT WHERE status='processing' AND created_at < now()-2min
→ Reconciliation-запрос в банк: "ты списал или нет?"
→ Банк: "списал" → status=success / "не списал" → status=expired
```

## Обработка сбоев

| Сценарий | Что происходит | Решение |
|---|---|---|
| Сеть моргнула (касса → backend) | Сессия не создалась | Касса повторяет запрос |
| Сеть моргнула (мобилка → банк) | Деньги не списались | Мобилка повторяет, idempotency_key |
| **Банк списал, ответ не дошёл** | Деньги списаны, мы не знаем | Reconciliation в банк по idempotency_key |
| Payment Service → PG упал | Статус не обновился | Kafka retry, идемпотентный UPDATE |
| Payment Service полностью лёг | Новые оплаты невозможны | Kafka копит, при подъёме догонит. Fallback: карта/наличные |

## Масштабируемость

| Компонент | Тип | Как скейлится |
|---|---|---|
| Session Service | Stateless | Горизонтально, 2-3 инстанса для отказоустойчивости |
| Payment Processor | Stateless | Горизонтально, можно по инстансу на банк |
| Status Updater | Stateless | Offset в Kafka, горизонтально |
| Bank Adapter | Stateless | Горизонтально |
| PG | Stateful | Master + sync replica. Шардирование не нужно (146 ГБ) |
| Redis | Stateful | Один инстанс, копейки по памяти |
| Kafka | Stateful | 3 партиции для отказоустойчивости |

**Bottleneck — банки.** Чужие API, мы не контролируем. Банк тормозит — мы ждём. Банк лёг — таймаут + fallback.

## Ключевые решения и trade-offs

| Решение | Почему | Trade-off |
|---|---|---|
| PG + sync replica | Деньги = strong consistency | Latency записи выше |
| Kafka + outbox | Не потерять ответ банка | Сложность, eventual для статуса |
| Redis (кэш статусов) | Снять поллинг с PG | Ещё один компонент |
| 3 микросервиса | Graceful degradation при падении | Overhead на 30 RPS |
| Поллинг (не WebSocket) | Проще реализация | Задержка 1-2 сек |
| Статусная машина | Идемпотентность без доп. инфраструктуры | — |
| Таймаут 2 мин + reconciliation | Не потерять деньги при сбое | Сложность воркера |
