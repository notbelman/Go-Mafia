- **Retry + Backoff** — повторение запроса с нарастающей задержкой (константной, экспоненциальной, с jitter). Пример: Aviasales -> Аэрофлот не ответил -> ждём и пробуем снова
- **Circuit Breaker** — три состояния: Closed (нормально), Open (сервис лежит, трафик стоп), Half-Open (проверяем 20% трафика). Разрывает лавину ретраев
- **Idempotency** — запрос можно выполнить несколько раз с одинаковым результатом. Ключ идемпотентности защищает от повторных списаний (20К x 3 = 60К)
- **Backpressure** — сигнал отправителю «сбавь темп» (медленные ответы, спецкоды). **Rate Limiting** — грубый отказ 429 Too Many Requests
- **Graceful Degradation** — отключение вспомогательных фич ради core-функционала. Яндекс.Такси: Яндекс+ упал — такси ездит
- **Fallbacks** — заготовленные данные на случай отказа. Ozon: рекомендашка недоступна -> показываем подушки, гантели, вентиляторы
- **DLQ (Dead Letter Queue)** — очередь для сообщений, которые не удалось обработать после N ретраев. Не теряем, обрабатываем позже
- Все паттерны работают вместе: retry -> circuit breaker -> fallback/DLQ. Это цепочка защиты

## Retry + Backoff

Повторение запроса при ошибке с нарастающей задержкой между попытками.

### Зачем Retry

Сервис временно недоступен — не сразу отдавать ошибку пользователю, а попробовать ещё раз. Пример: Aviasales идёт за билетами в Аэрофлот, Аэрофлот не ответил — подождать и попробовать снова.

### Backoff (задержка между ретраями)

Без backoff: 5 ретраев подряд -> сервису и так плохо, а тут x5 трафика -> лавина, сервис падает окончательно.

**Стратегии:**
- **Константный:** +100мс каждый раз (100, 200, 300, 400...)
- **Экспоненциальный:** x2 каждый раз (100, 200, 400, 800...)
- **С jitter:** добавляем случайный разброс, чтобы ретраи от разных клиентов не приходили одновременно

### Важно: компромисс Retry

Либо расшибаться, пробуя снова и снова — либо вовремя ответить ошибкой. Иногда лучше честно сказать пользователю «сервис недоступен», чем перегрузить чужой сервис ретраями. Балун говорил: «верю в гуманность в сети» — если сервису плохо, не надо его добивать.

## Circuit Breaker (выключатель)

Автоматическое прекращение запросов к сервису, который начал сбоить. Защищает и клиента (не ждёт таймаута), и сервер (не добивают трафиком).

### Три состояния Circuit Breaker

**Closed (нормальная работа):** трафик проходит свободно. Circuit breaker отслеживает процент ошибок.

**Open (сервис лежит):** порог ошибок превышен (например, 20% фейлов). Трафик полностью останавливается. Клиенту сразу возвращается ошибка (или [[#Fallbacks (заглушки)|fallback]]). Выжидаем таймаут — даём серверу время восстановиться.

**Half-Open (проверка):** таймаут прошёл. Пропускаем часть трафика — например, 20%. Всё ок -> 50% -> 100% -> переходим в Closed. Ошибки -> обратно в Open.

### Где живёт Circuit Breaker

Может быть реализован как прокси между сервисами, как библиотека в клиентском SDK, или как часть service mesh.

### Зачем Circuit Breaker

Сервису плохо -> ему шлют ретраи -> ему ещё хуже -> лавинообразный каскад. Circuit breaker разрывает эту цепочку: «сервис болеет, не трогаем его, пусть восстановится».

## Idempotency (идемпотентность)

Запрос [[Паттерны отказоустойчивости#Idempotency (идемпотентность)|идемпотентен]], если его можно выполнить несколько раз подряд и результат будет одинаковым.

### Идемпотентные vs неидемпотентные

**Идемпотентные:**
- GET — сколько бы раз ни читал, результат один
- PUT — «баланс Кати = 500», сколько раз ни повтори — 500
- DELETE — удалится только один раз, повторное удаление ничего не сделает

**Неидемпотентные:**
- POST (создание) — каждый повтор создаёт новую запись
- Операции инкремента — «списать 20.000 руб» повторили 3 раза -> списали 60.000 руб

### Проблема с ретраями

Клиент отправил оплату 20.000 руб. Сервер обработал, но ответ потерялся. Клиент ретраит -> ещё 20.000 руб списалось. Ещё раз -> ещё 20.000 руб. Итого 60.000 руб вместо 20.000 руб.

### Решение: ключ идемпотентности

Клиент генерирует уникальный идентификатор запроса (request_id, sequence_id, idempotency_key). Сервер запоминает, какие ключи уже обработал. Пришёл повторный запрос с тем же ключом — сервер не обрабатывает заново, а возвращает сохранённый результат.

### Правило идемпотентности

Ретраить неидемпотентные запросы **нельзя** без ключа идемпотентности. Это стандарт — при проектировании ретраев всегда учитывать идемпотентность.

## Backpressure и Rate Limiting

Что делать, когда сервис получает больше трафика, чем может обработать.

### Проблема перегрузки

Сервис 1 шлёт 150 RPS. Сервис 2 может обработать 100 RPS. Через час — 180.000 необработанных запросов. Система захлёбывается.

### Rate Limiting (грубый подход)

Пришёл 101-й запрос — обрубаем. Отвечаем ошибкой (429 Too Many Requests). Просто, работает, но грубо — клиент получает отказ без объяснений.

### Backpressure (гуманный подход)

Обратное давление — не обрубаем, а сигнализируем отправителю «сбавь темп»:

- **Отвечать медленнее.** Обычно response time 200мс, при перегрузке — 500мс. Ещё больше трафика — 1 секунда. Клиент сам замедляется, потому что ждёт ответа.
- **Специальные коды ответов.** Отправляем код, который говорит клиенту «шли меньше». Клиент адаптирует свою частоту.

### Разница Rate Limiting и Backpressure

Rate limiting: «101-й запрос? Нет, до свидания.»
Backpressure: «101-й запрос? Ок, но отвечу медленнее, подстройся.»

Backpressure — не всегда применим. Иногда проще и надёжнее рейтлимитить. Но знать оба подхода полезно.

## Graceful Degradation

Система продолжает работать при отказе отдельных компонентов, жертвуя второстепенными фичами ради core-функционала.

### Принцип деградации

Разделяем фичи на **core** (без них продукт бесполезен) и **вспомогательные** (улучшают опыт, но не критичны).

**Яндекс.Такси:** core — водитель довёз, деньги списались (payment, navigator, driver). Вспомогательные — Яндекс+, реклама, пробки, ценообразование спроса. Если вспомогательный сервис лёг — отключаем его, core продолжает работать.

### Feature Toggles (выключатели)

Механизм отключения фич. Могут быть на уровне всей системы («вырубить Яндекс+») или внутри сервиса («отключить эту конкретную фичу платёжки»). Должны быть заготовлены **заранее** — когда пожар, уже поздно писать тоглы.

## Fallbacks (заглушки)

Заранее подготовленные данные на случай отказа сервиса. «Сервис превратился в тыкву» (термин из Яндекса).

**Пример:** рекомендательная система Ozon. Если рекомендашка недоступна — вместо 500-й ошибки показываем заготовленный список товаров (подушки, гантели, вентиляторы). Пользователь не увидит персональных рекомендаций, но и не увидит ошибки.

### Важно про Fallbacks

Fallbacks должны быть подготовлены заранее. Когда всё горит — поздно придумывать заглушки. Это проектируется на этапе разработки.

## Dead Letter Queue (DLQ)

Очередь для сообщений, которые не удалось обработать. Вместо того чтобы терять запрос — складываем его в отдельную очередь на потом.

### Зачем DLQ

Сервис недоступен, а запрос нужно выполнить обязательно (не синхронный ответ пользователю, а фоновая задача). Обрубать нельзя, ретраить бесконечно нельзя. Складываем в DLQ — когда сервис восстановится, воркер разгребёт очередь.

### Когда подходит DLQ

- Фоновые/асинхронные задачи, которые не требуют мгновенного ответа пользователю
- Сообщения, упавшие после нескольких ретраев
- Задачи, которые нельзя терять (финансовые операции, уведомления)

### Когда DLQ не подходит

Синхронные запросы, где пользователь ждёт ответ прямо сейчас. Пользователю нечем ответить — DLQ не поможет, нужен fallback или честная ошибка.

### Как работает DLQ

1. Сообщение не удалось обработать после N ретраев
2. Вместо потери -> складываем в DLQ
3. Воркер периодически читает DLQ и пытается обработать
4. Обработал -> удаляет из DLQ. Не обработал -> оставляет (или алертит)
