- **2PC (Two-Phase Commit)** — координатор спрашивает участников «готовы?» (prepare), все ответили ACK -> COMMIT, кто-то ошибся -> ROLLBACK. Аналогия: бракосочетание
- **Saga** — набор локальных транзакций, каждая коммитится сразу. При ошибке — компенсирующие транзакции откатывают предыдущие шаги
- 2PC даёт **изоляцию** (блокировки между prepare и commit), но медленно. Saga даёт **скорость**, но допускает грязные чтения
- 2PC: два участника — нормально, три — терпимо, четыре-пять — «самоубийство» (Балун)
- **[[Распределённые транзакции#Transaction Outbox|Transaction Outbox]]** — гарантированная доставка события в очередь через вспомогательную таблицу в одной транзакции с основной записью
- **[[Распределённые транзакции#Transaction Inbox|Transaction Inbox]]** — зеркало Outbox на стороне получателя: быстро ACK-нуть очередь, обработать асинхронно из inbox-таблицы
- Saga бывает двух видов: **оркестрация** (центральный координатор) и **хореография** (сервисы общаются через события)
- Outbox решает проблему «записал в БД, но не отправил в очередь» через at-least-once доставку

---

|                             | 2PC                | Saga                      |
| --------------------------- | ------------------ | ------------------------- |
| Изоляция                    | Да (блокировки)    | Нет (грязные чтения)      |
| Скорость                    | Медленно           | Быстро                    |
| Откат                       | Настоящий ROLLBACK | Компенсирующая транзакция |
| Промежуточные данные видны? | Нет                | Да                        |

**2PC** — когда нужна изоляция, готов платить скоростью.
**Saga** — когда нужна скорость, готов мириться с [[Eventual Consistency|eventual consistency]].

## 2PC (Two-Phase Commit)

Протокол распределённой транзакции: данные фиксируются в нескольких хранилищах атомарно — либо везде, либо нигде.

### Не путать

2PC (Two-Phase **Commit**) != 2PL (Two-Phase **Locking**). 2PL — про блокировки внутри одной БД. 2PC — про координацию между несколькими хранилищами.

### Аналогия: бракосочетание

Ведущий спрашивает жениха: «Готов?» Спрашивает невесту: «Готова?» Оба сказали «да» -> брак заключён. Кто-то сказал «нет» -> брак не состоялся.

### Две фазы

**Фаза 1 — Prepare:** координатор (сервис) отправляет участникам (БД) `START TRANSACTION` + данные. Каждый участник выполняет операцию, но **не коммитит**. Отвечает `ACK` (готов) или ошибкой.

**Фаза 2 — Commit/Rollback:** все ответили `ACK` -> координатор шлёт всем `COMMIT`. Кто-то ответил ошибкой -> координатор шлёт всем `ROLLBACK`.

### Точка невозврата

После prepare проводится черта. Если перешли в фазу commit — **обратного пути нет**. Координатор будет долбить `COMMIT` до последнего. Если в фазе prepare — можно откатиться.

### Что может пойти не так

**Участник упал после prepare:** координатор продолжает слать `COMMIT` (или `ROLLBACK`) пока не примет.

**Координатор упал между фазами:** участники держат блокировки, не знают — коммитить или откатывать. Решение — координатор пишет решение на диск перед отправкой, после рестарта читает и продолжает. Но это костыль.

### Главное свойство

2PC — про **изоляцию**. Между prepare и commit висят блокировки. Никто не видит промежуточных результатов. Согласованно, но **медленно** — блокировки держатся всё время транзакции.

### Сколько участников

Два — нормально. Три — терпимо. Четыре-пять — «самоубийство» (цитата Балуна). Чем больше участников, тем больше шанс, что кто-то упадёт и заблокирует всех.

## Saga

Набор локальных транзакций, выполняемых последовательно. Каждая коммитится сразу. При ошибке — компенсирующие транзакции откатывают предыдущие шаги.

### Два подхода Saga

**Оркестрация:** есть центральный оркестратор, который управляет шагами. Похоже на 2PC, но с очередью внутри и без блокировок.

**Хореография:** нет центрального координатора. Сервисы общаются через события — каждый публикует результат, следующий подписан и реагирует.

### Хореография — подробнее

1. **Create Order** -> сохраняет заказ (локальная транзакция, `COMMIT`) -> публикует `order_created`
2. **Customer Service** подписан -> обновляет данные клиента (локальная транзакция, `COMMIT`) -> публикует `customer_updated`
3. **Create Order** подписан -> финализирует заказ (локальная транзакция, `COMMIT`)

Каждый шаг — отдельный `START TRANSACTION` -> `COMMIT`. Между шагами блокировок **нет**.

### Если что-то сломалось в Saga

Customer Service не смог обновить -> публикует `customer_failed`. Create Order подписан -> выполняет **компенсирующую транзакцию** (отдельная транзакция, которая откатывает изменения первого шага).

### Грязное чтение в Saga

Между шагом 1 (заказ создан, закоммичен) и компенсацией (заказ откачен) пользователь **может увидеть** этот заказ. Данные уже в БД, блокировок нет. Это грязное чтение — сага **не про изоляцию**.

## Transaction Outbox

Гарантированная доставка события в очередь через вспомогательную таблицу в той же БД.

### Проблема Outbox

Сервис должен сохранить заказ в БД **и** отправить событие в очередь ([[Apache Kafka|Kafka]]). Что если БД сохранила, а очередь недоступна? Данные в БД есть, а событие потеряно. Кто подписан — не узнает.

Это не 2PC — нам не нужна синхронность. Нам нужна гарантия: если записал в БД, событие **когда-нибудь** дойдёт до очереди.

### Решение Outbox

В **одной транзакции** с основной записью сохраняем событие в таблицу `outbox`:

```
BEGIN;
  INSERT INTO orders (...) VALUES (...);
  INSERT INTO outbox (event_type, payload) VALUES ('order_created', ...);
COMMIT;
```

Одна транзакция -> атомарно: либо оба INSERT прошли, либо оба откатились.

### Доставка из Outbox

Рядом поднят **воркер** (отдельный поток/процесс). Он периодически сканирует таблицу `outbox`, отправляет события в очередь, после успешной отправки — удаляет из `outbox`.

Очередь недоступна? Ок, событие лежит в `outbox`. Очередь поднялась -> воркер отправит. Гарантия доставки — at-least-once.

### Важно про Outbox

Пользователю отвечаем **сразу** после коммита entity + outbox. Доставка в очередь — асинхронная. Не ждём очередь.

## Transaction Inbox

Гарантированная обработка сообщения из очереди через вспомогательную таблицу. Зеркало Outbox — но на стороне получателя.

### Проблема Inbox

Наивный подход: вычитал сообщение из очереди -> обработал -> отправил ACK. Если сервис упал до ACK — не страшно, перечитаем. Но что если обработка **длительная** (поднять виртуалку, настроить, прогнать тесты)?

Пока обрабатываем — таймаут ACK истекает. Очередь считает, что сообщение не обработано -> отдаёт его ещё раз. Другой воркер (или тот же, в другом потоке) начинает **параллельно** обрабатывать то же самое. Две виртуалки вместо одной.

### Решение Inbox

1. Вычитал сообщение из очереди
2. Сохранил в таблицу `inbox`
3. **Сразу** отправил ACK очереди — отпустил её
4. Отдельный воркер периодически читает `inbox` и обрабатывает
5. Обработал -> удаляет из `inbox`

### Зачем Inbox

Разделяем «получение сообщения» и «обработку сообщения». Очередь освобождается быстро (ACK сразу). Длительная обработка идёт асинхронно из inbox. Нет дублирования из-за таймаутов.

### Когда использовать Inbox

Длительные операции по сообщениям из очереди — создание инфраструктуры, тяжёлые вычисления, внешние вызовы с непредсказуемым временем.
