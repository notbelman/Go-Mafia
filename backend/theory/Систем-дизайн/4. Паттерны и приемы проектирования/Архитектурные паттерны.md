- **CQRS** — разделение сервиса на два: один для чтения (Query), другой для записи (Command). Когда разные требования к read и write
- **Heartbeat** — периодические сигналы «я жив». Нет heartbeat за 2-3 интервала -> узел мёртв. Используется и клиент-серверно, и сервер-серверно
- **Pub/Sub** — паблишер публикует событие в очередь, подписчики вычитывают. Паблишер не знает о подписчиках, слабая связанность
- **Service Discovery** — автоматическое обнаружение сервисов. Бэкенд регистрируется в SD, балансер узнаёт о нём автоматически
- **Вынос логики на клиента** — клиент тоже приложение, может вычислять. Разгружает бэкенд, но клиенты ограничены по ресурсам
- **Трёхзвенная архитектура** — фронт-сервер (Nginx, статика) + бэкенд (бизнес-логика) + хранилище (БД, кэш, S3). Масштабируются независимо
- Consul, etcd, ZooKeeper — реализации [[Архитектурные паттерны#Service Discovery|Service Discovery]]. [[Kubernetes — обзор (Kubernetes in Action)]] — встроенный механизм через DNS
- CQRS добавляет сложность (два сервиса, синхронизация) — не использовать для простого CRUD

## CQRS (Command Query Responsibility Segregation)

Разделение сервиса на два: один отвечает за чтение (Query), другой за запись (Command).

### Зачем CQRS

Бизнес приходит и говорит: «на чтение нужна доступность 99.99%, на запись — 99.9%». Или: чтение в 10 раз больше записи, нужны разные оптимизации. Один сервис не может эффективно обслуживать оба сценария.

### Пример CQRS

Ту-ту (бронирование ЖД-билетов). Разные требования к доступности: чтение расписания — почти всегда доступно, покупка билета — допускает чуть больше даунтайма. Разделяем на Ticket Reader и Ticket Writer.

### Проблема: где хранить данные в CQRS

**Вариант 1: общее хранилище.** Оба сервиса пишут/читают из одной БД. Проще, но нет независимости — одна БД связывает оба сервиса.

**Вариант 2: раздельные хранилища.** Read-база оптимизирована на чтение, write-база на запись. Нужна синхронизация между ними. Проблема: купил билет — а в read-базе ещё старые данные, кто-то может увидеть свободное место, которого уже нет.

### Когда использовать CQRS

- Разные требования к read и write (доступность, latency, нагрузка)
- Резко различное соотношение read/write
- Структура данных для чтения отличается от структуры для записи (пример: заказы из разных продуктов складываем в одно хранилище, приводим к общему формату)

### Когда не использовать CQRS

Простой CRUD без явного разделения нагрузки. Добавляет сложность: два сервиса вместо одного, синхронизация данных.

## Heartbeat (сердцебиение)

Периодические сигналы «я жив», которые отправляет узел. Если сигналов нет N интервалов — узел считается мёртвым.

### Как работает Heartbeat

Клиент (или сервис) каждые 5 секунд отправляет heartbeat серверу. Прошло 2-3 интервала (10-15 секунд) без heartbeat — сервер помечает клиента как оффлайн. Можно записать время последнего heartbeat, чтобы показать «был в сети 5 минут назад».

### Два контекста использования Heartbeat

**Клиент-серверный:** ВКонтакте — отображение «пользователь онлайн». Клиент шлёт heartbeat, сервер знает, кто в сети. Перестал слать — оффлайн.

**Сервер-серверный:** балансер проверяет здоровье бэкендов. Бэкенд не ответил на heartbeat — балансер перестаёт слать ему трафик. Тесно связан с [[Архитектурные паттерны#Service Discovery|Service Discovery]].

### Параметры Heartbeat

- **Интервал** — как часто слать (5 сек, 10 сек)
- **Таймаут** — сколько пропущенных интервалов = «мёртв» (обычно 2-3x)
- **Что отправлять** — просто пинг, или метрики (CPU, память, нагрузка)

## Pub/Sub (Publisher-Subscriber)

Паблишер публикует событие в очередь. Подписчики вычитывают и обрабатывают. Паблишер не знает, кто подписан.

### Пример Pub/Sub

ВКонтакте: пользователь публикует пост. Что нужно сделать: обновить ленты подписчиков, отправить в аналитику, запустить рекламу. Наивно — сервис постов сам ходит в каждый сервис. Добавился новый сервис — нужно менять код паблишера.

**С Pub/Sub:** сервис постов кладёт событие «пост создан» в очередь и отвечает клиенту «ок». Аналитика, нотификации, реклама — каждый подписан на очередь и забирает событие для своих нужд. Добавился новый подписчик — паблишер не меняется.

### Зачем Pub/Sub

- Слабая связанность: паблишер не знает о подписчиках
- Масштабируемость: добавление подписчика не затрагивает паблишера
- Асинхронность: паблишер не ждёт, пока все обработают

### Минусы Pub/Sub

- Сложнее дебажить (асинхронные цепочки)
- Очередь — потенциальная единая точка отказа
- Нет гарантии порядка обработки между подписчиками

## Service Discovery

Автоматическое обнаружение сервисов в системе. Сервисы сами регистрируются, балансер автоматически узнаёт о них.

### Проблема без Service Discovery

Добавили новый бэкенд -> нужно вручную обновить конфиг балансера, прописать новый хост. Удалили бэкенд -> вручную убрать. Не масштабируется.

### Как работает Service Discovery

1. Поднимается новый бэкенд
2. Бэкенд регистрируется в Service Discovery (отдельный инфраструктурный сервис)
3. Service Discovery оповещает балансер: «появился новый бэкенд»
4. Балансер начинает слать трафик на новый бэкенд

### Проверка здоровья в Service Discovery

Кто проверяет, что бэкенд жив?

**Вариант 1:** Service Discovery сам шлёт [[#Heartbeat (сердцебиение)|heartbeat]] бэкендам. Бэкенд не ответил -> SD говорит балансеру «убери его».

**Вариант 2:** балансер сам шлёт heartbeat своим апстримам. Бэкенд не ответил -> балансер перестаёт слать ему трафик.

### Примеры реализаций Service Discovery

Consul, etcd, ZooKeeper — выделенные сервисы для SD. [[Kubernetes]] — встроенный механизм через DNS и endpoints.

## Вынос логики на клиента

Не забывать, что клиент — тоже приложение, которое может выполнять вычисления.

### Пример выноса логики

Сервис профилирования: нужно сравнить два профиля (за 1:00 и за 2:00). Наивно — бэкенд получает оба профиля, сравнивает, отдаёт результат. Альтернатива — клиент получает профиль 1, получает профиль 2, сравнивает сам. Бэкенд разгружен.

### Когда подходит вынос на клиента

- Операция не требует данных, которых нет у клиента
- Вычисления не слишком тяжёлые
- Не нужна серверная валидация результата

### Ограничения выноса на клиента

Клиенты, как правило, ограничены по ресурсам: оперативная память меньше, CPU слабее (особенно мобилки — будут греться), диск ограничен. Нельзя переносить на клиент то, что требует больших вычислений или секретных данных.

## Трёхзвенная архитектура

Разделение системы на три слоя: фронт-сервер, бэкенд-сервер, хранилище.

### Проблема без разделения

Наивный подход (MVP): статика (JS, HTML, CSS) лежит рядом с бэкендом в файловой системе. При масштабировании бэкенда статика копируется вместе с ним. Обновляем версию — где-то может остаться старая HTML-ка, где-то новая. Всё разъезжается.

### Решение: три слоя

**Фронт-сервер** (Nginx) — отдаёт статику (JS, HTML, CSS). Ничего не знает про бизнес-логику.

**Бэкенд-сервер** — занимается исключительно бизнес-логикой. Ничего не знает про статику.

**Хранилище** — БД, кэш, S3 и т.д.

### Зачем трёхзвенка

Фронт-сервер и бэкенд масштабируются независимо. Обновление статики не затрагивает бэкенд. Можно использовать CDN или S3 для статики — ещё одна вариация того же принципа.

### Важно про фронт-сервер

Фронт-сервер в данном контексте — это **не** UI/фронтенд в привычном смысле. Это сервер (например, Nginx), который стоит перед бэкендом и отдаёт статический контент.

### Связь выноса логики и трёхзвенки

Тот же принцип разделения ответственности: статику отдаёт фронт-сервер, часть логики — клиент, бизнес-логику — бэкенд. Каждый делает то, что умеет лучше.
