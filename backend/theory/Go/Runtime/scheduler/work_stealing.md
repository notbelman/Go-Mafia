- Когда у P нет работы — он ищет. Если не нашёл — крадёт у других. ^ws-overview
- **spinning:** M без работы не засыпает сразу — крутится, ищет. Лимит: GOMAXPROCS/2 spinning M ^ws-spinning-summary

**Порядок поиска работы (цикл планирования):**
```
schedule():
1. globrunqget()              — каждый 61-й тик (GRQ)
2. runqget()                  — runnext → runq (LRQ)

findRunnable():
1.  traceReader()              — горутина трассировки (если включена)
2.  gcController worker        — GC worker (если GC активен)
3.  globrunqget()              — каждый 61-й тик (fairness, GRQ)
4.  runqget()                  — runnext → runq (LRQ)
5.  globrunqgetbatch()         — глобальная очередь (GRQ), берёт батч в LRQ
6.  netpoll(0)                 — неблокирующий poll (оптимизация перед стилингом)
7.  stealWork()                — 4 прохода по всем P в рандомном порядке:
                                  • проходы 1-3: только runqsteal() — крадёт половину LRQ чужого P
                                  • проход 4:    runqsteal() + checkTimers() — крадёт runq И таймеры
8.  globrunqget()              — повторная проверка GRQ (пока стилили, могли положить)
9.  gcMarkWorkerIdleMode       — idle GC worker (если есть незанятый P)
10. spinning reset + recheck   — если M был spinning:
                                  • сброс m.spinning, декремент nmspinning
                                  • повторная проверка ВСЕХ источников (LRQ, GRQ, netpoll, стилинг)
                                  • если нашёл работу → goto top
11. netpoll(delay)             — блокирующий poll до следующего таймера
12. stopm()                    — засыпает (mput → pidleput → futex)
```
^ws-order

**Почему 1/61:** глобальная очередь под мьютексом — дорого дёргать постоянно. 61 — простое число, меньше вероятность что потоки столкнутся на мьютексе одновременно. Проверка: `schedtick % 61 == 0`. ^ws-why61

**Почему рандомный P:** если выбирать адаптивно — нужно трекать размеры всех очередей, синхронизировать. Много сложности. Рандом — простое и достаточно хорошее решение. ^ws-why-random

**Сколько красть:** половину с головы очереди (head) — там самые старые G. Одну — быстро закончится, снова идти красть. Много — у жертвы закончится, ей придётся красть. Половина — золотая середина. ^ws-how-much

**Spinning:** M без работы не засыпает сразу (засыпание = syscall, дорого). Сначала крутится: проверяет очереди, пробует украсть. Лимит: максимум GOMAXPROCS/2 spinning M (баланс между тратой CPU впустую и быстрым подхватом работы). Не нашёл — засыпает. ^ws-spinning-detail
#### LIFO-компонент (runnext) и fairness:
**runnext** — LIFO для кэш-теплоты (только что положили → сразу выполнить).
**runq** — FIFO для справедливости (кто раньше пришёл, тот раньше выполнится).

**Проблема:** две горутины пинг-понгят через канал (G1 шлёт → будит G2 в runnext, G2 читает → будит G1 в runnext) — бесконечно занимают runnext,
горутины в runq голодают.

**Решение:** sysmon видит что runq не двигается >10ms → вытесняет → runq получает CPU.
