- **Финалайзер** — callback, вызываемый перед удалением объекта GC. Минимум **2 цикла GC** для освобождения: 1-й цикл — объект unreachable → финалайзер ставится в очередь, объект **НЕ удаляется**; 2-й цикл — объект удаляется
- **Два кейса:** (1) страховка закрытия дескрипторов — `os.File` уже имеет `runtime.SetFinalizer` внутри (если забыли `Close()`, финалайзер закроет файл); (2) освобождение **CGO-памяти** — вместо того чтобы просить программиста не забыть `C.free()`
- **`runtime.KeepAlive(obj)`** — гарантирует что объект жив до этой точки. Защита от преждевременного финалайзера когда `f` больше не используется напрямую, но связанный `fd` ещё нужен
- **Не работает** для стековых объектов (GC не трогает стек — нужен escape на heap). Не гарантирован при завершении программы. Циклические ссылки с финалайзером → утечка
- **Go 1.24+:** `runtime.AddCleanup` — замена `SetFinalizer` с меньшим количеством проблем

---

Функция, вызываемая когда объект становится unreachable. Использовать осторожно.

**Базовое использование:**
```go
obj := &MyResource{fd: openFile()}
runtime.SetFinalizer(obj, func(o *MyResource) {
    o.Close()
})
```
^fin-basic

**Как работает:**
```
1. GC находит unreachable объект с finalizer
2. Объект НЕ удаляется, finalizer ставится в очередь
3. Отдельная горутина выполняет finalizer
4. Следующий GC удаляет объект
   └── минимум 2 цикла GC для освобождения
```
^fin-how-works

**Два основных кейса:**

**1. Страховка закрытия дескрипторов.** `os.File` в Go уже имеет `runtime.SetFinalizer` внутри — если забыли `Close()`, финалайзер закроет файл. То же для connection, handler и любых ресурсов ОС. ^fin-case-descriptors

**2. Освобождение CGO-памяти.** Если через CGO аллоцируете память в C — поставьте финалайзер вместо того, чтобы просить программиста не забыть `C.free()`. Go — язык с автоматической сборкой мусора, CGO-память тоже должна очищаться автоматически. ^fin-case-cgo

**Стековые объекты:** GC не трогает стек → финалайзер скорее всего не сработает для объектов, которые не escape на хип. ^fin-stack

**Проблемы:** непредсказуемое время выполнения, не гарантировано при завершении программы, объект живёт +1 GC цикл, циклические ссылки с finalizer → утечка, порядок не определён. ^fin-problems

**runtime.KeepAlive:**
```go
func process(f *File) {
    fd := f.fd
    // после этой строки f больше не используется напрямую
    // GC может решить что f unreachable → запустить финалайзер → закрыть файл
    // ... долгая работа с fd ...
    syscall.Read(fd, buf) // финалайзер может закрыть файл ДО этого → ошибка!
    runtime.KeepAlive(f)  // говорит компилятору: f жив до этой точки
}
```
^fin-keepalive

**Когда использовать:**
```
✗ Закрытие файлов → лучше defer Close() (финалайзер = страховка)
✗ Освобождение Go-памяти → GC сам
✓ Страховка для CGO ресурсов
✓ Отладка утечек
```
^fin-when-use

**Очистка и новый API:**
```go
runtime.SetFinalizer(obj, nil)  // убрать finalizer

// Go 1.24+: runtime.AddCleanup — меньше проблем
runtime.AddCleanup(&obj, func(ptr *int) { /* cleanup */ }, &arg)
```
^fin-cleanup
