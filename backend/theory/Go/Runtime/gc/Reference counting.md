- **Reference counting:** каждый объект хранит счётчик ссылок. Копируют ссылку → инкремент. Удаляют → декремент. = 0 → free немедленно. Без фонового GC потока: основной поток сам видит `ref_count = 0` и освобождает
- **Минусы:** overhead на каждую операцию с указателем; синхронизация между потоками (атомики/мьютексы); **каскадное освобождение** — список на миллион элементов: удаляем head → поочерёдно освобождается каждый → spike latency
- **Циклические ссылки (главная проблема):** двусвязный список — `A.next→B, B.prev→A`. Удалили внешний указатель: `ref_count(A)=1, ref_count(B)=1` → никогда не станет 0 → **утечка памяти**. Решение в C++: `weak_ptr/shared_ptr` — но это доп. сложность для программиста
- **Почему не Go:** нужно знать про weak/strong refs, управлять ими — язык усложняется. Go выбрал tracing GC где программист **вообще не думает** об освобождении памяти

## Идея

Каждый объект содержит счётчик: сколько других объектов на него ссылаются. Копируют ссылку → инкремент. Удаляют ссылку → декремент. Счётчик = 0 → объект можно освободить. ^rc-idea

```
Object в heap:
  [данные | ref_count = 2]
       ↑           ↑
    obj_A        obj_B (копия)

obj_B уничтожен → ref_count = 1
obj_A уничтожен → ref_count = 0 → free!
```

## Плюсы

Не нужен никакой фоновый поток для сборки мусора. Основной поток сам видит ref_count = 0 и освобождает. ^rc-pros

## Минусы

**Overhead:** дополнительная память на счётчик + инструкции инкремента/декремента при каждой операции. ^rc-overhead

**Синхронизация:** из нескольких потоков нужны атомики или мьютексы для счётчика. ^rc-sync

**Каскадное синхронное освобождение:** связанный список на миллион элементов → удаляем head → поочерёдно освобождается каждый элемент → spike latency. ^rc-cascade

**Циклические ссылки (главная проблема):**
```
Двусвязный список:
  A.next → B     ref_count(A) = 2
  B.prev → A     ref_count(B) = 2

Удалили внешний указатель:
  ref_count(A) = 1 (B всё ещё ссылается)
  ref_count(B) = 1 (A всё ещё ссылается)
  → Никогда не станет 0 → утечка памяти!
```
^rc-cycles-problem

Решение в C++: `weak_ptr` / `shared_ptr` (слабые/сильные ссылки, разные счётчики). Но это **дополнительная сложность для программиста**: нужно знать, где weak, где strong. ^rc-cycles-solution

## Почему не подошло для Go

Если бы Go использовал ref counting, программисту пришлось бы знать про weak/strong refs, управлять ими. Дополнительные контейнеры, функции, вопросы на собесах — язык усложняется. Go выбрал tracing GC, где программист вообще не думает об освобождении. ^rc-why-not-go
