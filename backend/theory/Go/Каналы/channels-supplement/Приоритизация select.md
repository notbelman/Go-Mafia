- проблема: данные в обоих каналах → выбор **рандомный**, приоритет не гарантирован
- три способа: вложенный select (100%), дополнительная проверка сверху (вероятностный), дублирование кейсов (вес)
- ни один способ кроме первого не даёт 100% гарантии

---

## Проблема

```go
select {
case v := <-highPriority:  // хочу чтобы этот был приоритетнее
    process(v)
case v := <-lowPriority:
    process(v)
}
```

Если данные есть в обоих каналах — Go выбирает кейс **рандомно**. Приоритета нет. ^prio-problem

## Способ 1: вложенный select (100% гарантия)

```go
select {
case v := <-lowPriority:
    // перед обработкой проверяем приоритетный
    select {
    case hp := <-highPriority:
        process(hp)  // приоритетный есть — берём его
    default:
    }
    process(v)
case v := <-highPriority:
    process(v)
}
```

Единственный способ с **100% гарантией** приоритета. Недостатки: сложный код, нужно думать что делать с уже прочитанным `v` когда нашли `hp`. ^prio-nested-100

## Способ 2: дополнительный select сверху (вероятностный)

```go
for {
    select {
    case v := <-highPriority:
        process(v)
        continue
    default:
    }

    select {
    case v := <-highPriority:
        process(v)
    case v := <-lowPriority:
        process(v)
    }
}
```

Сначала проверяем приоритетный (с default — не блокируемся). Если пусто — идём в общий select. **Не 100% гарантия**: данные могут прийти одновременно во второй select, где снова рандом. Но вероятность выбора приоритетного значительно выше. ^prio-top-select-prob

## Способ 3: дублирование кейсов (увеличение веса)

```go
select {
case v := <-highPriority:
    process(v)
case v := <-highPriority:  // тот же канал второй раз!
    process(v)
case v := <-lowPriority:
    process(v)
}
```

2 кейса на highPriority, 1 на lowPriority → вероятность ~2:1. Рандомный выбор из 3 кейсов, но 2 из них — приоритетный канал. **Не 100% гарантия**. ^prio-duplicate-cases
