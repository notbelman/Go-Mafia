- Moving Letter — параллельный запрос во все реплики, возвращаем ответ первой откликнувшейся
- Ключ: буферизированный канал `make(chan T, len(replicas))` + select с default в горутинах
- Буфер обязателен: без него горутины могут уйти в default и результат потеряется

---

## Идея

Кластер БД с синхронной репликацией — данные одинаковые на всех репликах. Хотим минимальное время ответа: ^ml-idea

```
     ┌─→ replica 1 (100ms) ──┐
req ─┼─→ replica 2 (50ms)  ──┼─→ берём первый ответ (50ms)
     └─→ replica 3 (200ms) ──┘
```

## Реализация

```go
func distributedQuery(addrs []string, query string) (string, error) {
    // ВАЖНО: буферизированный канал!
    resultCh := make(chan string, len(addrs))

    for _, addr := range addrs {
        go func(a string) {
            result := db.Query(a, query)
            select {
            case resultCh <- result:  // записали
            default:                   // канал полон — результат не нужен
            }
        }(addr)
    }

    return <-resultCh, nil  // первый ответ
}
```

^ml-impl

## Почему буфер обязателен

```go
// ОШИБКА — небуферизированный канал:
resultCh := make(chan string)
```

Проблема: если все горутины завершатся **до** `<-resultCh`:
1. Горутина 1 → select → канал пуст, пишем → нет читателя → default
2. Горутина 2 → select → default
3. Горутина 3 → select → default
4. `<-resultCh` → deadlock! Все ушли в default ^ml-buf-required

С буфером `len(addrs)` — первая горутина **гарантированно** запишет (есть место), остальные тоже запишут или уйдут в default. Читатель получит первый результат. ^ml-buf-len

На практике хватит буфера 1 — но `len(addrs)` гарантирует что ни одна горутина не заблокируется (нет утечки горутин). ^ml-buf-1-vs-n

## Компромиссы

- Дополнительная нагрузка на все реплики
- Лишние запросы тратят ресурсы
- Но: минимальная латентность для клиента ^ml-tradeoff
