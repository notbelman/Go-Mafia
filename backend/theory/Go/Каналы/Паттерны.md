**Паттерны работы с каналами** — это то, что превращает каналы из простого средства передачи данных в мощный инструмент оркестрации сложных систем. На уровне Middle+/Senior от тебя ждут понимания не только того, как написать `go func()`, но и как правильно управлять жизненным циклом горутин и потоками данных, избегая утечек и дедлоков. ^patterns-intro

---

### 1. Порождающие паттерны: Генератор (Generator)

**Генератор** — это функция, которая переводит дискретный набор значений (или бесконечный процесс) в поток данных в канале. ^generator-def

- **Суть**: Функция создаёт канал внутри своего лексического пространства, запускает горутину для его заполнения и возвращает этот канал как `<-chan` (только для чтения). ^generator-mechanics
- **Владение (Ownership)**: Этот паттерн идеально реализует принцип владения — горутина, создавшая канал, сама его заполняет и сама же закрывает. ^generator-ownership
- **Пример**: Генерация чисел Фибоначчи или случайных чисел.

### 2. Структурные паттерны: Pipeline

**Pipeline (Конвейер)** — это серия этапов (stages), где каждый этап принимает данные из одного канала, трансформирует их и передаёт в следующий. ^pipeline-def

- **Свойства этапа**: Потребляет и возвращает один и тот же тип, является реифицированным (можно передавать как функцию). ^pipeline-stage-props
- **Преимущества**: Каждый этап работает независимо и конкурентно. Это позволяет легко добавлять новые трансформации, не меняя существующий код. ^pipeline-advantages
- **Потоковая обработка**: В отличие от пакетной обработки, конвейер на каналах потребляет ровно столько памяти, сколько нужно для одного элемента в каждый момент времени. ^pipeline-memory

### 3. Паттерны параллелизма: Fan-out и Fan-in

Эти паттерны используются для ускорения «узких мест» в конвейере, когда один из этапов слишком тяжёлый. ^fanout-fanin-purpose

- **Fan-out (Веерное развёртывание)**: Запуск нескольких горутин для чтения из одного и того же канала. Это эффективно, если порядок обработки не важен и операции независимы. ^fanout-def
- **Fan-in (Веерное свёртывание)**: Объединение результатов из множества каналов в один общий выходной канал. Для этого обычно используется `sync.WaitGroup`, чтобы закрыть результирующий канал только после завершения всех отправителей. ^fanin-def

### 4. Паттерны управления: Done Channel и Or-channel

Главная проблема конкурентности — **утечки горутин**. Горутины не собираются GC, поэтому их нужно явно останавливать. ^goroutine-leak-problem

- **Done Channel**: Конвенция, согласно которой родительская горутина передаёт дочерней канал (обычно `done <-chan struct{}`). Когда родитель закрывает этот канал, все дети должны завершить работу. ^done-channel-def
- **Or-channel**: Создаёт один композитный канал из множества каналов завершения. Если закрывается хотя бы один из них (например, системный сигнал или тайм-аут), закрывается и весь результирующий канал. Это часто реализуется через рекурсию и `select`. ^or-channel-def

### 5. Паттерны надёжности: Heartbeats (Сердцебиение)

**Heartbeats** используются в долгоживущих процессах для сигнализации о том, что горутина всё ещё жива и работает корректно. ^heartbeat-def

- **Интервальные (Time-based)**: Горутина периодически отправляет пустой сигнал в специальный канал `heartbeat`. Если слушатель не получает сигнал в течение ожидаемого времени, он может перезапустить горутину («исцеление» — healing). ^heartbeat-time-based
- **Перед началом работы**: Полезно для детерминированного тестирования. Тест ждёт первого «удара сердца», чтобы убедиться, что горутина прошла инициализацию и готова к обработке данных. ^heartbeat-startup

### 6. Специфические паттерны оркестрации

- **Worker Pool (Пул воркеров)**: Набор фиксированного количества горутин, которые обрабатывают задачи из общего канала. Позволяет контролировать использование ресурсов (CPU, память, соединения с БД). ^worker-pool-def
- **Replicated Requests (Дублирование запросов)**: Отправка одного и того же запроса нескольким обработчикам сразу. Тот, кто ответит первым, «побеждает», а остальные запросы отменяются. Это минимизирует задержки (latency) ценой повышенного расхода ресурсов. ^replicated-requests-def
- **Bridge Channel (Мост)**: Позволяет читать значения из последовательности каналов (`<-chan <-chan interface{}`) так, будто это один непрерывный поток данных. ^bridge-channel-def
- **Tee Channel**: Разделяет один входной поток данных на два идентичных выходных потока (аналог команды `tee` в Unix). ^tee-channel-def
