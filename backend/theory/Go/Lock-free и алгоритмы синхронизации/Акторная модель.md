- Акторная модель — математическая модель параллельных вычислений (1973, Карл Хьюит). Акторы общаются сообщениями, не разделяют состояние ^actor-def
- Актор: inbox (буферизированный канал), внутреннее состояние (изолировано), уникальный адрес. 3 действия: создать актор, отправить сообщение, изменить своё состояние ^actor-structure
- В Go: актор = горутина + канал. Круто для распределённых систем (YDB, Erlang), избыточно для продуктовой бизнес-логики ^actor-go

---

## Структура актора

```go
type Actor struct {
    inbox    chan Letter           // почтовый ящик (буферизированный)
    executor Executor              // поведение (интерфейс)
}

type Letter struct {
    To   string
    From string
    Body interface{}
}

func NewActor(exec Executor) *Actor {
    a := &Actor{inbox: make(chan Letter, 10), executor: exec}
    go func() {
        for letter := range a.inbox {   // одна горутина обрабатывает
            a.executor.Execute(letter)   // последовательно (FIFO)
        }
    }()
    return a
}
```

^actor-code

## Свойства

**Изоляция**: актор не может изменить состояние другого актора. Только отправить сообщение. ^actor-isolation

**Асинхронность**: отправка = запись в буферизированный канал. Обработка — по одному, FIFO. ^actor-async

**Параллелизм**: нужно обработать N сообщений параллельно → создать N акторов одного типа. ^actor-parallelism

**Actor Manager**: синглтон, хранит мапу `адрес → актор`. Маршрутизирует сообщения. Под мьютексом. ^actor-manager

## Где использовать

**Да**: распределённые системы. Актор сегодня локальный (канал), завтра — удалённый (gRPC). YDB (C++), мониторинг Яндекса (Java), Erlang/OTP. ^actor-use-yes

**Нет**: обычная продуктовая бизнес-логика. Избыточная абстракция, усложняет код. ^actor-use-no

## Минусы

- Как получать ошибки? Обратный канал? Две очереди (запрос/ответ)? ^actor-minus-errors
- Отладка сложнее: асинхронные цепочки вместо синхронных вызовов ^actor-minus-debug
- Overhead на сериализацию/десериализацию сообщений ^actor-minus-overhead
