- конкурентный yield из нескольких горутин = паника (Go запрещает)
- горутины внутри итератора можно, но yield только из основной горутины — дождаться завершения
- ошибки через Seq2[T, error]: итератор по результатам и ошибкам одновременно

---

## Конкурентный yield = паника

```go
func ConcurrentBad(n int) iter.Seq[int] {
    return func(yield func(int) bool) {
        var wg sync.WaitGroup
        for i := 0; i < n; i++ {
            wg.Add(1)
            go func(v int) {
                defer wg.Done()
                yield(v)  // yield из горутины!
            }(i)
        }
        wg.Wait()
    }
}

for v := range ConcurrentBad(5) {
    fmt.Println(v)  // ПАНИКА: concurrent yield
}
```

Go запрещает вызывать yield из нескольких горутин. Итератор = корутина, yield — точка переключения. Конкурентные переключения ломают конечный автомат.

## Горутины можно, но yield — из основной горутины

```go
func Sequential(n int) iter.Seq[int] {
    return func(yield func(int) bool) {
        for i := 0; i < n; i++ {
            ch := make(chan int, 1)
            go func(v int) {
                // вычисления в горутине
                ch <- v * 2
            }(i)
            result := <-ch  // ждём завершения
            if !yield(result) { return }  // yield из основной горутины
        }
    }
}
```

Бессмысленно для простых случаев — зачем горутина если ждём синхронно? Но сам факт: горутины внутри итераторов допустимы, если yield вызывается последовательно.

## Ошибки: Seq2[T, error]

```go
func QueryUsers(db *sql.DB, q string) (iter.Seq2[User, error], error) {
    rows, err := db.Query(q)
    if err != nil {
        return nil, err  // ошибка до итерации
    }

    return func(yield func(User, error) bool) {
        defer rows.Close()
        for rows.Next() {
            var u User
            err := rows.Scan(&u.ID, &u.Name)
            if !yield(u, err) { return }
        }
    }, nil
}

// Использование: чистый range вместо Next/Scan/Close
iter, err := QueryUsers(db, "SELECT id, name FROM users")
if err != nil { return err }

for user, err := range iter {
    if err != nil {
        return err
    }
    fmt.Println(user.Name)
}
```

## Корнер-кейс: паника между получением итератора и range

```go
iter, err := QueryUsers(db, query)
// rows.Close() внутри итератора — вызовется только когда range начнёт работу
panic("oops")  // rows.Close() никогда не вызовется!
```

Решение: возвращать cleanup-функцию:

```go
func QueryUsers(db *sql.DB, q string) (iter.Seq2[User, error], func(), error) {
    rows, err := db.Query(q)
    if err != nil { return nil, nil, err }

    cleanup := func() { rows.Close() }

    return func(yield func(User, error) bool) {
        defer rows.Close()
        // ...
    }, cleanup, nil
}

iter, cleanup, err := QueryUsers(db, query)
defer cleanup()  // вызовется даже при панике
```

Менее красиво, но безопасно. Нужно только когда между получением итератора и range может быть паника.
