- inlining — оптимизация компилятора: код функции **вставляется вместо вызова**
- убирает overhead вызова (CALL/RET, работа со стеком)
- модель: **бюджет ~80**; cost = сумма инструкций × вес каждой
- cost > бюджет → не инлайнится; cost ≤ бюджет → может быть встроена
- минус: увеличивается размер бинарника (код дублируется в каждом месте вызова)

---

## Как работает

```go
func add(a, b int) int { return a + b }

// До inlining:
result := add(3, 5)  // CALL add → выполнение → RET

// После inlining:
result := 3 + 5      // код add встроен прямо сюда
```

Inlining убирает overhead CALL/RET: нет сохранения/восстановления стека, нет перехода по адресу. ^inlining-what

## Budget-модель

Компилятор считает «стоимость» каждой функции:

```
cost(func) = Σ (инструкция × вес)
```

Каждая инструкция имеет вес (вызов функции — дорого, сложение — дёшево). ^inlining-budget-formula

Если общий cost ≤ ~80 — функция кандидат на inlining. ^inlining-budget-threshold

Бюджет и веса могут меняться в будущих версиях Go. ^inlining-budget-unstable

## Запрет inlining

```go
//go:noinline
func add(a, b int) int { return a + b }
// компилятор НЕ будет встраивать эту функцию
```

Директива `//go:noinline` явно запрещает компилятору встраивать функцию. ^inlining-noinline

## Почему не всё инлайнится

Если функция вызывается в 1000 мест и каждый раз встраивается — **бинарник растёт** (text segment увеличивается). Компромисс между скоростью и размером. ^inlining-tradeoff

## Практический вывод

Две причины писать **маленькие компактные функции**:
1. Читаемость, тестируемость, single responsibility
2. Go **эффективнее инлайнит** маленькие функции → лучше производительность ^inlining-small-funcs
