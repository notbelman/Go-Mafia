- KRaft = новый контроллер Kafka на базе **Raft** (с версии 2.8). Заменяет ZooKeeper
- Контроллеры = Raft quorum, хранят **лог метаданных** (те же events, что Kafka использует для данных)
- Active controller = лидер quorum. Follower controllers = hot standby (не нужно перезагружать состояние при failover)
- Брокеры **сами тянут** обновления через MetadataFetch API (pull вместо push), хранят метаданные на диске
- Fenced state — брокер с устаревшими метаданными не может обслуживать клиентов

---

## Зачем заменили ZooKeeper

Четыре проблемы ZK-контроллера: ^kraft-why

1. **Inconsistency:** метаданные пишутся в ZK синхронно, рассылаются брокерам асинхронно, получаются из ZK асинхронно → edge cases с несогласованными метаданными ^kraft-why-inconsistency

2. **Bottleneck при рестарте:** новый контроллер читает ВСЁ состояние из ZK → рассылает ВСЕМ брокерам. Чем больше партиций — тем дольше. Годы оптимизаций не решили проблему ^kraft-why-bottleneck

3. **Размытое владение метаданными:** часть операций через контроллер, часть через любой брокер, часть напрямую в ZK ^kraft-why-ownership

4. **Две распределённые системы:** нужно знать и Kafka, и ZooKeeper. Двойная операционная сложность ^kraft-why-two-systems

## Архитектура

#### Старая (ZK)

```text
  Controller ←→ ZooKeeper ←→ Brokers
  (push updates)
```

#### Новая (KRaft)

```text
  ┌──────────── Controller Quorum (Raft) ────────────┐
  │  Active Controller  │  Follower  │  Follower      │
  │  (лидер quorum)     │  (hot standby)              │
  └──────────────────────────────────────────────────┘
         ▲ MetadataFetch (pull)
         │
    ┌────┴────┐
    │ Brokers │  (хранят метаданные на диске)
    └─────────┘
```

^kraft-architecture

## Ключевая идея: лог метаданных

Kafka уже использует лог для данных пользователей. KRaft применяет **ту же идею к метаданным**: топики, партиции, ISR, конфигурации — всё хранится как поток событий в логе. ^kraft-metadata-log

Преимущества лога: упорядоченность, быстрый catch-up через replay, единая timeline. ^kraft-log-benefits

## Pull вместо Push

Раньше контроллер **пушил** обновления брокерам. Теперь брокеры **сами тянут** через MetadataFetch API — аналогично fetch request для данных. Брокеры хранят offset последнего полученного обновления и запрашивают только новые. ^kraft-pull

## Fenced state

Брокер online, но метаданные устарели → **fenced** → не обслуживает клиентов. Предотвращает ситуацию: клиент пишет в брокер, который уже не лидер, но не знает об этом. ^kraft-fenced

## Быстрый failover

Все контроллеры в quorum отслеживают актуальное состояние → при failover **не нужно перечитывать** всё состояние из ZK. Hot standby подхватывает мгновенно. ^kraft-fast-failover

## Регистрация брокеров

Брокеры регистрируются в quorum и остаются зарегистрированными до явного удаления админом. Остановленный брокер = offline, но registered (в отличие от ZK, где ephemeral node исчезала). ^kraft-broker-registration
