#### Когда RabbitMQ?

- Сложная маршрутизация (фильтрация по заголовкам, ключам)
- Минимальная задержка при обработке одиночных событий
- Краткосрочные задачи, которые исчезают после выполнения
- Нагрузка — миллионы, не миллиарды в день

#### Когда Kafka?

- Огромные потоки данных, аналитика в реальном времени
- Нужно перечитать историю (rewind, event sourcing, audit)
- Строгий порядок обработки связанных событий через ключи партиций
- Несколько независимых консьюмеров на один поток

#### Когда Redis (Pub/Sub / Streams)?

- Уже используешь Redis как кэш — не хочешь тащить отдельный брокер
- Минимальная латентность, данные в памяти
- Pub/Sub: потеря сообщений допустима (нет подписчика — сообщение пропало)
- Streams: нужен лёгкий аналог Kafka с consumer groups, но масштаб небольшой

#### Зачем брокер если есть gRPC/HTTP?

- gRPC/HTTP — **синхронные**: вызвал → ждёшь ответа → получатель должен быть онлайн
- Брокер — **асинхронный**: отправил и забыл, получатель обработает когда сможет
- Брокер развязывает сервисы: отправитель не знает кто читает, и сколько их
- Брокер переживает падение получателя: сообщения ждут в очереди
