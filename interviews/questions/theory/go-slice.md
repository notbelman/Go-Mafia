## 1. Что такое слайс, как устроен под капотом (структура в памяти)?

Слайс — это динамическая обёртка над массивом. Под капотом это структура из трёх полей:

```go
type slice struct {
    array unsafe.Pointer // указатель на underlying array
    len   int            // текущая длина
    cap   int            // ёмкость (от начала слайса до конца underlying array)
}
```

То есть слайс занимает 24 байта на 64-битной системе (8 + 8 + 8). Сами данные хранятся не в слайсе, а в массиве, на который он ссылается.

Если «читать байтики по адресу» слайса — увидим сначала 8 байт указателя, потом 8 байт len, потом 8 байт cap.

---

## 2. Чем слайс отличается от массива?

||Массив|Слайс|
|---|---|---|
|Размер|Фиксирован, часть типа (`[5]int ≠ [10]int`)|Динамический|
|Тип|Value type|Reference type (обёртка над массивом)|
|Передача в функцию|Копируется целиком|Копируется заголовок (24 байта), данные — нет|
|Comparable|Да (== работает)|Нет (== не работает, кроме сравнения с `nil`)|
|Ключ в мапе|Да|Нет|

---

## 3. В чём принципиальное отличие слайса, мапы и массива?

- **Массив** — value type фиксированного размера. При присваивании и передаче копируется полностью.
- **Слайс** — обёртка (ptr + len + cap) над массивом. При передаче копируется заголовок, но данные разделяются.
- **Мапа** — под капотом указатель на `runtime.hmap`. При передаче в функцию копируется только указатель, поэтому изменения внутри функции видны снаружи без возврата. В отличие от слайса, для мапы не нужен паттерн `m = append(m, ...)`.

---

## 4. Что означают параметры length и capacity в `make`?

```go
s := make([]int, length, capacity)
```

- **length** — сколько элементов уже «существует» (проинициализировано нулями). К ним можно обращаться по индексу `s[0]..s[len-1]`.
- **capacity** — сколько элементов вмещает underlying array. Пока `len < cap`, `append` не выделяет новый массив.

Если capacity не указан, он равен length:

```go
s := make([]int, 5) // len=5, cap=5
```

---

## 5. Что произойдёт при `make([]int, 100, 100)` и `append` ещё 100 элементов?

1. Создаётся слайс с len=100, cap=100, underlying array на 100 элементов (заполнен нулями).
2. При первом `append` len превышает cap → Go выделяет **новый массив**.
3. Все 100 существующих элементов копируются в новый массив.
4. После 100 append'ов len=200. Новый capacity будет больше 200 (Go выделяет с запасом).

---

## 6. Какого размера создаётся новый массив при выходе за capacity?

Стратегия роста (Go 1.18+):

- Если текущий cap < 256 — **удваивается** (×2).
- Если cap ≥ 256 — растёт примерно на **25%** (`newcap += (newcap + 3*256) / 4`).

Затем размер выравнивается по классам аллокации рантайма, поэтому реальный cap может быть чуть больше расчётного.

---

## 7. Как работает `append` — почему это функция, а не метод? Что возвращает?

`append` — встроенная функция (builtin), а не метод, потому что слайс — не именованный тип с методами, а generic-конструкция (работает с любым `[]T`). До дженериков в Go это было невозможно выразить через методы.

**Что происходит внутри:**

1. Если `len + кол-во новых элементов ≤ cap` → элементы записываются в существующий массив, len увеличивается.
2. Если не хватает cap → выделяется новый массив, данные копируются, указатель меняется.

**Возвращает новый слайс-заголовок** (ptr, len, cap). Даже если массив не менялся — len точно изменился, поэтому результат нужно присваивать:

```go
s = append(s, 42)
```

---

## 8. Какая сложность у `append`? Что такое амортизированная сложность?

- Единичный `append` без реаллокации — **O(1)**.
- `append` с реаллокацией — **O(n)** (копирование всех элементов).
- **Амортизированная сложность** — O(1). Это значит, что если сделать n append'ов подряд, суммарная стоимость будет O(n), то есть в среднем каждый append стоит O(1). Реаллокации происходят всё реже, потому что capacity растёт экспоненциально.

---

## 9. Как происходит динамическое расширение слайса?

1. Вызывается `append`, len + 1 > cap.
2. Рантайм вычисляет новый cap по стратегии роста (×2 при малых, ~×1.25 при больших).
3. Выделяется новый underlying array нужного размера.
4. Данные из старого массива копируются в новый.
5. Новый элемент записывается.
6. Возвращается слайс-заголовок с новым указателем, новым len и новым cap.
7. Старый массив станет мусором (если на него больше никто не ссылается) и будет собран GC.

---

## 10. Как слайс передаётся в функцию — копируется или по ссылке?

**Копируется заголовок** (24 байта: ptr, len, cap). Это передача по значению, но поскольку внутри заголовка — указатель на массив, функция может **изменять существующие элементы** через этот указатель. Однако:

- `append` внутри функции изменит **локальную копию** len/cap — вызывающий код этого не увидит.
- Изменение `s[i] = x` — увидит, потому что массив общий.

---

## 11. В чём разница передачи в функцию слайса и массива с вычислительной точки зрения?

- **Массив** копируется **целиком**. Если `[1_000_000]int` — скопируется ~8 МБ. Это дорого.
- **Слайс** копирует только заголовок — **24 байта** независимо от размера данных.

Поэтому массивы в функции почти всегда передают по указателю (`*[N]int`), а слайсы — по значению.

---

## 12. Как сделать так, чтобы `append` внутри функции изменил оригинальный слайс без `return`?

Передать **указатель на слайс**:

```go
func addElement(s *[]int, val int) {
    *s = append(*s, val)
}

func main() {
    s := []int{1, 2, 3}
    addElement(&s, 4)
    fmt.Println(s) // [1 2 3 4]
}
```

Так функция меняет оригинальный заголовок (ptr, len, cap) напрямую.

---

## 13. Лучше передавать слайс по указателю или по значению и почему?

**По значению (обычно).** Копия заголовка стоит 24 байта — это дёшево. Код проще, безопаснее, нет неожиданных мутаций.

**По указателю** — только если функция должна изменить сам слайс (append, переприсвоение). Это паттерн для функций-мутаторов.

Идиоматичный Go предпочитает возврат нового слайса:

```go
s = append(s, val) // лучше, чем указатель
```

---

## 14. Изменение элемента по индексу внутри функции — меняется ли исходный массив?

**Да.** Слайс содержит указатель на underlying array. При передаче в функцию копируется заголовок, но указатель тот же → обе копии смотрят на один массив.

```go
func mutate(s []int) {
    s[0] = 999
}

func main() {
    s := []int{1, 2, 3}
    mutate(s)
    fmt.Println(s[0]) // 999
}
```

Но если внутри функции произойдёт реаллокация (append за пределы cap) — указатель изменится, и связь с оригинальным массивом разорвётся.

## 15. Что будет, если объявить слайс через `var` без `make` и вызвать `append`?

```go
var s []int       // s == nil, len=0, cap=0
s = append(s, 1)  // работает!
```

`append` корректно обрабатывает nil-слайс — выделяет новый underlying array. Это идиоматичный способ: не нужно делать `make`, если собираешься сразу наполнять через `append`.

`nil`-слайс и пустой слайс (`[]int{}`) ведут себя одинаково с `append`, `len`, `cap`, `range`, но отличаются при `json.Marshal`: nil → `null`, пустой → `[]`.

---

## 16. Является ли слайс comparable типом? Можно ли использовать слайс ключом в мапе?

**Нет и нет.** Слайс нельзя сравнивать через == (кроме сравнения с `nil`) и нельзя использовать как ключ в мапе. Компилятор выдаст ошибку.

Массив — comparable, поэтому `[3]int` можно использовать ключом в мапе, а `[]int` — нельзя.

Если нужен слайс как ключ — конвертируй в массив (Go 1.17+: `[3]int(s)`) или в строку.

---

## 17. Какие подводные камни и контр-кейсы при работе со слайсами?

1. **Утечка памяти через субслайс.** `s2 := s[1:3]` — underlying array всё ещё жив целиком. Если исходный слайс большой, а нужен маленький кусок — лучше `copy`.
    
2. **Неожиданная мутация через субслайс.** `s2 := s[1:3]` и `append(s2, x)` может перезаписать `s[3]`, если cap позволяет.
    
3. **Потеря изменений после append.** `append` внутри функции не меняет внешний слайс (копия заголовка).
    
4. **Гонки данных.** Несколько горутин работают с одним underlying array → data race.
    
5. **Неочевидный рост capacity.** После нескольких append'ов cap может быть сильно больше len — лишняя память.
    
6. **nil vs empty slice.** Разное поведение при сериализации (JSON).

## 18. Что выведет код при операциях со слайсами (make, append, copy, mutate, субслайсы) — и почему?

Типичный пример:

```go
s := make([]int, 3, 5) // [0 0 0], len=3, cap=5
s = append(s, 1)       // [0 0 0 1], len=4, cap=5
s2 := s[1:3]           // [0 0], len=2, cap=4 (тот же массив!)
s2 = append(s2, 99)    // s2=[0 0 99], но 99 записался в s[3] тоже!
fmt.Println(s)         // [0 0 0 99] — сюрприз!
```

**Почему:** `s2` имеет cap=4 (от индекса 1 до конца underlying array). `append` не вызвал реаллокацию, а записал 99 в позицию `s[3]` через общий массив.

**Как избежать:** использовать full slice expression `s[1:3:3]` — ограничить cap, чтобы append гарантированно выделил новый массив.

---

## 19. Почему при append и изменении данных через субслайс результат может быть неожиданным?

Потому что субслайс **разделяет underlying array** с оригиналом. Если cap субслайса позволяет — `append` пишет в тот же массив, затрагивая данные оригинального слайса.

```go
a := []int{1, 2, 3, 4, 5}
b := a[1:3]          // [2, 3], cap=4
b = append(b, 100)   // b=[2, 3, 100], но a[3] тоже стал 100!
fmt.Println(a)       // [1 2 3 100 5]
```

Решение — `a[1:3:3]` (ограничить cap) или `copy`.

---

## 20. Что выведет код с `add(s[1:2])` и `append` внутри — почему?

Типичная задача:

```go
func add(s []int) {
    s = append(s, 100)
}

func main() {
    s := []int{1, 2, 3, 4}
    add(s[1:2]) // передаём [2], len=1, cap=3
    fmt.Println(s)
}
```

**Вывод:** `[1 2 100 4]`

**Почему:** `s[1:2]` имеет cap=3 (до конца исходного массива). `append` внутри `add` не выходит за cap → пишет 100 в позицию `s[2]` исходного массива. Внешний `s` видит изменение, потому что массив общий. Но len внешнего слайса не изменился.

---

## 21. Почему Y и Z принимают разные значения при ссылке на один массив?

Типичная задача:

```go
a := []int{1, 2, 3, 4, 5}
y := a[0:2] // [1 2], len=2, cap=5
z := a[2:4] // [3 4], len=2, cap=3

y = append(y, 10) // y=[1 2 10], записал в a[2]
fmt.Println(z)    // [10 4] — z[0] изменился!
```

**Почему:** `y` и `z` ссылаются на один массив. `append` к `y` записал 10 в `a[2]`, а `z[0]` — это тоже `a[2]`. Поэтому `z` «увидел» изменение.

Это ключевой контр-кейс: **два субслайса одного массива могут неявно влиять друг на друга.**
