Для обеспечения идемпотентности каждое сообщение должно содержать **уникальный идентификатор** (idempotency key). Этот ключ проверяется перед обработкой.

### Где хранить ключ в сообщении

- **В headers сообщения Kafka** - предпочтительный способ, не загрязняет payload
- **В теле сообщения** - если headers недоступны или неудобны

### Где хранить обработанные ключи

| Хранилище | Когда использовать |
|-----------|-------------------|
| **Та же БД, что и бизнес-данные** | Лучший вариант - можно обернуть в одну транзакцию: записал данные + записал ключ |
| **Redis с TTL** | Для stateless сервисов или когда нужна скорость, но есть риск потери при рестарте |
| **Отдельная таблица idempotency_keys** | Универсальный подход для SQL баз |

**Важно:** проверка ключа и бизнес-логика должны быть в одной транзакции, иначе возможен race condition.
