
| Метод      | Формат      | Протокол   | Типизация | Use-case                        |
|------------|-------------|------------|-----------|----------------------------------|
| REST       | JSON        | HTTP/1.1   | Нет       | CRUD, публичные API             |
| GraphQL    | JSON        | HTTP/1.1   | Да (schema) | Сложные UI, mobile apps       |
| gRPC       | Protobuf    | HTTP/2     | Да (.proto) | Microservices, high-load      |
| SOAP       | XML         | HTTP/1.1   | Да (WSDL)   | Enterprise, legacy            |
| JSON-RPC   | JSON        | HTTP/1.1   | Нет       | Простые internal APIs           |

## Что выбрать?
REST - default выбор для большинства случаев
GraphQL - если UI требует гибкости и разных вьюшек
gRPC - для microservices и high-load (internal APIs)
SOAP - только если legacy система требует
JSON-RPC - если REST избыточен для простого internal API

## REST (Representational State Transfer)
HTTP методы + ресурсы + статус-коды.

GET /users/123 -> 200 OK {"id": 123, "name": "Ivan"}
POST /users -> 201 Created
PUT /users/123 -> 200 OK
DELETE /users/123 -> 204 No Content

Плюсы:
- Простота (HTTP семантика)
- Кешируемость (GET, HEAD)
- Stateless
- Читается человеком (JSON)

Минусы:
- Over-fetching (получаешь всё, даже если нужно только name)
- Under-fetching (нужно несколько запросов: user + orders + payments)
- Нет строгой типизации

Use-case: CRUD API, публичные API, простые сервисы

## GraphQL
Язык запросов. Клиент сам решает какие поля получить.

POST /graphql
query {
  user(id: 123) {
    name
    orders { id, total }
  }
}

Response: {"data": {"user": {"name": "Ivan", "orders": [...]}}}

Плюсы:
- Только нужные поля (no over-fetching)
- Один запрос вместо нескольких REST (user + orders)
- Строгая типизация (schema)
- Интроспекция (API самодокументируется)

Минусы:
- Сложнее кешировать (всё POST /graphql)
- N+1 проблема (нужен DataLoader)
- Overkill для простых CRUD
- Сложнее авторизация (поля вложенные)

Use-case: сложные UI с разными вьюшками, мобильные приложения (экономия трафика)

## gRPC (Google RPC)
Бинарный протокол поверх HTTP/2, использует Protocol Buffers.

// user.proto
service UserService {
  rpc GetUser(GetUserRequest) returns (User);
}

Клиент вызывает метод как локальную функцию:
user = userService.GetUser({userId: 123})

Плюсы:
- Быстрый (бинарный формат, HTTP/2 multiplexing)
- Строгая типизация (Protobuf схемы)
- Code generation (клиент/сервер из .proto)
- Streaming (bidirectional, server-side, client-side)

Минусы:
- Не читается человеком (бинарный)
- Сложнее дебажить
- Нужен gRPC-Web для браузеров

Use-case: microservices (internal APIs), high-load системы, streaming (video, logs)

## SOAP (Simple Object Access Protocol)
XML-based протокол с WSDL контрактами.

POST /soap
<soap:Envelope>
  <soap:Body>
    <GetUser><userId>123</userId></GetUser>
  </soap:Body>
</soap:Envelope>

Плюсы:
- Строгие контракты (WSDL)
- Встроенная безопасность (WS-Security)
- Enterprise стандарт (банки, страховые, госсектор)

Минусы:
- Огромный оверхед (XML verbose)
- Сложность (WS-* стандарты)
- Медленный (парсинг XML)
- Legacy (новые проекты не используют)

Use-case: банки, страховые, legacy enterprise системы

## JSON-RPC
RPC поверх JSON. Один endpoint, методы в теле.

POST /rpc
{"jsonrpc": "2.0", "method": "getUser", "params": {"userId": 123}, "id": 1}

Response:
{"jsonrpc": "2.0", "result": {"id": 123, "name": "Ivan"}, "id": 1}

Плюсы:
- Простота (JSON, один endpoint)
- Легко тестировать
- Читается человеком

Минусы:
- Нет стандартизации (каждый делает по-своему)
- Нет HTTP семантики (всё POST)
- Нет кеширования

Use-case: простые internal APIs, когда REST избыточен
