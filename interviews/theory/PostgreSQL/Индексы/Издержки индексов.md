## Стоимость индекса

**По месту:** каждый индекс — отдельная структура на диске (B-tree). Индекс на таблицу 1GB может занять 200-500MB+. Чем больше индексов — тем больше диска.

**По записи:** при каждом INSERT/UPDATE/DELETE нужно обновить ВСЕ индексы на таблице. Каждый индекс — это дополнительный random I/O + возможные page split'ы в B-tree.
```
INSERT без индексов:  запись в heap → готово
INSERT с 5 индексами: запись в heap + обновить 5 B-tree деревьев
```

## Почему не индексировать всё подряд

- Каждый лишний индекс замедляет запись (INSERT/UPDATE/DELETE)
- Больше потребление диска и RAM (индексы кэшируются в shared_buffers)
- Планировщик может запутаться и выбрать неоптимальный индекс
- VACUUM должен чистить больше структур → дольше работает
- Низкоселективные колонки (bool, enum на 3 значения) — планировщик всё равно выберет seq scan

## Какие запросы индексы НЕ ускоряют

- `SELECT *` без WHERE — полный перебор и так быстрее
- `WHERE column != value`, `NOT IN` — B-tree не помогает
- `LIKE '%middle%'` — B-tree не работает (нужен GIN + pg_trgm)
- Запросы к таблицам < ~1000 строк — seq scan быстрее из-за overhead индекса
- Запросы с низкой селективностью (WHERE gender = 'M' на 50% таблицы)

## Как выбрать индекс

### Шаг 1: Смотри запросы
```sql
-- Найди медленные запросы
SELECT * FROM pg_stat_statements ORDER BY total_time DESC;
-- Или EXPLAIN ANALYZE на конкретный запрос
EXPLAIN ANALYZE SELECT ... ;
```

### Шаг 2: Выбирай тип по паттерну

| Паттерн запроса              | Тип индекса         |
| :--------------------------- | :------------------ |
| `=`, `<`, `>`, `BETWEEN`    | B-tree (дефолт)     |
| Полнотекстовый поиск         | GIN + tsvector      |
| `LIKE '%text%'`             | GIN + pg_trgm       |
| Геоданные, диапазоны         | GiST                |
| JSON поля                    | GIN                 |
| Очень большая таблица, =     | Hash                |

### Шаг 3: Проверяй селективность
```sql
-- Хороший кандидат: много уникальных значений
SELECT COUNT(DISTINCT email)::float / COUNT(*) FROM users;
-- → 0.99 = высокая селективность ✅

-- Плохой кандидат
SELECT COUNT(DISTINCT status)::float / COUNT(*) FROM orders;
-- → 0.0001 = низкая селективность ❌
```

### Правило
Индексируй колонки из WHERE, JOIN ON, ORDER BY — но только те, где высокая селективность и запрос вызывается часто.
