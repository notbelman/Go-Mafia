Разбиение одной таблицы на несколько физических частей.

## Под капотом

- Партиции = отдельные таблицы-наследники, родительская пустая
- INSERT - роутинг по ключу в нужную партицию
- SELECT - планировщик отсекает ненужные партиции по WHERE (partition pruning)
- Каждая партиция: свои индексы, статистика, autovacuum

## Индексы

- Глобальных индексов нет - в PG это N отдельных индексов на каждой партиции
- CREATE INDEX на родителе - автоматически создает на всех партициях (PG11+)
- UNIQUE/PK обязан включать ключ партиции (иначе нельзя гарантировать уникальность cross-partition)

## Выбор ключа

- Должен быть в WHERE большинства запросов - иначе pruning не работает
- Не должен часто меняться (UPDATE ключа = DELETE + INSERT между партициями)
- Функция на ключе ломает pruning: WHERE YEAR(date) = 2024 - нет, WHERE date >= '2024-01-01' - да

## Грабли

- Запрос без ключа партиции - full scan ВСЕХ партиций, хуже чем одна таблица
- Количество партиций: десятки - ок, сотни - planning time растет, тысячи - боль
- Таблица < 10 млн строк - overhead на планирование съест профит
- NULL в ключе партиции - нельзя (кроме List с явным NULL)

## Эволюция

- PG10: declarative partitioning
- PG11: PK/FK на родителе, CREATE INDEX на родителе, runtime pruning
- PG12: FK могут ссылаться НА партицированные таблицы
