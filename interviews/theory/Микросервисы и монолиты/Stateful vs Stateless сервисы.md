
## Stateless

Сервис не хранит состояние между запросами. Каждый запрос содержит всё необходимое для обработки.
```
Запрос 1 → Pod A → ответ
Запрос 2 → Pod B → ответ   ← другой под, без разницы
Запрос 3 → Pod A → ответ
```

- ✅ Легко масштабировать — добавил подов и всё
- ✅ Любой под может обработать любой запрос
- ✅ Под упал — ничего не потеряли
- Примеры: API gateway, auth-service (проверяет JWT), notification-service

## Stateful

Сервис хранит состояние, привязанное к клиенту или данным. Запрос нужно направить на конкретный инстанс.
```
Запрос 1 → Pod A (создал сессию)
Запрос 2 → Pod A (нужна та же сессия)  ← sticky session
Запрос 3 → Pod B ← сессии нет, ошибка
```

- ❌ Масштабировать сложнее — нужна миграция состояния
- ❌ Под упал — состояние потеряно
- ❌ Нужен sticky routing или shared storage
- Примеры: БД, Redis, WebSocket-соединения, in-memory кэш

## Как сделать stateful → stateless

Выносим состояние во внешнее хранилище:
```
Было (stateful):
  Pod хранит сессию в памяти → sticky session

Стало (stateless):
  Pod читает сессию из Redis → любой под обработает запрос
```

| Состояние | Куда вынести |
|:----------|:-------------|
| Сессии | Redis |
| Данные пользователя | PostgreSQL |
| Файлы | S3 |
| Кэш | Redis / Memcached |

## Правило для микросервисов

Стремись к stateless — проще деплоить, масштабировать, переживать падения. Stateful только там где неизбежно (БД, брокеры, WebSocket).
