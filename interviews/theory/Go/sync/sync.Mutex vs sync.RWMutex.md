## Что происходит в процессоре

У каждого ядра CPU есть свой **локальный кэш** — очень быстрая память прямо на ядре. ^cpu-cache-intro

```
┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐
│  Ядро 1  │  │  Ядро 2  │  │  Ядро 3  │  │  Ядро 4  │
│  ┌────┐  │  │  ┌────┐  │  │  ┌────┐  │  │  ┌────┐  │
│  │кэш │  │  │  │кэш │  │  │  │кэш │  │  │  │кэш │  │
│  └────┘  │  │  └────┘  │  │  └────┘  │  │  └────┘  │
└────┬─────┘  └────┬─────┘  └────┬─────┘  └────┬─────┘
     │             │             │             │
     └─────────────┴──────┬──────┴─────────────┘
                          │
                   ┌──────┴──────┐
                   │  Общая RAM  │
                   │ readerCount │
                   └─────────────┘
```

Когда ядро читает `readerCount`, оно копирует значение в свой кэш. Следующие чтения берутся из кэша — это **очень быстро** (наносекунды). ^cpu-cache-read

## Проблема RWMutex

Каждый `RLock()` делает:
```go
atomic.Add(&readerCount, 1)  // ИЗМЕНЯЕТ readerCount
```
^rwmutex-rlock-atomic

Когда одно ядро **изменяет** `readerCount`:
```
Ядро 1: readerCount = 5 → 6  (изменил!)

CPU говорит остальным ядрам:
"Эй, ваши копии readerCount теперь неправильные, выбросьте их!"

Ядро 2: "Блин, мой кэш невалиден" → идёт в RAM → медленно
Ядро 3: "Блин, мой кэш невалиден" → идёт в RAM → медленно  
Ядро 4: "Блин, мой кэш невалиден" → идёт в RAM → медленно
```
^rwmutex-cache-invalidation

Это называется **cache invalidation** (инвалидация кэша). ^cache-invalidation-term

## Почему это плохо?

```
Чтение из кэша:     ~1-3 наносекунды
Чтение из RAM:      ~100 наносекунд (в 30-100 раз медленнее!)
```
^cache-vs-ram-latency

Теперь представь: 8 горутин на 8 ядрах одновременно делают `RLock()`:
```
Горутина 1: atomic.Add → readerCount = 1 → ВСЕ кэши инвалидированы
Горутина 2: atomic.Add → readerCount = 2 → ВСЕ кэши инвалидированы
Горутина 3: atomic.Add → readerCount = 3 → ВСЕ кэши инвалидированы
...
```
Каждая операция заставляет ВСЕХ остальных лезть в медленную RAM. **Больше ядер = больше инвалидаций = всё медленнее.** ^rwmutex-contention-cascade

## А что с Mutex?

`Mutex.Lock()` делает CAS:
```go
CompareAndSwap(&state, 0, 1)  // "если 0, поставь 1"
```
^mutex-cas

Ключевое отличие: **если лок занят, CAS НЕ меняет память**.
```
Горутина 1: CAS(0→1) — успех, изменил
Горутина 2: CAS(0→1) — лок занят, state уже 1, НЕ меняем → спим
Горутина 3: CAS(0→1) — лок занят, state уже 1, НЕ меняем → спим
```
Горутины 2 и 3 **не инвалидируют кэши** — они просто видят "занято" и уходят спать. Инвалидация происходит только когда лок реально переходит между горутинами. ^mutex-no-cache-invalidation-when-locked

## Когда RWMutex всё-таки выигрывает?

RWMutex выигрывает когда **время работы под локом >> время на инвалидацию кэша**. ^rwmutex-win-condition

```
Плохо для RWMutex (overhead не окупается):
┌─────────────────────────────────────────┐
│ RLock() │ return map[key] │ RUnlock()  │
│  100ns  │      10ns       │    100ns   │  ← большую часть времени тратим на лок
└─────────────────────────────────────────┘

Хорошо для RWMutex (параллелизм окупается):
┌───────────────────────────────────────────────────────────────┐
│ RLock() │ сложные вычисления 10ms │ RUnlock()                 │
│  100ns  │       10000000ns        │    100ns                  │
└───────────────────────────────────────────────────────────────┘
  ↑ overhead незаметен, зато 8 читателей работают параллельно
```
^rwmutex-tradeoff-examples

## Итого: когда что

**Используй Mutex (по умолчанию):**
- Не знаешь что выбрать
- Операции быстрые (меньше 1мс)
- Записей примерно столько же сколько чтений
- Одно ядро (тогда параллелизма всё равно нет)
^mutex-when-to-use

**Используй RWMutex только если:**
- Чтений реально много (в 10+ раз больше записей)
- Операция чтения долгая (парсинг, вычисления, I/O)
- Несколько ядер
- Замерил и убедился что быстрее
^rwmutex-when-to-use

**Пример где RWMutex хорош:**
```go
// Конфиг читается 1000 раз в секунду, меняется раз в час
// Чтение конфига занимает 5мс (парсинг, валидация)
var configMu sync.RWMutex
var config Config

func GetConfig() Config {
    configMu.RLock()
    defer configMu.RUnlock()
    return deepCopy(config)  // долгая операция
}
```
^rwmutex-good-example

**Пример где Mutex лучше:**
```go
// Счётчик меняется постоянно, операция мгновенная
var counterMu sync.Mutex
var counter int

func Increment() {
    counterMu.Lock()
    counter++  // 1 наносекунда
    counterMu.Unlock()
}
```
^mutex-good-example
