- ABA-проблема — CAS видит тот же адрес, но данные за ним уже другие. Аллокатор переиспользовал освобождённую память ^aba-def
- В Go не возникает: GC не освободит память пока есть ссылка. Актуально для C/C++ и кастомных аллокаторов ^aba-go-safe
- Решения: hazard pointers, tagged pointers, GC ^aba-solutions-list

## Суть проблемы

```
Горутина 1: загрузила head → указывает на элемент A (адрес 0x0A)
            ... засыпает ...

Горутина 2: Pop(A), Pop(B), Push(C)
            → аллокатор выделил C по тому же адресу 0x0A (переиспользование)

Горутина 1: просыпается
            CAS(&head, 0x0A, ...) → УСПЕХ! адрес совпал
            → но там уже элемент C, не A. Стек сломан.
```

CAS сравнивает **адреса**, не **содержимое**. Адрес 0x0A = 0x0A, хотя за ним совершенно другие данные. ^aba-cas-compares-addr

## Почему в Go не возникает

GC не освободит объект, пока на него есть хоть одна ссылка. Горутина 1 держит указатель на A → A не будет собран → аллокатор не переиспользует этот адрес → CAS корректно обнаружит изменение. ^aba-why-go-safe

**Возникает если**: пишете кастомный аллокатор на Go, или работаете в C/C++ где free() возвращает память немедленно. ^aba-go-custom-alloc

## Решения

**Hazard Pointers** — список "опасных" указателей. Если указатель в списке — нельзя освобождать память. Перед обращением — добавляешь в список, после — убираешь. ^aba-hazard-pointers

**Tagged Pointers** — в неиспользуемых битах адреса (например, верхние 16 из 64) хранится счётчик. При каждом обращении счётчик инкрементируется. CAS сравнивает адрес + счётчик → даже если адрес совпал, счётчик не совпадёт. ^aba-tagged-pointers

```
Адрес без тега:  0x000000000000_0A
Адрес с тегом:   0x0001_0000000000_0A  (тег=1)
После операции:  0x0002_0000000000_0A  (тег=2) → CAS не пройдёт
```

Используется в Boost (C++). Зависит от архитектуры (сколько бит доступно). ^aba-tagged-arch

**GC** — встроенный (как в Go) или локальный для структуры данных. Некоторые реализации пишут мини-GC специально для одной структуры. ^aba-gc-solution
