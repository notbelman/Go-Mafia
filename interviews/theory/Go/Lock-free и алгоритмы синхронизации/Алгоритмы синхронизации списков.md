- 4 уровня: грубая → тонкая → оптимистичная → ленивая синхронизация. Каждый увеличивает пропускную способность и сложность кода ^sync-levels
- Множество на отсортированном связанном списке как модельная структура. Метод find с двумя указателями (prev, curr) ^sync-model
- Аналогия с БД: блокировка таблицы → блокировка строк → оптимистичные транзакции ^sync-db-analogy

## Модельная задача

Множество (set) на отсортированном связанном списке. Операции: contains, add, remove. Инвариант: элементы по возрастанию, без дубликатов.

```
head(0) → 10 → 20 → 30 → 40 → nil
```

find(val) бежит двумя указателями (prev, curr) пока curr.value < val. ^sync-find

## 1. Грубая синхронизация (59→72 строки)

```go
type Set struct {
    mu   sync.Mutex
    head *Node
}
```

Один мьютекс на всё. Lock перед каждой операцией. Просто, но все горутины конкурируют за один мьютекс. ^sync-coarse

## 2. Тонкая синхронизация (72→85 строк)

Мьютекс в **каждом узле**. Итерация = hand-over-hand locking:

```
Lock(prev) → Lock(curr) → Unlock(prev) → prev=curr
→ Lock(curr.next) → Unlock(prev) → ...
```

Две горутины могут **одновременно** двигаться по списку если они на расстоянии друг от друга. ^sync-fine

**Удаление**: захватить prev + curr (2 мьютекса). Иначе аномалии: разрыв списка, потеря элементов. ^sync-fine-delete

**Добавление**: формально хватает 1 мьютекса, но на практике захватывают 2 (переиспользование find). ^sync-fine-add

## 3. Оптимистичная синхронизация (85→145 строк)

Итерация **без мьютексов** (только атомики). Мьютексы захватываются только для модификации. ^sync-optimistic-iter

Но между "нашёл элемент" и "захватил мьютекс" кто-то мог удалить/добавить. ^sync-optimistic-race

**Решение — валидация**: после захвата мьютексов пробежаться сначала списка → проверить что элементы ещё существуют и связь между ними цела. ^sync-optimistic-validate

```go
func (s *Set) Add(val int) bool {
    for {
        prev, curr := s.find(val)         // без мьютексов
        prev.Lock(); curr.Lock()           // захватили
        if s.validate(prev, curr) {        // повторный проход сначала
            // элементы на месте → добавляем
            break
        }
        prev.Unlock(); curr.Unlock()       // не валидно → заново
    }
}
```

## 4. Ленивая синхронизация (145→~130 строк)

Вместо повторного прохода — **флаг deleted** в каждом узле. ^sync-lazy-flag

Валидация: `!prev.dropped && !curr.dropped && prev.next == curr` ^sync-lazy-validate

```go
func (s *Set) validate(prev, curr *Node) bool {
    return !prev.dropped && !curr.dropped &&
           prev.getNext() == curr
}
```

**Важно**: внутри мьютексов всё равно нужны атомики для указателей — горутины бегают по списку без мьютексов (через атомики), поэтому модификация указателей должна быть атомарной. ^sync-lazy-atomics

Удаление: сначала `curr.dropped = true`, потом `prev.next = curr.next`. ^sync-lazy-delete-order
