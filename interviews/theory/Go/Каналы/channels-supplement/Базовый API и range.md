- 4 операции: `make(chan T, n)`, `ch <- v`, `v := <-ch`, `close(ch)` — всё, больше ничего нет
- второе значение `v, ok := <-ch` — ok=false когда канал закрыт И буфер пуст
- range по каналу = читает до закрытия, блокируется если пусто

## Четыре операции — и всё

```go
ch := make(chan int)    // создать
ch <- 42               // записать
v := <-ch              // прочитать
close(ch)              // закрыть
```

Казалось бы, максимально простой API. Но количество нюансов и тонкостей огромное. ^api-four-ops

## Второе значение при чтении

```go
v, ok := <-ch
// ok == true  → канал открыт, v = реальное значение
// ok == false → канал закрыт И буфер пуст, v = zero value
```

`ok=false` означает одновременно два условия: канал закрыт **И** буфер пуст. ^api-ok-semantics

**Важный нюанс с буферизированным каналом:** после close данные из буфера дочитываются с ok=true. Только когда буфер опустел — ok=false. ^api-ok-buffered

```go
ch := make(chan int, 2)
ch <- 10
ch <- 20
close(ch)

v1, ok1 := <-ch  // 10, true  ← данные из буфера!
v2, ok2 := <-ch  // 20, true  ← ещё данные
v3, ok3 := <-ch  // 0, false  ← буфер пуст, теперь false
```

## Range по каналу

```go
for v := range ch {
    fmt.Println(v)
}
```

Синтаксический сахар. Читает значения в цикле до тех пор, пока канал не закроют. ^api-range-sugar

Если данных нет — блокируется и ждёт. Если канал не закрыть — range не завершится никогда (утечка горутины). ^api-range-no-close-leak
