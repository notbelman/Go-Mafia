- hanging goroutines = горутины навсегда в waiting. Утечка памяти: горутина (стек) + канал (на него ссылается)
- кто закрывает: **пишущая сторона**. Если несколько писателей — тот, кто создал канал. Читатель **никогда**
- всегда ли закрывать: компромисс — overhead vs безопасность (код эволюционирует, другой разработчик посадит утечку)

## Утечка на читающей стороне

```go
func main() {
    ch := make(chan string)
    go func() {
        for v := range ch {  // ждёт закрытия
            fmt.Println(v)
        }
    }()
    ch <- "hello"
    // канал не закрыт → горутина в waiting НАВСЕГДА
    // утечка: горутина (стек) + канал (ссылка из горутины)
}
```

Решение: `close(ch)` когда нечего больше писать. ^leak-reader-pattern

Утечка горутины — это утечка памяти: горутина держит стек, а стек держит ссылку на канал. GC не может собрать ни горутину, ни канал. ^leak-memory-what

## Утечка на пишущей стороне (first-response-wins)

```go
func fastest() int {
    ch := make(chan int)
    for i := 0; i < 5; i++ {
        go func() { ch <- doWork() }()
    }
    return <-ch  // прочитали одно значение, вышли
    // 4 горутины навсегда заблокированы на записи
}
```

^leak-writer-frw

Решение 1: буферизированный канал `make(chan int, 5)` — все запишут в буфер и завершатся. ^leak-writer-fix-buf

Решение 2: неблокирующая запись (select + default). ^leak-writer-fix-select

## Правила закрытия

Закрывает **пишущая сторона** — она знает, когда данные закончились. ^close-rule-writer

Если несколько писателей — закрывает тот, кто создал канал и писателей (координатор). ^close-rule-coordinator

Читающая сторона **никогда** не закрывает: запись в закрытый канал = паника. ^close-rule-never-reader

## Всегда ли закрывать?

Если на канал никто не подписан (нет range, нет заблокированных горутин) — можно не закрывать, GC соберёт. ^close-always-gc

Но код эволюционирует: через месяц кто-то добавит range, а канал не закрывается → утечка. Безопаснее всегда закрывать. ^close-always-evolve
