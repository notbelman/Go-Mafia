- LRQ (Local Run Queue) — на каждом P, 256 слотов, lock-free. GRQ (Global Run Queue) — одна, под мьютексом
- LRQ = быстрый путь (без синхронизации). GRQ = fallback (когда LRQ переполнена или P недоступен)
- runnext — однокомпонентный LIFO перед LRQ: кэш-тёплая горутина выполнится первой
- почему 61: простое число → потоки проверяют GRQ в разные моменты → меньше contention на мьютексе
- при переполнении LRQ: **половина** LRQ + новая G уходят в GRQ

## Две очереди планировщика

У планировщика Go две структуры для хранения runnable-горутин: локальные очереди (по одной на каждый P) и одна глобальная очередь.

```
         ┌─── runnext (1, LIFO, кэш-тёплая)
         │
   P0 ───┼─── LRQ [G1 G2 G3 ... G256] (FIFO, lock-free)
         │
   P1 ───┼─── LRQ [G7 G8 ...]
         │
         └─── ...
         
   GRQ ─────── [Ga Gb Gc ...] (FIFO, под мьютексом, без лимита)
```

## LRQ — локальная очередь

Каждый P имеет свою LRQ. Размер: **256 горутин**. ^lrq-size

Синхронизация: **lock-free** для владельца (CAS для кражи другими). ^lrq-lockfree

Основной путь: `go func()` → runnext → LRQ текущего P. ^lrq-main-path

При переполнении: **половина** LRQ + новая G уходят в GRQ. ^lrq-overflow

**runnext** — специальный слот перед LRQ. Одна горутина. LIFO-семантика: только что созданная/разбуженная G попадает сюда и выполнится **следующей**. ^runnext-lifo

Зачем runnext: кэш-теплота — G, которая только что трогала данные, получит CPU пока кэши горячие. ^runnext-cache-warm

## GRQ — глобальная очередь

Одна на весь runtime. ^grq-one

Синхронизирована **мьютексом** (не lock-free). Без ограничения размера. ^grq-mutex

**Когда горутина попадает в GRQ:**
- LRQ текущего P переполнена (>256) — половина уходит в GRQ ^grq-when-overflow
- после syscall: G хочет вернуться в свой P, но он недоступен ^grq-after-syscall
- после netpoll: разбуженная G, если P недоступен ^grq-after-netpoll
- sysmon вытесняет G из runnext (fairness) ^grq-sysmon-fairness

**Когда P смотрит в GRQ:**
- каждый **61-й тик** планирования (`schedtick % 61 == 0`) ^grq-check-61
- когда LRQ пуста и work stealing не помог ^grq-check-empty

## Сравнение

^bc70b2

```
              LRQ                    GRQ
Количество    по одной на P          одна на runtime
Размер        256                    без лимита
Синхронизация lock-free              мьютекс
Скорость      быстро                 медленно (contention)
Когда         основной путь          fallback
```

## Почему 61

Простое число. Потоки проверяют GRQ в разные моменты → меньше вероятность столкновения на мьютексе. Не слишком часто (contention), не слишком редко (горутины голодают). ^why-61
