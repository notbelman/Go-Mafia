## Два подхода к балансировке нагрузки

Проблема: у одних P горутин много, у других — пусто. Как распределить? ^sharing-vs-stealing-problem

## Work Sharing (раздача)

Потоки **проактивно** делятся работой с другими. ^sharing-def

```
P0 [G1 G2 G3 G4 G5]  →  "У меня много, отдам кому-то"
P1 [G6]                   ← получает G4, G5
P2 []                     ← может тоже получить
```

**Проблемы:**
- **Кому отдавать?** Нужно знать загрузку всех P → трекинг размеров очередей → дополнительная синхронизация ^9c1038
- **Когда отдавать?** Слишком часто — overhead. Слишком редко — дисбаланс ^8e3044
- **Сколько отдавать?** Угадать сложно — можем отдать тому, у кого и так хватает ^aab2a7
- Постоянная синхронизация даже когда все P загружены равномерно (= зря)
^sharing-problems

## Work Stealing (кража)

Потоки **крадут** работу у других **только когда им нечего делать**. ^stealing-def

```
P0 [G1 G2 G3 G4 G5]      (работает, никто не мешает)
P1 []  →  "Пусто, украду у кого-то"  →  берёт половину у P0
P0 [G1 G2]    P1 [G3 G4 G5]
```

**Преимущества:**
- синхронизация **только при краже** — когда P и так простаивает
- не нужно трекать загрузку всех P
- рандомный выбор жертвы — просто и достаточно хорошо
- нулевой overhead когда все P заняты
^stealing-advantages

## Почему Go выбрал stealing

```
                Work Sharing           Work Stealing
Когда           постоянно              только при простое
Overhead        высокий                низкий
Синхронизация   постоянная             только при краже
Сложность       кому/сколько/когда     рандом + половина
Баланс          лучше в теории         достаточно хорош
```
^sharing-vs-stealing-comparison

В Go: P крадёт **половину** из рандомного P, **4 попытки**. Если не нашёл — GRQ → netpoll → засыпает. Детали — в карточке Work stealing. ^sharing-vs-stealing-go-details
