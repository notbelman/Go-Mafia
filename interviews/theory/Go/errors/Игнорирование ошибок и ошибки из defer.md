- игнорирование ошибки должно быть **явным**: `_ = f.Close()`, не просто `f.Close()` ^explicit-ignore
- без явного `_` у читателя вопрос: забыл или проигнорировал? (холиварно, но рекомендация коммьюнити) ^explicit-ignore
- в defer тоже: `defer func() { _ = f.Close() }()` — явное игнорирование ^defer-explicit-ignore
- можно в defer **подменить** возвращаемую ошибку: если err == nil, вернуть ошибку от Close() ^defer-err-replace
- декорирующие функции-обёртки предпочтительнее засорения бизнес-логики побочными эффектами ^decorator-pref

## Явное vs неявное игнорирование

```go
// ❌ неявно — забыл или проигнорировал?
f.Close()

// ✅ явно — читатель понимает: осознанное решение
_ = f.Close()
```

Явное `_ =` — сигнал читателю: разработчик осознанно решил не обрабатывать эту ошибку. ^explicit-ignore

## В defer

```go
// ❌ неявное игнорирование в defer
defer f.Close()

// ✅ явное
defer func() { _ = f.Close() }()
```

То же правило применяется и внутри defer. ^defer-explicit-ignore

## Подмена ошибки в defer

```go
func ReadFile(path string) (result []byte, err error) {
    f, err := os.Open(path)
    if err != nil {
        return nil, err
    }
    defer func() {
        closeErr := f.Close()
        if err == nil {  // основная операция прошла без ошибок
            err = closeErr  // подменяем на ошибку закрытия
        }
    }()

    return io.ReadAll(f)
}
```

Если основная работа прошла хорошо, но Close() упал — пользователь получит ошибку. Если уже была ошибка — не перезатираем. Работает через именованный возврат `err`. ^defer-err-replace

## Побочные эффекты в defer

```go
// Можно, но засоряет бизнес-логику
defer func() {
    if err != nil {
        log.Error("operation failed", err)
        metrics.Inc("errors_total")
    }
}()
```

Лектор рекомендует: для телеметрии (логи, метрики от ошибок) лучше декорирующие функции-обёртки, которые не влияют на бизнес-логику. ^decorator-pref
