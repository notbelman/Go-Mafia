- когда функция/библиотека не принимает ctx — оборачиваем: горутина + буферизированный канал + select ^wrap-pattern-overview
- канал результата ОБЯЗАТЕЛЬНО буферизированный (cap=1), иначе утечка горутины ^wrap-buffered-required
- стандартный паттерн для legacy-кода и библиотек без поддержки контекстов ^wrap-usecase

## Паттерн

```go
func fetchWithContext(ctx context.Context) (string, error) {
    ctx, cancel := context.WithTimeout(ctx, 3*time.Second)
    defer cancel()

    resultCh := make(chan string, 1)  // буферизированный!

    go func() {
        result := legacyFetch()  // не умеет работать с ctx
        resultCh <- result
    }()

    select {
    case result := <-resultCh:
        return result, nil
    case <-ctx.Done():
        return "", ctx.Err()
    }
}
```

## Почему канал буферизированный

```go
resultCh := make(chan string)  // ПЛОХО: без буфера

// Если ctx.Done() сработал первым:
// - select выбрал case <-ctx.Done(), функция вернулась
// - горутина закончила legacyFetch(), пытается записать в resultCh
// - никто не читает → горутина заблокирована навечно → УТЕЧКА

resultCh := make(chan string, 1)  // ХОРОШО: запись не заблокируется
```

С буфером 1 горутина запишет результат даже если никто не читает, и спокойно завершится. ^wrap-why-buffered

Конкретный сценарий утечки: ctx.Done() срабатывает раньше, select возвращает ошибку, функция выходит — небуферизированный канал остаётся без читателя, горутина с legacyFetch() зависает навечно. ^wrap-leak-scenario

## Когда нужен этот паттерн

В подавляющем большинстве случаев сетевые библиотеки и стандартная библиотека принимают ctx. Паттерн нужен для: legacy-кода без контекстов, сторонних библиотек, блокирующих вызовов (файловый I/O). ^wrap-when-needed
