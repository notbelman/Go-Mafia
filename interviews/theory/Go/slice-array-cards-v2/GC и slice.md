- GC может собрать underlying array даже если **дескриптор жив**, но к данным по ptr **никто не обращается**
- любое обращение к элементу `s[i]` → array остаётся в памяти
- `runtime.KeepAlive(s)` — явный запрет GC собирать объект раньше этой точки
- инкрементальное копирование: два массива + перенос по 2 элемента на каждый push → **O(1) worst-case**

## GC собирает array если данные не используются

Go видит: дескриптор жив, но обращений к `s[i]` нет — только к `len(s)`. Значит, underlying array можно собрать. ^gc-slice-collect-rule

```go
s := make([]int, 1<<27)  // ~1 ГБ
runtime.GC()
fmt.Println(len(s))       // 134217728 — len доступен
// Но память уже освобождена! GC понял, что к данным никто не лезет.
```

^469a4f

## Когда НЕ соберёт

Любое обращение к элементу `s[i]` удерживает underlying array в памяти. ^gc-slice-keep-rule

```go
s := make([]int, 1<<27)
runtime.GC()
fmt.Println(s[0])  // обращение к данным → array жив
```

^2350b2

## runtime.KeepAlive

`runtime.KeepAlive(s)` — явный запрет GC собирать объект раньше этой точки. ^gc-keepalive-what

`KeepAlive` должен стоять **после** использования, не до GC. ^gc-keepalive-placement

```go
p := &s[0]
runtime.GC()
fmt.Println(*p)           // используем данные
runtime.KeepAlive(s)      // KeepAlive ПОСЛЕ использования — гарантирует что s жив до этой строки
```

^090ef8

## Инкрементальное копирование

Проблема: при реаллокации большого среза — всплеск latency (копирование миллионов элементов разом). В realtime-системах недопустимо. ^gc-incr-problem

Алгоритм: держим два массива. На каждый push — переносим 2 элемента из старого в новый. К моменту заполнения — новый готов. ^gc-incr-algorithm

```
push(5) → добавили 5, перенесли элементы [0],[1] в новый
push(6) → добавили 6, перенесли элементы [2],[3] в новый
...
```

^c5c535

Трейдофф: 2x память, чуть больше работы на каждый push, зато O(1) worst-case вместо амортизированной O(1). ^gc-incr-tradeoff
