Система бронирования отелей. Ключевая особенность — **транзакционность** (деньги, бронирования, нельзя пустить двоих в один номер).

## Правило Балуна

"Когда проектируете систему, связанную с деньгами, бронированием, заказом, покупками — это **всегда** транзакции. Всегда транзакционные реляционки, всегда синхронная репликация."

## Функциональные требования

- Бронирование отелей для гостей
- Отмена и подтверждение бронирования
- Листинг отелей и комнат в отеле
- История бронирований и отмен
- Полнотекстовый поиск по характеристикам
- Добавление/удаление комнат, отелей администратором

## Нефункциональные требования

- DAU 30 млн
- 300.000 отелей
- Availability стандартная
- **Strong consistency** — нельзя двум клиентам забронировать один номер
- 1 бронирование в месяц на пользователя
- 10 просмотров отелей в день на пользователя
- Геораспределённости нет
- **Сезонность есть** (лето — курорты, зима — горнолыжные)

## ASR: strong consistency

Не read-intensive, не real-time. Это **система про согласованность данных.** Один номер — один постоялец. Никаких гонок, никаких двойных бронирований. Это определяет выбор базы (реляционка), репликации (синхронная), паттерна транзакций (saga).

## Два типа акторов

**Клиент (гость):** ищет отели, бронирует, отменяет, смотрит историю.

**Админ (администратор отеля):** добавляет/удаляет отели, управляет комнатами (закрыть на ремонт, изменить количество). Это **не** наш сотрудник, это владелец отеля.

**Два API Gateway:** разные роли, разные права. Один балансер роутит в нужный gateway.

```
Client → LB (Nginx) → API Gateway (client)
Admin  → LB (Nginx) → API Gateway (admin)
```

Балун: "Можно один gateway? Можно. Но я бы вынес на два — разные пользователи, разные точки входа."
