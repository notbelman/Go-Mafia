Здесь расчёт трафика **критически важен** — определяет, можно ли гнать данные через балансер.

## RPS

Соотношение read/write = 1:1. Из 6 обращений: 3 на запись, 3 на чтение.

```
RPS (write) = 50.000.000 × 3 / 86400 ≈ 1736
RPS (read)  = 50.000.000 × 3 / 86400 ≈ 1736
```

По RPS — ничего страшного. Но RPS — не главная метрика здесь.

## Трафик (главная метрика!)

Средний файл — 1 МБ. Каждый запрос передаёт ~1 МБ данных.

```
Traffic (write) = 1736 × 1 МБ ≈ 1736 МБ/с ≈ 2 ГБ/с
Traffic (read)  = 1736 × 1 МБ ≈ 2 ГБ/с
Итого:          ≈ 4 ГБ/с
```

**4 ГБ/с — это много.** Балансер может это пропустить (в Яндексе через один инстанс гоняли 2 ГБ/с и "пришли из команды балансеров и сказали: вы что творите?"). Но это не оптимально.

## Когда трафик слишком большой для балансера

Если бы было 200 ГБ/с (как у Google Cloud Storage) — гнать через балансер дорого. Каждый хоп требует CPU и RAM. На таком трафике — нужно минимизировать количество хопов.

**Решения для огромного трафика:**
- **Редирект:** клиент обращается к API → получает URL upload-сервера → грузит напрямую, минуя балансер
- **Клиентская балансировка:** клиент сам знает, куда грузить

В нашем случае (4 ГБ/с) — можно оставить балансер (Nginx). Но на интервью стоит проговорить этот трейдофф.

## Хранение (на 3 года)

```
2 ГБ/с × 86400 = 172 ТБ/день
172 ТБ × 365 × 3 = ~188 ПБ за 3 года
```

С учётом сжатия (×2): **~94 ПБ.** Плюс дедупликация (трудно оценить точно). Это очень много. Часть — на SSD (hot storage), часть — на HDD (cold storage).

Балун: "Метабаза — копейки. Вот эти чанки — вот где основные объёмы."

## Что следует из расчётов

1. **Трафик 4 ГБ/с** — балансер справится, но на грани
2. **188 ПБ за 3 года** — нужна стратегия хранения (hot/cold, дедупликация, сжатие)
3. **RPS 1736** — не проблема, обычная нагрузка
4. Главный вызов — не RPS, а объём данных и трафик
