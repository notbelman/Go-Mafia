Репликация, шардирование, финальная схема.

## Stateless сервисы

**Nginx (LB):** несколько инстансов за DNS. Скейлится без проблем.

**Uploader / Downloader:** скейлятся горизонтально. Балун их разделил по CQRS: Uploader — mutable операции (загрузка, удаление, создание каталогов), Downloader — immutable (только чтение + разжатие).

## PostgreSQL: репликация

Балун обсуждал два варианта:

**Асинхронная master-slave:** быстрее, но при падении мастера — потеря последних данных. А если потеряли метаданные чанков — файл не соберёшь. **Это плохо для файлового хранилища.**

**Синхронная master-slave:** медленнее, но гарантия: если мастер подтвердил запись — данные есть на реплике. При падении мастера — ничего не потеряли.

Балун: "Можно начать с асинхронной — трафик метаданных копеечный, синхронная не будет медленной. Но если мастер упал с асинхронной — можем потерять хвост данных и не соберём файл."

**Итог:** синхронная или master-master async (как в ленте). Зависит от того, насколько допустима потеря.

## PostgreSQL: шардирование

**По user_id.** Почему не по file_id: файлы одного пользователя — дерево (parent_file_id). Если шардировать по file_id — при обходе дерева каталогов будем прыгать по шардам. Это медленно.

По user_id — все файлы пользователя на одном шарде. Обход дерева — один шард, один запрос.

**chunk_per_file** тоже нужно шардировать по user_id → добавляем user_id в таблицу (денормализация).

## S3: масштабирование

Скейлится без проблем. Просто разносим по хостам. Нет реляционных связей, нет транзакций. Каждый чанк — независимый объект.

**Hot/cold storage:** часто запрашиваемые файлы — на SSD, редко — на HDD. Можно определять по дате последнего обращения.
## Итоговые решения и почему

| Решение | Почему |
|---|---|
| Чанки по 1 МБ | Средний файл 1 МБ, хорошо ложится на диск |
| Разбиение на клиенте | Восстановление загрузки, клиент знает индексы |
| Сжатие на сервере | Не греем клиентские устройства |
| CAS (хэш = ключ) | Дедупликация бесплатно |
| S3 для чанков | Дёшево, масштабируется, нет сложных запросов |
| PostgreSQL для метаданных | Реляционные связи (дерево каталогов), транзакции |
| Отдельные Uploader/Downloader | CQRS, разная нагрузка, независимое масштабирование |
| Удаление от обратного | Безопасно при дедупликации, нет race condition |
| Шардирование по user_id | Дерево каталогов на одном шарде |

## Что Балун говорил про Google Drive

"Казалось бы, пару компонентов, но тем не менее — много нюансов: как хранить, как добавлять, как удалять." Каждая система в курсе подсвечивает разные приёмы: здесь — работа с большими данными, дедупликация, коллизии хэшей.
