Хранилище, где адрес (ключ) файла = хэш его содержимого. Одинаковый контент → одинаковый ключ → храним один раз.

## Как работает

Обычное хранилище: файл называется `photo.jpg`, `backup_2024.zip` — имя не связано с содержимым. CAS: файл называется `a3f2b8c9d1e4...` — это хэш содержимого.

**Запись:** приходит чанк → считаем хэш → проверяем, есть ли чанк с таким хэшем → если есть и контент совпадает — не записываем, просто ссылаемся → если нет — записываем.

**Чтение:** знаем хэш → идём в хранилище → достаём по хэшу.

## Дедупликация

Мем "котик" разошёлся, 10.000 пользователей сохранили его в свой Google Drive. Без CAS: 10.000 копий одного файла. С CAS: один чанк в S3, 10.000 ссылок на него в метабазе.

Для отслеживания: когда на чанк ссылок ноль — можно удалить. Подсчёт ссылок через таблицу `chunk_per_file`.

**Важно:** нет модифицирующих операций. Если бы файлы можно было редактировать — пришлось бы делать copy-on-write (при изменении создаём копию, а не меняем оригинал). В Google Drive файлы неизменяемые (загрузил и всё), поэтому CAS работает чисто.

## Проблема: коллизии хэшей

Два разных чанка → одинаковый хэш. Редко, но возможно.

**Обнаружение:** при совпадении хэша — сравниваем побайтово содержимое. Если содержимое разное — коллизия.

**Решение:** те же подходы, что и в хэш-таблицах:
- **Double hashing** — считаем второй хэш другой функцией, записываем в дополнительный бакет
- **Цепочки (chaining)** — но в S3 непонятно, куда вешать связанный список
- **Линейное пробирование** — не подходит, нет линейного адресного пространства

Балун: "Когда вы смотрите на подобные задачи, это те же самые алгоритмы и структуры данных. В system design не придумано каких-то отдельных решений. Основополагающие подходы используются везде."

## Где ещё встречается

Git (объекты адресуются SHA-1 хэшем), Docker (слои образов), любые системы дедупликации бэкапов, IPFS.
