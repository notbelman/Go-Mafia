Кто следит за зависшими заказами. Что если пользователь не оплатил, а комната уже задекрементирована.

## Проблема

Заказ в статусе WAITING_PAYMENT. Комната уже "зарезервирована" (count уменьшен). Пользователь ушёл пить чай и не вернулся. Без контроля — комната навечно заблокирована.

## Таблица processing_order

```
processing_order:
  order_id       — какой заказ в процессе
  created_at     — когда начался процесс
```

**Зачем отдельная таблица, а не фильтр по статусу в order?**

Можно по статусу (`WHERE status = 'WAITING_PAYMENT'`), но:
- Индекс на статус — неоптимально (мало уникальных значений, плохая селективность)
- processing_order — маленькая таблица, быстрый полный скан
- Локальная в каждом шарде (если шардируем orders по user_id)

## Воркер таймаутов

Периодически (раз в минуту) проходит по processing_order:

1. Смотрит created_at: если прошло > N минут (например, 20) — таймаут
2. Запускает компенсирующую транзакцию через Kafka
3. Hotel Service инкрементирует available_room_type обратно
4. Order Service переводит статус → CANCELLED
5. Удаляет запись из processing_order

## Жизненный цикл processing_order

```
Создание заказа     → INSERT в processing_order
Оплата прошла       → DELETE из processing_order, статус → BOOKED
Оплата не прошла    → DELETE из processing_order, компенсация, статус → CANCELLED
Таймаут             → DELETE из processing_order, компенсация, статус → CANCELLED
```

## При шардировании

Если orders шардированы по user_id → processing_order локальная в каждом шарде. Воркер проходит мультисканом по всем шардам. Это не проблема — таблица маленькая.
