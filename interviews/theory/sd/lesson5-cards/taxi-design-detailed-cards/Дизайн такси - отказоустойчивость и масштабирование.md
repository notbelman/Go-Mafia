Что происходит при падении каждого компонента. Как скелить.

## Отказоустойчивость: stateless сервисы

**Load Balancer, API Gateway (оба)** — несколько инстансов. Один упал → балансер переключает. Без проблем.

**Geo Service, Ride Service, Matching Service, History Service** — несколько инстансов. Один упал → ретрай, попадаем на другой. Без проблем.

## Отказоустойчивость: stateful компоненты

**Matching Service (стейт матчинга)**

Matching Service сам stateless, но рядом — in-memory хранилище с matching_status. Если инстанс Matching Service упал → другой инстанс читает стейт из хранилища → продолжает опрос водителей. Без хранилища — пассажиру пришлось бы заново заказывать.

**Ride Service (стейт поездки)**

Аналогично: рядом — ride storage. Инстанс упал → другой читает стейт → продолжает вести поездку. Без этого — таксист и пассажир в подвешенном состоянии.

**Notification Service (WebSocket-соединения)**

Инстанс упал → клиент теряет WebSocket → reconnect на другой инстанс → регистрируется заново. Короткий разрыв, но восстановление автоматическое.

## Отказоустойчивость: Tarantool (позиции водителей)

**Потеря данных — не фатальна.** Водители шлют координаты каждые 5 секунд. Если Tarantool упал и потерял данные → через 5-10 секунд данные перенальются автоматически. Система самовосстанавливающаяся.

**Но недоступность — фатальна.** Если Tarantool недоступен несколько минут → матчинг не работает, поездки не трекаются. Поэтому: **WAL + репликация** обязательны. WAL для быстрого восстановления, репликация для переключения на реплику при падении.

## Отказоустойчивость: Tarantool (стейт поездок/матчинга)

Здесь **потеря данных критична** — теряем активные поездки и матчинги. WAL + репликация обязательны. Хоть и in-memory — данные не должны теряться.

## Отказоустойчивость: ClickHouse (история)

Async-репликация (дефолт). Потеря записи об истории — неприятно, но не фатально.

## Масштабирование: Tarantool (позиции)

Шардирование по **geohash**. Не просто случайное — **умное**: соседние квадратики на одном шарде. Почему: при поиске ближайших часто нужно проверить соседние ячейки. Если они на одном шарде — один запрос вместо нескольких.

## Масштабирование: Tarantool (стейт)

Шардирование по **user_id**. Мне нужен **мой** стейт поездки / матчинга. Не нужны чужие стейты в одном запросе.

## Масштабирование: Notification Service

Stateful — нельзя просто добавить инстансов. Три подхода (fan-out, Service Discovery, адрес в метаинформации). Подробно в карточке Notification Service.

## Масштабирование: остальное

- **API Gateway** — stateless, добавляем инстансы
- **Matching / Ride / History** — stateless, добавляем инстансы
- **ClickHouse** — шардирование + репликация (встроенное)
- **Kafka (если используется)** — заранее много партиций
## Итоговые решения и почему

| Решение | Почему |
|---|---|
| Два API Gateway | Разные клиенты, разные права |
| Tarantool для позиций | 3300 RPS апдейтов → только in-memory |
| Geohash (5 символов) | Быстрый поиск без перестроения деревьев |
| Base / active разделение | Matching не должен находить занятых |
| Синхронный перебор | Хороший UX для водителей, укладываемся в 1 мин |
| WebSocket для уведомлений | Много разнородных событий, стриминг |
| Прикапывание стейта | Matching и Ride не должны терять сессии |
| ClickHouse для истории | Append-only, OLAP, не нужны транзакции |
| Отдельный Ride Service | Не грузить Matching ведением поездки |

## Что Балун говорил про такси vs ленту

Лента = read-intensive (заточка на чтение). Такси = **real-time** (постоянный поток данных). "Здесь нет разделения на чтение/запись. Здесь я сразу выделил, что мне нужно постоянно много обновлять координат."
