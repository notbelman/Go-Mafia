Гарантированная доставка события в очередь через вспомогательную таблицу в той же БД.

## Проблема

Сервис должен сохранить заказ в БД **и** отправить событие в очередь (Kafka). Что если БД сохранила, а очередь недоступна? Данные в БД есть, а событие потеряно. Кто подписан — не узнает.

Это не 2PC — нам не нужна синхронность. Нам нужна гарантия: если записал в БД, событие **когда-нибудь** дойдёт до очереди.

## Решение

В **одной транзакции** с основной записью сохраняем событие в таблицу `outbox`:

```
BEGIN;
  INSERT INTO orders (...) VALUES (...);
  INSERT INTO outbox (event_type, payload) VALUES ('order_created', ...);
COMMIT;
```

Одна транзакция → атомарно: либо оба INSERT прошли, либо оба откатились.

## Доставка

Рядом поднят **воркер** (отдельный поток/процесс). Он периодически сканирует таблицу `outbox`, отправляет события в очередь, после успешной отправки — удаляет из `outbox`.

Очередь недоступна? Ок, событие лежит в `outbox`. Очередь поднялась → воркер отправит. Гарантия доставки — at-least-once.

## Важно

Пользователю отвечаем **сразу** после коммита entity + outbox. Доставка в очередь — асинхронная. Не ждём очередь.

## Связь
- [[2PC (Two-Phase Commit)]] — 2PC для синхронной гарантии, outbox для асинхронной
- [[Transaction Inbox]] — зеркальный паттерн на стороне получателя
- [[Idempotency (идемпотентность)]] — воркер может отправить дважды → получатель должен быть идемпотентным
