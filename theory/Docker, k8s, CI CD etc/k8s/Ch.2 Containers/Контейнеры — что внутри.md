- Контейнер = **обычный процесс** в host OS, изолированный через Linux kernel: **namespaces** (что видит) + **cgroups** (сколько потребляет) + **capabilities/seccomp** (что может делать)
- Container vs VM: контейнер — один процесс с изолированным окружением, без guest OS. VM — полная ОС с отдельным ядром. Контейнер легче, быстрее, но изоляция слабее (общее ядро)
- **Image layers:** образ = стек read-only слоёв + один read/write слой сверху (CoW). Слои переиспользуются между образами. Удаление файла не уменьшает размер — файл маркируется как удалённый
- Container Runtime: **containerd** (default с K8s 1.24+), CRI-O, Docker. K8s общается через **CRI** (Container Runtime Interface). OCI стандартизирует формат образов

## Container vs VM

```
VM:                                Container:
┌──────────────┐                   ┌──────────────┐
│   App A      │                   │   App A      │
│   Libraries  │                   │   Libraries  │
│   Guest OS   │  ← отдельное ядро │              │  ← нет guest OS
│   Kernel     │                   │              │
├──────────────┤                   ├──────────────┤
│  Hypervisor  │                   │  Host OS     │  ← общее ядро
│  Host OS     │                   │  Kernel      │
│  Hardware    │                   │  Hardware    │
└──────────────┘                   └──────────────┘

VM:        сильная изоляция, свой kernel, но тяжёлая (GB RAM, минуты старт)
Container: слабее изоляция (общий kernel), но лёгкий (MB RAM, секунды старт)
```
^ci-vs-vm

**Безопасность:** VM — баг в guest kernel не затрагивает другие VM. Container — баг в shared kernel может затронуть все контейнеры. Полная изоляция = только разные физические машины. ^ci-security-tradeoff

## Linux Namespaces — ЧТО видит процесс

```
Namespace       Что изолирует
─────────────────────────────────────────────
mnt             Файловая система (mount points)
pid             Дерево процессов (свои PID)
net             Сетевые интерфейсы, порты, стек
ipc             IPC (shared memory, message queues)
uts             Hostname, domain name
user            User/Group IDs
time            Смещение системных часов
cgroup          Корневая директория cgroups

Контейнер = процесс с выделенным namespace каждого типа
PID 1 внутри контейнера = PID 3175580 на хосте (разные PID namespaces)
```
^ci-namespaces

**Namespace sharing:** контейнеры в одном Pod'е K8s разделяют net и uts namespaces → видят одни сетевые интерфейсы, один hostname. Но у каждого свой mnt (своя файловая система). ^ci-namespace-sharing

## Cgroups — СКОЛЬКО потребляет процесс

```
Namespaces: ЧТО видит процесс (изоляция ресурсов)
Cgroups:    СКОЛЬКО может использовать (лимиты ресурсов)

Контролируют:
  CPU       → --cpus="0.5" (половина ядра)
             → --cpuset-cpus="1,2" (конкретные ядра)
  Memory    → --memory="100m" (максимум 100MB)
  Disk I/O  → ограничение пропускной способности
  Network   → ограничение bandwidth

Без лимитов: контейнер может забрать все ресурсы хоста
→ в K8s: requests (гарантия) и limits (потолок) через Pod spec
```
^ci-cgroups

## Image Layers и Copy-on-Write

```
Container Image:
  ┌─────────────────────────┐
  │ Read/Write layer (CoW)  │  ← изменения контейнера
  ├─────────────────────────┤
  │ ENTRYPOINT ["node"...]  │  ← слой из Dockerfile
  │ COPY html/ /html        │  ← слой из Dockerfile
  │ COPY app.js /app.js     │  ← слой из Dockerfile
  ├─────────────────────────┤
  │ node:23-alpine layers   │  ← слои base image
  │ alpine layers           │
  └─────────────────────────┘

Каждая инструкция Dockerfile = новый слой
Слои read-only, переиспользуются между образами
Изменение файла → копируется в R/W слой (CoW)
Удаление файла → маркируется в R/W слой, НЕ уменьшает размер
```
^ci-layers

## Безопасность контейнеров

```
Capabilities (Linux):
  Вместо полного root — гранулярные привилегии
  CAP_NET_ADMIN     → сетевые операции
  CAP_NET_BIND_SERVICE → привязка к портам < 1024
  CAP_SYS_TIME      → изменение системных часов
  → Docker/K8s дропают лишние capabilities по умолчанию
  → принцип least privilege

Seccomp:
  Фильтрация отдельных syscalls через JSON-профиль
  → контейнер может делать только разрешённые syscalls

AppArmor / SELinux:
  Mandatory Access Control (MAC)
  → дополнительный слой защиты поверх capabilities

Privileged container:
  --privileged → ПОЛНЫЙ доступ к хосту, все syscalls
  → использовать ТОЛЬКО когда необходимо и доверяешь коду
```
^ci-security

## Container Runtime в Kubernetes

```
Docker → containerd → CRI-O

K8s 1.24+: Docker runtime удалён (dockershim deprecated)
Теперь: containerd или CRI-O через CRI (Container Runtime Interface)

OCI (Open Container Initiative):
  Image Spec  → стандартный формат образов
  Runtime Spec → стандартный интерфейс запуска

→ Образ собранный через Docker работает на containerd/CRI-O
→ Выбор runtime не влияет на приложение
```
^ci-runtime

## Портабельность: ограничения

```
Образ НЕ содержит ядро Linux → зависит от ядра хоста
  → если приложение требует kernel module → может не работать на другом хосте
  → x86 образ НЕ запустится на ARM без эмуляции

Образ СОДЕРЖИТ всё остальное:
  → библиотеки, бинарники, конфиги
  → одинаковый результат на dev и prod (если kernel совместим)
```
^ci-portability
