### Shared Memory (Java, C++, C#):
Потоки общаются через общую память + защищают её локами/мьютексами. ^shared-memory-def
```
  Thread1 ──┐
            ├──→ [Shared Memory] ←── Lock/Mutex
  Thread2 ──┘
```

Проблемы: race conditions, deadlocks, сложная синхронизация. ^shared-memory-problems

### CSP — Communicating Sequential Processes (Go):
Горутины общаются через каналы, не делят память напрямую. ^csp-def

  ```
  Goroutine1 ──→ [Channel] ──→ Goroutine2
  ```

Данные копируются в канал → владение передаётся → нет общего состояния. ^csp-ownership

---

**Главный принцип Go:** ^go-main-principle

> "Don't communicate by sharing memory; share memory by communicating."

Вместо: защищать общую память локами
Делаем: передавать данные через каналы

---

**CSP придумал Tony Hoare в 1978.** ^csp-author

Go не единственный — Erlang тоже использует message passing (Actor model, похоже на CSP). ^csp-erlang

---

**Go всё равно поддерживает shared memory:**
`sync.Mutex`, `sync.RWMutex`, `sync/atomic` — когда каналы избыточны (например, счётчики). ^go-shared-memory-support

## Когда каналы vs мьютексы

| Задача | Инструмент |
|:-------|:-----------|
| Разделяемое состояние (кэш, счётчик) | Мьютекс / atomic |
| Передача владения данными | Канал |
| Распределение вычислений (fan-out) | Канал |
| Получение асинхронного результата | Канал |
| Простой флаг (ready/done) | atomic или chan struct{} |
^channels-vs-mutex-table

Каналы не заменяют мьютексы — они для разных задач. Если нужно защитить общий участок памяти, канал будет избыточным и медленным. Если нужно передать данные между горутинами — мьютекс потребует лишней сложности. ^channels-vs-mutex-principle
