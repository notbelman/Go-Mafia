- пул переиспользуемых объектов: `Get` (забрать/создать) и `Put` (вернуть)
- **синхронизирован** — безопасен из разных горутин ^5c8d35
- после `Get` объект нужно **реинициализировать** (могут остаться чужие данные)
- GC может забирать объекты из пула (защита от бесконечного роста)

---
[[memory Flashcards - sync_pool]]
## Идея

Когда плодите огромное количество однотипных объектов: вместо создания/уничтожения — переиспользование. Меньше аллокаций → меньше нагрузка на аллокатор и GC.

## API

```go
type sync.Pool struct {
    New func() any  // конструктор: вызывается если пул пуст
}

pool.Get() any      // забрать объект (или создать через New)
pool.Put(x any)     // вернуть объект в пул
```
^pool-api

## Пример с обёрткой (типизация)

```go
type PersonPool struct { pool sync.Pool }

func NewPersonPool() *PersonPool {
    return &PersonPool{
        pool: sync.Pool{
            New: func() any { return &Person{} },
        },
    }
}

func (p *PersonPool) Get() *Person  { return p.pool.Get().(*Person) }
func (p *PersonPool) Put(v *Person) { p.pool.Put(v) }
```
^pool-typed-wrapper

## Использование

```go
pool := NewPersonPool()

for i := 0; i < 1000000; i++ {
    person := pool.Get()

    // ⚠️ ОБЯЗАТЕЛЬНО реинициализировать!
    person.Name = "Alice"
    person.Age = 30

    // ... используем ...

    pool.Put(person)  // возвращаем в пул
}
```
^pool-usage-reinit

## Жизненный цикл

```
Get() → пул пуст → New() создаёт объект → используем → Put() → объект в пуле
Get() → пул не пуст → достаём готовый → реинициализируем → используем → Put()
```
^pool-lifecycle

GC может забирать объекты из пула (не сразу, через несколько циклов сборки). Это защита от бесконечного роста пула. ^pool-gc-eviction

Не гарантируется, что Put-объект переживёт следующую сборку мусора. ^pool-no-guarantee

## Когда использовать

Массовое создание однотипных объектов: HTTP-реквесты, сообщения, буферы. Бенчмарк показывает существенный выигрыш при большом количестве аллокаций. ^pool-use-cases
