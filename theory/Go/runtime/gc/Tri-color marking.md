- **Tri-color marking** — алгоритм маркировки живых объектов. **White** = не помечен (кандидат на удаление), **Grey** = обнаружен но ссылки не просканированы (фронт волны), **Black** = полностью просканирован. Три цвета нужны для concurrent режима: без grey невозможно понять какой объект обработан, а какой нет пока мутаторы меняют указатели
- В чистом виде требует **STW** — иначе мутатор может создать ситуацию «чёрный → белый» (invariant нарушен → GC удалит живой объект). Go concurrent режим требует доп. механизмов: **[[Write barrier]]** (корректность) и **[[Mark Assist]]** (скорость)
- **Strong invariant** (Go до 1.8): чёрный НЕ может указывать на белый. **Weak invariant** (Go 1.8+): чёрный МОЖЕТ указывать на белый, НО белый достижим через серый. Hybrid write barrier поддерживает weak → нет rescan стеков → паузы короче
- **Go 1.26+ ([[Green Tea GC (new)]]):** tri-color **инварианты** и **цвета** те же. Изменился unit работы: work list хранит страницы 8 KiB (FIFO), а не объекты (LIFO). Обход внутри страницы в memory order

## Основа

Алгоритм маркировки живых объектов. Три цвета = состояние объекта.

**Цвета:**

White — не помечен, кандидат на удаление. ^tc-white

Grey — обнаружен, но ссылки ещё не просканированы (фронт волны обхода). ^tc-grey

Black — просканирован, все ссылки обработаны. ^tc-black

**Зачем три цвета, а не два?** Для concurrent маркировки. Grey означает «обнаружен, но дети ещё не просканированы». Без него невозможно понять, какой объект уже полностью обработан, а какой нет, пока мутаторы параллельно меняют указатели. Два цвета хватило бы только для STW-сборщика. ^tc-why-three

**Алгоритм:**

Обход можно параллелить: каждый поток забирает элемент из очереди и идёт в глубину. ^tc-parallel

**Инварианты (гарантии корректности):**

**Strong tri-color invariant**: чёрный объект НЕ может указывать на белый. Go использовал до 1.8 (Dijkstra barrier). ^tc-strong

**Weak tri-color invariant**: чёрный МОЖЕТ указывать на белый, НО белый должен быть достижим через серый. Go 1.8+ использует это (hybrid **[[Write barrier]]**). ^tc-weak

**Почему базовый tri-color marking требует STW?** В чистом виде: если мутатор одновременно меняет указатели, он может создать ситуацию когда чёрный указывает на белый (invariant нарушен), и GC удалит живой объект. Concurrent режим требует write barrier для поддержания инвариантов. ^tc-stw-reason

## Алгоритм (до Go 1.26 / graph flood)

> [!warning] Устарело (до Go 1.26 / до Green Tea)
> До Go 1.26 work list содержал **объекты** (LIFO stack, depth-first обход).
> Go 1.26+: [[Green Tea GC (new)]] — work list содержит **страницы** (FIFO queue). Tri-color инварианты остались теми же.

```
1. Объекты не помечены (white по умолчанию)
2. Root objects → grey (стеки горутин + глобальные + runtime)
3. Цикл пока есть серые:
   - берём серый объект из очереди (LIFO stack)
   - смотрим на кого он ссылается (его дети)
   - для каждого ребёнка:
     - ребёнок white → красим в grey, кладём в очередь
     - ребёнок grey/black → пропускаем
   - всех детей просмотрели → ТЕКУЩИЙ → black
4. Конец: серых нет → всё что white = мусор → sweep
```

## Green Tea и tri-color marking

Tri-color **инварианты** (strong / weak) и **цвета** остались теми же в Go 1.26+. ^tc-greentea-invariants

Изменился **unit работы** в work list:

| | До Go 1.26 | Go 1.26+ (Green Tea) |
|---|---|---|
| Work list | объекты (LIFO stack) | страницы 8 KiB (FIFO queue) |
| Порядок обхода | depth-first | memory order (sequential) |
| Cache locality | плохая | хорошая |

Внутри страницы объекты сканируются в **memory order** (left-to-right по адресам). Tri-color логика применяется на уровне объектов внутри этого процесса. ^tc-greentea-unit
