- Linux **не выделяет** физическую страницу до первой записи (lazy allocation)
- RSS = физическая память (в RAM). VSS = виртуальное адресное пространство (включая lazy + swap)
- ballast работает из-за этого: `make([]byte, 2GB)` без записи → RSS не растёт, только VSS
- RSS растёт **постранично**: каждая запись в новую страницу → page fault → +4KB RSS (не целиком сразу)

## Lazy allocation (Linux)

При аллокации памяти ОС сразу расширяет адресное пространство процесса, но **не выделяет физическую страницу** до первой записи. Можно даже прочитать — вернётся ноль. Только запись вызывает page fault → ОС выделяет реальную страницу. ^lazy-alloc

```
make([]byte, 2GB)     → VSS +2GB, RSS +0
buf[0] = 1            → page fault → RSS +4KB (одна страница)
buf[4096] = 1         → page fault → RSS +4KB (ещё одна)
```
 ^lazy-alloc-example

**Плюс:** процесс может запросить больше памяти, чем реально использует. ^lazy-alloc-plus

**Минус:** первое обращение к странице дороже (page fault). ^lazy-alloc-minus

## RSS vs VSS

**RSS (Resident Set Size):** сколько памяти физически в RAM прямо сейчас. Это то, что реально потребляет процесс. ^rss

**VSS (Virtual Memory Size):** всё виртуальное адресное пространство: RSS + swap + lazy (аллоцировано, но не использовано). ^vss

RSS растёт постранично: каждая запись в новую страницу → page fault → +4KB RSS (не целиком сразу). ^rss-pagewise

## Пример с ballast

```go
var ballast = make([]byte, 2<<30)  // 2GB
// RSS: ~несколько MB (ничего не записали)
// VSS: +2GB

// Без записи в ballast — физическая память не расходуется!
// Но GOGC считает heap size бо́льшим → реже запускает GC
```

Если начать писать в каждую страницу — RSS растёт, при превышении RAM → swap → замедление. ^ballast-lazy

## Где работает

Linux — точно есть lazy allocation. macOS — аналогичное поведение. Windows — нужно проверять. Lazy allocation нельзя отключить без пересборки ядра. ^lazy-platforms
