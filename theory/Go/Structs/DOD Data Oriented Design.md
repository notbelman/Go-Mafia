- **DOD** (Data Oriented Design) — вместо среза структур → структура срезов (поля в отдельных срезах)
- **cache-friendly**: при итерации по одному полю в кэшлинию подгружается только это поле
- OOD: `[]Object{F1,F2,...F8}` → при чтении F1 в кэш попадают F2–F8 (бесполезно)
- DOD быстрее на итерации по одному полю, меньше памяти (меньше padding из-за выравнивания)
- хуже читаемость и поддержка; паттерн из gamedev

---

## OOD (привычный подход)

```go
type Entity struct {
    Field1 int
    Field2 string
    Field3 float64
    // ... ещё 5 полей
}

entities := make([]Entity, 1_000_000)

// Итерация по Field1:
for _, e := range entities {
    if e.Field1 > threshold { ... }
}
// В кэшлинию загружается ВЕСЬ Entity (Field1–Field8)
// Field2–Field8 не нужны → кэш тратится зря
```

При OOD итерации по одному полю: в кэшлинию загружается весь объект, все ненужные поля тратят кэш впустую. ^dod-ood-problem

## DOD (data oriented)

```go
type Entities struct {
    Field1 []int
    Field2 []string
    Field3 float64
    // ... ещё 5 срезов
}

data := Entities{
    Field1: make([]int, 1_000_000),
    Field2: make([]string, 1_000_000),
    // ...
}

// Итерация по Field1:
for _, v := range data.Field1 {
    if v > threshold { ... }
}
// В кэшлинию загружаются ТОЛЬКО значения Field1
// Последовательно, без "мусора" от других полей
```

При DOD итерации по одному полю: в кэшлинию загружаются только значения этого поля — последовательно, без «мусора». ^dod-dod-benefit

## Визуально

```
OOD (срез структур):
[F1 F2 F3 F4 F5 F6 F7 F8] [F1 F2 F3 F4 F5 F6 F7 F8] [...]
 ↑ нужен только F1, но в кэш попадает всё

DOD (структура срезов):
Field1: [F1 F1 F1 F1 F1 F1 F1 F1 ...]  ← всё в кэше полезно
Field2: [F2 F2 F2 F2 F2 F2 F2 F2 ...]
```

OOD — срез структур: каждый элемент содержит все поля вперемешку. DOD — структура срезов: каждое поле лежит в своём непрерывном срезе. ^dod-layout

## Дополнительное преимущество: padding

DOD экономит память за счёт меньшего padding: когда поля одного типа лежат вместе (`[]int`, `[]float64`), компилятор не вставляет выравнивающие байты между разнотипными полями как в структуре. ^dod-padding

## Бенчмарк

Разница видна на глаз — DOD значительно быстрее при итерации по одному полю. ^dod-bench

## Когда использовать

Gamedev, высоконагруженные системы, обработка больших массивов по одному-двум полям. ^dod-when-use

В обычном бизнес-коде — OOD проще читать и поддерживать. ^dod-tradeoff
