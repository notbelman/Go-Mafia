- **Селективность** = доля строк, которую вернёт условие. **<5-10%** → Index Scan, **>10-15%** → Seq Scan выгоднее
- Каждый индекс = **отдельная структура на диске** + обновление при каждом INSERT/UPDATE/DELETE. 5 индексов = 5 дополнительных записей
- Индексируй колонки из **WHERE, JOIN ON, ORDER BY** — но только с **высокой селективностью** и **частыми запросами**
- B-tree помогает **GROUP BY** (данные уже отсортированы → GroupAggregate без хеширования/сортировки)

## Селективность

```sql
-- Таблица 1M строк:
WHERE email = 'user@example.com'  -- 1 строка    → Index Scan ✅
WHERE age = 25                    -- ~16K (1.6%)  → Index Scan ✅
WHERE gender = 'M'                -- ~500K (50%)  → Seq Scan ✅
```

Низкая уникальность — не приговор:

```sql
-- Частичный индекс для редкого значения
CREATE INDEX idx_active ON users(id) WHERE is_active = true;

-- Составной индекс повышает селективность
CREATE INDEX idx_gender_age ON users(gender, age);
```

### Откуда планировщик знает статистику

```sql
ANALYZE users;  -- собирает статистику

SELECT attname, n_distinct, most_common_vals
FROM pg_stats WHERE tablename = 'users';
```

Устаревшая статистика = плохие планы. После массовых INSERT/UPDATE — `ANALYZE`.

## Издержки индексов

**По месту:** индекс на таблицу 1GB = 200-500MB+.

**По записи:**
```
INSERT без индексов:  запись в heap → готово
INSERT с 5 индексами: запись в heap + обновить 5 B-tree деревьев
```

**Почему не индексировать всё:**
- Каждый лишний индекс замедляет запись
- Больше потребление диска и RAM (shared_buffers)
- VACUUM чистит больше структур
- Планировщик может выбрать неоптимальный индекс

## Какие запросы индексы НЕ ускоряют

- `SELECT *` без WHERE — seq scan и так быстрее
- `WHERE column != value`, `NOT IN` — B-tree не помогает
- `LIKE '%middle%'` — нужен GIN + pg_trgm
- Таблицы < ~1000 строк — seq scan быстрее из-за overhead
- Запросы с низкой селективностью (`WHERE gender = 'M'` на 50% таблицы)

## Индекс для GROUP BY

B-tree хранит ключи **отсортированными** → GroupAggregate без хеширования:

```sql
CREATE INDEX idx_status ON orders(status);
SELECT status, COUNT(*) FROM orders GROUP BY status;

-- В EXPLAIN:
GroupAggregate
  → Index Only Scan using idx_status on orders   ← уже отсортировано
```

Без индекса: Seq Scan → HashAggregate (хеш-таблица в памяти) или Sort → GroupAggregate.

GROUP BY по выражению → нужен expression индекс: `GROUP BY LOWER(name)` → индекс на `LOWER(name)`.

## Как выбрать индекс

### Шаг 1: Найди медленные запросы
```sql
SELECT * FROM pg_stat_statements ORDER BY total_time DESC;
```

### Шаг 2: Тип по паттерну

| Паттерн запроса | Тип индекса |
|:--|:--|
| `=`, `<`, `>`, `BETWEEN` | B-tree (дефолт) |
| Полнотекстовый поиск | GIN + tsvector |
| `LIKE '%text%'` | GIN + pg_trgm |
| Геоданные, диапазоны | GiST |
| JSON поля | GIN |
| Огромная таблица, `=` | Hash |

### Шаг 3: Проверь селективность
```sql
SELECT COUNT(DISTINCT email)::float / COUNT(*) FROM users;
-- → 0.99 = высокая ✅

SELECT COUNT(DISTINCT status)::float / COUNT(*) FROM orders;
-- → 0.0001 = низкая ❌
```
