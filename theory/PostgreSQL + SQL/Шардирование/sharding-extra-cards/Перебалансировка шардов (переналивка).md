Перенос данных с одного шарда на другой. Штатная операция — происходит когда шард живой, не когда упал.

## Зачем

- Данные распределились неравномерно — один шард перегружен
- Добавляем новый шард — нужно перенести часть данных
- Выводим шард из эксплуатации — переносим всё на другие

## Почему это трудно

Во время переналивки данные продолжают читаться и писаться. Приходит UPDATE на запись, которая уже переехала — куда его применять? Много подводных камней.

## 4 способа

### 1. Read-only
Запрещаем все модифицирующие операции. Договариваемся с бизнесом: «в 3 ночи переналиваемся». Просто, но нужен даунтайм на запись.

### 2. Immutable (только INSERT)
Убираем UPDATE — представляем его как INSERT новой версии. Пишем в target-шард, читаем из source + target. Нет проблемы «апдейт попал не туда».

### 3. Репликация (самый популярный)
Поднимаем репликацию между source и target шардами. После синхронизации переключаемся на target. Минимальный даунтайм — только момент переключения.

### 4. Смешанный
Комбинация: лочим конкретного пользователя на время его миграции, остальные работают. Или другие комбинации под конкретный кейс.

## Золотое правило

Если можно не шардировать — не шардируй. Перебалансировка — одна из главных причин, почему шардирование откладывают как можно дольше.

**Связь:**

- [[Consistent Hashing]] — минимизирует количество данных для переноса
