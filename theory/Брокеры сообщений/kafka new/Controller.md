- Controller = один из брокеров Kafka, который дополнительно отвечает за **выбор лидеров партиций**
- Выборы контроллера: первый брокер создаёт ephemeral node `/controller` в ZK → он контроллер. Остальные получают "node already exists"
- Controller epoch — защита от zombie: каждый новый контроллер получает больший epoch. Брокеры игнорируют сообщения от контроллера со старым epoch
- При падении брокера: контроллер определяет новых лидеров партиций → пишет в ZK → рассылает LeaderAndISR всем брокерам

## Выборы контроллера (ZooKeeper)

```
1. Брокер стартует → пытается создать ephemeral node /controller в ZK
2. Первый успевший — контроллер
3. Остальные получают "node already exists" → создают watch на /controller
4. Контроллер упал → ephemeral node исчезает
5. Брокеры получают уведомление → гонка: кто первый создаст /controller
6. Новый контроллер получает новый controller epoch (инкремент через ZK)
```
^ctrl-election

## Controller Epoch (zombie fencing)

Каждый новый контроллер получает **больший epoch** через ZooKeeper conditional increment. ^ctrl-epoch-def

**Проблема zombie:** контроллер завис на GC pause → ZK сессия истекла → новый контроллер выбран. Старый контроллер "проснулся" и продолжает слать команды. ^ctrl-zombie-problem

**Решение:** брокеры знают текущий epoch. Сообщение с устаревшим epoch → игнорируется. Это **zombie fencing**. ^ctrl-zombie-fencing

## Что делает контроллер при падении брокера

```
1. Контроллер замечает: брокер ушёл (watch на ZK или ControlledShutdownRequest)
2. Определяет партиции, чей лидер был на упавшем брокере
3. Для каждой партиции: новый лидер = следующая реплика в replica list
4. Пишет новое состояние в ZK (async pipelined запросы)
5. Шлёт LeaderAndISR запрос всем брокерам с репликами этих партиций
   (батчами — один запрос на брокер с информацией о всех его партициях)
6. Шлёт UpdateMetadata всем брокерам → обновляют MetadataCache
```
^ctrl-broker-failure

**Ключевое:** LeaderAndISR батчится для эффективности — один запрос содержит информацию о множестве партиций. ^ctrl-batching

## При старте нового контроллера

Контроллер загружает всё состояние реплик из ZK (async pipelined запросы). В кластерах с большим количеством партиций это занимает **секунды** — bottleneck. Одна из причин перехода на KRaft. ^ctrl-loading-bottleneck

## При возвращении брокера

Все реплики на вернувшемся брокере стартуют как **followers**. Им нужно догнать лидера, прежде чем они станут eligible для выборов в лидеры. ^ctrl-broker-return
