- **Elasticsearch** для полнотекстового поиска отелей с морфологией (стемминг, fuzzy search)
- **Синхронизация:** PostgreSQL (источник правды) → асинхронная репликация в Elasticsearch
- **Поисковый запрос:** клиент → Elasticsearch (hotel_id) → PostgreSQL (полные данные)
- **Фильтры и ранжирование:** по корню слова ("бел-" → "белая", "белейший"), расстояние редактирования
- **Если ES упал** — поиск не работает, но бронирования продолжают; можно переналить из PostgreSQL

## Проблема

Обычный `LIKE '%белое%'` в PostgreSQL не найдёт "белая" и "белейший". Нужен полнотекстовый поиск с учётом морфологии: корень "бел-" → все словоформы.

PostgreSQL имеет встроенный full-text search, но ElasticSearch делает это лучше и масштабируется отдельно от основной базы.

## Решение: дублирование в ElasticSearch

```
PostgreSQL (основное хранилище) ──→ ElasticSearch (поисковый индекс)
```

При создании/обновлении отеля: пишем в PostgreSQL **и** дублируем name + description в ElasticSearch. ElasticSearch используется **только для поиска**, не для хранения. Источник правды — PostgreSQL.

**Поисковый запрос:** клиент ищет → идём в ElasticSearch → получаем hotel_id → идём в PostgreSQL за полными данными.

## Как работает ElasticSearch

Основан на алгоритмах нечёткого поиска (fuzzy search), в частности на **расстоянии редактирования** (edit distance). Варианты реализации: на основе словарей (стемминг — обрезаем окончание до корня) или на основе количества отличающихся символов.

Ввёл "белое" → ElasticSearch нашёл документы с "белая", "белое", "белейший" через обрезку до корня "бел-".

## Репликация ElasticSearch

**Асинхронная.** Поиск — не критичная операция. Если ElasticSearch отстаёт на секунду — пользователь не заметит. Strong consistency здесь не нужна (в отличие от бронирований).

Балун: "Там, где вам нужна strong consistency — синхронная. Где хватит eventual — асинхронная. Искать с задержкой — ок. Пускать двух клиентов в один номер — не ок."

**Если ElasticSearch упал?** Поиск не работает, но бронирования продолжают работать. Переналить ластик из PostgreSQL — можно, но лучше иметь реплику.
