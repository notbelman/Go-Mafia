- **Saga (не 2PC):** нет single point of failure, компенсирующие транзакции проще блокировок
- **Шаги:** создать заказ (PENDING) → проверить доступность → оплата → подтверждение (BOOKED)
- **Компоненты:** Order Service + Hotel Service + Payment Service, связаны через Kafka
- **Оплата синхронная** — деньги должны списываться прозрачно для пользователя
- **Компенсации:** нет комнат → CANCELLED; оплата не прошла → инкремент обратно; таймаут → воркер

---

Распределённая транзакция: создать заказ → уменьшить доступность → принять оплату. Три разных сервиса, нужна согласованность.

## Почему Saga, а не 2PC

Обсуждались оба варианта. Saga подходит лучше: нет единого координатора (single point of failure), компенсирующие транзакции проще, чем блокировки 2PC на время всей операции.

## Компоненты

```
Order Service (заказы) ──→ Kafka (saga) ──→ Hotel Service (доступность)
      │                                            │
      └──────── Payment Service (внешний) ←────────┘
```

**Order Service + PostgreSQL:** хранит заказы.

```
order:
  id
  user_id
  hotel_id
  room_type_id
  count          — сколько комнат (спортсмены бронируют по 20)
  price
  status         — PENDING → WAITING_PAYMENT → BOOKED / CANCELLED
```

**Hotel Service + PostgreSQL:** отели, комнаты, доступность.

**Payment Service:** внешний сервис оплаты. Мы его не разрабатываем. Возвращает ОК/не ОК.

**Kafka:** брокер для саги (топики для событий).

## Процесс бронирования (happy path)

**Шаг 1:** Клиент нажимает "Забронировать". Order Service создаёт заказ со статусом **PENDING**.

**Шаг 2:** Order Service отправляет событие `order_created` в Kafka.

**Шаг 3:** Hotel Service подписан на `order_created` → декрементирует `available_room_type.count` на нужные даты. Если комнат достаточно → отправляет `reservation_confirmed`. Если нет → отправляет `reservation_failed`.

**Шаг 4 (reservation_confirmed):** Order Service переводит статус в **WAITING_PAYMENT**. Отправляет синхронный запрос в Payment Service.

**Шаг 5:** Payment прошёл → статус **BOOKED**. Готово.

## Почему оплата синхронная, а не через Kafka

Балун категорически: "Деньги — не та штука, которая должна непрозрачно работать. Списание пользователь должен понимать. Никаких 'оплата спишется через час, когда payments заработает'."

Пользователь нажал "Оплатить" → ждёт ответа → получает подтверждение или ошибку. Прозрачно.

## Ошибки и компенсации

**Нет свободных комнат:** Hotel Service возвращает `reservation_failed` → Order Service переводит статус в CANCELLED (или удаляет заказ).

**Оплата не прошла (нет денег):** Order Service запускает компенсирующую транзакцию → событие в Kafka → Hotel Service инкрементирует обратно `available_room_type.count`. Статус → CANCELLED.

**Пользователь не оплатил (таймаут):** ждём N минут. Если не оплатил → компенсирующая транзакция. Но кто следит за таймаутом? Отдельная таблица + воркер (см. следующую карточку).

**Payment Service недоступен:** ретраим. Если недоступен долго — запасной сервис оплаты (резервная платёжка). Балун: "Банально — одна рука не работает, вторая есть."

## Отмена бронирования

Та же логика, но в обратную сторону:
1. Клиент (или админ) отменяет → событие `order_cancelled` в Kafka
2. Hotel Service инкрементирует available_room_type.count
3. Payment Service делает возврат (отдельная логика)
4. Статус → CANCELLED

**Админ тоже может отменить** (комната затопилась). Та же цепочка компенсаций, только инициатор — админ, а не клиент.
