- **PostgreSQL** для метаданных: file (id, user_id, name, type, parent_file_id, ready), chunk_per_file (file_id, chunk_hash, index)
- **S3** для чанков: ключ = хэш содержимого (CAS), значение = сжатый контент
- **Дерево каталогов** через parent_file_id: файлы и каталоги в одной таблице (type = FILE/DIR)
- **Флаг ready:** файл полностью загружен или нет — защита от отдачи недозагруженного файла
- **Шардирование:** user_id добавляется в chunk_per_file (денормализация), чтобы всё дерево на одном шарде

Два хранилища: S3 (чанки) + PostgreSQL (метаданные). Разберём метабазу подробно.

## Два хранилища и почему

**S3 (Object Storage):** хранит сами чанки. Ключ = хэш содержимого (CAS), значение = сжатый контент. Просто KV-хранилище для блобов. Дёшево, масштабируется, нет сложных запросов.

**PostgreSQL:** хранит метаинформацию — какие файлы, в каких каталогах, из каких чанков состоят. Реляционные связи (файл → каталог, файл → чанки), нужны джойны и транзакции.

## Таблица file (файлы и каталоги)

```
file:
  id            — уникальный идентификатор
  user_id       — владелец
  name          — локальное имя (photo.jpg, Documents)
  type          — FILE или DIR
  parent_file_id — родительский каталог
  ready         — флаг: файл полностью загружен или нет
```

**Почему файлы и каталоги в одной таблице?** В Linux "всё есть файл". Каталог — это файл с типом DIR. Одна таблица, одна логика обхода дерева.

**Почему name не может быть PK?** В разных каталогах могут быть файлы с одинаковым именем (`Documents/photo.jpg` и `Backup/photo.jpg`).

**parent_file_id:** строим дерево снизу вверх. Каждый файл/каталог указывает на родителя. Корневой каталог: `parent_file_id = -1` (magic number).

**Как найти корневой каталог пользователя:**
```sql
SELECT * FROM file WHERE user_id = 'vova' AND parent_file_id = -1 AND type = 'DIR'
```

**Как найти содержимое каталога:**
```sql
SELECT * FROM file WHERE parent_file_id = <id каталога>
```

**Альтернатива — children (массив дочерних ID):** работает, но хуже — хранить массив, обновлять при каждом добавлении. parent_file_id проще.

## Таблица chunk_per_file (связь файл → чанки)

```
chunk_per_file:
  file_id       — какой файл
  chunk_hash    — хэш чанка (= ключ в S3)
  index         — порядковый номер чанка в файле
```

**Зачем отдельная таблица, а не массив в file?** Файл 100 ГБ / 1 МБ = 100.000 чанков. Массив из 100.000 элементов — плохо. Отдельная таблица масштабируется лучше.

**Зачем index?** Чанки могут грузиться параллельно и приходить в разном порядке. Третий чанк может загрузиться раньше второго. Без индекса — не соберёшь файл в правильном порядке.

**Кто проставляет index?** Клиент. Клиент разбивает файл на чанки, нумерует их (0, 1, 2...), отправляет. Сервер сохраняет как есть. При скачивании — сортируем по index, собираем файл.

**Может ли быть два одинаковых chunk_hash в одном файле?** Да, если содержимое повторяется. Поэтому PK = (file_id, chunk_hash, index) или просто (file_id, index).

## Флаг ready

Пользователь загрузил 2 из 10 чанков и ушёл. Другой пользователь (или он сам) запрашивает файл. Нельзя отдать недозагруженный файл. Поэтому `ready = false` до завершения загрузки. При чтении: если `ready = false` — отбиваем запрос.

## user_id в chunk_per_file (для шардирования)

При шардировании по user_id — нужно чтобы chunk_per_file тоже шардировался по user_id. Иначе — мультишардовые запросы. Поэтому добавляем user_id в таблицу (денормализация ради шардирования).
