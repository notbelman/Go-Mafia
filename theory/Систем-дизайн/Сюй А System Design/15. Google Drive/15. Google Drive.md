- **Google Drive** — облачное файловое хранилище + синхронизация. Загрузка, скачивание, синхронизация между устройствами, история версий, шаринг, уведомления. **10M DAU**, 50M зарегистрированных
- **500 ПБ** общее хранилище (50M × 10 ГБ). QPS загрузки ~240 (пик ~480). Средний файл 500 КБ, макс. 10 ГБ. Read/write = 1:1
- **Блочное хранение:** файл делится на блоки (до 4 МБ, как Dropbox) → каждый **сжимается + шифруется** → загружается в S3. **Дельта-синхронизация** — только изменённые блоки
- **Строгая согласованность** обязательна (файл не может выглядеть по-разному на разных клиентах). Реляционная БД (ACID) для метаданных. Кэш инвалидируется при записи
- **Уведомления через Long Polling** (не WebSocket — взаимодействие одностороннее, не частое). Dropbox использует тот же подход
- **Конфликты синхронизации:** кто первый обработан — тот и победил. Второму показываем обе версии (локальную + серверную) — сам решает
- **Экономия хранилища:** дедупликация блоков (одинаковый хеш = один блок), лимит версий, только важные версии, **холодное хранилище** (S3 Glacier) для неактивных данных
- **Потеря данных недопустима.** S3 реплицируется между регионами. Метаданные: master-slave репликация + шардирование

1. **Загрузка** файлов (простая + возобновляемая для больших)
2. **Скачивание** файлов
3. **Синхронизация** между устройствами (автоматическая)

- **Масштабируемость** и **высокая доступность**

## Расчёт нагрузки

```
50M зарегистрированных × 10 ГБ = 500 ПБ общее хранилище
10M DAU × 2 файла/день × 500 КБ = 10 ТБ/день

QPS загрузки: 10M × 2 / 86400 ≈ 240
Пиковый QPS: 240 × 2 = 480

Read/Write = 1:1
```

## Блочные системы хранения — подробно

![[15.11.png]]
### Процесс загрузки нового файла
1. Файл **разделяется на блоки** (≤4 МБ)
2. Каждый блок **сжимается** (gzip/bzip2 для текста, другие для медиа)
3. Каждый блок **шифруется**
4. Блоки **загружаются в S3**

![[15.12.png]]

При редактировании — **только изменённые блоки** передаются в S3. Экономия трафика.

## Строгая согласованность

- Файл **не может выглядеть по-разному** на разных клиентах
- **Реляционная БД** (ACID) для метаданных
- **Кэш инвалидируется** при записи в БД
- Реплики кэша согласованы с master

## Процесс загрузки

![[15.14.png]]

Два параллельных процесса:

**Добавление метаданных:**
1. Клиент 1 → запрос на добавление метаданных
2. Система → БД: состояние = **"ожидается"**
3. Сервис уведомлений оповещён
4. Клиент 2 узнаёт о загрузке

**Загрузка файла:**
2.1. Клиент 1 → блочные серверы
2.2. Блочные серверы → разбивка + сжатие + шифрование → S3
2.3. S3 → callback завершения → серверы API
2.4. Состояние = **"загружено"**
2.5-2.6. Уведомление клиенту 2: файл загружен

## Процесс скачивания

![[15.15.png]]

1. Сервис уведомлений → клиент 2: файл изменён
2. Клиент 2 → серверы API: дай метаданные изменений
3-4. API → БД → метаданные
5. Клиент 2 получает метаданные
6-7. Клиент 2 → блочные серверы → S3: скачать блоки
8-9. Блоки → клиент 2 → восстановление файла

**Офлайн:** изменения в очереди автономной архивации → синхронизация при подключении.

## Сервис уведомлений — Long Polling

**Почему Long Polling, а не WebSocket:**
- Взаимодействие **одностороннее** (сервер → клиент)
- Уведомления **не частые** и не провоцируют всплески
- Dropbox использует тот же подход

Клиент держит HTTP-соединение → файл изменился → соединение закрывается → клиент качает изменения → открывает новое соединение.

## Экономия места в хранилище

| Метод | Описание |
|---|---|
| **Дедупликация блоков** | Одинаковый хеш = один блок. Не хранить дубли |
| **Лимит версий** | Макс. N версий, старые удаляются |
| **Только важные версии** | Файл редактируется 1000 раз → хранить не все, а ключевые |
| **Холодное хранилище** | Неактивные данные → S3 Glacier (намного дешевле S3) |

## Обработка сбоев

| Компонент | Решение |
|---|---|
| **Балансировщик** | Резервный экземпляр (heartbeat) |
| **Блочный сервер** | Другие серверы подхватывают задания |
| **S3** | Бакеты реплицированы между регионами |
| **Сервер API** | Stateless → LB перенаправляет на другой |
| **Кэш метаданных** | Реплицирован → другой сервер |
| **БД метаданных** | Master упал → promote slave. Slave упал → другой slave |
| **Сервис уведомлений** | Клиенты теряют Long Polling → переподключаются (медленно при >1M соединений) |
| **Очередь архивации** | Реплицирована → потребители подписываются на другую |

## Дополнительные вопросы

- **Загрузка напрямую в S3** (без блочных серверов) — быстрее, но логику разбивки/сжатия/шифрования нужно реализовать на каждом клиенте (iOS, Android, web) + шифрование на клиенте небезопасно
- **Сервис присутствия** — вынести из сервиса уведомлений для независимой интеграции
