- **Система автозаполнения** (typeahead/autocomplete) — пользователь вводит префикс → система возвращает **топ-5 самых популярных** запросов. Google, Amazon, Facebook
- **10M DAU**, 10 запросов/день, 20 символов/запрос → **~24 000 QPS** (пик ~48 000). Каждый символ = запрос к серверу. 20% запросов новые → **0.4 ГБ/день** новых данных
- **Префиксное дерево (Trie)** — основная структура данных. Каждый узел = символ. Путь от корня = строка. В узлах хранится **частота** запросов
- **Оптимизация 1:** ограничить длину префикса (≤50) → поиск O(1). **Оптимизация 2:** кэшировать **топ-k** в каждом узле → не обходить всё поддерево. Обе вместе → **O(1)**
- **Два сервиса:** сервис сбора данных (логи → агрегаторы → рабочие узлы → формируют Trie **еженедельно**) и сервис запросов (LB → API → кэш Trie → ответ)
- **Не обновлять в реальном времени** — миллиарды запросов/день, обновление при каждом вводе замедлит систему. Популярные запросы меняются редко → **еженедельно** достаточно
- **Хранилище Trie:** кэш в памяти (для быстрого чтения) + БД (MongoDB для сериализованных снимков ИЛИ KV store: префикс = ключ, топ-k = значение)
- **Масштабирование:** шардирование по первым буквам (a-m на сервер 1, n-z на сервер 2). Неравномерность → **диспетчер карты сегментов** (анализ распределения)

## Префиксное дерево (Trie) — основная структура

![[13.5.png]]

### Свойства
- **Иерархическая** структура данных
- Корень = пустая строка
- Каждый узел = символ, 26 дочерних (a-z)
- В узлах хранится **частота** запроса (если узел = конец слова)

![[13.6.png]]

### Алгоритм поиска топ-k (наивный)

1. Найти префиксный узел → O(p)
2. Обойти всё поддерево → найти все подходящие → O(c)
3. Отсортировать → взять топ-k → O(c log c)

**Проблема:** в худшем случае — обход всего дерева. Слишком медленно.

![[13.7.png]]

### Оптимизация 1: ограничить длину префикса

Пользователи не вводят длинные запросы → ограничиваем p ≤ 50 → поиск узла **O(1)** вместо O(p).

### Оптимизация 2: кэшировать топ-k в каждом узле

В каждом узле заранее храним 5 самых популярных завершений. Не нужно обходить поддерево → **O(1)**.

![[13.8.png]]

**Компромисс:** больше памяти (дублирование данных в каждом узле), но мгновенный ответ.

**Итого после оптимизаций:** O(1) + O(1) = **O(1)** на запрос.

## Сервис сбора данных

![[13.9.png]]
### Почему НЕ обновлять в реальном времени
- Миллиарды запросов/день → обновление Trie при каждом вводе замедлит сервис
- Популярные варианты меняются **незначительно** изо дня в день
- Достаточно обновлять **раз в неделю** (для Google). Twitter нужно чаще

### Компоненты

| Компонент | Описание |
|---|---|
| **Логи анализа** | Сырые данные: запрос + время. Append-only, не индексированы |
| **Агрегаторы** | Группируют запросы за неделю: запрос + частота |
| **Рабочие узлы** | Формируют Trie из агрегированных данных (асинхронно, по расписанию) |
| **БД Trie** | Постоянное хранилище: MongoDB (сериализованный снимок) или KV store |
| **Кэш Trie** | В памяти для быстрого чтения. Еженедельный снимок из БД |

### Пример агрегированных данных

| Запрос | Неделя | Частота |
|---|---|---|
| tree | 2019-10-01 | 12 000 |
| tree | 2019-10-08 | 15 000 |
| toy | 2019-10-01 | 8 500 |

### Хранилище Trie — два варианта

**1. Документное (MongoDB):** сериализованный снимок всего дерева. Генерируется еженедельно.

**2. KV Store:** каждый префикс = ключ, топ-k = значение.

![[13.10.png]]

```
Ключ  → Значение
"b"   → [be:15, bee:20, beer:10, best:35]
"be"  → [be:15, bee:20, beer:10, best:35]
"bee" → [bee:20, beer:10]
"bes" → [best:35]
```

## Сервис запросов

![[13.11.png]]

### Флоу

1. Пользователь вводит символ → запрос к **балансировщику**
2. LB → **серверы API**
3. API → **кэш Trie** (в памяти) → топ-5 для префикса
4. Нет в кэше → достаём из **БД Trie** → кэшируем

### Оптимизации сервиса запросов

| Оптимизация | Описание |
|---|---|
| **AJAX** | Не перезагружать всю страницу, только подсказки |
| **Кэш в браузере** | Варианты не меняются часто → cache-control: max-age=3600 (1 час) |
| **Выборка данных** | Логировать 1 из N запросов (не все — экономия ресурсов) |

## Операции с Trie

### Создание
Рабочие узлы формируют Trie из агрегированных данных (логи/БД анализа).

### Обновление
- **Способ 1:** полностью перегенерировать еженедельно → заменить старое
- **Способ 2:** обновить узлы напрямую (медленно — нужно обновить всех предков)

![[13.13.png]]

### Удаление (фильтрация)
Нежелательный контент (ненависть, насилие, откровенный контент) → **слой фильтрации** перед кэшем.

![[13.14.png]]
Удаление из БД — асинхронно. При следующем обновлении Trie → нежелательное не попадёт.

## Масштабирование хранилища

Trie не помещается на одном сервере → **шардирование по первым буквам**.

```
2 сервера: a-m → сервер 1, n-z → сервер 2
3 сервера: a-i → 1, j-r → 2, s-z → 3
26 серверов: по одной букве
```

**Проблема:** неравномерность (на "c" больше слов, чем на "x").

**Решение:** **диспетчер карты сегментов** — анализирует распределение данных и назначает умные границы шардов.

> 📸 **Вставить скрин: Рис. 13.15** (стр. 241) — шардирование через диспетчер карты сегментов

Пример: запросов на "s" столько же, сколько на "u-z" вместе → отдельный шард для "s", один шард для "u-z".

## Дополнительные вопросы на собесе

### Поддержка других языков
Вместо ASCII → **Unicode** в узлах Trie. Покрывает все системы письма.

### Зависимость от страны
Разные Trie для разных стран. Хранить в **CDN** для снижения латентности.

### Обновление в реальном времени (trending)
Сложная задача. Советы:
- Уменьшить рабочий набор через **шардинг**
- Повысить **вес недавних** запросов в ранжировании
- Потоковая обработка: Apache Kafka, Spark Streaming, Storm
