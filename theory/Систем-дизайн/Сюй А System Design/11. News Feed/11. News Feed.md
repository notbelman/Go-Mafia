- **Лента новостей** — постоянно обновляемый список постов от друзей/подписок. Facebook, Instagram, Twitter. Два процесса: **публикация** и **составление ленты**
- **10M DAU**, до 5000 друзей. Лента: обратный хронологический порядок. Поддержка: текст + изображения + видео. Мобильное + браузерное приложение
- **Публикация:** пользователь → LB → веб-сервер (auth + rate limit) → сервис постов (БД + кэш) → **сервис ветвления** (fan-out в ленты друзей) → сервис уведомлений
- **Fan-out при записи (push):** пост сразу помещается в кэш лент друзей. Быстрое чтение, но медленно при большом кол-ве друзей (hot key problem)
- **Fan-out при чтении (pull):** лента собирается при запросе. Нет проблемы с hot key, но медленное чтение
- **Гибридный подход:** обычные пользователи → push, знаменитости/много друзей → pull (по требованию). Consistent hashing для распределения
- **Составление ленты:** запрос → LB → веб-сервер → сервис ленты → кэш (ID постов) → обогащение данными (user info, post content, media из CDN) → JSON клиенту
- **5 слоёв кэша:** лента (post_id), контент (hot/обычный), социальный граф (подписки), действия (лайки, ответы), счётчики (лайки, подписчики)

### Fan-out при записи (push)
После публикации пост **сразу** помещается в кэш лент каждого друга.

**Плюсы:**
- Лента генерируется в реальном времени
- Получение ленты — мгновенное (уже в кэше)

**Минусы:**
- У пользователя много друзей → получение списка + генерация для каждого = **медленно** (hot key problem)
- Для неактивных пользователей — пустая трата ресурсов

### Fan-out при чтении (pull)
Лента собирается **в момент запроса** — загружаются последние посты друзей.

**Плюсы:**
- Нет проблемы с горячими ключами
- Ресурсы не тратятся на неактивных пользователей

**Минусы:**
- Загрузка ленты **медленная** (собирается на лету)

### Гибридный подход (выбранное решение)
- **Обычные пользователи** → push (fan-out при записи). Быстрое получение ленты
- **Знаменитости / много друзей** → pull (fan-out при чтении). Не перегружаем систему
- **Consistent hashing** для равномерного распределения запросов

### Флоу сервиса ветвления (5 шагов)

1. Извлекаем ID друзей из **графовой БД**
2. Получаем информацию о друзьях из **кэша пользователей**. Фильтруем: заглушённые, скрытые посты, ограниченный круг
3. Отправляем список друзей + ID поста в **очередь сообщений**
4. **Узлы ветвления** достают из очереди → сохраняют `<post_id, user_id>` в **кэш ленты**
5. Кэш ленты хранит **только ID** (не полные данные) — экономия памяти. Лимит на количество постов

## Модель данных

### Кэш новостной ленты
Хеш-таблица `<post_id, user_id>`. Хранит **только ID**, не полные данные (экономия памяти). Лимит на количество — большинство людей не листают дальше последних постов.

### Графовая БД
Хранит связи друзей. Позволяет быстро получить список друзей пользователя.

### БД постов
Текст, ссылки на медиа, метаданные.

### CDN
Изображения, видео — статический контент из CDN для быстрого доступа.

## Масштабирование (дополнительные вопросы)

- БД: вертикальное/горизонтальное, SQL/NoSQL, репликация, шардирование
- Веб-уровень: **stateless** → горизонтальное масштабирование
- Кэширование: как можно активнее
- Несколько ДЦ
- Очереди сообщений для ослабления связанности
- Мониторинг: QPS в пиках, латентность при обновлении ленты
