- **Система мгновенного обмена сообщениями** (Facebook Messenger). Приватный чат + групповой (до 100 чел.) + индикатор сетевого статуса + push-уведомления. **50M DAU**
- **WebSocket** — основной протокол. Двунаправленный, постоянный. HTTP для остального (auth, профили, регистрация). Polling и Long Polling рассмотрены, но отвергнуты
- **Три части системы:** stateless сервисы (auth, профили, группы — HTTP, за LB), stateful сервис чата (WebSocket, постоянные соединения), сторонние (push-уведомления)
- **Хранение:** KV store (HBase/Cassandra), НЕ реляционная. Причины: 60 млрд сообщений/день, горизонтальное масштабирование, низкая латентность, длинные последовательности данных
- **Обнаружение сервисов (Zookeeper):** при логине подбирает лучший сервер чата (по географии, нагрузке). Клиент подключается к нему по WebSocket
- **Приватный чат:** отправитель → сервер чата → генератор ID → очередь синхронизации → KV store. Получатель в сети → WebSocket. Не в сети → push
- **Групповой чат:** сообщение копируется в очередь (почтовый ящик) **каждого** участника. Подходит для небольших групп (≤500, как WeChat)
- **Сетевой статус:** heartbeat каждые 5 сек → сервер статуса → KV store. Нет пульса x секунд → offline. Распространение через Pub/Sub каналы (A-Б, A-В, A-Г)

## Хранилище — почему KV, а не SQL

Два типа данных:
1. **Общие** (профили, настройки, друзья) → **реляционная БД** + репликация + шардирование
2. **Сообщения** → **KV store** (HBase, Cassandra)

### Почему KV для сообщений

- **60 млрд сообщений/день** (Facebook + WhatsApp)
- Активный доступ только к **недавним** чатам
- Read/write примерно **1:1** (не read-heavy)
- Нужен произвольный доступ (поиск, переход к сообщению)
- KV store **горизонтально масштабируется** + низкая латентность
- Реляционные БД плохо с **длинными последовательностями** (индекс растёт → замедляется)
- Используют: Facebook Messenger (**HBase**), Discord (**Cassandra**)

### Приватный чат

| Поле | Тип |
|---|---|
| **message_id** | bigint PK (определяет порядок) |
| message_from | bigint |
| message_to | bigint |
| content | text |
| created_at | timestamp |

### Групповой чат

| Поле           | Тип                         |
| -------------- | --------------------------- |
| **channel_id** | bigint (ключ раздела)       |
| **message_id** | bigint (ключ кластеризации) |
| user_id        | bigint                      |
| content        | text                        |
| created_at     | timestamp                   |

### Генерация message_id
- Должен быть **уникальным** + **сортируемым по времени**
- **auto_increment** — нет в NoSQL
- **Snowflake** (глобальный) — работает
- **Локальный генератор** — ID уникальны только в пределах канала/группы. Проще реализовать

## Обнаружение сервисов (Zookeeper)

![[12.11.png]]

1. Пользователь A логинится
2. LB → серверы API
3. API аутентифицирует → **Zookeeper подбирает** лучший сервер чата (по географии, нагрузке)
4. Пользователь A подключается к выбранному серверу по **WebSocket**

## Маршрут сообщения — приватный чат

![[12.12.png]]

1. Пользователь A → сообщение → **сервер чата 1**
2. Сервер чата 1 → **генератор ID** → получает message_id
3. Сообщение → **очередь синхронизации**
4. Сообщение → **KV store** (персистентность)
5. a) Получатель **в сети** → сообщение → сервер чата 2 → WebSocket → получатель
   b) Получатель **не в сети** → **push-уведомление**
6. Сервер чата 2 доставляет по WebSocket

## Синхронизация между устройствами

![[12.13.png]]

Каждое устройство хранит **cur_max_message_id** — ID последнего полученного сообщения.

Новые сообщения = те, у которых:
- `recipient_id == текущий юзер`
- `message_id > cur_max_message_id`

Каждое устройство — своё значение cur_max_message_id → независимая синхронизация.

## Маршрут сообщения — групповой чат

![[12.14.png]]

![[12.15.png]]

Сообщение пользователя A **копируется в очередь (почтовый ящик) каждого** участника группы.

**Почему работает для небольших групп:**
- Каждый клиент проверяет **свой почтовый ящик** → простая синхронизация
- Для ≤500 участников — приемлемый расход ресурсов (WeChat так делает)
- Для 100 000+ — **неприемлемо** → нужен другой подход

## Сетевой статус (Presence)

### Вход в систему

![[12.16.png]]

После WebSocket-соединения → `{status: online, last_active_at: timestamp}` → KV store

### Выход из системы

![[12.17.png]]

API серверы → серверы статуса → `{status: offline}` → KV store

### Отключение от сети (нестабильное соединение)

![[12.18.png]]

**Проблема:** юзер в тоннеле → соединение рвётся → переподключение → статус мигает.

**Решение — heartbeat:**
- Клиент шлёт пульс каждые **5 секунд**
- Сервер получает → юзер **в сети**
- Нет пульса **x секунд** (например, 30) → статус **offline**

### Распространение статуса друзьям

![[12.19.png]]

Модель **Pub/Sub**: между каждой парой друзей — канал (A-Б, A-В, A-Г).

Статус A изменился → событие в каналы → друзья Б, В, Г получают обновление по WebSocket.

**Для больших групп (100 000+):** слишком много событий → получать статус только при входе в группу или ручном обновлении.

## Дополнительные вопросы на собесе

- **Медиафайлы** — сжатие, облачное хранение (S3), миниатюры
- **Сквозное шифрование** — WhatsApp поддерживает
- **Кэш на клиенте** — сокращает трафик между клиентом и сервером
- **Географическое распределение** — кэширование данных ближе к юзерам (Slack Flannel)
- **Ошибки сервера чата** — Zookeeper даёт клиенту новый сервер для переподключения
- **Retry** — неотправленные сообщения → в очередь → повторная отправка
