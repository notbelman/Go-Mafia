РАСПРЕДЕЛЁННОЕ ОКРУЖЕНИЕ — ДВЕ ПРОБЛЕМЫ:

1. СОСТОЯНИЕ ГОНКИ (Race Condition):
   Два запроса параллельно читают счётчик=3 из Redis.
   Оба инкрементируют до 4. Но должно быть 5.

   Решение: Lua-скрипт в Redis (атомарная операция)
   или Redis sorted sets.
   НЕ использовать блокировки — замедлят систему.

2. СИНХРОНИЗАЦИЯ между серверами:
   Несколько серверов RL → клиент может попасть на разные.
   Каждый RL не знает о запросах других.

   Решение: ЦЕНТРАЛИЗОВАННЫЙ Redis.
   Все серверы RL ходят в один Redis.
   НЕ использовать sticky sessions (немасштабируемо).

   Данные синхронизируются через eventual consistency. ^n_dist

- Обработка исключений (понятное сообщение об ошибке) ^n_nfr

5 АЛГОРИТМОВ ОГРАНИЧЕНИЯ ТРАФИКА:

1. МАРКЕРНАЯ КОРЗИНА (Token Bucket)
   Корзина с маркерами, пополняется с постоянной скоростью.
   Запрос = 1 маркер. Нет маркеров → отклоняем.
   + Простой, справляется со всплесками
   - Подобрать размер корзины и частоту пополнения непросто
   Используют: Amazon, Stripe

2. ДЫРЯВОЕ ВЕДРО (Leaking Bucket)
   Очередь FIFO фиксированного размера.
   Запросы обрабатываются с постоянной скоростью.
   Очередь полна → отклоняем.
   + Стабильная скорость обработки
   - Всплеск забивает очередь старыми запросами
   Использует: Shopify

3. СЧЁТЧИК ФИКСИРОВАННЫХ ИНТЕРВАЛОВ (Fixed Window)
   Время делится на равные интервалы, у каждого счётчик.
   Счётчик >= лимит → отклоняем.
   + Простой, экономит память
   - Всплеск НА ГРАНИЦЕ интервалов → 2x лимита

4. ЖУРНАЛ СКОЛЬЗЯЩИХ ИНТЕРВАЛОВ (Sliding Window Log)
   Храним временные метки каждого запроса в Redis sorted set.
   Просроченные удаляем, считаем оставшиеся.
   + Очень точный
   - Много памяти (метка даже для отклонённых)

5. СЧЁТЧИК СКОЛЬЗЯЩИХ ИНТЕРВАЛОВ (Sliding Window Counter)
   Гибрид: запросы_текущего + запросы_предыдущего × % перекрытия
   Пример: 3 + 5 × 0.7 = 6.5 ≈ 6 (при лимите 7 → пропускаем)
   + Сглаживает всплески, экономит память
   - Приблизительный (ошибка ~0.003% по данным Cloudflare) ^n_algo

ГДЕ РАЗМЕЩАТЬ ОГРАНИЧИТЕЛЬ:

1. На клиенте — ненадёжно (легко подделать)
2. На сервере — полный контроль
3. Промежуточный слой (middleware) — рекомендуется
4. API Gateway — если уже есть микросервисы
   (поддерживает: rate limiting, SSL, аутентификация,
   белые списки IP, статический контент)
