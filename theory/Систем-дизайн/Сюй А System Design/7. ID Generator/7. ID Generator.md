- **Задача:** генерировать уникальные ID в распределённой системе. `auto_increment` не работает — несколько БД, ID пересекаются
- **Требования:** уникальные, числовые, 64 бита, упорядочены по дате, **10 000 ID/сек**
- **4 подхода:** репликация с шагом k (просто, но не хронологично), UUID (128 бит, не числовой), сервер тикетов (SPOF), **Twitter Snowflake** (выбранное решение)
- **Snowflake:** 64 бита = 1 бит знака + **41 бит timestamp** + 5 бит ID ДЦ + 5 бит ID машины + **12 бит sequence**
- 41 бит timestamp = ~69 лет (2^41 мс). 5+5 бит = до 32 ДЦ × 32 машины = **1024 генератора**. 12 бит sequence = **4096 ID/мс** на машину
- Timestamp обеспечивает **хронологическую сортировку**. Sequence сбрасывается каждую миллисекунду. >1 ID за мс → sequence инкрементируется
- **Проблема синхронизации часов** (NTP). Эпоха начала: чем ближе к текущей дате, тем дольше прослужит генератор

| Вопрос кандидата | Ответ интервьюера |

| Какие характеристики у ID? | Уникальные и подлежат сортировке |
| Инкрементируется на 1? | Нет, инкрементируется по времени (вечерние > утренних) |

## Функциональные требования

1. ID должны быть **уникальными** глобально
2. ID должны быть **числовыми** (только цифры)
3. ID должны умещаться в **64 бита**
4. ID должны быть **упорядочены по дате** (позднее = больше)

## Нефункциональные требования

- Генерация **10 000 ID/сек**
- Низкая латентность
- Высокая доступность (генератор — критический компонент)

## 4 подхода к генерации ID

### 1. Репликация с несколькими источниками (multi-master)

Каждая БД использует `auto_increment` с шагом k (= число серверов). Сервер 1: 1, 3, 5... Сервер 2: 2, 4, 6...

| Плюсы | Минусы |
|---|---|
| Просто | ID **не хронологичны** между серверами |
| Масштабируется | Плохо масштабируется при добавлении/удалении серверов |
| | Сложно с несколькими ДЦ |

### 2. UUID

128-битное случайное число. `09c93e62-50b4-468d-bf8a-c07e1040bfb2`. Каждый сервер генерирует независимо, без координации.

| Плюсы | Минусы |
|---|---|
| Просто, нет координации | **128 бит** (нужно 64) |
| Масштабируется | **Не хронологичны** |
| | **Не числовые** |

### 3. Сервер тикетов (Flickr)

Один выделенный сервер БД с `auto_increment`. Все ходят к нему за ID.

| Плюсы | Минусы |
|---|---|
| Числовые ID | **SPOF** (единая точка отказа) |
| Просто | Если упал — все системы стоят |
| Подходит для малых/средних | Несколько серверов = синхронизация |

### 4. Twitter Snowflake (выбранное решение) ✓

Разделяем 64-битный ID на части. Каждый генератор собирает ID из компонентов.

## Snowflake — структура ID

```
| 1 бит  | 41 бит          | 5 бит    | 5 бит      | 12 бит           |
|--------|-----------------|----------|------------|------------------|
| знак=0 | timestamp (мс)  | ID ДЦ   | ID машины  | sequence number  |
```

### Каждая часть

| Часть | Бит | Описание | Диапазон |
|---|---|---|---|
| **Знак** | 1 | Всегда 0, зарезервирован | — |
| **Timestamp** | 41 | Миллисекунды с начала эпохи | ~69 лет (2^41 мс) |
| **ID ДЦ** | 5 | Идентификатор датацентра | 0–31 (32 ДЦ) |
| **ID машины** | 5 | Идентификатор сервера в ДЦ | 0–31 (32 машины/ДЦ) |
| **Sequence** | 12 | Порядковый номер в миллисекунде | 0–4095 (4096 ID/мс) |

### Ключевые числа

```
Максимум ДЦ:        2^5 = 32
Максимум машин/ДЦ:  2^5 = 32
Всего генераторов:   32 × 32 = 1024
ID/мс на машину:    2^12 = 4096
ID/сек на машину:   4 096 000
Время жизни:        2^41 мс ≈ 69 лет
```

### Timestamp — почему 41 бит

- Обеспечивает **хронологическую сортировку** (позднее = больше)
- 2^41 - 1 = 2 199 023 255 551 мс ≈ **69 лет**
- Начало эпохи: Twitter = Ноя 04, 2010 (1288834974657)
- Чем **ближе эпоха к текущей дате**, тем дольше прослужит генератор
- После 69 лет → нужна новая эпоха или миграция

### Пример декодирования ID

```
0-00100010101001011010011011000101101011000-01010-01100-000000000000

Timestamp (двоичный): 00100010101001011010011011000101101011000
  → десятичный: 297616116568
  + эпоха Twitter: 1288834974657
  = 1586451091225 мс
  = Апр 09, 2020, 16:51:31 UTC

ID ДЦ: 01010 = 10
ID машины: 01100 = 12
Sequence: 000000000000 = 0 (первый ID в этой миллисекунде)
```

### Sequence — 12 бит

- Инкрементируется на 1 при генерации >1 ID в одну миллисекунду
- **Сбрасывается в 0** каждую новую миллисекунду
- Максимум 4096 ID/мс на одном сервере
- Если за мс только 1 ID → sequence = 0

## ID ДЦ и ID машины

- Выбираются **при запуске** системы
- Обычно **не меняются** во время работы
- Изменение требует тщательного анализа (возможны конфликты)

## Дополнительные вопросы на собесе

### Синхронизация часов
- Предполагается что часы синхронизированы
- На многоядерных серверах или в multi-server — **не гарантировано**
- Решение: **NTP** (Network Time Protocol)
- Если часы рассинхронизированы → ID перестают быть хронологичными

### Оптимизация длины частей
- Больше бит для timestamp (за счёт sequence) → для приложений с **долгим сроком жизни** и **низким параллелизмом**
- Больше бит для sequence (за счёт timestamp) → для приложений с **высоким параллелизмом**

### Высокая доступность
- Генератор ID — **критический компонент** (незаменимый)
- Должен быть высокодоступным
- Каждая машина генерирует ID независимо → нет SPOF

## Сравнение всех подходов

| | Multi-master | UUID | Сервер тикетов | **Snowflake** |
|---|---|---|---|---|
| Уникальность | Да | Да | Да | **Да** |
| 64 бита | Да | Нет (128) | Да | **Да** |
| Числовой | Да | Нет | Да | **Да** |
| Хронологичность | Нет | Нет | Да (один сервер) | **Да** |
| 10K ID/сек | Зависит | Да | Ограничен 1 сервером | **4M/сек на машину** |
| Координация | Нет | Нет | Да (SPOF) | **Нет** |
| Масштабируемость | Плохая | Хорошая | Плохая | **Отличная** |
