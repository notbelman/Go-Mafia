- **Система уведомлений** — push (iOS APNs / Android FCM), SMS (Twilio, Nexmo), email (Sendgrid, Mailchimp). Мягкое реальное время — задержки допустимы при нагрузке
- **10M push/день + 1M SMS + 5M email.** Инициируются: клиентские приложения, серверные cron-задания, микросервисы
- Каждому типу уведомлений — **отдельная очередь сообщений** (iOS PN, Android PN, SMS, Email). Отказ одного сервиса не влияет на другие
- **Рабочие узлы** достают события из очередей → отправляют сторонним сервисам (APNs, FCM, Twilio, Sendgrid). Retry при ошибке → обратно в очередь
- **Контактная информация** собирается при регистрации: таблица user (email, phone) + таблица device (device_token). У пользователя может быть несколько устройств
- **Надёжность:** уведомления записываются в **журнал (лог)** перед отправкой → не теряются. Дедупликация по ID события — проверяем, отправляли ли уже
- **Шаблоны** — отформатированный текст с параметрами (НАЗВАНИЕ ПРОДУКТА, ДАТА). Не генерировать каждое уведомление с нуля
- **Доп. компоненты:** аутентификация (appKey/appSecret), rate limiting (не заваливать юзера), параметры opt-in/opt-out, аналитика (open rate, click rate), мониторинг очередей

## Функциональные требования

1. Поддержка **трёх типов**: push-уведомления (iOS + Android), SMS, email
2. Инициирование **из разных источников** (микросервисы, cron, клиенты)
3. Возможность **отписки** (opt-out) для каждого типа
4. Уведомления **не должны теряться** (могут задерживаться, но не пропадать)

## Нефункциональные требования

- **Мягкое реальное время** — как можно быстрее, но задержки при нагрузке допустимы
- **Масштабируемость** — миллионы уведомлений в день
- **Отказоустойчивость** — отказ одного канала не ломает другие
- **Расширяемость** — легко подключать новые сторонние сервисы

## Типы уведомлений — как работают

![[10.6.png]]

### iOS Push
**Провайдер** → **APNs** (Apple Push Notification Service) → **устройство iOS**

Провайдер формирует запрос с:
- **Device token** — уникальный идентификатор устройства
- **Payload** — JSON с содержимым уведомления

```json
{
  "aps": {
    "alert": {
      "title": "Game Request",
      "body": "Bob wants to play chess",
      "action-loc-key": "PLAY"
    },
    "badge": 5
  }
}
```

### Android Push
Аналогично iOS, но вместо APNs — **FCM** (Firebase Cloud Messaging).

**Важно:** FCM недоступен в Китае → альтернативы: Jpush, PushY. Система должна быть расширяемой для замены провайдеров.

### SMS
Сторонние сервисы: **Twilio**, **Nexmo**. Коммерческие, платные.

### Email
Собственный почтовый сервер или коммерческий: **Sendgrid**, **Mailchimp**. Повышенная скорость доставки + аналитика.

## Начальная архитектура (с проблемами)

![[10.9.png]]

```
Сервисы 1..N → Система уведомлений (один сервер) → Сторонние сервисы → Устройства
```

### Три проблемы
1. **SPOF** — один сервер = единая точка отказа
2. **Плохая масштабируемость** — БД, кэш, обработка — всё на одном сервере
3. **Узкое место** — генерация HTML + ожидание сторонних сервисов перегружает систему в пик

## Улучшенная архитектура

![[10.10.png]]

### Что улучшили
- БД и кэш **вынесены** за пределы сервера уведомлений
- **Несколько серверов** уведомлений + автомасштабирование
- **Очереди сообщений** для каждого типа (iOS PN, Android PN, SMS, Email)

### Компоненты

| Компонент | Описание |
|---|---|
| **Сервисы 1..N** | Микросервисы, cron, системы — инициируют уведомления |
| **Серверы уведомлений** | API для отправки, валидация, извлечение данных из БД, запись в очередь |
| **Кэш** | Пользовательские данные, информация об устройствах, шаблоны |
| **БД** | Данные о пользователях, уведомлениях, настройках |
| **Очереди** | **Отдельная на каждый тип** (iOS, Android, SMS, Email). Буфер при нагрузке |
| **Рабочие узлы** | Достают из очереди → отправляют сторонним сервисам |
| **Сторонние сервисы** | APNs, FCM, Twilio, Sendgrid |

### Флоу отправки (6 шагов)

1. Сервис вызывает API серверов уведомлений
2. Серверы извлекают из БД/кэша: user info, device token, настройки
3. Событие записывается в **соответствующую очередь** (iOS PN → очередь iOS)
4. Рабочие узлы достают события из очередей
5. Рабочие узлы отправляют сторонним сервисам
6. Сторонние сервисы доставляют на устройства

### Пример API

```
POST https://api.example.com/v1/sms/send

{
  "to": [{"user_id": 123456}],
  "from": {"email": "from@example.com"},
  "subject": "Hello, World!",
  "content": [{"type": "text/plain", "value": "Hello, World"}]
}
```

## Надёжность

### Предотвращение потери данных

![[10.11.png]]

Уведомления записываются в **журнал (лог) в БД** перед отправкой. Если отправка не удалась → retry из журнала. Данные **не теряются**.

### Дедупликация (exactly-once?)
**Нет**, exactly-once доставку гарантировать нельзя (распределённая система). Но минимизируем дубли:
- При поступлении события → проверяем **event ID** → уже отправляли? → отклоняем
- Если новый → отправляем

## Дополнительные компоненты

### Шаблоны уведомлений
Отформатированный текст с параметрами:

```
ТЕЛО: Вы об этом мечтали. [НАЗВАНИЕ ПРОДУКТА] снова в продаже — до [ДАТА].
CTA: Заказать сейчас. Или сохранить [НАЗВАНИЕ ПРОДУКТА].
```

**Плюсы:** единый формат, меньше ошибок, экономия времени.

### Параметры уведомлений (opt-in / opt-out)

```
notification_settings:
  user_id    bigint
  channel    varchar   # push / email / sms
  opt_in     boolean   # получать или нет
```

**Перед отправкой** → проверяем opt_in. Пользователь отписался → не отправляем.

### Ограничение трафика (Rate Limiting)
Не заваливать пользователя. Слишком много уведомлений → пользователь отключит ВСЕ.

### Механизм повторных вызовов (Retry)
Не удалось отправить → **обратно в очередь** → повторная попытка. Проблема остаётся → алерт разработчикам.

### Безопасность push-уведомлений
API защищены парой **appKey / appSecret**. Только аутентифицированные клиенты могут отправлять push.

### Мониторинг очередей
Ключевая метрика: **количество ожидающих сообщений в очереди**. Растёт → рабочие узлы не успевают → **добавить узлов**.

![[10.13.png]]

Метрики: open rate, click rate, вовлечённость.
