- **Монолит** — одно приложение, всё в одном бинаре. Просто написать, просто деплоить, нет сетевых вызовов между компонентами. Монолит ≠ плохо
- **Микросервисы** — система разбита на сервисы по зонам ответственности. Независимое масштабирование, деплой, деградация. Но сложнее отладка, тестирование, распределённые транзакции
- **SOA** — несколько сервисов, но с **одной общей БД**. Промежуточный этап между монолитом и микросервисами. Нарушает [[#Мандат Безоса]]
- **Мандат Безоса** — у каждого сервиса **своя БД**, общение **только через API**. Нельзя лезть в чужую БД напрямую
- Монолит — для стартапов, [[Свойства и типы нагрузки|low latency]], маленьких команд. Микросервисы — **по умолчанию** для всего остального
- Микросервис — не про размер, а про **границу ответственности**
- Очереди не нарушают мандат Безоса — даже через очередь я прихожу в API сервиса, сервис сам решает как обработать

## Монолит

Одно приложение, которое отвечает за всё. Кредиты, депозиты, история — всё в одном бинаре, одной кодовой базе.

### Плюсы
- просто написать, быстро проверить гипотезу
- нет сетевых вызовов между компонентами — всё локальные вызовы функций
- просто тестировать — поднял одно приложение и всё
- просто деплоить — один артефакт

### Минусы
- масштабирование: хочу масштабировать только депозиты — придётся масштабировать всё
- один деплой на всё: изменил кредиты — передеплоил и депозиты тоже
- упал монолит — лежит всё
- кодовая база растёт, усложняется, замедляет разработку

### Когда использовать
- стартап, проверка гипотезы — не тратим время на архитектуру
- [[Свойства и типы нагрузки|low latency]] — никаких лишних сетевых хопов
- маленькая команда

**Важно:** монолит ≠ плохо. Можно [[Масштабирование|горизонтально масштабировать]] монолит (несколько инстансов за балансировщиком). Есть команды, которые отлично живут на монолитах.

## Микросервисы

Система разбита на отдельные сервисы, каждый отвечает за свою зону ответственности. Микросервис — не про размер, а про границу ответственности.

### Плюсы
- независимое масштабирование: нужно масштабировать только депозиты — масштабируем только их
- независимая разработка и деплой (если API не ломаем)
- независимая деградация: депозиты лежат — кредиты работают
- разные технологии для разных задач: Rust тут, Go там, своя БД у каждого
- распределённая кодовая база — команды не зависят друг от друга

### Минусы
- сетевой вызов отвалится вероятнее, чем локальный — больше точек отказа
- распределённые транзакции — отдельная сложная тема
- удалённый вызов дороже локального ([[Производительность|latency]], сериализация)
- сложность отладки: запрос прошёл через 20 сервисов — где проблема?
- сложность тестирования: нужно развернуть всю архитектуру
- зоопарк технологий: экспертиза размазывается

### Когда использовать
- большие компании, большие продукты
- долгосрочные проекты с растущей нагрузкой
- по умолчанию для всего, кроме стартапов и low latency

## SOA (Service-Oriented Architecture)

Несколько сервисов, но с **одной общей базой данных**. Это ключевое отличие от микросервисов.

```
SOA:                              Микросервисы:
┌─────────┐ ┌─────────┐          ┌─────────┐ ┌─────────┐
│ Сервис A│ │ Сервис B│          │ Сервис A│ │ Сервис B│
└────┬────┘ └────┬────┘          └────┬────┘ └────┬────┘
     │           │                    │           │
     ▼           ▼                    ▼           ▼
   ┌───────────────┐              ┌──────┐    ┌──────┐
   │   Общая БД    │              │ БД A │    │ БД B │
   └───────────────┘              └──────┘    └──────┘
```

### Проблемы общей БД
- один сервис может сломать данные другого
- нет изоляции — нельзя независимо масштабировать хранилище
- миграции схемы затрагивают всех

**На собеседовании:** "чем SOA отличается от микросервисов?" → общая БД vs своя БД у каждого сервиса.

## Мандат Безоса

Правило Джефа Безоса (основатель Amazon) для проектирования микросервисов:
- у каждого сервиса должна быть **своя база данных**
- сервисы общаются **только через API** (интерфейс)
- нельзя лезть в чужую БД напрямую

### Почему
- если дать другому сервису доступ к БД — он может её дропнуть, записать мусор, сломать данные
- API ограничивает: авторизация, валидация, rate limiting — контролируем, что можно делать
- изоляция: каждый сервис — хозяин своих данных

### А что с очередями?
Очереди — ok. Даже через очередь приходим в API сервиса. Сервис сам решает, как обработать сообщение. Это не обходной путь (как прямая запись в чужую БД).

### Исключения
Инфраструктурные сервисы ([[Observability|трейсинг, логирование]], потоки данных) иногда пишут напрямую в общие хранилища. Мандат — больше про продуктовые сервисы.
