- **Вертикальное** — делаем сервер мощнее (больше ядер, RAM, быстрее диск). Просто, но есть потолок и нелинейные затраты
- **Горизонтальное** — ставим несколько серверов вместо одного мощного. Нет потолка, дешевле, отказоустойчивее, но сложнее архитектура
- Вертикальное — для стартапов, проверки гипотез, [[Свойства и типы нагрузки#Low latency приложения|low latency]] (монолит на одной мощной машине)
- Горизонтальное — **по умолчанию**, если играем вдолгую. Сразу закладываемся + минимально необходимые ресурсы на узел
- Можно **комбинировать**: кластер Kafka из 10 брокеров, каждому подняли RAM с 4 до 8 ГБ — вертикальное внутри горизонтального
- Горизонтальное для [[Stateless vs Stateful сервисы|stateless]] — тривиально. Для [[Stateless vs Stateful сервисы|stateful]] — всегда головная боль (миграция данных, партиционирование, [[Балансировка — алгоритмы#Sticky Sessions (привязка к инстансу)|sticky sessions]])
- Вертикальное ×2 по цене ≠ ×2 по производительности. Ближе к потолку — огромные деньги за минимальный прирост

## Сравнение

| | Вертикальное | Горизонтальное |
|---|---|---|
| Суть | Мощнее сервер | Больше серверов |
| Потолок | Есть (физика) | Нет |
| Сложность | Просто | Сложнее (балансировка, синхронизация) |
| Отказоустойчивость | Одна точка отказа | Упал один — остальные работают |
| Стоимость | Нелинейно дорожает | Линейно растёт |
| Stateful | Ок | Головная боль |
| Когда | Стартап, low latency | По умолчанию |

## Вертикальное масштабирование

Берём существующий сервер и делаем его мощнее — больше ядер, больше RAM, быстрее диск, выше тактовая частота.

**Плюсы:**
- просто: купил мощнее железо, поставил, работает
- не нужно менять архитектуру приложения
- подходит для стартапов, проверки гипотез — когда нужно быстро

**Минусы:**
- потолок: рано или поздно упрёшься в физические ограничения (тактовая частота, максимум RAM на плате)
- нелинейные затраты: ×2 по цене ≠ ×2 по производительности
- downtime: не все серверы позволяют на горячую менять процессор или RAM

**Когда использовать:**
- стартап, быстрая проверка гипотезы
- не хочется думать об архитектуре прямо сейчас
- [[Свойства и типы нагрузки#Low latency приложения|Low latency]] ([[Архитектура бэкенда#Монолит|монолит]] на одной мощной машине)

## Горизонтальное масштабирование

Вместо одного мощного сервера — ставим несколько недорогих. Задачу выполняет не один сервер, а N серверов.

```
Вертикальное:              Горизонтальное:
┌──────────────┐           ┌──────┐ ┌──────┐ ┌──────┐
│              │           │      │ │      │ │      │
│  МОЩНЫЙ      │    vs     │ узел │ │ узел │ │ узел │
│  СЕРВЕР      │           │      │ │      │ │      │
│              │           └──────┘ └──────┘ └──────┘
└──────────────┘              ↑ балансировщик ↑
```

**Плюсы:**
- нет потолка: нужно больше — добавляй ещё машины
- дешевле: N недорогих серверов обычно выгоднее, чем один дорогой
- отказоустойчивость: упал один — остальные работают

**Минусы:**
- сложнее архитектура: нужно думать о [[Балансировка — алгоритмы|балансировке]], синхронизации данных, миграциях
- дороже в разработке: больше усилий на проектирование
- особенно больно с [[Stateless vs Stateful сервисы|stateful]] сервисами — миграция данных, партиционирование, [[Балансировка — алгоритмы#Sticky Sessions (привязка к инстансу)|sticky sessions]]

**Когда использовать:**
- по умолчанию, если играем вдолгую
- система, которая будет расти и держать нагрузку
- сразу закладываемся + берём минимально необходимые ресурсы на каждый узел

**Когда НЕ заморачиваться:**
- стартап, проверка гипотезы — просто пишем код, если нужно — вертикалим

## Связь
- [[Stateless vs Stateful сервисы]] — stateless масштабируется горизонтально тривиально
- [[Архитектура бэкенда]] — [[Архитектура бэкенда#Монолит|монолит]] чаще вертикалят, [[Архитектура бэкенда#Микросервисы|микросервисы]] горизонталят
