**Суть:** Приложение общается **только с кэшом**. Кэш сам ходит в БД при промахе. Приложение не знает, что БД существует.

## Чтение

1. Приложение идёт в кэш
2. Hit → возвращает данные
3. Miss → **кэш сам** идёт в БД → получает данные → сохраняет у себя → возвращает приложению

## Запись

1. Приложение пишет в кэш
2. Кэш пишет в БД
3. Кэш подтверждает приложению

**Плюсы:**
- простая логика приложения — одна точка обращения
- быстрый response time на чтение (после первого запроса)
- консистентность: кэш и БД всегда синхронны (кэш сам управляет)

**Минусы:**
- сложная инфраструктура — кэш должен уметь ходить в БД
- кэш упал → **сервис недоступен** (критическая зависимость)
- нужен умный кэш (не просто Redis из коробки)

**Ключевое отличие от cache aside:** кто координирует. Cache aside — приложение. Cache through — кэш.

**Связь:**
- кэш = критическая зависимость (в отличие от cache aside, где кэш опционален)
- [[Availability (доступность, девятки)]] системы зависит от availability кэша
