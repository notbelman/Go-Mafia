- **L4 (Network LB)** — работает на уровне **соединений**. Не заглядывает внутрь — просто пробрасывает connection на бэкенд. Быстрее, но тупее
- **L7 (Application LB)** — работает на уровне **запросов**. Видит HTTP, понимает содержимое — раскидывает отдельные запросы по разным серверам. Умнее, но медленнее
- L4 видит одно соединение с 10 000 запросов внутри — пробросил всё на один сервер. L7 видит каждый запрос отдельно
- **Комбинация (Яндекс):** на входе L4 (раскидывает по датацентрам по соединениям) → за ними L7 (умно распределяет запросы внутри датацентра)
- **DNS балансировка** — за одним доменом несколько IP. DNS отдаёт их в разном порядке → нагрузка размазывается. Решает проблему **единой точки отказа** балансировщика
- **GeoDNS** — DNS, который знает географию. Определяет регион по IP → направляет на ближайший датацентр. Москва → Нью-Йорк ≈ 200 мс по сети

## Сравнение L4 vs L7

| | L4 | L7 |
|---|---|---|
| Видит | Соединения | Запросы |
| Скорость | Быстрее | Медленнее (полный разбор до 7 уровня) |
| Умность | Тупее | Умнее |
| Другое название | Network LB | Application LB |

## L4 vs L7 балансировка

Уровни — из модели OSI. L4 = транспортный (TCP/порты), L7 = прикладной (HTTP).

### L4 (Network Load Balancer)

Работает на уровне **соединений**. Не заглядывает внутрь — просто пробрасывает connection на бэкенд.

- Клиент открыл соединение, отправляет 10 000 запросов → L4 видит **одно** соединение, пробросил его на один сервер
- Другой клиент, 100 запросов → пробросил на другой сервер
- Не понимает, сколько запросов внутри соединения

### L7 (Application Load Balancer)

Работает на уровне **запросов**. Видит HTTP, понимает содержимое — может раскидывать отдельные запросы по разным серверам.

[[Проксирование|Reverse Proxy]] — L7 = application level, часто тот же Nginx.

### Комбинация (как в Яндексе)

```
Клиенты
   │
   ▼
┌──────┐ ┌──────┐
│  L4  │ │  L4  │   ← раскидывают по ДЦ (по соединениям)
└──┬───┘ └──┬───┘
   │        │
   ▼        ▼
┌──────┐ ┌──────┐
│  L7  │ │  L7  │   ← умно распределяют запросы внутри ДЦ
└──────┘ └──────┘
```

## DNS балансировка

### Проблема
Балансировщик — единая точка отказа. Кто будет балансировать на балансировщик? Ещё один балансировщик?

### Решение
За одним доменным именем прячем несколько IP-адресов. DNS отдаёт их в разном порядке каждый раз.

```
$ nslookup mail.ru
→ 94.100.180.70
→ 94.100.180.71
→ 217.69.139.70
→ 217.69.139.71
```

Следующий запрос — те же IP, но в другом порядке. Клиент идёт на первый в списке → нагрузка размазывается. Если первый недоступен — клиент пробует следующий (retry).

По сути **round robin на уровне DNS**.

## GeoDNS

DNS, который знает географию. Направляет пользователя на ближайший датацентр по его IP-адресу.

### Как работает
1. Пользователь из США делает запрос
2. GeoDNS смотрит его IP → идёт в GeoIP базу (MaxMind) → определяет регион
3. Отдаёт IP ближайшего датацентра

### Зачем
[[Производительность|Latency]] зависит от расстояния. Москва → Нью-Йорк по сети ≈ 200 мс. Если есть датацентр в США — лучше направить туда.

**Нужны ли несколько датацентров?** Зависит от требований. Если latency не критичен — можно один датацентр и не заморачиваться.
