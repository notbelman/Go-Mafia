- **CRUD** — четыре базовые операции: Create (POST), Read (GET), Update (PUT/PATCH), Delete (DELETE). Отправная точка при проектировании API
- **REST** — глагол (HTTP метод) + существительное (URI ресурса). Самый распространённый стиль для внешних API. REST — концепция, RESTful — строгое соблюдение (мало кто делает)
- **gRPC** — RPC от Google. Бинарный формат Protobuf, кодогенерация, типизация из коробки. Основной кейс: **сервис → сервис** внутри [[Архитектура бэкенда|микросервисов]]
- **GraphQL** — клиент сам описывает, какие поля нужны (как SQL для API). Один endpoint, нет overfetching. Минус: сложнее на бэкенде, кэширование сложнее
- **SOAP** — XML, всё в теле запроса. Устарел. Где встречается: банки, госсистемы, legacy 15–20 лет
- **Overfetching** — API отдаёт больше данных, чем нужно. **Underfetching** — не додаёт, нужны доп. запросы. Решения: GraphQL, BFF, параметр `?fields=`
- PUT — полная замена ресурса (все поля). PATCH — частичное обновление (только изменённые)
- gRPC компактнее и быстрее JSON, но нечитаемый (бинарный) и требует кодогенерации

## Сравнение

| | REST | gRPC | GraphQL | SOAP |
|---|---|---|---|---|
| Формат | JSON | Protobuf (бинарный) | JSON | XML |
| Транспорт | HTTP | HTTP/2 | HTTP | HTTP |
| Типизация | Нет | Из коробки (.proto) | Schema | WSDL |
| Кейс | Внешний API | Сервис → сервис | Гибкие клиенты | Legacy |
| Читаемость | Высокая | Низкая | Высокая | Низкая |

## CRUD

Четыре базовые операции, покрывающие большинство API:

| Операция | Что делает | HTTP метод |
|---|---|---|
| **C**reate | Создать | POST |
| **R**ead | Прочитать | GET |
| **U**pdate | Обновить | PUT / PATCH |
| **D**elete | Удалить | DELETE |

```
POST   /users        — создать пользователя
GET    /users/{id}   — получить пользователя
PUT    /users/{id}   — полная замена
PATCH  /users/{id}   — частичное обновление
DELETE /users/{id}   — удалить
```

### PUT vs PATCH
- **PUT** — полная замена ресурса (отправляем все поля)
- **PATCH** — частичное обновление (отправляем только изменённые поля)

## REST, RESTful

Архитектурный стиль API. Запрос = **глагол** (HTTP метод) + **существительное** (URI ресурса).

### Структура запроса
- Метод: GET, POST, PUT, DELETE
- URI: `/users/5`, `/orders/123`
- Headers: метаинформация (Content-Type, Authorization)
- Body: данные в JSON (для POST, PUT, PATCH)

### Коды ответа
- **2xx** — успех (200 OK, 201 Created, 204 No Content)
- **3xx** — перенаправление
- **4xx** — ошибка клиента (400 Bad Request, 401, 403, 404)
- **5xx** — ошибка сервера (500, 502, 503)

### REST vs RESTful
- REST — концепция, набор принципов
- RESTful — API, которое строго соблюдает все принципы REST
- На практике мало кто делает строго RESTful — обычно "REST-like"

### Холивары
- GET vs POST для расчётов (`GET /rides/estimate` или `POST /rides/estimate`)
- DELETE vs PATCH для отмены (`DELETE /orders/123` или `PATCH /orders/123 {canceled: true}`)
- Правильного ответа нет — зависит от команды и контекста

**Когда использовать:** по умолчанию для внешних API (клиент → сервер).

## gRPC (Protobuf)

Remote Procedure Call от Google. Вместо JSON — бинарный формат Protobuf. Вместо HTTP-глаголов — вызов функций.

### Как работает
1. Описываем контракт в `.proto` файле (типы, методы)
2. Кодогенерация — из `.proto` получаем клиент и сервер на любом языке
3. Вызываем удалённую функцию как локальную

### Плюсы
- компактнее JSON — бинарный формат, меньше трафика
- типизация из коробки — ошибки на этапе компиляции, а не в рантайме
- кодогенерация — не нужно писать клиент руками
- быстрее сериализация/десериализация

### Минусы
- нечитаемый формат (бинарный) — сложнее дебажить
- нужна кодогенерация — дополнительный шаг в сборке

### Когда использовать
- внутри [[Архитектура бэкенда|микросервисов]] (сервис → сервис) — основной кейс
- можно и для клиентов (пример: Яндекс.Облако отдаёт gRPC SDK)

## GraphQL

Язык запросов для API. Клиент сам описывает, какие поля ему нужны — как SQL, но для API.

### Пример запроса
```graphql
query {
  user(id: 5) {
    name
    email
    posts { title }
  }
}
```

Клиент получит только `name`, `email` и `titles` постов — ничего лишнего.

### Три типа операций
- **Query** — чтение данных
- **Mutation** — изменение данных (аналог POST/PUT/DELETE)
- **Subscription** — подписка на события (реалтайм)

### Плюсы
- клиент запрашивает ровно то, что нужно — нет overfetching
- один endpoint для всего (обычно `POST /graphql`)
- клиент не зависит от структуры бэкенда

### Минусы
- сложнее на бэкенде — нужен резолвер для каждого поля
- кэширование сложнее — один endpoint, разные запросы
- может быть тяжёлым, если клиент запросит слишком глубокую вложенность

### Когда использовать
- много разных клиентов с разными потребностями (mobile, desktop, TV)
- нужна гибкость запросов

## SOAP

Протокол API, где всё передаётся в теле запроса в формате XML.

```xml
<soap:Envelope>
  <soap:Body>
    <GetUser>
      <UserId>5</UserId>
    </GetUser>
  </soap:Body>
</soap:Envelope>
```

### Почему устарел
- многословный — XML тяжелее JSON
- трудночитаемый, сложнее в отладке

**Где встречается:** банки, госсистемы, legacy 15–20 лет.

## Overfetching и Underfetching

### Overfetching
API отдаёт **больше** данных, чем нужно. Мобилке нужно только имя, а `GET /users/5` возвращает имя, email, адрес, историю заказов, аватарку в base64.

### Underfetching
API **не додаёт** данные. Нужен пост + автор + комменты — три отдельных запроса вместо одного.

### Почему проблема
Один API переиспользуется для разных платформ: Desktop (мощный, хорошая сеть), Mobile (слабый, дорогой трафик), TV. Один endpoint не может угодить всем.

### Решения
- **GraphQL** — клиент сам выбирает поля
- **BFF (Backend for Frontend)** — отдельный API для каждой платформы
- **Разные endpoints** — `/users/5/short`, `/users/5/full`
- **Параметр fields** — `GET /users/5?fields=name,email`
