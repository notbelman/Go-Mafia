- Расчёт нагрузки — прикидка на коленке: RPS → трафик → storage → диски/шарды. Не точный расчёт, а оценка порядка величин
- **RPS** = DAU x действий_на_пользователя / 86400 (секунд в сутках). Пиковый RPS может быть в 2-5 раз выше среднего
- **Трафик** = RPS write x размер_одного_запроса. Из трафика считаем storage и понимаем нагрузку на диски/сеть
- **Storage** = трафик на запись x retention period x replication factor + бэкапы
- **Шарды** — считаем по объёму (диски / ёмкость) и по RPS (RPS / пропускная способность одной БД). Если оба дают похожую цифру — хороший знак
- Константы: 1 день = **86400** секунд, 1000 байт ~ 1 КБ, UTF-8 кириллица = 2 байта на символ
- HDD vs SSD выбираем по пропускной способности, не по объёму. HDD: 100-200 МБ/с, SSD в разы быстрее
- Точно посчитать можно только нагрузочным тестированием на реальном железе. Балун: «Нельзя сказать, какой RPS держит PostgreSQL. It depends»

---

### Порядок расчёта

1. **RPS** — сколько запросов в секунду (из DAU)
2. **Трафик** — сколько данных в секунду/день/год (из RPS x размер запроса)
3. **Storage** — сколько хранить на N лет (из трафика x retention)
4. **Диски и шарды** — сколько физического железа нужно

### Константы для быстрого счёта

- 1 день = **86400** секунд (запомнить)
- 1000 байт ~ 1 КБ, 1.000.000 ~ 1 МБ, 1.000.000.000 ~ 1 ГБ (грубая оценка)
- UTF-8 кириллица: 1 символ = 2 байта

### Расчёт RPS

```
RPS = DAU × действий_на_пользователя_в_день / 86400
```

### Пример: WhatsApp (чтение)

- DAU = 100.000.000 (100 млн)
- Пользователь читает сообщения 10 раз в день
- RPS read = 100.000.000 x 10 / 86400 ~ **11.574 RPS**

### RPS на запись

Если соотношение read/write = 5:1 (читают в 5 раз чаще, чем пишут):

```
RPS write = RPS read / 5 ≈ 2.315 RPS
```

Или считаем напрямую: пользователь пишет 2 сообщения в день -> 100M x 2 / 86400 ~ 2.315 RPS.

### Откуда брать входные данные

**DAU** — спрашиваем у бизнеса. Не знает — предлагаем целевую цифру для MVP.

**Действий на пользователя** — спрашиваем или прикидываем из пользовательского опыта. «Сколько в среднем сообщений в день отправляет/читает пользователь?»

**Read/write ratio** — характер нагрузки. Мессенджер: читают больше, чем пишут. Аналитика: пишут больше, чем читают.

### Нюансы RPS

RPS — усреднённый. Пиковый RPS может быть в 2-5 раз выше (все активны вечером, никого ночью). На интервью можно упомянуть пики, но считать по среднему — ок.

Разные операции — разный RPS. Чтение сообщений, отправка, просмотр чатов, статусы — у каждого свой RPS. Считаем для core-операций.

### Расчёт трафика

```
Traffic per second = RPS write × размер_одного_запроса
```

### Пример: WhatsApp (запись)

- RPS write ~ 2.315
- Максимальный размер сообщения: 1000 символов x 2 байта (UTF-8 кириллица) = 2000 байт

```
Per second = 2.315 × 2.000 = 4.630.000 байт ≈ 4.6 МБ/с
Per day    = 4.6 МБ × 86.400 ≈ 397 ГБ/день (≈ 400 ГБ)
Per year   = 400 ГБ × 365 ≈ 146 ТБ/год (≈ 150 ТБ)
```

### Быстрый перевод единиц

Убираем три нуля — переходим на следующий уровень:

```
4.630.000 байт
    → убрали 1000 → 4.630 КБ
    → убрали 1000 → 4.6 МБ
```

Грубая оценка (в реальности 1024, но для коленочных расчётов — 1000).

### Трафик на чтение

Если read/write = 5:1, то трафик на чтение ~ 4.6 МБ x 5 = 23 МБ/с. Суммарный трафик ~ 27 МБ/с. Это копейки — даже HDD справится (100+ МБ/с throughput).

### Расчёт Storage

Трафик на запись x retention period:

```
150 ТБ/год × 2 года = 300 ТБ (если хранить 2 года)
150 ТБ/год × ∞ = считаем на 2-5 лет вперёд
```

WhatsApp: «хранить всегда» -> закладываемся на 2 года ~ 300 ТБ.

### Репликация и бэкапы

Replication factor 2 (одна реплика): 300 x 2 = 600 ТБ. Плюс бэкапы — округляем до 700 ТБ.

### Выбор типа диска (HDD vs SSD)

Зависит от **пропускной способности**, не от объёма.

Суммарный трафик (read + write) ~ 27 МБ/с. Плюс индексы, служебные чтения — пусть 200 МБ/с. HDD даёт 100-200 МБ/с. Хватает? Хватает -> берём HDD (дешевле).

Если бы трафик был 2 ГБ/с — HDD не справится, нужен SSD. Или охлаждение данных: свежие на SSD, старые партиции на HDD.

**IOPS** (операций в секунду): SSD и HDD отличаются в 100 раз. Но БД батчат запросы, не ходят на диск на каждый чих — это нивелирует разницу.

### Количество дисков

```
Дисков = общий объём / ёмкость одного диска
       = 700 ТБ / 6 ТБ (HDD) = 117 дисков
```

С учётом репликации: 117 / 2 = ~59 дисков на одну реплику.

### Нужно ли шардировать

Смотрим: 59 дисков влезут в один сервер? В дисковую полку помещается 8-16 дисков. 59 дисков / 8 дисков на шард ~ **7-8 шардов**.

Смотрим RPS: 11.500 read + 2.300 write. Одна БД держит ~1-2К RPS (грубо, it depends). 11.500 / 2.000 ~ 6 шардов по RPS. Совпадает с оценкой по дискам — хороший знак.

### Итоговый сетап

```
7 шардов × 2 (replication factor) = 14 инстансов БД
В каждом шарде: 8 HDD по 6 ТБ
```

### Важно помнить

Это **усреднённая** оценка. Есть пики (утро/вечер активнее ночи), сезонность (праздники). RPS плавает. Точно посчитать можно только под реальную нагрузку на реальном железе. На коленке — только порядок величин.
