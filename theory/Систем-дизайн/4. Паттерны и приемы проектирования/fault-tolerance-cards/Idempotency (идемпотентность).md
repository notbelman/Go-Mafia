Запрос идемпотентен, если его можно выполнить несколько раз подряд и результат будет одинаковым.

## Идемпотентные vs неидемпотентные

**Идемпотентные:**
- GET — сколько бы раз ни читал, результат один
- PUT — «баланс Кати = 500», сколько раз ни повтори — 500
- DELETE — удалится только один раз, повторное удаление ничего не сделает

**Неидемпотентные:**
- POST (создание) — каждый повтор создаёт новую запись
- Операции инкремента — «списать 20.000₽» повторили 3 раза → списали 60.000₽

## Проблема с ретраями

Клиент отправил оплату 20.000₽. Сервер обработал, но ответ потерялся. Клиент ретраит → ещё 20.000₽ списалось. Ещё раз → ещё 20.000₽. Итого 60.000₽ вместо 20.000₽.

## Решение: ключ идемпотентности

Клиент генерирует уникальный идентификатор запроса (request_id, sequence_id, idempotency_key). Сервер запоминает, какие ключи уже обработал. Пришёл повторный запрос с тем же ключом — сервер не обрабатывает заново, а возвращает сохранённый результат.

## Правило

Ретраить неидемпотентные запросы **нельзя** без ключа идемпотентности. Это стандарт — при проектировании ретраев всегда учитывать идемпотентность.

## Связь
- [[Retry + Backoff]] — ретраи безопасны только с идемпотентностью
- [[Transaction Outbox]] — outbox worker может повторно отправить сообщение → получатель должен быть идемпотентным
