- **Event-Driven Architecture** — сервисы взаимодействуют через события вместо прямых синхронных вызовов. Публикация факта -> подписчики реагируют
- **Event Notification** — один топик, паблишер публикует факт «это случилось», подписчики обрабатывают. Самый простой паттерн
- **Event Collaboration (шина)** — все сервисы общаются **исключительно** через топики. Десятки топиков, цепочка событий проходит через шину
- **Event-carried State Transfer** — вместе с событием передаются данные. Подписчик хранит локальную копию, не ходит за данными каждый раз
- Пример Яндекс.Еда: заказ бургера -> цепочка асинхронных событий: «кафе приняло», «готовится», «курьер найден», «доставлено»
- Предупреждение Балуна: не притуливать EDA везде. Как с темплейтами в C++ — «изучил, теперь везде метапрограммирование»
- Шина = единая точка отказа. Асинхронные цепочки сложнее дебажить, чем синхронные вызовы
- Event-carried State Transfer — дублирование данных ради latency и слабой связанности, но [[Eventual Consistency|eventual consistency]]

---

| Паттерн | Что в событии | Связанность | Сложность | Когда |
|---|---|---|---|---|
| Event Notification | Факт + минимум данных | Слабая | Низкая | Одно действие -> несколько независимых реакций |
| Event Collaboration | Факт + данные для следующего шага | Слабая (через шину) | Высокая | Полная асинхронность всей системы |
| Event-carried State Transfer | Факт + полные данные сущности | Минимальная | Средняя | Жёсткие требования по latency |

### Зачем Event-Driven

Яндекс.Еда: пользователь заказал бургер. Дальше нужно: подтвердить в кафе, найти курьера, доставить. Это может занять часы. Нельзя всё это время держать пользователя с крутящимся спиннером. Заказ создаётся -> пользователя отпускаем -> дальше цепочка асинхронных событий: «кафе приняло», «готовится», «курьер найден», «курьер в пути», «доставлено». Пользователя оповещаем о каждом событии.

### Плюсы и минусы EDA

**Плюс:** слабая связанность, масштабируемость, асинхронность.

**Минус:** сложнее дебажить. Асинхронные цепочки труднее отследить, чем синхронные вызовы. Очередь/шина — единая точка отказа.

### Предупреждение Балуна

Многие, изучив event-driven, пытаются притулить его везде. Как с шаблонами в C++ — «изучил темплейты, теперь везде метапрограммирование». Использовать там, где действительно нужна асинхронность, а не везде подряд.

### Event Notification

Сервис публикует событие в топик. Подписчики вычитывают и обрабатывают. Самый простой паттерн событийной архитектуры.

### Пример Event Notification

Яндекс.Еда: сервис заказов создал заказ -> положил событие `order_created` в топик -> отпустил клиента. Кафе-сервис подписан на топик — забирает событие и начинает обработку. Delivery-сервис тоже подписан — начинает искать курьера.

### Отличие от Pub/Sub

По сути то же самое. [[Архитектурные паттерны#Pub/Sub (Publisher-Subscriber)|Pub/Sub]] — название паттерна коммуникации. Event Notification — название в контексте событийной архитектуры. Один топик, несколько подписчиков, паблишер не знает о них.

### Ключевое свойство Event Notification

Событие — **факт, что что-то произошло**. Не запрос «сделай что-то», а уведомление «это случилось». Подписчик сам решает, что с этим делать. Паблишер не управляет подписчиками.

### Когда использовать Event Notification

- Одно действие порождает несколько независимых реакций
- Паблишеру не важен результат обработки подписчиками
- Подписчики могут добавляться/удаляться без изменения паблишера

### Event Collaboration (шина)

Все сервисы общаются **исключительно** через шину событий (очередь с множеством топиков). Никаких прямых вызовов между сервисами.

### Пример Event Collaboration: оформление заказа

1. **Basket** -> кладёт `order_requested` в топик
2. **Order** подписан -> валидирует -> кладёт `order_validated` в топик
3. **Payment** подписан -> обрабатывает оплату -> кладёт `payment_processed` в топик
4. **Order** подписан -> подтверждает заказ -> кладёт `order_confirmed` в топик
5. **Basket** подписан -> показывает пользователю результат

Цепочка событий проходит через шину. Сервисы не знают друг о друге напрямую — только через топики.

### Отличие от Event Notification

Event Notification — один топик, один паблишер, несколько подписчиков. Простая веерная рассылка.

Event Collaboration — **десятки топиков**, сервисы и публикуют, и подписываются. Полноценная шина для всей коммуникации между сервисами. Маршрут запроса проходит через несколько топиков последовательно.

### Плюсы Event Collaboration

- Полная асинхронность всей системы
- Слабая связанность — сервисы не знают друг о друге
- Иногда даёт больше прозрачности: по топикам видно маршрут запроса

### Минусы Event Collaboration

- **Шина = единая точка отказа.** Шина упала -> всё упало
- Сложнее дебажить асинхронные цепочки, чем синхронные вызовы
- Иногда наоборот запутывает — непонятно, кто куда подписан и где что ломается
- Злоупотребление: не нужно пихать шину везде, только там, где асинхронность оправдана

### Event-carried State Transfer

Сервис хранит у себя локальную копию данных другого сервиса, полученную через события. Не ходит за данными каждый раз — они уже есть.

### Пример State Transfer

Кафе-сервис обрабатывает заказы. Ему нужна информация о заказчике (имя, адрес, телефон). Наивно — каждый раз ходить в сервис пользователей. С state transfer — данные о заказчиках реплицируются в кафе-сервис через события. Кафе-сервис хранит локальную копию и отвечает быстро.

### Как работает State Transfer

1. Сервис пользователей обновил профиль -> публикует `user_updated` с данными
2. Кафе-сервис подписан -> получает событие -> обновляет свою локальную копию
3. При обработке заказа кафе-сервис берёт данные пользователя из своей БД, а не ходит в чужой сервис

### Зачем State Transfer

- Уменьшает latency — данные локальные, не нужен сетевой вызов
- Уменьшает связанность — кафе-сервис не зависит от доступности сервиса пользователей
- Разгружает сервис-источник — меньше входящих запросов

### Минусы State Transfer

Дублирование данных — антипаттерн в классическом понимании. Данные о пользователях хранятся в двух местах. [[Eventual Consistency|Eventual consistency]] — локальная копия может отставать. Нужна синхронизация, которая может сломаться.

### Когда State Transfer оправдан

Жёсткие требования по latency. Сервис-источник перегружен. Данные меняются редко, а читаются часто.
