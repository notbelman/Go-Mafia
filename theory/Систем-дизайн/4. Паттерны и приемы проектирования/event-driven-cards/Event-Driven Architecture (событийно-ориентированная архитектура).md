Сервисы взаимодействуют через события. Вместо прямых синхронных вызовов — публикация событий, на которые подписаны другие сервисы.

## Зачем

Яндекс.Еда: пользователь заказал бургер. Дальше нужно: подтвердить в кафе, найти курьера, доставить. Это может занять часы. Нельзя всё это время держать пользователя с крутящимся спиннером. Заказ создаётся → пользователя отпускаем → дальше цепочка асинхронных событий: «кафе приняло», «готовится», «курьер найден», «курьер в пути», «доставлено». Пользователя оповещаем о каждом событии.

## Три паттерна внутри

**Event Notification** — сервис публикует событие, подписчики обрабатывают. Самый простой.

**Event-carried State Transfer** — вместе с событием передаются данные других сущностей. Подписчик хранит локальную копию, не ходит за ней.

**Event Collaboration (шина)** — все сервисы общаются исключительно через топики. Цепочка событий проходит через шину.

## Плюсы и минусы

**Плюс:** слабая связанность, масштабируемость, асинхронность.

**Минус:** сложнее дебажить. Асинхронные цепочки труднее отследить, чем синхронные вызовы. Очередь/шина — единая точка отказа.

## Предупреждение Балуна

Многие, изучив event-driven, пытаются притулить его везде. Как с шаблонами в C++ — «изучил темплейты, теперь везде метапрограммирование». Использовать там, где действительно нужна асинхронность, а не везде подряд.
