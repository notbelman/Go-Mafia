- **Leader Election** — выбор нового мастера, когда текущий упал. 4 способа: etcd/ZK lease, Bully, Raft, Paxos
- Через **etcd/ZooKeeper** — атомарная запись с lease (TTL). Кто первый записал — тот лидер. Lease истёк -> фолловеры пытаются записать
- **Bully** — у каждой реплики ранг, мастер — с наивысшим. Не нужен внешний сервис, но зависит от определения «узел мёртв»
- **Raft** — голосование: кандидат отправляет RequestVote, большинство голосов -> лидер. [[Архитектурные паттерны#Heartbeat (сердцебиение)|Heartbeat]] лидера пропал -> новый раунд
- **Distributed Lock** — эксклюзивный доступ к ресурсу через [[Redis]]: `SET resource NX PX 30000`. NX = только если нет, PX = TTL
- TTL в блокировке — страховка от мёртвых клиентов. Random value — защита от удаления чужой блокировки (data race)
- Leader Election и Distributed Lock строятся на одном принципе: «кто первый записал, тот и владелец»

## Leader Election

### Способ 1: через etcd/ZooKeeper (lease)

Используем KV-хранилище с механизмом **lease** (аренда = TTL, который можно продлевать).

1. Реплика пытается записать `PUT /database/leader = my_id` с lease на 5 секунд
2. Запись атомарная — только один получит `true`
3. Лидер периодически продлевает lease ([[Архитектурные паттерны#Heartbeat (сердцебиение)|heartbeat]])
4. Фолловеры **watch**-ат этот ключ
5. Лидер упал -> lease истёк -> ключ удалился -> фолловеры получают событие
6. Фолловеры пытаются записать — кто первый, тот новый лидер

**Плюс:** простой, надёжный, etcd/ZK обеспечивают консистентность.
**Минус:** зависимость от внешнего сервиса (etcd/ZK).

### Способ 2: алгоритм забияки (Bully)

Каждой реплике заранее назначается **ранг** (0, 1, 2, 3, 4, 5). Мастер — с наивысшим рангом.

1. Узел замечает: мастер (ранг 5) не отвечает
2. Рассылает «ВЫБОРЫ» всем узлам **выше** своего ранга
3. Те в свою очередь рассылают «ВЫБОРЫ» ещё выше
4. Узел с наивысшим рангом из живых понимает: я главный
5. Рассылает всем: «Я новый лидер»

**Плюс:** не нужен внешний сервис.
**Минус:** зависит от корректности определения «узел мёртв».

### Способ 3: Raft

Узлы голосуют. Кандидат отправляет `RequestVote`, получает большинство голосов -> становится лидером. Лидер шлёт [[Архитектурные паттерны#Heartbeat (сердцебиение)|heartbeat]] -> фолловеры знают, что он жив. Нет heartbeat -> новый раунд голосования.

Есть отличная визуализация: [thesecretlivesofdata.com/raft](http://thesecretlivesofdata.com/raft) — 5 минут прокликать, и принцип понятен.

### Способ 4: Paxos

Более академический алгоритм. Сложнее Raft, но решает ту же задачу. На практике чаще используют Raft.

## Distributed Lock (распределённая блокировка)

Механизм, обеспечивающий эксклюзивный доступ к ресурсу в распределённой системе. В одну единицу времени — только один клиент.

### Реализация через Redis

Блокировка — одна атомарная команда:

```
SET resource_name my_random_value NX PX 30000
```

- **NX** — вставить только если ключа нет (атомарно)
- **PX 30000** — TTL 30 секунд (автоудаление)
- **my_random_value** — уникальное значение клиента

Два клиента одновременно шлют SET NX -> только один получит OK. Второй получит отказ — ресурс залочен.

### Зачем TTL

Если клиент взял блокировку и упал — без TTL блокировка останется навсегда. Никто больше не сможет работать с ресурсом. TTL — страховка: через 30 секунд блокировка снимется автоматически.

### Зачем random value

Снятие блокировки — в одной мини-транзакции [[Redis]]:

```
GET resource_name
если значение == my_random_value → DELETE resource_name
```

**Без random value — data race:** у блокировки осталось 50мс TTL. Клиент 1 шлёт DELETE, но запрос идёт 100мс. За это время TTL истёк, блокировка удалилась. Клиент 2 успел взять блокировку. И тут приходит DELETE от клиента 1 — удаляет **чужую** блокировку.

Random value решает: клиент 1 проверяет — значение не моё -> не удаляю.
