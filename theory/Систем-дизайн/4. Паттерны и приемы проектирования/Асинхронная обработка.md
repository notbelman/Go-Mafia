## MapReduce

Модель распределённых вычислений: разбить большую задачу на части, обработать параллельно на разных машинах, собрать результат.

### Проблема MapReduce

Google Analytics: приходит файл от гигабайта до терабайта. Нужно посчитать, сколько раз встречается каждое слово. Файл не помещается на одной машине. Как обработать?

### Четыре этапа

**1. Split** — большой файл разбивается на чанки определённого размера. Чанки раскидываются по разным хостам в кластере.

**2. Map** — на каждом хосте выполняется функция map, которую пишет программист. Пример: встретил слово -> записал `(слово, 1)`. Для каждого чанка — локальный результат.

**3. Shuffle** — инфраструктура собирает одинаковые ключи (слова) с разных хостов на одни чанки. Группировка перед reduce. Программист это не пишет — делается автоматически.

**4. Reduce** — на каждом хосте выполняется функция reduce, которую пишет программист. Пример: суммировать все единички для каждого слова. На выходе — итоговый результат.

### Что пишет программист

Только две функции: **map** и **reduce**. Всё остальное (split, shuffle, распределение по хостам, отказоустойчивость) — делает инфраструктура.

### Это не про latency

MapReduce — система про **пропускную способность**, не про скорость ответа. Обработка терабайта может занять часы. Зато кластер из тысячи машин обрабатывает параллельно — throughput огромный.

### Map и Reduce — откуда названия

Из функционального программирования. `map` — применить функцию к каждому элементу. `reduce` (fold) — свернуть список в одно значение. В JavaScript, Java (Streams), Python — те же самые функции. Если незнакомо — лучше сначала разобраться на примерах в своём языке.

### Реализации MapReduce

Hadoop (оригинальная), Yandex YT (Яндекс), Spark (более современная альтернатива).

## Отложенное выполнение (Deferred Execution)

Длительная операция не выполняется синхронно — задача складывается в очередь и обрабатывается в своём темпе.

### Проблема отложенного выполнения

YouTube: пользователь загружает видео на 1 ГБ. Его нужно декодировать, проверить цензуру, распознать контент, сгенерировать превью. Это может занять минуты или часы. Нельзя держать пользователя с крутящимся спиннером всё это время.

### Решение

1. Пользователь загружает видео
2. Сервер принимает файл, складывает задачу в **очередь**
3. Пользователю сразу ответ: «видео принято, обрабатывается»
4. У пользователя — список загрузок со статусами и прогнозом времени
5. Воркеры вычитывают задачи из очереди и обрабатывают в своём ритме

### Почему время обработки плавает

Сегодня видео загрузилось за 30 минут, завтра — за 3 часа. Разница — в размере очереди. Много пользователей загружают одновременно -> очередь длиннее -> дольше ждать. Воркеры обрабатывают с постоянной скоростью, а входящий поток переменный.

### Ключевая идея

Очередь — буфер между непредсказуемым входящим потоком и фиксированными мощностями обработки. Размазывает пики нагрузки во времени. Пользователь не ждёт — его отпускают сразу.

### Когда использовать отложенное выполнение

- Операция занимает значительно больше допустимого response time
- Пользователю не нужен результат прямо сейчас
- Нагрузка неравномерная — бывают всплески
