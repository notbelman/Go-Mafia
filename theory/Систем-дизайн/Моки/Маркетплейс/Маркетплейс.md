- Маркетплейс с двумя акторами: **покупатель** (ищет, покупает) и **менеджер/CCM** (управляет каталогом, ценами, остатками)
- **MAU 1M, DAU 30K.** 4 категории, ~100-150 товаров. Read-heavy: 20 просмотров vs 1 покупка на юзера
- **RPS read 7** (пик 35), **RPS write 0.35** (пик 1.7) — копейки. Трафик: 70 МБ/с через CDN (фото), backend ~70 КБ/с
- **ASR: read-heavy + консистентность остатков.** Каталог кэшируем агрессивно, при покупке — strong consistency
- **Два каталога:** Global Catalog (менеджер пишет) → Kafka → Product Service (покупатель читает). Изоляция
- **Эволюция:** простой монолит → + Redis кэш → + Kafka синхронизация каталогов → + Inventory Service (Saga) → + ClickHouse (аналитика) → партиции/реплики PG

## Функциональные требования

1. **Категории товаров** — 4 категории, навигация по ним
2. **Отображение товаров** — листинг, карточка товара (фото, описание, цена, название)

**Два актора:**
- **Покупатель** — просматривает, покупает

## Нефункциональные требования

| Параметр | Значение |
|---|---|
| MAU | 1 000 000 |
| DAU | 30 000 (~3% от MAU) |
| Категорий | 4 |
| Товаров | ~100-150, динамически меняется |
| Просмотров/день на юзера | 20 |
| Покупок/день на юзера | 1 |
| Read/Write ratio | 20:1 |
| P95 latency | < 120 мс |
| Availability | 99.95% |
| Retention | без ограничений |

### ASR

1. **Read-heavy** — 20 просмотров vs 1 покупка = 20:1. Определяет: кэширование, CDN для фото, реплики на чтение
2. **P95 < 120 мс** — жёсткий latency, нужен кэш для каталога
3. **Консистентность остатков** — нельзя продать товар которого нет. При покупке — strong consistency
4. **Каталог маленький** (100-150 товаров) — целиком влезает в Redis

### Где eventual допустима

- Каталог для покупателя — менеджер поменял цену, юзер увидит через 1-2 сек
- История заказов — задержка секунды ок
- Уведомления — асинхронно

### Где strong обязательна

- Остатки при покупке — `UPDATE quantity - N WHERE quantity >= N`
- Создание заказа, оплата — деньги

## Расчёт нагрузки

### RPS

```
Read:  30 000 × 20 / 86 400 ≈ 7 RPS, пик ×5 = 35 RPS
Write: 30 000 × 1 / 86 400 ≈ 0.35 RPS, пик ×5 = 1.7 RPS
```

### Трафик (сеть)

```
Карточка товара = ~2 МБ (в основном фото)
Фото → через CDN, не через backend

Backend (JSON без фото):
  Read:  7 × 5 КБ = 35 КБ/с, пик = 175 КБ/с
  Write: 0.35 × 1 КБ = 0.35 КБ/с

CDN (фото):
  35 × 2 МБ = 70 МБ/с — CDN справится

Итого backend: ~175 КБ/с в пике — ничто
```

### Storage

```
Каталог: 150 товаров × 5 КБ = 750 КБ — копейки
Фото: 150 товаров × 5 фото × 500 КБ = 375 МБ → S3

Заказы:
  1 заказ ≈ 0.5 КБ
  В день = 30 000 × 0.5 КБ = 15 МБ
  В год = 5.5 ГБ
  За 5 лет + реплика = 55 ГБ — один диск
```

**Итог:** шардирование не нужно. Один PG с репликой. Каталог целиком в Redis. Фото через CDN/S3.

```sql
  id              UUID PK

  updated_at      TIMESTAMP
```

### PG_ORDER

```sql
orders:
  id              UUID PK
  user_id         UUID
  total_amount    DECIMAL
  status          ENUM        -- pending → reserved → paid → delivering → delivered / failed / expired
  delivery_address TEXT
  payment_method  VARCHAR

  id              UUID PK

```

```
{
```

## Архитектура — два каталога

### Зачем два каталога

| | Global Catalog | Product Service (Users Catalog) |
|---|---|---|
| Кто пользуется | Менеджер/CCM | Покупатель |
| Операции | CRUD товаров, цены, остатки | Только чтение |
| БД | PG (global catalog) | PG (product) + Redis |
| Консистентность | Источник правды | Eventual (через Kafka) |

**Изоляция:** менеджер сломал что-то в CMS → покупатели продолжают видеть последний валидный каталог.

### Синхронизация Global → Product

```
1. Менеджер добавил товар / поменял цену / обновил остаток
2. Global Catalog Service → PG (global catalog)
3. Global Catalog Service → Kafka (топик: catalog.updates)
   { event: "product.updated", product_id: 5, price: 500, quantity: 80 }
4. Consumer читает из Kafka → пишет в PG (product) + инвалидирует Redis
5. Покупатель видит обновлённые данные (через 1-2 сек)
```

## Кэширование каталога (Redis)

### Стратегия: Cache-Aside + Event-driven инвалидация

**Чтение:**
```
GET /products/{id} → Redis GET product:123
  → hit? → отдаём
  → miss? → PG_CATALOG → Redis SET product:123 TTL 1h → отдаём
```

**Инвалидация:**
```
Менеджер обновил товар → Global Catalog → Kafka (catalog.updates)
→ Consumer → PG_CATALOG + Redis: DEL product:{id}
```

TTL 1 час как подстраховка — даже если Kafka consumer отстал, через час протухнет.

### Вытеснение: LRU

```
maxmemory-policy: allkeys-lru
```

150 товаров × 5 КБ = 750 КБ — всё влезает, вытеснения реально не будет.

## Saga — флоу покупки (хореография)

```
1. Order Service → PG_ORDER: INSERT order (status: pending)
                 → Kafka: order.created

2. Inventory Service ← Kafka (order.created)
   → PG_CATALOG: UPDATE quantity - N WHERE quantity >= N
   → affected rows = 1? → Kafka: inventory.reserved
   → affected rows = 0? → Kafka: inventory.failed ("товар закончился")

3. Order Service ← Kafka (inventory.reserved)
   → PG_ORDER: UPDATE status = reserved
   → Kafka: order.reserved → Payment Service

4. Payment Service ← Kafka (order.reserved)
   → контур → оплата
   → Kafka: payment.success / payment.failed

5a. Order Service ← Kafka (payment.success)
    → PG_ORDER: UPDATE status = paid
    → Kafka: order.paid → Notification Service ("Заказ оплачен")

5b. Order Service ← Kafka (payment.failed)
    → PG_ORDER: UPDATE status = failed
    → Kafka: order.failed → Inventory Service (quantity + N, вернуть резерв)
    → Notification Service ("Оплата не прошла")
```

### Outbox внутри каждого шага Saga

```
BEGIN TX
  INSERT INTO orders (...)
  INSERT INTO outbox (event_type: 'order.created', payload, sent: false)
COMMIT

Outbox Relay → SELECT WHERE sent=false → Kafka → UPDATE sent=true
```

Saga определяет **что делать**, outbox гарантирует **что сообщение дойдёт**.

### Почему хореография, а не оркестратор

3 шага — хореография достаточна. Если добавятся промокоды, лояльность, кэшбэк (7+ шагов) → тогда Saga Orchestrator.

## Масштабирование PG_ORDER

### Реплики

```
PG_ORDER (master) → sync replica (failover, деньги)
                  → async replica 1 (саппорт, админка)
                  → async replica 2 (аналитики) или ClickHouse
```

| Кто | Куда ходит |
|---|---|
| Покупатель | Master |
| Саппорт | Async replica 1 |
| Аналитики | ClickHouse (OLAP) |

### Партиционирование

```sql
PARTITION BY RANGE (created_at)
  orders_2026_01, orders_2026_02, ...
```

- "Мои заказы за месяц" → одна партиция
- Старые партиции → холодное хранилище (HDD)

### Шардирование (если вырастем)

```
По user_id: Shard N = user_id % N
```

При 35 RPS не нужно. Но если DAU вырастет в 100x — готовы.

## Bottlenecks при росте нагрузки

| Компонент | Проблема | Решение |
|---|---|---|
| **PG_CATALOG (остатки)** | Горячий товар — все декрементят одну строку, lock contention | Optimistic locking, очередь покупок, Redis DECR |
| **PG_ORDER** | CPU на потолке от аналитиков | Отдельная реплика → ClickHouse |
| **Redis (каталог)** | Товаров > 100К | Redis Cluster |
| **Kafka consumer lag** | Consumer не успевает | Больше партиций + consumer group |
| **Платёжный шлюз** | Внешняя зависимость, тормозит | Таймаут + очередь + retry |

### Горячий товар — главный bottleneck

```
Решения по нарастанию:
1. Optimistic locking: UPDATE WHERE version = X → retry
2. Очередь покупок: горячий товар → Kafka → последовательно
3. Redis DECR: атомарный декремент без лока → синхронизация с PG
```

## Stateless vs Stateful

| Компонент | Тип |
|---|---|
| Все сервисы (Product, Cart, Order, Inventory, Payment, Notification, Global Catalog) | **Stateless** |
| Outbox Relay / Consumers / Воркеры | **Stateless** (offset в Kafka, sent в PG) |
| PG, Redis, Kafka | **Stateful** |

Все сервисы stateless → горизонтально масштабируемы без проблем.

## Эволюция архитектуры (от простого к сложному)

| Стадия | Что добавили | Зачем |
|---|---|---|
| 1. Монолит + PG | Один сервис, одна БД | 35 RPS — достаточно |
| 2. + Redis | Кэш каталога | P95 < 120 мс гарантирован |
| 3. + Два каталога + Kafka | Global → Product синхронизация | Изоляция менеджера от покупателя |
| 4. + Inventory Service | Saga: заказ → резерв → оплата | Убрали bottleneck из Order Service |
| 5. + ClickHouse | OLAP для аналитиков | Аналитики не убивают PG |
| 6. + Реплики + Партиции PG | Async replica, partition by date | Масштабирование при росте |

## Ключевые решения и trade-offs

| Решение | Плюс | Trade-off |
|---|---|---|
| Два каталога (global + product) | Изоляция, менеджер не ломает покупателям | Eventual consistency каталога, дублирование данных |
| Redis кэш + event-driven инвалидация | P95 < 120 мс | Ещё один компонент |
| Redis для корзины, TTL 7 дней | Быстро, просто | Потеря корзины при рестарте |
| Kafka + Outbox | Не потерять события | Сложность |
| Saga (хореография) | Резерв → оплата с компенсацией | Нужен мониторинг, DLQ |
| ClickHouse для аналитиков | OLAP не убивает PG | Eventual consistency для отчётов |
| Партиции PG по дате | Старые заказы не тормозят | Больше партиций = сложнее DDL |
