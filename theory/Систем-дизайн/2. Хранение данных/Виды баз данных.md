- **Реляционные** (PostgreSQL, MySQL) — таблицы, строки, SQL, ACID, связи через FK. Дефолтный выбор, закрывает 80–90% задач. Хранение **построчное** → быстро получить/обновить одну строку
- **Колоночные** (ClickHouse, Cassandra) — данные по колонкам, каждая колонка — отдельный файл. Сжатие 10–50x. Для **аналитики** (OLAP): поднять миллион строк по 2 колонкам из 50. НЕ для транзакций
- **Key-Value** (Redis, Memcached, Tarantool) — хэш-таблица: ключ → значение. Основное применение — **кэширование**. etcd/ZooKeeper — для инфраструктуры (service discovery, конфиг кластера)
- **Документоориентированные** (MongoDB, CouchDB) — JSON/BSON документы, гибкая схема (NoSQL = No Schema). Для **независимых сущностей** без сложных связей. JOIN-ы работают плохо
- **Графовые** (Neo4j, Neptune) — вершины (сущности) + рёбра (отношения). Для сложных связей: соцсети, рекомендации, маршруты, "друзья друзей"
- **Time Series** (Prometheus, VictoriaMetrics, InfluxDB) — событие + таймстемп. Для **метрик**, датчиков, котировок. Можно на реляционке, но TS-базы оптимизированы под временные диапазоны
- **Blob/Object Storage** (S3, MinIO) — сырые файлы (картинки, видео, бэкапы). Положил → получил → удалил. Модификация не предусмотрена
- **Поисковые движки** (Elasticsearch, Sphinx) — надстройка над документными БД. Полнотекстовый поиск: однокоренные формы, опечатки, [[Индексы|inverted index]]. Антипаттерн: хранить всё только в ES (кроме логов)
- Много связей → реляционка. Независимые документы → документная. Аналитика по колонкам → колоночная. Ключ-значение → KV

## Сравнение

| Тип | Модель | Кейс | Пример |
|---|---|---|---|
| Реляционная | Таблицы, строки, SQL | Транзакции, связи, OLTP | PostgreSQL, MySQL |
| Колоночная | Колонки = отдельные файлы | Аналитика, OLAP, агрегации | ClickHouse, Cassandra |
| Key-Value | Ключ → значение | Кэш, сессии, счётчики | Redis, Memcached |
| Документная | JSON/BSON документы | Гибкая схема, независимые сущности | MongoDB, CouchDB |
| Графовая | Вершины + рёбра | Соцсети, маршруты, рекомендации | Neo4j, Neptune |
| Time Series | Событие + таймстемп | Метрики, датчики, котировки | Prometheus, InfluxDB |
| Blob Storage | Сырые файлы | Картинки, видео, бэкапы | S3, MinIO |
| Поисковый движок | Inverted index | Полнотекстовый поиск | Elasticsearch, Sphinx |

## Реляционные базы данных

Данные в таблицах, связанных отношениями (relations). Строки = записи, колонки = поля.

### Особенности
- хранятся **построчно** — вся строка в одном блоке на диске → быстро получить/обновить
- **типизация** — если поле integer, строку не засунешь
- SQL как язык запросов
- связи между таблицами (1:1, 1:N, N:N)

### Когда использовать
80–90% задач закрываются реляционками. Дефолтный выбор. Особенно когда нужны транзакции и связи.

## Колоночные базы данных

Данные хранятся **по колонкам**, а не по строкам. Каждая колонка — отдельный файл.

### Зачем
Аналитик хочет посчитать среднее по двум полям из таблицы с 50 колонками. В реляционке — вычитать все 50 колонок каждой строки. В колоночной — только 2 нужные. Меньше данных с диска = быстрее.

### Почему быстрее
- **Меньше I/O:** читаешь 2 колонки из 50 — только их
- **Сжатие:** однотипные данные рядом → LZ4/ZSTD жмут в 10–50x
- **Vectorized execution:** CPU обрабатывает батч значений через SIMD

### НЕ про транзакции
UPDATE/DELETE дорогие — нужно переписать значение в каждом колоночном файле. INSERT батчами — ок, поштучно — медленно.

## Key-Value базы данных

Хэш-таблица, вынесенная за пределы процесса. Ключ → значение. Самая простая модель.

### Примеры данных
- `video_id` → количество просмотров
- `session_token` → user_id
- `author_id` → количество подписчиков

### Особые Key-Value
etcd, ZooKeeper — для инфраструктуры: конфигурация кластера, service discovery, механизмы репликации. Не для пользовательских данных.

## Документоориентированные базы данных

JSON/BSON документы. Каждый документ — независимая сущность. Нет строгой схемы.

### Гибкая схема
Сегодня поле `name` есть, завтра нет — всё работает. Не нужны миграции как в реляционках.

### Когда использовать
- независимые сущности без сложных связей (резюме, анкеты, профили)
- бизнес часто меняет формат данных
- не нужны JOIN-ы

### Когда НЕ использовать
- много связей → реляционка
- нужны транзакции и строгая типизация

## Графовые базы данных

Вершины — сущности (люди, города). Рёбра — отношения (дружит, живёт, родился).

### Когда использовать
- сложные отношения (соцсети, рекомендации)
- зависимости (библиотеки, сборки)
- дороги, маршруты
- вопросы вида "друзья друзей", "кратчайший путь"

**Можно ли на реляционке?** Да. Но графовые БД лучше справляются со сложными запросами по графу.

## Time Series базы данных

Оптимизированы для данных на временной шкале. Событие + таймстемп.

### Когда использовать
- [[Observability|метрики]] сервисов (CPU, memory, RPS)
- показания датчиков (температура, давление)
- финансовые данные (котировки)

**Можно ли на реляционке?** Да, индекс по таймстемпу. Но TS-базы оптимизированы под много записей + запросы по временным диапазонам.

## Blob Storage (Object Storage)

Хранилище для сырых файлов — картинки, видео, MP3, бэкапы. Данные, которые нельзя "распотрошить" на поля.

**Модель:** положил → получил → удалил. Модификация не предусмотрена.

**Антипаттерн:** сохранять файлы и постоянно модифицировать. Blob storage не для этого.

## Поисковые движки (Search Engines)

Надстройка над документными БД. Полнотекстовый поиск — по словам, однокоренным формам, опечаткам.

### Как работает
- слова разбираются на корни
- поиск по однокоренным: "мама" → "маму", "мамы"
- используется редакционное расстояние и словари
- основа — [[Индексы|inverted index]]

### Антипаттерн
Хранить все данные только в Elasticsearch. Правильно — основные данные в реляционке, рядом ES для поиска. **Исключение:** логи и трейсы можно прямо в ES.
