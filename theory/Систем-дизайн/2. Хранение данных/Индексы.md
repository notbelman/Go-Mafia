- **B-tree** — самый популярный. Широкое неглубокое дерево (100–200 ключей в узле). Точечный поиск O(log N) + диапазоны. B+ tree — связи между листьями для range-запросов
- **Hash** — хэш-таблица: ключ → позиция. O(1) для точечного поиска. **Нельзя** диапазоны и сортировку
- **Sparse (разреженный)** — индексируем каждую N-ю запись (засечки). Между засечками — линейный поиск. ClickHouse. Для [[OLTP, OLAP, HTAP|OLAP]] — данные читаются пачками
- **Bitmap** — битовая карта: каждый бит = дискретный признак (да/нет). Побитовое AND по маске → мгновенная фильтрация. CPU AVX инструкции
- **Inverted Index** — для каждого слова список документов, где встречается. Основа [[Виды баз данных|Elasticsearch]]. "Слово → где встречается" вместо "документ → какие слова"
- **Spatial** — индексация координат. Quad-tree: пространство делится на 4 квадранта рекурсивно. Для геолокации, карт, gamedev
- **Covering (покрывающий)** — в индекс добавлены доп. данные, запрос обслуживается **без похода на диск**. Минус: больше памяти, медленнее запись
- **Кластерный** — строки **физически отсортированы** по ключу на диске. Один на таблицу (= primary key). **Некластерный** — отдельная структура, ссылается на строки. Может быть много
- B-tree оптимизирован под диск: узел = один блок чтения (512 B – 4 KB). Прочитать и просканить 200 ключей в RAM — копейки. Дорого — прыжок на диск (seek)

---

## Сравнение

| Индекс | Точечный поиск | Диапазон | Кейс |
|---|---|---|---|
| **B-tree** | O(log N) | Да (B+ tree) | Дефолт в реляционках, OLTP |
| **Hash** | O(1) | Нет | Только точечный поиск по ключу |
| **Sparse** | Медленнее (линейный между засечками) | Пачками | OLAP, ClickHouse |
| **Bitmap** | Побитовый AND | Комбинация признаков | Фильтрация по булевым полям |
| **Inverted** | По слову → список документов | Полнотекстовый | Elasticsearch, поиск |
| **Spatial** | По координатам | Область | Геолокация, карты |
| **Covering** | Без похода на диск | Да | Горячие запросы (тысячи RPS) |

## B-tree индекс

Самый популярный индекс в реляционных БД. Сильно ветвистое дерево — в каждом узле 100–200 значений.

### Почему B-tree, а не бинарное дерево
Диски любят последовательное чтение. Бинарное дерево = глубокое → много прыжков по диску (seek time). B-tree = широкое, неглубокое → мало прыжков.

### Как работает
1. В каждом узле — вектор отсортированных ключей (параметр T = 100–200)
2. Между ключами — указатели на дочерние узлы
3. Ищем 50: корень → 50 < 100 → влево → нашли → ссылка на данные

### Почему 100–200 ключей в узле — не проблема
Диск — блочное устройство. Даже при чтении 1 байта подтягивается блок (512 B – 4 KB). Прочитать узел и просканить 200 ключей в RAM — копейки. Дорого — прыжок на диск.

### B+ tree
Вариация: между листовыми узлами есть связи → можно искать диапазоны (от 121 до 200).

**Сложность:** O(T × log_T(N))

## Hash индекс

Хэш-таблица рядом с данными. Ключ → хэш → позиция. Поиск за **O(1)**.

### Когда использовать
Нужно найти ровно одну запись по точному значению. "Найди user с id = 42" — идеальный кейс.

### Ограничение
Нельзя диапазон и сортировку. "Users с id от 100 до 200" — не работает. Хэш-таблица не упорядочена.

**Правило:** нужен диапазон или сортировка → B-tree. Только точечный → hash.

## Разреженный индекс (Sparse Index)

Индексируем не каждую запись, а каждую N-ю (засечки). Между засечками — линейный поиск.

```
Засечки: [0] [1000] [2000] [3000] ...
Ищем 1500 → между 1000 и 2000 → читаем блок → находим
```

### Плюсы
- меньше памяти под индекс
- быстрее вставка (не обновляем индекс на каждую запись)

### Минус
Точечный поиск одной записи медленнее.

**Где используется:** ClickHouse — засечки на каждую N-ю строку. [[OLTP, OLAP, HTAP|OLAP]] нагрузка — данные пачками, точечный поиск не нужен.

## Bitmap индекс

Каждой записи — битовая карта: каждый бит = дискретный признак.

```
Кафе А: 1101 (кальян ✓, собаки ✓, музыка ✗, веган ✓)
Кафе Б: 0110 (кальян ✗, собаки ✓, музыка ✓, веган ✗)
```

### Как поиск работает
"Кальян + собаки" → маска: `1100` → побитовое AND по всем записям → мгновенно.

### Почему быстро
- bitmap в RAM — копейки памяти
- CPU AVX инструкции для векторных побитовых операций
- хоть 128, хоть 256 бит — мгновенно

**Когда:** много дискретных признаков (да/нет). Фильтрация по комбинации булевых полей.

## Inverted Index (обратный индекс)

Для каждого слова — список документов, в которых встречается.

```
Тексты:
  0: "it is what it is"
  1: "what is it"
  2: "it is a banana"

Обратный индекс:
  banana → [2]
  is     → [0, 1, 2]
  it     → [0, 1, 2]
  what   → [0, 1]
```

**Поиск по нескольким словам:** "is" + "banana" → пересечение [0,1,2] ∩ [2] = [2].

**Где:** [[Виды баз данных|Elasticsearch, Sphinx]] — основа полнотекстового поиска.

## Spatial индекс (пространственный)

Индексация объектов в пространстве (координаты).

### Quad-tree (простейший)
1. Пространство делится на 4 квадранта
2. Слишком много объектов → делим ещё на 4
3. Мало объектов в соседних → сливаем
4. Максимальная глубина конфигурируется

**Другие структуры:** R-деревья, KD-деревья, октодеревья (3D).

**Где:** геолокация (ближайшие такси), карты, gamedev.

## Покрывающий индекс (Covering Index)

В индекс добавлены доп. данные → запрос обслуживается **без похода на диск**.

```sql
-- Обычный индекс по (id, date):
SELECT name FROM users WHERE id = 1 AND date = '2024-01-01'
-- нашли в индексе → пошли на диск за name

-- Покрывающий индекс по (id, date, name):
-- нашли в индексе → name уже тут, на диск НЕ идём
```

### Плюс
Индекс часто в RAM — ответ мгновенный.

### Минус
Больше памяти, медленнее запись (обновлять больше данных в индексе).

**Когда:** горячий запрос тысячи раз в секунду. Добавить пару полей = убрать поход на диск.

## Кластерный vs некластерный индекс

### Кластерный
Строки **физически отсортированы** по ключу на диске. Кластерный индекс = порядок хранения.

- **только один** на таблицу (данные нельзя отсортировать двумя способами)
- по умолчанию = primary key
- таблица без кластерного индекса = **heap** (произвольный порядок)

### Некластерный
Отдельная структура (B-tree, hash, bitmap...), ссылается на строки. **Не влияет** на физический порядок.

- может быть **много** на одну таблицу
- это все индексы, которые "прикручиваем сверху"

### Соотношение с типами

| Концепция | Примеры |
|---|---|
| Кластерный | Primary key (определяет порядок строк) |
| Некластерный | B-tree, hash, bitmap, spatial, inverted — любой доп. индекс |

Кластерный/некластерный — **где хранятся данные**. B-tree/hash/bitmap — **структура данных** индекса. Разные оси.
