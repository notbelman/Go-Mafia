Аналитика: "выручка по регионам за год", "средний чек по категориям", дашборды. Мало запросов, но каждый сканирует миллионы строк.

## Характеристики

- Десятки аналитиков, запросы на миллионы/миллиарды строк
- Операции: SELECT с GROUP BY, JOIN, агрегации (SUM, AVG, COUNT)
- Латентность: секунды (допустимо)
- Данные исторические (append-only, редко обновляются)
- ACID не критичен

## Хранение: колоночное (column-based)

Каждая колонка хранится отдельно. Запрос трогает только нужные колонки.
```
id:    [1, 2, 3, 4, 5, ...]       ← отдельный файл
name:  [Alice, Bob, Carol, ...]    ← отдельный файл
age:   [30, 25, 28, ...]          ← отдельный файл
```

`SELECT AVG(age)` — читает ТОЛЬКО колонку age, остальные не трогает.

## Почему колоночное хранение быстрее для аналитики

- **Меньше I/O:** читаешь 2 колонки из 50 — читаешь только их, а не все 50
- **Сжатие:** одинаковые типы рядом → LZ4/ZSTD жмут в 10-50x (строковое: 2-3x)
- **Vectorized execution:** CPU обрабатывает батч значений одного типа через SIMD, а не строку за строкой

## Почему не использовать для OLTP

UPDATE/DELETE дорогие — нужно переписать значение в каждом колоночном файле отдельно. INSERT батчами — ок, поштучно — медленно.

## ClickHouse — почему быстрый

- Колоночное хранение + сжатие (10-50x)
- MergeTree engine: данные вставляются частями (parts), мержатся в фоне
- Vectorized execution: батчевая обработка через SIMD
- Sparse primary index: быстрый поиск без overhead полного B-tree
- Масштабируется горизонтально (шардирование из коробки)
