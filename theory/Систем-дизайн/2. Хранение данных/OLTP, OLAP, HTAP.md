- **OLTP** — обработка транзакций: создать заказ, обновить юзера, списать деньги. Тысячи мелких быстрых запросов. Хранение **строковое** (row-based). БД: PostgreSQL, MySQL, MongoDB
- **OLAP** — аналитика: "выручка по регионам за год", дашборды. Мало запросов, но каждый сканирует **миллионы строк**. Хранение **колоночное** (column-based). БД: ClickHouse, BigQuery, Redshift
- OLTP: INSERT/UPDATE/DELETE + SELECT по ключу, ACID обязателен, [[Производительность|latency]] = миллисекунды
- OLAP: SELECT с GROUP BY/JOIN/агрегации, ACID не критичен, latency = секунды (допустимо)
- **Строковое** — вся строка рядом на диске → быстро получить одну строку. Медленно: `AVG(age)` по всей таблице (читает все колонки)
- **Колоночное** — каждая колонка отдельно → `AVG(age)` читает только колонку age. Сжатие 10–50x. UPDATE/DELETE дорогие
- **ClickHouse**: колоночное + сжатие + MergeTree + vectorized SIMD + sparse index + горизонтальное шардирование
- **HTAP** — гибрид, одна БД для обоих типов. Пример: YDB (Яндекс). Концепция с ~2014, ещё не мейнстрим

## Сравнение

| | OLTP | OLAP |
|---|---|---|
| Нагрузка | Тысячи мелких запросов | Мало тяжёлых запросов |
| Операции | INSERT, UPDATE, DELETE, SELECT по ключу | SELECT + GROUP BY, JOIN, агрегации |
| Latency | Миллисекунды | Секунды (ок) |
| Данные | Актуальные (current state) | Исторические (append-only) |
| ACID | Обязателен | Не критичен |
| Хранение | Строковое (row-based) | Колоночное (column-based) |
| БД | PostgreSQL, MySQL, MongoDB | ClickHouse, BigQuery, Redshift |

## OLTP — Online Transaction Processing

Много мелких быстрых запросов: создать заказ, обновить юзера, списать деньги.

### Хранение: строковое (row-based)

Строка целиком лежит рядом на диске. Читаешь юзера по id — одно чтение, все поля сразу.

```
| id | name  | email       | age |   ← вся строка в одном блоке
| 1  | Alice | a@mail.com  | 30  |
| 2  | Bob   | b@mail.com  | 25  |
```

**Быстро:** получить/обновить одну строку.
**Медленно:** `SELECT AVG(age) FROM users` — нужно прочитать ВСЕ строки, хотя нужна одна колонка.

## OLAP — Online Analytical Processing

Аналитика: "выручка по регионам за год", дашборды. Мало запросов, но каждый сканирует миллионы строк.

### Хранение: колоночное (column-based)

Каждая колонка хранится отдельно. Запрос трогает только нужные.

```
id:    [1, 2, 3, 4, 5, ...]       ← отдельный файл
name:  [Alice, Bob, Carol, ...]    ← отдельный файл
age:   [30, 25, 28, ...]          ← отдельный файл
```

`SELECT AVG(age)` — читает ТОЛЬКО колонку age.

### Почему колоночное быстрее для аналитики
- **Меньше I/O:** читаешь 2 колонки из 50 — только их
- **Сжатие:** одинаковые типы рядом → LZ4/ZSTD жмут в 10–50x (строковое: 2–3x)
- **Vectorized execution:** CPU обрабатывает батч значений через SIMD

### Почему не использовать для OLTP
UPDATE/DELETE дорогие — нужно переписать значение в каждом колоночном файле. INSERT батчами — ок, поштучно — медленно.

### ClickHouse — почему быстрый
- Колоночное хранение + сжатие (10–50x)
- MergeTree engine: данные вставляются частями, мержатся в фоне
- Vectorized execution: батчевая обработка через SIMD
- [[Индексы|Sparse primary index]]: быстрый поиск без overhead полного B-tree
- [[Масштабирование|Масштабируется горизонтально]] (шардирование из коробки)

## HTAP (Hybrid Transactional/Analytical Processing)

Гибрид — одна БД для обоих типов нагрузки. Концепция с ~2014 года, ещё не мейнстрим.

**Пример:** YDB (Яндекс) — движок и колоночного, и построчного хранения в одной БД.

## Связь
- [[Виды баз данных]] — реляционные → OLTP, колоночные → OLAP
- [[Индексы]] — B-tree для OLTP, sparse index для OLAP
- [[Производительность]] — OLTP оптимизирует latency, OLAP оптимизирует throughput
