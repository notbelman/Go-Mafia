Репликация каждого компонента. Два датацентра (Москва + Новосибирск). Что синкаем, что нет и почему.

## GeoDNS на входе

Пользователь идёт через GeoDNS → резолвится, откуда он → роутится в ближайший ДЦ (Москва или Новосибирск). Обсуждали на первом занятии.

## PostgreSQL (посты): Master-Master + Async Replication

**Почему не Master-Slave async?** Если ДЦ с мастером упадёт — потеряем незареплицированные посты. Пользователь создал пост, ДЦ лёг — поста нет. Это плохо.

**Почему не синхронная?** Синхронная между ДЦ — медленно. Ждать подтверждения из Новосибирска при каждой записи в Москве — теряем все преимущества геораспределённости.

**Решение: Master-Master + async.** Пишем в два мастера (один в Москве, один в Новосибирске). Асинхронная репликация между ними. Если один ДЦ записал, а второй не успел синкнуться, при чтении подмёрживаем. Можно красиво сделать через очередь: запись → очередь → разъезжается по ДЦ с задержкой, не ждём.

**Базовое правило:** Master-Master + async — когда нужна асинхронная репликация И нельзя терять данные при падении ДЦ.

## Tarantool (ленты): НЕ синкаем между ДЦ

**Home feed** (моя лента из подписок) хранится только в моём ДЦ. Если я в Москве — мой home feed в московском Tarantool. Зачем хранить его в Новосибирске? Вряд ли я туда перелечу.

**User feed** (моя страница) — тоже в моём ДЦ. Когда другой пользователь из Новосибирска заходит на мою страницу, у него уже свой кэш user feed.

**Но Kafka синкается между ДЦ!** Почему: Вова в Москве создал пост. Петя подписан на Вову, но живёт в Новосибирске. Событие из Kafka должно дойти до Feed Service в Новосибирске, чтобы обновить Петину home feed. Kafka пишется в оба ДЦ (можно через master-master или специальную конфигурацию брокера).

## Tarantool: WAL + репликация обязательны

Что если Tarantool упадёт? Вся нагрузка на чтение посыпется в Post Service (PostgreSQL). А там **не заложен профицит ресурсов** — система заточена на то, что чтением занимается Tarantool. PostgreSQL не справится с 5787 RPS чтения.

Поэтому: **WAL** (write-ahead log) для восстановления + **репликация** для отказоустойчивости. Обязательно.

## PostgreSQL (посты): репликация внутри ДЦ

Помимо master-master между ДЦ — внутри каждого ДЦ тоже репликация. Для отказоустойчивости (если один инстанс упал) и для разгрузки чтения (read replicas).

## Feedback Service: зависит от типа данных

**Лайки — async между ДЦ.** Если ДЦ упадёт и лайк потеряется — не критично. Пользователь даже может не заметить. Крайне редкая ситуация.

**Комменты — master-master async.** Коммент терять не хотим — пользователь написал текст, ожидает его увидеть. Поэтому для комментов та же схема, что для постов.

Именно здесь оправдано **разделить лайки и комменты на два сервиса** — разные требования к репликации.

## S3 (медиа): синхронизация + CDN

S3 бакеты **синкаются между ДЦ**. Потеря картинок — очень плохо. Перед S3 стоит **CDN**: прокси проверяет кэш в POP (point of presence), есть — отдаёт, нет — идёт в origin (S3), отдаёт и кэширует.

**Нюанс с авторизацией:** для соцсети картинки публичны — идём в S3 напрямую через CDN. Если бы это был Google Drive (приватные файлы) — пришлось бы идти через Media Service для проверки прав.

## Сводная таблица

| Компонент | Между ДЦ | Почему |
|---|---|---|
| PostgreSQL (посты) | Master-master async | Нельзя терять посты |
| Tarantool (ленты) | Не синкаем | Home feed локальный |
| Kafka | Синкается | Событие должно дойти в оба ДЦ |
| Feedback (лайки) | Async | Потеря лайка не критична |
| Feedback (комменты) | Master-master async | Комменты терять не хотим |
| S3 | Синкается | Потеря картинок = плохо |
