Как скелить каждый компонент. Финальная картина системы.
## Stateless-сервисы: без проблем

**Load Balancer, API Gateway, Post Service, Feed Service, Media Service, Feedback Service** — все stateless. Добавляем инстансы, балансер раскидывает трафик. Если один выпадает — остальные подхватывают. Никаких проблем с масштабированием.

## Tarantool (ленты): шардирование по user_id

Почему user_id: мне нужна **моя** лента. Не нужны ленты других пользователей в одном запросе. Один пользователь = один шард. Запрос всегда попадает в один шард — никаких мультишардовых запросов.

Шардирование Tarantool — простое. По user_id хэшируем, попадаем в нужный шард.

## PostgreSQL (посты): шардирование по post_id

**Минус:** если шардируем по post_id и хотим найти все посты Васи — посты Васи разбросаны по разным шардам. Пойдёт **мультишардовый запрос** (scatter-gather по нескольким шардам параллельно).

Не сказать, что критично — но компромисс. Мы с этим миримся, потому что основное чтение идёт из Tarantool (уже готовые ленты), а Post Service сканим редко (пагинация за пределами 10 постов, давно не заходивший пользователь).

**Альтернатива:** шардировать по user_id — тогда посты Васи на одном шарде, но распределение менее равномерное (у кого-то 10 постов, у кого-то 10.000).

## Kafka: заранее нарезать партиции

Партиции по **user_id** или **post_id**. Ключевой приём: **нарезать заранее много партиций**, даже если серверов мало.

Пример: 3 брокера, нарезали 3 партиции. Потом упёрлись — нужно 10 брокеров. Придётся перенарезать партиции, перебалансировать, обновлять клиентский код.

Если сразу нарезали 100 партиций на 3 брокера — при добавлении новых брокеров просто раскидываем готовые партиции. Аналогия с шардированием БД: заранее нарезать больше шардов.

## Feedback (PostgreSQL): шардирование по post_id

Основной паттерн доступа: "покажи лайки/комменты по этому посту". Шардируем по post_id — все данные одного поста на одном шарде.

## S3: бакеты по машинам

Разные бакеты можно разносить по разным машинам. Если упираемся в пропускную способность — добавляем серверы.

## Итоговые решения и почему

| Решение | Почему |
|---|---|
| Tarantool для лент | Read-intensive, 2ТБ in-memory, мгновенное чтение |
| PostgreSQL для постов | Реляционные связи, 115 RPS — хватит |
| Отдельный Feedback | 25K RPS лайков — нельзя мешать с лентами |
| Fan-out on write | ASR = read-intensive → готовим ленты заранее |
| Гибрид для celebrities | 1M друзей → нельзя пушить, подмёрживаем при чтении |
| Staging bucket | Осиротевшие медиа при двухэтапной загрузке |
| Transaction Outbox | Гарантия доставки Post → Kafka |
| Master-master async | Геораспределённость без потери данных |
| CDN перед S3 | Быстрая выдача картинок |

## Что Балун говорил про точность

"Ребят, как вы ответите, выдерживает ли система нагрузку? Да никак. Это на коленочные расчёты. У вас нет реальных данных, реальных метрик. Когда система в эксплуатации — тогда можете точно сказать. Здесь — примерно оценить, примерно предположить."

На интервью от вас не ждут, что вы всё в подробностях расскажете. Ждут: верхнеуровневую схему, базовое взаимодействие, расчёт нагрузки где нужно, data model, обсуждение отказоустойчивости. И главное — что вы **лидите процесс**.
