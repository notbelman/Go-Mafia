 - Обзорная карточка архитектуры такси-сервиса: все основные сервисы и их взаимодействие
- Geo Service (Tarantool in-memory) + geohash для позиций водителей, Matching Service для подбора, Notification Service (WebSocket), Ride Service + History Service (ClickHouse)
- Отказоустойчивость: прикапывание стейта для Matching и Ride, reconnect для WebSocket, самовосстановление Tarantool через поток координат
- Масштабирование: шардирование по geohash (позиции), по user_id (стейт), fan-out/SD для Notification Service

---

Полный разбор проектирования ride-hailing сервиса. 100M DAU пассажиров, 5M водителей, real-time система.

## ASR: real-time обновление позиций

5M водителей × 8 часов работы × обновление каждые 5 секунд. RPS на апдейт позиций:

```
5.000.000 / 86400 × 8 × 60 / 5 ≈ 3300+ RPS
```

Это определяет всю архитектуру: in-memory хранилище для позиций, geohash вместо деревьев.

## Два типа клиентов

Пассажир и водитель — разные приложения, разные API. Поэтому **два API Gateway** с разными правами доступа. Общий Load Balancer роутит трафик в нужный gateway.

## Компоненты и почему именно они

**Geo Service + Tarantool (in-memory)**
Хранит текущие позиции всех водителей. Почему in-memory: ~3300 RPS на запись (обновление координат каждые 5 сек) — дисковая БД не справится с такой частотой апдейтов. Почему не квадродерево: перестроение дерева на 3300 RPS — медленно. Geohash — просто перезапись строки.

Структура: geohash (5 символов ≈ 5 км) + driver_id. Вторичный хэш-индекс на driver_id — при обновлении проверяем, сменился ли квадратик. Если да — удаляем из старого, добавляем в новый. Если нет — просто обновляем lat/lng.

**Две структуры позиций:**
- **Base driver position** — свободные водители (для Matching Service)
- **Active driver position** — занятые водители (для Ride Service)

Почему разделили: без разделения Matching Service может предложить 10 водителей, все из которых уже везут пассажиров.

**Matching Service**
Подбор водителя для пассажира. Логика:
1. Пассажир приходит с координатами → вычисляем geohash
2. Идём в Geo Service → получаем до 10 свободных водителей в этом квадратике
3. **Синхронно** предлагаем каждому по очереди (5 секунд на ответ)
4. 10 водителей × 5 секунд = 50 секунд + 10 секунд поиск = укладываемся в 1 минуту response time

Почему синхронно, а не всем сразу: если предложить всем — 9 водителей подтвердят и получат отказ. Плохой UX ("подтвердил, а заказ не мой").

**Matching Status (in-memory хранилище рядом с Matching Service)**
Прикапываем стейт матчинга: user_id, список водителей, текущий статус. Зачем: если Matching Service упадёт — восстановим из стейта и продолжим опрос. Без этого пользователю придётся заново заказывать такси.

**Notification Service (WebSocket)**
Держит постоянные соединения с водителями и пассажирами. Через него летят все события: "предложение поездки", "водитель найден", "водитель подъехал", "маршрут изменился".

Почему WebSocket, а не polling: много разнородных событий с непредсказуемой частотой. Стриминг подходит лучше.

Масштабирование: stateful сервис (хранит коннекшны). Три подхода: fan-out, Service Discovery, прокидывание адреса. На практике часто fan-out (отбивка лишних запросов — копеечная операция).

**Ride Service**
Ведёт активную поездку. Когда водитель подтвердил заказ → создаётся ride-сессия. Ride Service периодически отправляет пассажиру обновления позиции водителя через Notification Service. Координаты берёт из Geo Service (active driver position), а не хранит сам.

**Ride Storage (in-memory)**
Прикапываем стейт поездки: user_id, driver_id, from, to, route. Зачем: если Ride Service упадёт — пользователь переподключится к другому инстансу, который восстановит сессию из storage. Без этого — таксист в подвешенном состоянии, клиент не знает, что делать.

**History Service + ClickHouse**
Почему ClickHouse: история поездок — append-only (только пишем, не модифицируем, не удаляем). Идеальный сценарий для колоночной OLAP-базы. Поездка закончилась → Ride Service скинул событие → History Service записал.

## Позиция пассажира во время поездки

Не нужно отдельно трекать. Пассажир едет в машине → просто показываем координаты автомобиля (из active driver position). До посадки — показываем свою позицию (GPS клиента) и позицию приближающегося водителя.

## Отказоустойчивость

- Stateless сервисы → несколько инстансов, балансер переключает
- Matching Service упал → восстанавливаем из matching status, продолжаем опрос
- Ride Service упал → восстанавливаем из ride storage, продолжаем поездку
- Notification Service упал → клиент reconnect на другой инстанс
- Geo Service (Tarantool) упал → данные перенальются через 5-10 секунд (водители шлют координаты постоянно). WAL + репликация для подстраховки
- ClickHouse → async replication (дефолт)

## Масштабирование

- Tarantool (позиции) → шардирование по geohash (соседние квадратики на одном шарде)
- Tarantool (стейт поездок/матчинга) → шардирование по user_id
- Notification Service → через Service Discovery / fan-out
- Kafka → заранее много партиций
