Ключевой компонент системы. Здесь живёт вся оптимизация на чтение.

## Зачем вообще Feed Service

Наивный подход: пользователь открывает ленту → идём в Post Service → ищем всех друзей → собираем их посты → сортируем → отдаём. Это **медленно**: нужно сканить много данных на диске, джойнить таблицы. При 5787 RPS на чтение — не справимся.

Решение: **заранее собирать ленты** (fan-out on write). При создании поста сразу раскладываем его в ленты всех друзей. При чтении — просто достаём готовую ленту из кэша.

## Как работает запись (fan-out on write)

```
Post Service → Transaction Outbox → Kafka → Feed Service
```

1. Пользователь создал пост → Post Service записал в PostgreSQL
2. Transaction Outbox + воркер → событие уходит в Kafka
3. Feed Service подписан на Kafka → получает событие "Вася создал пост"
4. Feed Service идёт в **Relation Service** → спрашивает: "С кем дружит Вася?"
5. Получает список друзей → обновляет **home feed** каждого друга
6. Также обновляет **user feed** самого Васи

**Почему Post Service не обновляет ленты сам?** Разделение ответственности. Post Service не должен знать про отношения и ленты. Его задача — сохранить пост. Всё остальное — через событие в Kafka.

**Почему Transaction Outbox?** Гарантия: если записали в PostgreSQL, событие **когда-нибудь** дойдёт до Kafka. Даже если Kafka временно недоступна.

## Структура кэша
```
user_feed:                    home_feed:
  user_id                       user_id
  posts [                       posts [
    { id, text, url, ... },       { id, text, url, ... },
    ...                           ...
  ]                             ]
```

**Храним полные посты**, не айдишники. Чтобы не ходить потом в Post Service за текстом и URL. Один запрос — одна выдача.

**Структура — дека (deque).** Новый пост → добавляем в начало. Переполнение (>10) → выкидываем с конца. Инвалидация простейшая.

**10 постов** — выбрано из пользовательского опыта. Большинство не скроллят дальше 10. Точное число покажет эксплуатация.

## Расчёт memory

```
50M пользователей × 10 постов × 2 КБ = 1 ТБ (user feed)
+ 1 ТБ (home feed)
= 2 ТБ суммарно
```

**Дорого ли 2 ТБ in-memory?** Нет. Балун: "В Ozon коллекторы сперва 3 ТБ, потом до 5 расширяли". Когда бизнес хочет быстрее — хранят в оперативке. 2 ТБ — не копейки, но и не космос.

**Можно ли хранить только для активных пользователей?** Можно — если не заходил >1 дня, не кэшируем. Но это экономия на копейках, концептуально всё равно ~2 ТБ.

## Хранилище: Tarantool (in-memory)

**Почему in-memory, а не диск?** Система read-intensive. Чтение должно быть максимально быстрым. In-memory = минимальная latency. Запись можем позволить чуть дороже — она и так редкая (115 RPS постов).

**Почему Tarantool, а не Redis?** Балун больше работал с Tarantool. Redis тоже подойдёт. Оба — in-memory KV с поддержкой сложных структур.

## Celebrity Problem (проблема знаменитостей)

Максимум 1.000.000 друзей. Павел Дуров написал пост → нужно обновить 1M home feeds. **Одна операция записи порождает миллион операций.**

**Решение — гибридный подход:**

- **Обычный пользователь** (<5-10K друзей) → fan-out on write. Пост раскладываем в ленты друзей.
- **Знаменитость** (>5-10K подписчиков) → **не пушим** в ленты. Просто обновляем user feed знаменитости.

**При чтении:** Feed Service достаёт home feed пользователя → смотрит дату первого поста → проверяет user feed всех знаменитостей, на которых подписан → если есть свежее — **подмёрживает на лету** и отдаёт.

Порог (5-10K) — приблизительный. Точное число покажет эксплуатация, можно подкрутить.

## Пагинация и "давно не заходил"

Закэшировано 10 постов. Пользователь хочет листать дальше → **гибридный подход**: Feed Service идёт в Post Service и сканит оттуда. Медленнее, но это редкий кейс.

Пользователь давно не заходил, кэша нет → то же самое. Идём в Post Service, собираем ленту, кладём в кэш, отдаём.

## Kafka: партиционирование

Партиции по **user_id** или **post_id** — оба дают хорошее распределение. Заранее нарезать много партиций (даже если серверов мало). Потом при масштабировании — просто раскидываем партиции по новым брокерам. Не нужно перенарезать и перебалансировать.
