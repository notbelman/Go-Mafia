- **Партиционирование** — разбиение одной таблицы на несколько физических частей. Партиции = отдельные таблицы-наследники, родительская пустая. Каждая со своими индексами, статистикой, autovacuum
- **Partition pruning** — планировщик отсекает ненужные партиции по WHERE. Без ключа партиции в WHERE → full scan ВСЕХ партиций, **хуже** чем одна таблица
- **4 типа:** Range (по диапазону, time-series), List (по значениям, регионы/статусы), Hash (равномерное распределение, hash % N), Composite (многоуровневое: Range × Hash)
- **Ключ партиции:** должен быть в WHERE большинства запросов, не должен часто меняться (UPDATE ключа = DELETE + INSERT между партициями), функция на ключе ломает pruning
- **Вертикальное** — разбиение по столбцам: hot данные (name, email) отдельно от cold (avatar_blob, settings_json). Меньше ширина строки → больше строк в страницу → быстрее seq scan
- Глобальных индексов нет — UNIQUE/PK **обязан включать** ключ партиции. CREATE INDEX на родителе → автоматически на всех партициях (PG11+)
- Таблица < 10 млн строк → overhead на планирование съест профит. Десятки партиций — ок, сотни — planning time растёт, тысячи — боль
- **pg_partman** — расширение для автоматизации: создание партиций (daily/weekly/monthly), retention policy (auto-drop старых), background worker

## Типы партиционирования

| Тип | Как делит | Когда использовать | Pruning работает | Нюансы |
|---|---|---|---|---|
| **Range** | По диапазону [FROM, TO) | Time-series, логи, retention (DROP PARTITION) | `WHERE date >= '2024-01-01'` | Неравномерные данные → одна партиция разбухает |
| **List** | По конкретным значениям | Регионы, статусы, юрисдикции | `WHERE region = 'EU'` | Нет DEFAULT + неизвестное значение = ошибка INSERT |
| **Hash** | hash(key) % N | Равномерное распределение, нет естественного ключа | Только `WHERE key = value` | Modulus нельзя изменить — пересоздавать |
| **Composite** | Партиция → субпартиции | Огромные таблицы, фильтры по 2 измерениям | На каждом уровне последовательно | Полный pruning только если WHERE содержит оба ключа |

## Под капотом

- Партиции = отдельные таблицы-наследники, родительская пустая
- INSERT — роутинг по ключу в нужную партицию
- SELECT — планировщик отсекает ненужные партиции по WHERE (partition pruning)
- Каждая партиция: свои индексы, статистика, autovacuum

## Индексы

- Глобальных индексов нет — в PG это N отдельных индексов на каждой партиции
- CREATE INDEX на родителе — автоматически создаёт на всех партициях (PG11+)
- UNIQUE/PK **обязан** включать ключ партиции (иначе нельзя гарантировать уникальность cross-partition)

## Выбор ключа

- Должен быть в WHERE большинства запросов — иначе pruning не работает
- Не должен часто меняться (UPDATE ключа = DELETE + INSERT между партициями)
- Функция на ключе ломает pruning: `WHERE YEAR(date) = 2024` — нет, `WHERE date >= '2024-01-01'` — да

## Грабли

- Запрос без ключа партиции — full scan ВСЕХ партиций, хуже чем одна таблица
- Количество партиций: десятки — ок, сотни — planning time растёт, тысячи — боль
- Таблица < 10 млн строк — overhead на планирование съест профит
- NULL в ключе партиции — нельзя (кроме List с явным NULL)

## Вертикальное партиционирование

Разбиение таблицы по столбцам — выносим часть колонок в отдельную таблицу, связываем по ключу.

### Зачем
- разделить hot и cold данные (часто читаемые vs редко нужные)
- уменьшить ширину строки — больше строк влезает в страницу, быстрее seq scan
- изолировать тяжёлые поля (blob, jsonb, text) от лёгких

### Когда использовать
- есть явное разделение hot/cold по частоте доступа
- тяжёлые поля тянут вниз производительность
- TOAST не справляется или хочется явный контроль

### Когда не использовать
- большинство запросов всё равно нужны все столбцы — JOIN overhead
- таблица небольшая — усложнение без профита
- нет явного паттерна доступа hot/cold

### Пример

```sql
-- было
users (id, name, email, avatar_blob, settings_json, bio_text)

-- стало
users_main (id, name, email)              -- 100 байт, читаем постоянно
users_heavy (id, avatar_blob, settings_json, bio_text)  -- 10 КБ, читаем редко

-- запрос списка пользователей
SELECT id, name, email FROM users_main;  -- быстро, компактно

-- запрос профиля с аватаром
SELECT m.*, h.avatar_blob
FROM users_main m
JOIN users_heavy h ON m.id = h.id
WHERE m.id = 123;
```

## Термины

| Термин | Что это |
|---|---|
| Partition pruning | Отсечение ненужных партиций на этапе планирования по WHERE |
| Runtime pruning | Отсечение во время выполнения (значение из подзапроса/параметра, PG11+) |
| Planning time | Время построения плана запроса (растёт с количеством партиций) |
| Execution time | Время выполнения самого запроса |
| Partition key | Столбец/выражение, по которому строки распределяются |
| Partition bounds | Границы (FROM/TO для Range, IN для List, MODULUS/REMAINDER для Hash) |
| Default partition | Партиция для строк, не попавших ни в одну другую |
| Partition-wise join | JOIN между соответствующими партициями двух таблиц (OFF по умолчанию) |
| Partition-wise aggregate | GROUP BY внутри каждой партиции отдельно (OFF по умолчанию) |
| ATTACH/DETACH PARTITION | Присоединить/отсоединить существующую таблицу как партицию |
| pg_partman | Расширение: автосоздание партиций + retention policy |

## Эволюция в PostgreSQL

- **PG10:** declarative partitioning
- **PG11:** PK/FK на родителе, CREATE INDEX на родителе, runtime pruning
- **PG12:** FK могут ссылаться НА партицированные таблицы
