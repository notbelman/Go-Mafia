Журнал всех изменений в базе. Сначала пишем в лог, потом применяем к данным на диске.

## Зачем

- **Crash recovery** — после падения воспроизводим WAL, данные не теряются
- **Репликация** — отправляем WAL на реплики, они воспроизводят изменения

## Как работает

1. `BEGIN; INSERT INTO users(name) VALUES('Alex');`
2. Изменения записываются в WAL buffer (память) + данные меняются в shared buffers (память)
3. `COMMIT` — WAL buffer сбрасывается на диск (fsync)
4. Ответ клиенту "ok"
5. Позже (checkpoint) — грязные страницы из shared buffers пишутся на диск

## Почему сначала WAL

- Последовательная запись в лог — быстро (append-only)
- Случайная запись в таблицы — медленно (seek time)
- Упали до checkpoint? При старте воспроизводим WAL — данные не потеряны
- По сути два хранилища: WAL (быстрая запись) + движок (медленная перестройка)

## PostgreSQL: детали

| Вопрос | Ответ |
|---|---|
| Что такое LSN? | Log Sequence Number — позиция в WAL (формат: 0/3A8B2C0) |
| Что такое checkpoint? | Сброс грязных страниц из shared buffers на диск, после него старый WAL можно удалить |
| Где лежат WAL-файлы? | pg_wal/, сегменты по 16MB |
| Параметр wal_level? | minimal (crash recovery), replica (physical, default), logical (logical replication) |
