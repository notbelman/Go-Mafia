## Синхронная → Strong Consistency

```
COMMIT → WAL на диск → отправка на реплики → ждём подтверждения ВСЕХ → ответ клиенту
```

После записи любое чтение с любого узла вернёт свежее значение.

**Плюс:** данные консистентны, потеря данных невозможна.
**Минус:** медленно. Одна реплика зафейлилась — откат всей операции, клиент получает ошибку. Больше участников = больше шансов на сбой.

## Асинхронная → Eventual Consistency

```
COMMIT → WAL на диск → ответ клиенту → потом асинхронно отправка на реплики
```

Клиент получает ответ мгновенно. Данные на репликах появятся через какое-то время.

**Плюс:** быстро. Для пользователя как будто репликации нет — просто пишет в локальную БД.
**Минус:** replication lag. Чтение с реплики может вернуть устаревшие данные. При падении мастера — потеря последних транзакций.

## Полусинхронная (Semi-Sync)

```
COMMIT → WAL на диск → отправка на реплики → ждём что реплики ПОЛУЧИЛИ (не применили) → ответ клиенту
```

Компромисс: не ждём применения, только подтверждение доставки по сети. Данные скорее всего согласованы, но не гарантированно. На практике встречается редко.

**Вариация (lossless semi-sync):** отправка на реплики → подтверждение получения → только потом применение в движке. Плюс: не нужно откатывать движок при сбое.

## PostgreSQL: synchronous_commit

| Значение | Что ждём |
|---|---|
| off | Ничего (даже локальный flush не ждём) |
| local | Flush на мастере (default) |
| remote_write | Получение репликой (в память) — полусинхронная |
| on / remote_apply | Применение на реплике — синхронная |

## Когда что

Потеря данных недопустима (деньги, бронирование) → **синхронная**.
Важна скорость, eventual consistency ок → **асинхронная**.
