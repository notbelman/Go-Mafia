- **Consistent Hashing** — ключи и шарды на кольце (0 → 2^32). Ключ идёт к ближайшему шарду по часовой. Добавление шарда перемещает только **~1/N** данных вместо почти всех
- **Проблема обычного хеша:** hash(key) % N → при N+1 почти все ключи меняют шард. Consistent hashing решает это кольцом
- **Virtual Nodes** — один физический шард = 100–200 точек на кольце. Без них 3 шарда могут встать неравномерно (один получит 60% ключей)
- **Virtual Buckets** — 1024 виртуальных бакета, приложение всегда делает hash % 1024. Маппинг бакет→физический шард обновляется при добавлении. Для приложения **ничего не меняется**
- **Рандеву хеширование (HRW)** — альтернатива без кольца: для каждого ключа считаем хеш со **всеми** шардами, выбираем максимум. Проще, но N хешей на запрос
- Virtual Buckets ≠ Virtual Nodes: Buckets = абстракция над шардами (приложение не знает про физику), Nodes = приём внутри consistent hashing (равномерность)
- Consistent hashing используется в DynamoDB, Cassandra, Memcached, Redis Cluster, CDN

---

## Сравнение подходов

| | Обычный хеш | Consistent Hashing | Рандеву (HRW) | Virtual Buckets |
|---|---|---|---|---|
| При добавлении шарда | ~100% переезжает | ~1/N переезжает | ~1/N переезжает | Переносим бакеты |
| Структура | hash % N | Кольцо + virtual nodes | Нет, просто функция | hash % 1024 + маппинг |
| Реализация | Тривиальная | Средняя | Простая | Средняя |
| Overhead на запрос | 1 хеш | 1 хеш + поиск на кольце | N хешей (по числу шардов) | 1 хеш + lookup маппинга |

## Consistent Hashing

### Проблема обычного хеша
`hash(key) % N` шардов — при добавлении (N → N+1) почти все ключи меняют шард.

```
hash("user_123") % 4 = 2
hash("user_123") % 5 = 3  ← нужно переместить
```

### Как работает кольцо
1. Кольцо от 0 до 2^32
2. Каждый шард хешируется → позиция на кольце: `hash(shard_ip)`
3. Каждый ключ хешируется → позиция на кольце: `hash(key)`
4. Ключ принадлежит **ближайшему шарду по часовой стрелке**

```
        0
        |
   K1 --+-- Shard A
       /
      /
 Shard C        Shard B
      \        /
       \--K2--/

K1 → Shard A (ближайший по часовой)
K2 → Shard B (ближайший по часовой)
```

### Добавление шарда
Новый шард встаёт на кольцо → забирает только ключи между собой и предыдущим шардом. Остальные не двигаются. **~1/N данных** вместо почти всех.

### Virtual Nodes
Проблема: 3 шарда могут встать неравномерно, один получит 60% ключей.

Решение: каждый физический шард = **100–200 виртуальных точек** на кольце. Равномерное распределение даже при малом числе шардов.

### Где используется
DynamoDB, Cassandra, Memcached, Redis Cluster, CDN.

## Virtual Buckets (виртуальное шардирование)

Прослойка абстракции между приложением и физическими шардами.

### Проблема
Приложение знает о 3 шардах → `hash(key) % 3`. Добавили 4-й → `hash(key) % 4` → почти всё переехало.

### Решение
Создаём заранее **1024** виртуальных бакетов. Приложение **всегда** делает `hash(key) % 1024`. Не меняется никогда.

3 физических шарда → бакеты 0–340 на шарде 1, 341–681 на шарде 2, 682–1023 на шарде 3.

### Добавление физического шарда
Было 3, стало 4. Перемещаем часть бакетов на новый шард. Для приложения **ничего не меняется** — просто маппинг «бакет → физический шард» обновился.

### Почему 1024
Чтобы **никогда не менять** количество бакетов. Изменение = решардинг (пересчёт всех хешей). 1024 хватает надолго — даже при 100 шардах по 10 бакетов на шард.

### Virtual Buckets ≠ Virtual Nodes
- **Virtual Buckets** — абстракция над физическими шардами. Приложение работает с бакетами
- **Virtual Nodes** — приём внутри consistent hashing. Один шард = 100+ точек на кольце

Разные уровни, могут использоваться вместе.

## Рандеву хеширование (Rendezvous, HRW)

Альтернатива consistent hashing. Нет кольца — для каждого ключа считаем хеш со **всеми** шардами и выбираем максимум.

### Как работает
```
Ключ 123:
  hash(123, shard_1) = 345
  hash(123, shard_2) = 456  ← максимум → записываем сюда
  hash(123, shard_3) = 121
```

Чтение: пересчитываем → тот же максимум → тот же шард.

### Добавление/удаление шарда
Добавили shard_4 → пересчитываем. Если новый хеш стал максимумом → ключ переезжает. Остальные не двигаются. **~1/N переезжает** (как в consistent hashing).

**Важно:** после добавления нужно пересчитать и перенести затронутые данные — автоматически не переедут.

### На практике
Встречается реже consistent hashing. Проще в реализации (несколько строк кода), но на каждый запрос **N хешей** (по числу шардов). При большом N — overhead.
