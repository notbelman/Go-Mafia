## Проблема

Локальный auto-increment на каждом шарде → ID пересекаются. Шард 1 выдал id=1, шард 2 тоже выдал id=1. Два разных пользователя с одинаковым ID.

То же самое если несколько инстансов приложения генерируют ID до записи в БД.

## Решения

### UUID
Случайный 128-битный идентификатор. Вероятность коллизии исчезающе мала.

**Плюс:** генерируется где угодно без координации.
**Минус:** большой (16 байт), плохо ложится в B-tree (случайный порядок → page splits), нечитаемый.

### Выделенный генератор
Отдельный сервис, который выдаёт уникальные ID. Все инстансы ходят к нему.

**Плюс:** гарантированная уникальность, можно делать монотонные ID.
**Минус:** единая точка отказа, дополнительный сетевой хоп.

### Диапазоны (ranges)
Каждый шард/инстанс заранее получает свой диапазон: шард 1 → ID 1–1000000, шард 2 → ID 1000001–2000000.

**Плюс:** нет координации при каждой записи.
**Минус:** диапазоны могут закончиться, неравномерное использование.

### Snowflake-подобные (Twitter)
ID = timestamp + machine_id + sequence. Монотонный, уникальный, сортируемый по времени.

**Плюс:** лучшее из обоих миров — уникальный и упорядоченный.
**Минус:** зависимость от синхронизации часов.

## Связь с шардированием

ID генерируется **до** записи в БД → по нему считаем хеш → определяем шард → пишем. Если ID генерирует сама БД (auto-increment), мы не знаем шард заранее — проблема.
