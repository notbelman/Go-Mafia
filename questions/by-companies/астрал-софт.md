## Вопросы

### Docker / Helm / Nginx
1. Приходилось ли вам самостоятельно настраивать Docker-образы и Helm-чарты?
> Непосредственно этим занимались DevOps-инженеры в команде. Я со своей стороны писал и правил `Dockerfile` для своих сервисов — multi-stage сборка, финальный образ на `scratch`. Helm-чарты трогал по минимуму: мог зайти и поправить env-переменную или resource limits если нужно было что-то проверить на стейдже, но владели чартами девопсы. Понимаю структуру чарта (templates, values.yaml, Chart.yaml), понимаю что делает `helm upgrade --install` и как работает rollback, но глубокой экспертизы в Helm у меня нет.

2. Какие подходы вы использовали при сборке Docker-образов?
> Multi-stage build: первый стейдж на `golang:1.22-alpine` — собираем бинарник с `CGO_ENABLED=0 GOOS=linux`, второй стейдж — `FROM scratch`, копируем только бинарник и TLS-сертификаты (`ca-certificates`). Итоговый образ около 20 МБ. Никаких shell, никаких лишних утилит — минимальная attack surface. `.dockerignore` чтобы не тащить `vendor`, `*.md`, `_test.go` в контекст сборки.

3. Углублялись ли вы во внутренности Docker (например, слои, оптимизация образов)?
> Понимаю механику слоёв: каждая инструкция в `Dockerfile` — отдельный слой, слои кешируются. Поэтому `COPY go.mod go.sum` и `RUN go mod download` идут до `COPY . .` — чтобы зависимости не перекачивались при каждом изменении кода. В остальном глубоко не погружался — это зона DevOps.

4. Как в Nginx настроить маршрутизацию между несколькими сервисами (контейнерами)?
> Базово понимаю: в блоке `http` определяешь несколько `upstream` блоков — по одному на каждый upstream-сервис. В `server` блоке прописываешь `location` правила: `location /api/orders { proxy_pass http://orders_upstream; }`, `location /api/tracking { proxy_pass http://tracking_upstream; }`. В upstream прописываешь адреса контейнеров (по имени сервиса в docker-compose или по DNS в K8s). У нас на проекте роутинг был на уровне Kubernetes Ingress (nginx ingress controller), конкретные nginx конфиги писали девопсы.

### Kubernetes / Observability
5. Какие инструменты вы использовали для логирования?
> Со стороны приложения — **zap** (uber-go/zap). В hot path (Kafka consumer-ы, обработка событий трекинга) — `Logger` без аллокаций. В менее нагруженных местах — `SugaredLogger`. Формат — JSON, чтобы ELK мог парсить без доп. конфигурации. Каждая строка лога содержит `trace_id`, `service`, `level`, `msg`. Со стороны инфраструктуры — ELK стек: Fluent Bit → Elasticsearch → Kibana.

6. Как организован сбор логов в Kubernetes: как логи из контейнеров попадают в централизованное хранилище?
> Контейнер пишет в stdout/stderr — это стандарт в K8s. Kubelet забирает эти логи и пишет их на ноду. Fluent Bit задеплоен как DaemonSet — по одному поду на каждой ноде. Он читает логи с ноды, добавляет метаданные (имя пода, namespace, контейнер), и отправляет в Elasticsearch. В Kibana настроены индексы по сервисам, можно фильтровать по `trace_id`, по уровню, по времени. Это делали девопсы, я пользовался уже готовым стеком.

7. Работали ли вы с метриками? Какие инструменты использовали?
> Да. **Prometheus + Grafana**. В каждом сервисе подключали `prometheus/client_golang`, поднимали эндпоинт `/metrics`. Определял какие метрики важны для своих сервисов и добавлял их в код: счётчики, гистограммы латенций, гейджи. Prometheus scrape-ил эти эндпоинты по расписанию, данные хранил у себя. Grafana строила дашборды на основе PromQL-запросов. Alertmanager рассылал алерты в Telegram при превышении порогов.

8. Использовали ли бизнес-метрики (например, upstream, SLA и т.д.)?
> Да. Помимо технических (latency, error rate, goroutines) у нас были бизнесовые: `delivery_status_updated_total` — количество обновлений статусов доставки с разбивкой по перевозчику, `slot_allocation_duration_seconds` — время расчёта слотов доставки (SLA бизнеса — до 200 мс), `carrier_errors_total` — ошибки по каждому перевозчику. Когда один перевозчик начинал деградировать — это сразу было видно на дашборде carrier health ещё до того, как пойдут жалобы от клиентов. По `carrier_errors_total` был настроен алерт: > 50 ошибок за 5 минут по одному перевозчику → warning в Telegram.

9. Создавали ли вы дашборды (например, в Grafana)? Что именно отображали?
> Да, участвовал в создании. Три основных дашборда: **Overview** — RPS, латенсии (P50/P95/P99), error rate по всем сервисам; **Carrier Health** — доступность и латенсии запросов к каждому из трёх перевозчиков, `carrier_errors_total`, `carrier_request_duration_seconds`; **Business Metrics** — заказы по статусам, SLA доставки (процент доставок в срок), consumer lag Kafka, количество обновлений статусов. После инцидента с перевозчиком добавил отдельный дашборд "Carrier Contract Violations" — фиксировал когда перевозчик возвращает ответ не по схеме.

### Архитектура / Коммуникация
10. Как сервисы взаимодействовали между собой?
> Два протокола в зависимости от характера взаимодействия. **gRPC (protobuf)** — для синхронного: когда один сервис ждёт ответа от другого здесь и сейчас. Например, API Gateway → Routing Service за расчётом маршрута, или Integration Service → WMS за подтверждением. Даёт строгий типизированный контракт, низкую латентность, встроенный streaming если нужен. **Kafka** — для асинхронного: события о смене статуса доставки, нотификации клиентам, биллинговые события. Здесь важна развязка — Integration Service публикует событие и не ждёт пока Notification Service его обработает. Буферизация Kafka защищает от пиковых нагрузок.

11. Как устроен контракт (protobuf)?
> В `.proto`-файле описываешь `message` (структуры данных) и `service` (RPC-методы). Запускаешь `protoc` с нужным плагином (для Go — `protoc-gen-go` + `protoc-gen-go-grpc`) — получаешь готовый клиент и серверный интерфейс. Контракт строго версионируется: поле нельзя удалить или изменить его номер — это сломает сериализацию. Можно только добавлять новые поля с новыми номерами. Если поле убрать из .proto — оно просто игнорируется при десериализации (backward compatible). У нас proto-файлы лежали в отдельном shared-репозитории, изменения в контрактах — только через RFC и обсуждение на грумминге.

12. Как в protobuf реализовать повторяющиеся поля (repeated)?
> Ключевое слово `repeated` перед типом поля: `repeated string tags = 1;`. При кодогенерации для Go это компилируется в слайс: `Tags []string`. Порядок элементов сохраняется — это не set, а list. Может применяться к любому типу, включая message: `repeated DeliveryStatusEvent events = 2;` — получишь `[]*DeliveryStatusEvent`. Пустой repeated в wire-формате просто отсутствует (не занимает байты), что отличается от обязательных полей.

### Командная работа
13. Как была организована работа команд? (одна команда / несколько команд, зоны ответственности)
> Одна кросс-функциональная команда из 9 человек: 4 бэкендера на Go, 1 фронтендер (React, диспетчерский интерфейс), 2 DevOps, 1 QA, тимлид. Внутри бэкенда — зоны ответственности: я отвечал за интеграционный слой с перевозчиками и WMS, сервис маршрутизации и real-time трекинг. Антон (второй сеньор) — слотирование и сервис распределения заказов. Игорь — нотификации и биллинг перевозок. Ксения — API Gateway и аутентификация. Формально мы были одной командой, но каждый владел своим куском — так было меньше конфликтов при ревью и понятно кто отвечает за что при инциденте. DevOps работали в той же команде, но с отдельным бэклогом по инфраструктуре. Взаимодействие с WMS-командой на стороне заказчика — по контрактам API и формату событий, периодически подключали их представителя на грумминг.

### Базы данных
14. Как удалять данные в ClickHouse?
> ClickHouse не поддерживает DELETE в классическом смысле — строки immutable после записи. Три варианта. Первый: `ALTER TABLE t DELETE WHERE condition` — это мутация, выполняется асинхронно в фоне, может идти минуты на больших таблицах, не подходит для частых удалений. Второй: `ReplacingMergeTree` + `FINAL` — дедупликация при мерже: пишешь новую строку с тем же ключом и `is_deleted=1`, при `SELECT ... FINAL` дубли схлопываются и удалённые фильтруются. Третий (самый ClickHouse-way): **TTL** — `TTL event_date + INTERVAL 90 DAY DELETE` прямо в DDL таблицы. Данные удаляются автоматически по истечении срока при очередном мерже партов.

15. Какой объём данных был в PostgreSQL (примерно: гигабайты / терабайты)?
> Несколько сотен гигабайт — ближе к нижней границе терабайта. Основные таблицы: заказы на доставку, события статусов (их больше всего — каждый заказ генерирует 5-10 статусных переходов), слоты, биллинговые записи. Самая большая таблица — `delivery_status_events`, партиционированная по дате. За год работы системы там было несколько десятков миллионов строк. На аналитику события дополнительно реплицировались в ClickHouse — там хранился полный исторический архив.

16. Приходилось ли оптимизировать SQL-запросы?
> Да. Основные инструменты: `EXPLAIN ANALYZE` — смотришь план, ищешь Seq Scan на больших таблицах, высокий cost, loops × rows. Добавление индексов — составные индексы по полям которые всегда идут вместе в WHERE: `(carrier_id, created_at)`, `(order_id, status)`. Переписывание коррелированных подзапросов в JOIN — коррелированный подзапрос выполняется по разу на каждую строку внешнего запроса, JOIN работает принципиально иначе. Избегание `SELECT *` — тянешь только нужные поля, особенно важно если есть jsonb-колонки с большим payload. Партиционирование таблицы событий по `created_at` — запросы за конкретный период сканируют только нужные партиции. Был конкретный случай: запрос по незаиндексированному `carrier_id` на 30 млн строк падал по таймауту — добавление индекса сократило время с 8 сек до 40 мс.

17. Объясните разницу между: EXPLAIN, EXPLAIN ANALYZE, COST
> `EXPLAIN` — показывает план выполнения запроса без реального выполнения. Видишь какие узлы (Seq Scan, Index Scan, Hash Join, etc.) PostgreSQL собирается использовать и почему. Полезно чтобы убедиться что индекс вообще задействован, не запуская тяжёлый запрос. `EXPLAIN ANALYZE` — реально выполняет запрос (данные читаются, но изменения через DML можно обернуть в транзакцию и откатить) и показывает plan + actual: реальное время выполнения каждого узла, реальное количество строк vs оценка планировщика. Если оценка сильно расходится с реальностью — устаревшая статистика, нужен `ANALYZE`. `COST` — оценка планировщика в условных единицах (не миллисекунды, не байты — абстрактные единицы). Состоит из `startup cost` (до первой строки) и `total cost` (до последней). Планировщик выбирает план с наименьшим total cost. Значения зависят от `seq_page_cost`, `random_page_cost` и статистики таблиц.

18. Что такое транзакция? Как она реализована в PostgreSQL? Какие механизмы используются (MVCC и т.д.)?
> Транзакция — атомарная единица работы, подчиняется свойствам ACID. Atomicity: либо все операции выполнились, либо ни одна (rollback). Consistency: данные переходят из одного валидного состояния в другое. Isolation: транзакции не видят промежуточных состояний друг друга. Durability: после коммита данные сохранены даже при падении. В PostgreSQL транзакции реализованы через **MVCC** (Multi-Version Concurrency Control). Каждая строка хранит `xmin` (xid транзакции которая её создала) и `xmax` (xid транзакции которая её удалила/обновила). Когда читающая транзакция стартует, PostgreSQL фиксирует снапшот — список активных транзакций на этот момент. Строка видима если `xmin` закоммичен и не в снапшоте активных, `xmax` не закоммичен или в снапшоте активных. Это значит читающие не блокируют пишущих и наоборот — главное преимущество MVCC над lock-based. Обратная сторона: старые версии строк накапливаются (dead tuples), нужен vacuum чтобы их убирать. Уровни изоляции в PG: Read Committed (дефолт), Repeatable Read, Serializable. Read Committed берёт новый снапшот на каждый statement, поэтому может видеть изменения других транзакций внутри одной своей. Repeatable Read держит снапшот на всю транзакцию.

19. Если таблица партиционирована (например, по времени), и запрос не содержит ключ партиции — как будет выполняться запрос?
> Partition pruning не сработает. PostgreSQL просканирует все партиции — по Seq Scan или Index Scan в каждой. Если партиций 365 (по дням за год) — будет 365 сканов. Это дорого и убивает смысл партиционирования. Именно поэтому ключ партиции должен обязательно быть в WHERE. У нас таблица `delivery_status_events` партиционирована по `created_at` (по месяцам), и все запросы к ней всегда включали диапазон дат. Если кто-то писал запрос без даты — на ревью это было блокером.

### Брокеры сообщений (Kafka)
20. Почему нельзя просто использовать один топик для всех типов сообщений?
> Несколько причин. Разные типы событий — разные схемы, разные producer-ы и consumer-ы. Если всё в одном топике — consumer читает всё подряд и должен смотреть тип каждого сообщения, чтобы понять как его обрабатывать. Это усложняет код и создаёт ненужные зависимости. Разные consumer-группы с разной скоростью обработки — Notification Service может не успевать за Billing Service, и они начинают мешать друг другу по lag. В отдельных топиках каждая группа потребляет независимо. Невозможно масштабировать отдельные потоки: если события статусов доставки идут в 100 раз чаще биллинговых — нужно больше партиций и consumer-ов именно для статусов. В общем топике это не сделать без увеличения для всех. Версионирование схемы: если изменилась схема события одного типа — затрагиваются все consumer-ы топика, а не только заинтересованные.

21. Как определяется, в какую партицию попадет сообщение?
> Зависит от наличия ключа. Если задан ключ — `murmur2(key) % num_partitions` (в Java-клиенте, в Go-клиентах алгоритм аналогичный). Все сообщения с одинаковым ключом гарантированно попадают в одну партицию — это даёт гарантию порядка в рамках одного ключа. У нас ключом был `order_id` — все события одного заказа шли в одну партицию и обрабатывались строго по порядку. Если ключ не задан — round-robin по партициям (или sticky partitioning для батчей — producer накапливает сообщения и отправляет их в одну партицию батчем для эффективности). Никакой гарантии порядка между разными ключами нет.

22. Может ли в одной партиции быть несколько типов событий?
> Технически — да. Kafka не знает ничего о содержимом сообщения, это просто байты. Несколько типов событий вполне могут оказаться в одной партиции — либо намеренно если они в одном топике, либо случайно при hash-коллизии ключей разных типов. Но это антипаттерн: consumer должен десериализовать каждое сообщение, определять тип и по-разному обрабатывать. Растёт связность, усложняется schema evolution. Правило: один топик — одна схема, одна семантика события.

23. Есть ли гарантия, что определённый тип события попадёт в конкретную партицию?
> Только при явно заданном ключе. Если всегда передавать один и тот же ключ для событий данного типа — `hash(key) % N` детерминирован, пока не меняется `N` (количество партиций). Если количество партиций изменилось — распределение меняется, один и тот же ключ может попасть в другую партицию. Это один из аргументов против изменения количества партиций в продакшне. Без ключа никакой гарантии нет.

### Linux
24. Насколько хорошо вы знакомы с Linux?
> Уверенный пользовательский уровень, достаточный для работы с серверами. Навигация и работа с файлами — без вопросов. Управление процессами: `ps aux`, `kill`, `top`/`htop`, `lsof` чтобы посмотреть открытые файловые дескрипторы. Сеть: `netstat -tlnp` или `ss -tlnp` — открытые порты, `curl` для отладки HTTP. Работа с правами: `chmod`, `chown`, `umask`. Переменные окружения, `systemd` (старт/стоп/статус сервисов). В контексте K8s — `kubectl exec` внутрь контейнера, `kubectl logs`, `kubectl describe pod`. Системное программирование — понимаю концептуально (как работает fork, inode, файловые дескрипторы), в продакшне с этим напрямую не работал.

25. Как передать файл между машинами в Linux?
> `scp file.txt user@remote:/destination/path` — простейший вариант через SSH, подходит для разовых передач. `rsync -avz --progress file.txt user@remote:/path` — более умный: передаёт только дельту (изменившиеся блоки), показывает прогресс, удобен для больших файлов и повторных передач одного и того же. Ещё варианты: `sftp` для интерактивной работы. Если нет прямого SSH-доступа — через S3/объектное хранилище: `aws s3 cp file s3://bucket/key` с одной машины, `aws s3 cp s3://bucket/key ./` с другой.

26. Что такое Load Average? Как его интерпретировать?
> Load Average — среднее количество процессов находящихся в состоянии выполнения (runnable, то есть уже запущены или ждут CPU) плюс в состоянии uninterruptible wait (обычно ждут I/O) за последние 1, 5 и 15 минут. Видно в `top` или `uptime`. Интерпретация: значение 1.0 означает что один процессор был полностью занят. Для интерпретации нужно знать количество CPU: load 4.0 на однопроцессорной машине — катастрофа, очередь растёт. Load 4.0 на 8-ядерной — половина ядер свободна. Практическое правило: load ≤ количества CPU — норма. Load > количества CPU * 1.5 — начинаются задержки. Load растёт 15-минутное значение — проблема нарастает. Если load высокий но CPU не загружен — скорее всего I/O bottleneck (uninterruptible wait, столбец `wa` в top).

27. Как работает fork() в Linux?
> `fork()` — системный вызов, создаёт новый процесс (дочерний) как почти точную копию вызвавшего (родительского). Копируется: адресное пространство, файловые дескрипторы, переменные окружения, маски сигналов, PID группы. Ключевая оптимизация — **Copy-on-Write (CoW)**: физическая память не копируется сразу. Родитель и дочерний процесс используют одни и те же физические страницы памяти, помеченные как read-only. Только при попытке записи (первый write в страницу) происходит реальное копирование этой страницы. Это делает `fork()` очень дешёвым для сценариев типа `fork()` + `exec()` (создание нового процесса с другим кодом) — exec немедленно заменяет адресное пространство, старые страницы не нужны.

28. Как процесс может определить, является ли он родительским или дочерним после fork()?
> По возвращаемому значению `fork()`. Родитель получает PID дочернего процесса (целое положительное число > 0). Дочерний процесс получает 0. При ошибке (например, превышен лимит процессов) возвращается -1 только родителю, дочерний не создаётся. Стандартный паттерн в C: `pid_t pid = fork(); if (pid == 0) { /* дочерний */ } else if (pid > 0) { /* родитель, pid — это PID дочернего */ } else { /* ошибка */ }`.

29. Почему при удалении открытого файла место на диске не освобождается?
> Потому что в Linux имя файла и сами данные — разные сущности. Файловая система хранит данные через **inode** — структуру с метаданными (размер, права, указатели на блоки данных). Имя файла в директории — просто ссылка на inode. `unlink()` (или `rm`) удаляет эту ссылку из директории и уменьшает счётчик жёстких ссылок на inode на 1. Но inode и данные существуют пока счётчик > 0 ИЛИ пока есть открытые файловые дескрипторы на этот inode. Открытый `fd` — это ссылка на уровне ядра. Место освободится только когда: счётчик ссылок = 0 И все процессы закрыли свои fd. Практическое следствие: процесс может удалить файл во время работы другого процесса — тот продолжит читать/писать через свой fd, новые процессы файл уже не найдут. Место освободится когда первый процесс закроет fd (или умрёт).

### Go / Concurrency
30. Что такое race condition?
> Race condition — ситуация когда корректность результата зависит от относительного порядка выполнения нескольких горутин, обращающихся к разделяемым данным без синхронизации. Классический пример: `counter++` — это не атомарная операция, а три: read → modify → write. Если две горутины делают это одновременно, обе читают одно значение, обе вычисляют +1 и обе пишут — итог: +1 вместо +2. Go Memory Model определяет что без явной синхронизации нет гарантий видимости записей между горутинами. Даже чтение простого `int` без синхронизации формально является data race если другая горутина пишет.

31. Как работает проверка -race в Go?
> `-race` флаг при компиляции (`go build -race`, `go test -race`) подключает **ThreadSanitizer** (TSan) — инструментацию от Google. Компилятор вставляет в каждую операцию чтения/записи обращение к **shadow memory** — параллельной структуре данных где для каждого слова памяти хранится последнее обращение (горутина, тип операции — read/write, стек). При каждом доступе к памяти runtime проверяет: было ли недавно обращение из другой горутины без синхронизации между ними? Если да — это race, runtime паникует и печатает стек трейсы обеих горутин. Оверхед значительный: ~2-20x по CPU, ~5-10x по памяти — поэтому только в тестах и dev/staging, никогда в проде. У нас `go test -race ./...` обязательно в CI — ни один PR не мержился без прохождения этой проверки.

32. Что произойдёт, если несколько goroutine одновременно пишут в одну переменную без синхронизации?
> Undefined behavior по спецификации Go Memory Model. Физически: на уровне железа запись в переменную может быть не атомарной (особенно для типов > 8 байт — например `int64` на 32-битных платформах или строки, интерфейсы). Читающая горутина может увидеть частично записанное значение — torn read. Кроме того, компилятор и процессор могут переупорядочивать инструкции (reordering) и кешировать значения в регистрах — без барьера памяти другая горутина может никогда не увидеть запись или увидеть её в неожиданный момент. В Go гарантируется атомарность только для операций через `sync/atomic` (пакет `sync/atomic`) или при использовании `sync.Mutex`/`sync.RWMutex`/каналов. Race detector поймает это в тестах (`-race`). В продакшне без детектора — тихая порча данных, трудновоспроизводимые баги.
