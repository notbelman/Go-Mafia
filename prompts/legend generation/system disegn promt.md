2. **Интеграции.** "Указаны интеграции с N внешними системами. С какими конкретно? Например: ГЛОНАСС-провайдер, 1С, система маршрутизации X, телематика Y. Какой протокол у каждого (REST/SOAP/FTP)? Для каждой интеграции нужно понимать: что получаем, что отдаём, как часто."

Если пользователь ответит "ничего не добавлять" или "всё ок" — генерируй на основе того что есть в легенде.

Шаг 2 — Определить ASR. Из достижений и описания проекта в легенде определи Architecture Significant Requirement. Что определяет всю архитектуру? Read-intensive? Write-intensive? Real-time? Транзакционность? Strong consistency? Хранение больших объёмов? Проговори явно, как у Балуна: "Если это не учесть, архитектуру можно выбросить."

Шаг 3 — Расчёт нагрузки. Из данных в легенде и достижениях (RPS, количество сущностей, пользователей, транспортных средств и т.д.) посчитай:

- RPS на ключевые операции (read/write отдельно)
- Трафик (МБ/с, ГБ/с если релевантно)
- Объём хранения (на 1-3 года)
- Вывод: что является bottleneck (RPS? трафик? объём данных?)

Считай по формуле Балуна: DAU × действия / 86400 = RPS. Если точных DAU нет — выведи правдоподобные из контекста (размер компании, количество ТС, количество клиентов). Все цифры должны быть непротиворечивы с достижениями из резюме.

Шаг 4 — Определить сервисы. Из достижений резюме + ответов пользователя на шаге 1 определи какие сервисы есть. Если пользователь добавил свои сервисы — включи их. Добавь инфраструктурные компоненты (API Gateway, Load Balancer) которые подразумеваются.

Шаг 5 — Детальное проектирование каждого сервиса. По каждому сервису:

- Что делает (1-2 предложения)
- API: конкретные методы, протокол (gRPC для межсервисных вызовов, Kafka consumer/producer для событий). REST-эндпоинты не описывать на уровне сервиса — они живут в API Gateway как трансляция REST → gRPC.
- Data model: таблицы, поля, типы, PK, индексы (B-tree/hash/covering), партиционирование, почему именно такая структура
- RPS: на сервис в целом, на ключевые методы, на БД (read/write)
- БД: какая, почему именно она (реляционка vs KV vs колоночная vs in-memory), ссылайся на критерии из словаря
- Кеширование: что кешируем, где (in-process / внешний Redis), стратегия (cache aside / cache through / cache ahead), TTL, eviction policy (LRU/LFU/TTL), прогрев кеша если нужен
- Паттерны: circuit breaker (на внешних интеграциях), retry + backoff, transaction outbox, saga, idempotency — где применимо, с обоснованием
- K8s: количество реплик, HPA (по какой метрике — CPU/RPS/custom), resource requests/limits, readiness/liveness probes

Шаг 6 — Инфраструктурные компоненты. Отдельные секции по:

- API Gateway: auth (JWT/API key), rate limiting, routing, трансляция REST → gRPC (клиенты шлют REST, Gateway проксирует в gRPC-сервисы)
- Load Balancer: L4 vs L7, алгоритм (round robin / least connections / power of two choices)
- Kafka (если в стеке): топики (названия), количество партиций, consumer groups, гарантии (at-least-once / exactly-once), retention, формат сообщений (protobuf/JSON), шардирование (по какому ключу)
- PostgreSQL: партиционирование (по чему — времени/гео/user_id), шардирование (по чему и почему), репликация (sync/async и почему — ссылайся на правило Балуна: "деньги и бронирования = синхронная"), пул соединений (pgxpool, max connections)
- Redis: что кешируем по каждому сервису, структуры данных (string/hash/sorted set/stream), TTL, eviction policy, Cluster/Sentinel
- S3/Object Storage (если есть): бакеты, hot/cold storage

Шаг 7 — Отказоустойчивость. По каждому компоненту: что происходит при падении, как восстанавливаемся.

- Stateless сервисы: как балансировщик переключает
- Stateful компоненты: WAL, репликация, прикапывание стейта
- БД: failover, потеря данных при async vs sync
- Брокер: что если Kafka partition leader упал
- Внешние зависимости: circuit breaker, fallback, graceful degradation

Шаг 8 — Масштабирование. По каждому компоненту: как скейлим.

- Stateless сервисы: горизонтальное, HPA
- БД: шардирование (по какому ключу, почему именно по нему, какие запросы станут мультишардовыми и почему это ок)
- Кеш: шардирование по user_id / entity_id
- Kafka: заранее нарезать партиции (стратегия Балуна)
- Что является bottleneck и как его расшить

<quality_rules>

- Протоколы коммуникации: **REST** — только на внешнем контуре (API Gateway → клиенты, внешние интеграции). **gRPC** — для всей межсервисной коммуникации внутри системы. Kafka — для асинхронного обмена событиями между сервисами. Исключений нет. В таблицах API каждого сервиса указывай протокол явно: gRPC для внутренних методов, Kafka consumer/producer для событий.
- Трансляция REST ↔ gRPC: через **gRPC-Gateway** (grpc-ecosystem/grpc-gateway). API описывается один раз в `.proto`-файлах с HTTP-аннотациями (`google.api.http`). Из proto автоматически генерируются и gRPC-стабы, и REST-прокси. Proto — единственный источник правды для контрактов. Не должно быть отдельных REST-хендлеров, написанных вручную.
- Версионирование контрактов: при изменении контракта — новая версия proto-пакета (`package service.v2;`), новый gRPC-сервис, новый REST-префикс (`/api/v2/...`). Старая версия живёт параллельно до миграции клиентов. Внутри системы сервисы переходят на новую версию сразу (контролируемая среда), наружу — плавно. В файле API Gateway описать активные версии и маппинг.
- Все цифры (RPS, трафик, объём) должны быть непротиворечивы между файлами и с достижениями из резюме.
- Не выдумывай технологии за пределами стека резюме + справочника дефолтов.
- Не добавляй сервисы которых нет в достижениях (кроме инфраструктурных: LB, API GW).
- Каждое решение должно иметь обоснование "почему". Без "почему" решение бесполезно.
- Data model — конкретные таблицы с полями, не абстрактные "хранит данные".
- Используй терминологию из словаря сисдиз-паттернов: CQRS, transaction outbox, saga, circuit breaker, fan-out on write/read, cache aside, graceful degradation и т.д.
- Для каждой БД обосновывай выбор через критерии: OLTP vs OLAP, нужны ли транзакции, нужны ли связи (JOIN), форма данных, тип нагрузки.
- Для репликации: sync если strong consistency / деньги / бронирования, async если eventual ок.
- Для шардирования: обосновывай ключ через основной паттерн доступа ("пользователю нужны свои данные" → по user_id, "ищем по гео" → по geohash). </quality_rules>

# Tracking Service

## Назначение

Обработка потоковых данных от транспортных средств в реальном времени. Приём координат, обновление текущей позиции, хранение истории перемещений.

## API

|Метод|Протокол|Описание|RPS|
|---|---|---|---|
|UpdatePosition|gRPC|Обновление координат ТС|~3500 write|
|GetCurrentPosition|gRPC|Текущая позиция ТС|~2000 read|
|GetPositionHistory|gRPC|История перемещений за период|~500 read|
|Kafka consumer: `tracking-events`|Kafka|Обработка событий от телематики|~5000 events/s|

> Все методы — gRPC (межсервисная коммуникация). Клиенты обращаются через API Gateway, который транслирует REST → gRPC.

## Data model

```sql
-- Текущие позиции (горячие данные)
CREATE TABLE vehicle_position (
    vehicle_id    BIGINT PRIMARY KEY,
    latitude      DECIMAL(9,6) NOT NULL,
    longitude     DECIMAL(9,6) NOT NULL,
    speed         SMALLINT,
    heading       SMALLINT,
    updated_at    TIMESTAMPTZ NOT NULL
);
-- Индекс: PK (hash) по vehicle_id — точечный поиск O(1)

-- История перемещений (партиционированная)
CREATE TABLE position_history (
    vehicle_id    BIGINT NOT NULL,
    recorded_at   TIMESTAMPTZ NOT NULL,
    latitude      DECIMAL(9,6) NOT NULL,
    longitude     DECIMAL(9,6) NOT NULL,
    speed         SMALLINT
) PARTITION BY RANGE (recorded_at);
-- Партиция: помесячная. Старые партиции → cold storage.
-- Индекс: B-tree по (vehicle_id, recorded_at) — диапазонные запросы по истории одного ТС.
```

**Почему PostgreSQL для истории, а не ClickHouse:** данные нужно джойнить с метаданными ТС (маршрут, водитель), нужны транзакции при обновлении текущей позиции. Если объём истории вырастет до миллиардов записей — можно вынести историю в ClickHouse отдельным шагом.

## Хранилище

- **PostgreSQL** для position_history. RPS: ~3500 write, ~500 read (история). Пул: pgxpool, max 50 connections.
- **Redis** для vehicle_position (текущие позиции). RPS: ~3500 write, ~2000 read. Почему Redis, а не PostgreSQL: текущая позиция — hot data с частыми перезаписями, Redis даёт O(1) read/write без нагрузки на диск.

## Кеширование

- Текущие позиции кешируются в **Redis** (hash: `vehicle:{id}` → lat, lng, speed, updated_at).
- Стратегия: **cache aside**. Запись: сначала Redis, потом async в PostgreSQL (history). Чтение: Redis, miss → PostgreSQL.
- TTL: 5 минут (если ТС не обновляет позицию > 5 мин — считаем offline).
- Eviction: **volatile-lru** (вытесняем по LRU среди ключей с TTL).

## Паттерны

- **Idempotency:** дубликаты координат (одно и то же событие) идемпотентны по vehicle_id + timestamp.
- **Backpressure:** если Kafka consumer не успевает — consumer lag растёт, HPA добавляет реплики.

## K8s

- Реплики: 3 (min) — 10 (max).
- HPA: по кастомной метрике `kafka_consumer_lag` (порог 5000).
- Probes: readiness — `/health`, liveness — `/health` + проверка Kafka consumer heartbeat.
- Resources: requests 256Mi / 250m, limits 512Mi / 500m.
