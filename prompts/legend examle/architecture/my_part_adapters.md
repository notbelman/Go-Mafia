# Моя часть — Телематический Pipeline

## Контекст

Телематический pipeline TMS ЛАНИТ. Моя зона ответственности — весь hot path от провайдеров до нормализованных событий в Kafka:

**5 адаптеров → Kafka (telematics.raw) → Telematics Service → Kafka (3 топика) → downstream сервисы**

Детальный разбор каждого адаптера (edge cases, failure modes, протоколы): [[prompts/legend examle/architecture/adapters_deep_dive]]

## Провайдеры и адаптеры

### Решение: 1 провайдер = 1 отдельный сервис-адаптер

Причина: у каждого провайдера свой протокол с разной моделью соединения — WebSocket-клиент, HTTP-сервер для webhook, TCP-сервер, REST-поллер, SOAP-клиент. Объединять = смешивать разные failure-режимы в одном процессе. Один адаптер упал — остальные четыре работают.

| Адаптер | Провайдер | Протокол | Модель | Как работает |
|---|---|---|---|---|
| Navixy Adapter | Navixy | **WebSocket** | Push | Persistent WS соединение, event-driven. Провайдер стримит события |
| СКАУТ Adapter | СКАУТ | **REST JSON** | Pull (батч) | `GET /events?from=last_ts` раз в 1 сек. Один запрос = пачка событий от всех ТС провайдера |
| Omnicomm Adapter | Omnicomm | **Webhook** | Push | Провайдер POST-ит на наш HTTP endpoint при каждом событии |
| Wialon Adapter | Wialon | **TCP binary** (Wialon IPS) | Push | Persistent TCP-соединение, открытый бинарный протокол, парсим фреймы |
| АвтоГРАФ Adapter | АвтоГРАФ | **SOAP XML** | Pull (батч) | Legacy провайдер. Забираем батч по расписанию, кастомный маршалинг XML в Go |

### Все адаптеры stateless

- Без PG, без Redis, без кеша
- Задача: принял пакет от провайдера → распарсил → смаппил в protobuf → отправил в Kafka
- При рестарте: push-адаптеры (WS, Webhook, TCP) — провайдер переподключается или досылает. Pull-адаптеры (СКАУТ, АвтоГРАФ) — запрашивают с небольшим overlap, дубли ловит Telematics Service

### Pull vs Push — trade-offs

| | Push (WS, Webhook, TCP) | Pull (REST, SOAP) |
|---|---|---|
| Задержка | Минимальная — событие приходит сразу | До 1 сек (интервал поллинга) |
| Контроль нагрузки | Провайдер контролирует — может заспамить | Мы контролируем — забираем когда готовы |
| Reconnect | Наша ответственность — нужен reconnect с backoff | Не нужен — каждый запрос независимый |
| Дубли | Провайдер может дослать при реконнекте (2-3 сек окно) | При ретрае тот же батч (5-10 сек окно) |
| Потеря данных | Если мы лежим — провайдер может копить или терять | Данные копятся на стороне провайдера, заберём позже |

## Разделение ответственности

| Слой | Что делает | Чего НЕ делает |
|---|---|---|
| **Адаптер** | Парсит формат провайдера, маппит в protobuf, разбивает один пакет трекера на 1-3 события по типу (GPS/ENGINE/DRIVER_EVENT) | Не валидирует бизнес-правила, не дедуплицирует |
| **Telematics Service** | Валидация, дедупликация (in-memory), роутинг в нужный топик | Не знает ничего про формат провайдеров |

**Адаптер = структурная нормализация** (из формата провайдера → единый protobuf).
**Telematics Service = бизнес-нормализация** (валидно? дубль? куда роутить?).

Adapter Pattern в чистом виде: если завтра добавится шестой провайдер — пишем один адаптер, Telematics Service не трогаем.

### Один пакет от трекера → несколько событий

Трекер на машине шлёт всё в одном пакете: GPS + engine + alerts. Адаптер разбирает и генерит 1-3 события:

```
Пакет от Wialon (бинарный):
  lat: 55.7, lon: 37.6, speed: 80, fuel: 45%, rpm: 2100, ignition: true

Адаптер генерит:
  → RawTelematicsEvent{type: GPS, lat: 55.7, lon: 37.6, speed: 80, ...}
  → RawTelematicsEvent{type: ENGINE, fuel_level: 45, rpm: 2100, ignition: true, ...}
```

Driver events — по триггеру (резкое торможение, превышение скорости). Если в пакете есть alert-флаг → адаптер генерит третье событие.

## Формат данных — Protobuf

### Почему Protobuf, а не JSON

| | Protobuf | JSON |
|---|---|---|
| Размер | ~300 байт на событие | ~500-700 байт |
| Типизация | Из коробки (.proto файл = контракт) | Нет, строки везде |
| Скорость сериализации | Быстрее (бинарный) | Медленнее (текстовый парсинг) |
| Читаемость | Нечитаемый (бинарный) | Читаемый |
| Совместимость с gRPC | Нативная (gRPC в стеке) | Нужна конвертация |
| Версионирование | Backward/forward compatible (новые поля = новые номера) | Ломается при изменении структуры |

При 15K events/sec разница 200-400 байт на событие = **3-6 МБ/с экономии трафика** в Kafka.

### Как Kafka работает с Protobuf

Kafka хранит **просто байты** — ей безразлично что внутри: JSON, protobuf, avro, картинка.

```
Producer (адаптер):
  event := &RawTelematicsEvent{...}
  bytes, _ := proto.Marshal(event)     // Go: google.golang.org/protobuf
  producer.Send("telematics.raw", bytes)  // Kafka получает []byte

Consumer (Telematics Service):
  bytes := consumer.Read("telematics.raw")
  event := &RawTelematicsEvent{}
  proto.Unmarshal(bytes, event)         // обратно в структуру
```

**Schema Registry (Confluent)** — опционально. Хранит .proto-схемы, проверяет совместимость при деплое нового producer-а. Мы использовали: producer регистрирует схему, consumer валидирует — защита от случайного слома контракта при деплое.

### Незаполненные поля = 0 байт

Protobuf не сериализует дефолтные значения. Событие типа GPS с 7 заполненными полями из 25 возможных → в проводе только эти 7. Это ключевое: одна структура на все типы событий, но каждое событие компактное.

### .proto файл

```protobuf
syntax = "proto3";
package telematics;

message RawTelematicsEvent {
  // === Общее (всегда заполнено) ===
  string    event_id    = 1;   // UUID, генерит адаптер
  string    vehicle_id  = 2;   // ID транспортного средства у нас в системе
  string    provider    = 3;   // "navixy", "scout", "omnicomm", "wialon", "avtograf"
  EventType type        = 4;   // тип события — определяет какие поля заполнены
  int64     timestamp   = 5;   // unix ms, время от трекера (его часы)
  int64     received_at = 6;   // unix ms, когда адаптер получил (наши часы)

  enum EventType {
    GPS          = 0;
    ENGINE       = 1;
    DRIVER_EVENT = 2;
  }

  // === GPS (заполнено при type = GPS) ===
  double lat         = 10;   // широта
  double lon         = 11;   // долгота
  double speed       = 12;   // км/ч
  double heading     = 13;   // 0-360 градусов, направление движения
  double altitude    = 14;   // метры над уровнем моря
  int32  satellites  = 15;   // кол-во спутников (качество GPS-сигнала)
  double hdop        = 16;   // horizontal dilution of precision (чем меньше — тем точнее)

  // === Engine (заполнено при type = ENGINE) ===
  double fuel_level      = 20;  // % (0-100), текущий уровень топлива
  double fuel_consumed   = 21;  // литры, абсолютное значение с начала поездки
  int32  engine_rpm      = 22;  // обороты двигателя
  double odometer        = 23;  // км, пробег
  bool   ignition        = 24;  // зажигание вкл/выкл
  double coolant_temp    = 25;  // °C, температура охлаждающей жидкости
  double battery_voltage = 26;  // вольты, напряжение бортовой сети
  int32  engine_hours    = 27;  // моточасы (для расчёта ТО)

  // === Driver events (заполнено при type = DRIVER_EVENT) ===
  string driver_event_code = 30;  // код события:
                                   // "harsh_brake"    — резкое торможение
                                   // "harsh_accel"    — резкое ускорение
                                   // "speeding"       — превышение скорости
                                   // "geofence_exit"  — выход из геозоны
                                   // "geofence_enter" — вход в геозону
                                   // "idle_start"     — начало простоя
                                   // "idle_end"       — конец простоя
                                   // "sos"            — тревожная кнопка
  double event_value       = 31;  // контекст: скорость при превышении, G-force при торможении
  double event_lat         = 32;  // широта в момент события
  double event_lon         = 33;  // долгота в момент события
}
```

**Нумерация с пропусками (1-6, 10-16, 20-27, 30-33):** protobuf best practice. Оставляет место для новых полей в каждой секции. Например, добавить `tire_pressure = 28` в Engine — без конфликтов и без слома обратной совместимости.

**`received_at` vs `timestamp`:** разница между ними = лаг доставки. Мониторили: если `received_at - timestamp > 30 сек` → алерт, провайдер тормозит или сеть между нами деградирует.

## Kafka

### Кластер

Kafka — общая шина на весь проект TMS. Один кластер, не отдельная инсталляция для телематики.

| Параметр | Значение |
|---|---|
| Брокеров | 3 (стандартный минимум) |
| Replication factor | 3 (каждое сообщение на всех брокерах) |
| min.insync.replicas | 2 (запись успешна когда подтвердили 2 из 3) |
| Деплой | K8s, Strimzi оператор (управляет брокерами как CRD) |

**Зачем 3 брокера:** минимум для отказоустойчивости. Один упал → два оставшихся держат все данные (replication factor = 3), запись продолжается (min.insync.replicas = 2). На нашей нагрузке (15K/sec, 4.7 МБ/с) — 3 брокера с огромным запасом, Kafka держит сотни тысяч msg/sec на кластер.

### Как работает Consumer Group

Kafka не "отправляет" сообщения сервисам. **Сервисы сами тянут** (poll).

```
Топик: telematics.raw (12 партиций)
Ключ партиционирования: vehicle_id
  → hash("truck-42") % 12 = 7 → партиция 7
  → ВСЕ события truck-42 ВСЕГДА в партиции 7

Consumer group: "telematics-service" (3 инстанса)

Kafka-координатор распределяет:
  Инстанс 1 ← партиции [0, 1, 2, 3]    → ~5 000 ТС
  Инстанс 2 ← партиции [4, 5, 6, 7]    → ~5 000 ТС
  Инстанс 3 ← партиции [8, 9, 10, 11]  → ~5 000 ТС

Правило: одну партицию читает СТРОГО ОДИН consumer в группе.
→ нет гонок, нет дублей между инстансами
→ порядок событий для конкретного ТС гарантирован
```

Каждый инстанс при старте говорит Kafka: "я в группе `telematics-service`". Координатор (один из брокеров) распределяет партиции. Инстансы **сами** вычитывают сообщения из своих партиций.

### Топики

#### Сырые данные (вход)

| Топик | Кто пишет | RPS | Партиций |
|---|---|---|---|
| `telematics.raw` | Все 5 адаптеров | ~15 530/sec | 12 |

**Почему 12 партиций:** 3-5 инстансов Telematics Service в consumer group. 12 делится на 3, 4, 6 — удобно масштабировать. При 5 инстансах: 2-3 партиции на каждый, нагрузка ровная.

**Ключ партиционирования: `vehicle_id`.** Все события одного ТС в одной партиции → один consumer → порядок гарантирован → in-memory кеш дедупликации работает локально.

#### Нормализованные данные (выход Telematics Service)

| Топик | Что внутри | RPS | Кто читает |
|---|---|---|---|
| `telematics.gps` | Координаты, скорость, heading | ~15 000/sec | Tracking, Routing |
| `telematics.engine` | RPM, топливо, одометр, зажигание | ~500/sec | Analytics |
| `telematics.driver-events` | Резкое торможение, превышение, геозоны | ~30/sec | Notification, Analytics |

**Почему 3 топика, а не один:**
- **Разный RPS** — GPS 15K/sec, engine 500/sec. В одном топике GPS забивает consumer-ов которым нужно только engine
- **Разные consumer-ы** — Routing-у не нужно топливо, Notification-у не нужны координаты. Если один топик — каждый consumer читает всё и дропает 95% сообщений впустую
- **Разный retention** — GPS жрёт 95% storage. Можно поставить retention 7 дней на `.gps` и 90 дней на `.driver-events`
- **Независимое масштабирование** — `.gps` нужно 12 партиций, `.driver-events` хватит 3

## Telematics Service

### Почему один сервис

Все операции — один pipeline над одним событием:
1. Десериализация protobuf (наносекунды)
2. Валидация (in-memory, микросекунды)
3. Дедупликация (in-memory lookup, наносекунды)
4. Роутинг в топик по `type` (один `producer.Send`)

Разделять на 3 сервиса (Validation → Dedup → Router) = 3 сетевых хопа через Kafka, 3 деплоя, 3 consumer group. Latency вырастет в 3 раза, операционная сложность — тоже. Выигрыша ноль: логика простая, bottleneck — Kafka I/O, не CPU.

### PG — нет. Redis — нет.

Telematics Service **ничего не хранит персистентно**. Он чистый pipe: прочитал из Kafka → обработал в памяти → записал в другой топик Kafka. База данных не нужна.

Дедупликация — in-memory кеш (подробнее ниже). Внешний Redis убрали — лишняя зависимость и сетевой хоп без необходимости.

### Stateless или Stateful?

**Stateless.** In-memory кеш с TTL 10 сек — это ephemeral state (временное состояние). Потеря кеша при рестарте = пропустим несколько дублей = не страшно (downstream идемпотентен). С точки зрения K8s — сервис можно убивать, масштабировать, ребалансить без последствий. Нет PVC, нет persistent volume, нет миграций.

Для сравнения, **stateful** — это когда потеря данных = проблема: PG с заказами, Redis с кешем позиций. Там нужны реплики, бэкапы, PVC. У Telematics Service ничего этого нет.

### Валидация

| Правило | Действие | Зачем |
|---|---|---|
| lat/lon == 0,0 | Drop | Баг провайдеров — трекер потерял GPS, шлёт нули |
| satellites < 4 | Drop | Минимум 4 спутника для 3D-позиции. Меньше = мусор |
| hdop > 5 | Drop | Точность хуже 5 метров — для логистики бесполезно |
| timestamp > now() | Drop | Часы трекера сбились вперёд |
| timestamp < now() - 24h | Drop | Старые данные — повторная отправка после долгого офлайна |
| vehicle_id пустой | Drop | Невалидное событие |

Каждый дроп — метрика `telematics_dropped_total{reason="...", provider="..."}`. Видно на дашборде: если у Wialon внезапно 30% дропов — проблема на стороне провайдера, эскалируем.

### Дедупликация — In-Memory Sharded Map

#### Почему не Redis

Первая версия была на Redis. Потом поняли что не нужен:

| | Redis | In-memory |
|---|---|---|
| Latency | ~0.1 мс (сетевой round-trip) | ~0.001 мс (наносекунды, доступ к RAM) |
| Инфра | Нужен Redis + Sentinel (ещё 3 пода) | Ничего |
| Точка отказа | Redis лёг → нужен fallback | Нет внешней зависимости |
| Расшаренный между инстансами | Да | Нет — но и не нужно (см. ниже) |

**Ключевой аргумент:** события партиционированы по `vehicle_id`. Все события truck-42 **всегда** попадают в одну партицию → в один инстанс. Дубль того же события попадёт туда же → в тот же in-memory кеш. Расшаривать между инстансами нечего.

**На интервью:** "Сначала поставили Redis для дедупликации, потом поняли что не нужен — Kafka партиционирует по vehicle_id, дубли всегда попадают в тот же инстанс. Убрали сетевой хоп и внешнюю зависимость. Это упростило и архитектуру, и деплой."

#### Как работает

```
Пришло событие: vehicle_id=truck-42, timestamp=1704067200000

Ключ: "truck-42:1704067200000"
  → lookup в sharded map → ключ не найден → новое событие → добавить ключ, пропустить
  → lookup в sharded map → ключ найден → дубль → дропнуть
```

#### Почему Sharded Map, а не sync.Map / map+Mutex / map+RWMutex

**Проблема:** на один инстанс приходит ~5 000 events/sec (15K / 3 инстанса). Каждое событие = lookup + возможная вставка в map. Нужна конкурентная структура.

| Вариант | Проблема |
|---|---|
| `map + sync.Mutex` | Один мьютекс на всю map. 5 000 ops/sec — все горутины стоят в очереди на один лок. Bottleneck |
| `map + sync.RWMutex` | RWMutex помогает когда много чтений и мало записей. У нас каждая операция = check + insert — это **всегда write lock**. RWMutex не даёт выигрыша |
| `sync.Map` | Оптимизирован для "ключи стабильны, много чтений". У нас ключи живут 10 сек и исчезают — постоянные вставки и удаления. sync.Map для этого паттерна **медленнее** обычной map+mutex (подтверждено бенчмарками Go team) |
| **Sharded Map** | Разбиваем на N шардов (256), каждый со своим `sync.Mutex`. `shard = hash(key) % 256`. Contention уменьшается в 256 раз. 5 000 ops/sec / 256 шардов ≈ 20 ops/sec на шард — мьютекс даже не замечает |

**Решение: sharded map с 256 шардами.**

```go
const numShards = 256

type DedupCache struct {
    shards [numShards]shard
}

type shard struct {
    mu    sync.Mutex
    items map[string]int64  // key → expiry timestamp (unix ms)
}

func (d *DedupCache) IsDuplicate(vehicleID string, timestamp int64) bool {
    key := vehicleID + ":" + strconv.FormatInt(timestamp, 10)
    idx := fnv32(key) % numShards

    sh := &d.shards[idx]
    sh.mu.Lock()
    defer sh.mu.Unlock()

    now := time.Now().UnixMilli()
 // проверяем — это "чтение"                                                                                                                          
      if expiry, exists := sh.items[key]; exists && expiry > now {                                                                                       
          return true  // дубль, ничего не вставляем                                                                                                       
      }                                                                                                                                                    
                                                                                                                                                           
      // защита от переполнения — перед вставкой                                                                                                           
      if len(sh.items) > maxPerShard {                                                                                                                   
          // flush: удаляем всё, метрика                                                                                                                   
          sh.items = make(map[string]int64)                                                                                                                
          metrics.DedupCacheFlushTotal.Inc()                                                                                                               
      }                                                                                                                                                    
                                                                                                                                                           
      // вставляем
      sh.items[key] = now + 10_000                                                                                                                         
      return false
}
```

#### Очистка просроченных ключей (GC)

Ключи с истёкшим TTL не удаляются автоматически — это не Redis. Нужен фоновый cleanup:

```go
// Горутина на каждый шард, раз в 5 секунд
func (d *DedupCache) startCleanup() {
    for i := range d.shards {
        go func(sh *shard) {
            ticker := time.NewTicker(5 * time.Second)
            for range ticker.C {
                sh.mu.Lock()
                now := time.Now().UnixMilli()
                for key, expiry := range sh.items {
                    if expiry <= now {
                        delete(sh.items, key)
                    }
                }
                sh.mu.Unlock()
            }
        }(&d.shards[i])
    }
}
```

**Почему раз в 5 секунд:** TTL = 10 сек, ключи живут 10-15 сек (до следующего cleanup). Память не растёт бесконтрольно. Более частый cleanup = больше lock contention. 5 сек — хороший компромисс.

#### TTL = 10 секунд — обоснование

Дубли приходят из двух источников:

**1. Pull-адаптеры (СКАУТ, АвтоГРАФ):**
```
Нормальный режим: poll раз в 1 сек → батч новых событий
Ошибка: запрос зафейлился → retry с exponential backoff:
  попытка 1: через 1 сек
  попытка 2: через 2 сек
  попытка 3: через 4 сек
Худший случай: тот же батч придёт повторно через ~7 сек
→ TTL 10 сек покрывает с запасом
```

**2. Push-адаптеры (WS, TCP, Webhook):**
```
Разрыв соединения → провайдер реконнектится → досылает последние события
Окно дублей: обычно 2-3 секунды
→ TTL 10 сек покрывает многократно
```

**Что когда TTL истёк:** ключ удаляется из кеша (при следующем cleanup). Если то же событие придёт через 15 секунд — пройдёт как "новое". Но:
- GPS шлётся каждую секунду. Через 15 сек будет 15 новых позиций. Провайдер не шлёт данные 15-секундной давности
- Даже если пройдёт — downstream идемпотентен: `INSERT ... ON CONFLICT (vehicle_id, timestamp) DO NOTHING`

**Почему не больше?**
```
TTL 10s: ~5 000 ключей/инстанс × 10 сек = 50 000 ключей × ~100 байт = 5 МБ
TTL 60s: 50 000 × 6 = 300 000 ключей = 30 МБ
TTL 5 мин: 1.5M ключей = 150 МБ
```
Дубли с задержкой > 10 сек не встречались на практике. Растить кеш без причины — бессмысленно.

#### Память

```
На инстанс: ~5 000 events/sec × 10 сек TTL = ~50 000 ключей
Ключ "truck-42:1704067200000" ≈ 35 байт + int64 expiry + map overhead ≈ 100 байт
50 000 × 100 байт ≈ 5 МБ на инстанс
```

Копейки. Даже при ×10 нагрузке — 50 МБ, Go аллокатор не заметит.

## Масштабирование Telematics Service

### HPA (Horizontal Pod Autoscaler)

```yaml
min replicas: 3      # минимум для отказоустойчивости
max replicas: 8      # потолок (12 партиций, но с запасом)

Метрики:
  primary:   kafka_consumer_lag > 1000  → scale up
  secondary: CPU > 70%                  → scale up (подстраховка)

Cooldown: 5 мин (не дёргать реплики туда-сюда)
```

**Почему lag, а не RPS:**
- RPS — входящая нагрузка, мы её не контролируем
- Lag — "насколько мы отстаём". Lag = 0 → всё ок даже при 50K RPS. Lag растёт при 10K → проблема в обработке
- Consumer lag экспортируется в Prometheus через кастомную метрику `kafka_consumer_lag`, HPA читает через Prometheus Adapter

**Потолок:** максимум 12 инстансов = количество партиций `telematics.raw`. Больше инстансов чем партиций → лишние idle. Нужно больше 12 → сначала добавляем партиции.

### Как работает масштабирование

```
Нормальный режим (3 инстанса):
  Инстанс 1 ← [0,1,2,3]     4 партиции × ~1 300 events/sec = ~5 200/sec
  Инстанс 2 ← [4,5,6,7]
  Инстанс 3 ← [8,9,10,11]

Burst от провайдера (lag > 1000):
  HPA поднимает 4-й инстанс
  Kafka ребаланс (секунды):
  Инстанс 1 ← [0,1,2]       3 партиции
  Инстанс 2 ← [3,4,5]
  Инстанс 3 ← [6,7,8]
  Инстанс 4 ← [9,10,11]
  → нагрузка размазалась, lag падает

Lag упал (cooldown 5 мин):
  HPA убирает 4-й инстанс → обратно 3 инстанса
```

## Сценарии отказа

### Инстанс Telematics Service упал — пошаговый разбор

```
Исходное состояние:
  Инстанс 1 ← партиции [0,1,2,3]   кеш: ~50 000 ключей для ~5 000 ТС
  Инстанс 2 ← партиции [4,5,6,7]   кеш: ~50 000 ключей для ~5 000 ТС
  Инстанс 3 ← партиции [8,9,10,11] кеш: ~50 000 ключей для ~5 000 ТС
```

**t=0 — Инстанс 2 умер (OOM / segfault / нода K8s упала)**

Кеш инстанса 2 (50 000 ключей) потерян безвозвратно. Сообщения для партиций [4,5,6,7] перестают обрабатываться — копятся в Kafka.

**t=0...6 сек — Kafka ждёт heartbeat**

Consumer шлёт heartbeat координатору каждые `heartbeat.interval.ms` (3 сек). Координатор ждёт `session.timeout.ms` (у нас 6 сек). Не дождался → считает consumer мёртвым.

В это окно сообщения для партиций [4,5,6,7] **не обрабатываются**, lag растёт: 6 сек × ~5 000 events/sec = ~30 000 необработанных сообщений.

**t=6...10 сек — Ребаланс**

Координатор перераспределяет партиции мёртвого consumer-а:

```
  Инстанс 1 ← [0,1,2,3,4,5]     получил партиции 4 и 5
  Инстанс 3 ← [6,7,8,9,10,11]   получил партиции 6 и 7
```

**t=10 сек — Consumer-ы начинают читать новые партиции**

Инстанс 1 получает партицию 5. Но с какого offset?

```
Партиция 5 (была у инстанса 2):
  offset 1000 — последний committed offset (инстанс 2 подтвердил)
  offset 1001-1020 — инстанс 2 прочитал и обработал, но НЕ закоммитил
  offset 1021-1150 — накопились за 6 сек простоя

Инстанс 1 начинает с offset 1001 (первый после committed)
→ сообщения 1001-1020 будут обработаны ПОВТОРНО (at-least-once)
```

**t=10...12 сек — Дубли проходят**

```
Событие: truck-42, ts:1704067200000
  Это событие уже было обработано инстансом 2 (offset 1005)
  Инстанс 2 уже отправил его в telematics.gps

Теперь инстанс 1 перечитывает это событие:
  → проверяет свой in-memory кеш → ключа "truck-42:1704067200000" НЕТ
    (кеш инстанса 2 умер, а инстанс 1 никогда не видел этот ключ)
  → считает событие новым → отправляет в telematics.gps повторно

Это дубль. Он прошёл.
```

**t=10...12 сек — Downstream получает дубль**

```
Tracking Service получает дубль из telematics.gps:

  PostgreSQL:
    INSERT INTO position_history (vehicle_id, timestamp, lat, lon, speed, heading)
    VALUES ('truck-42', 1704067200000, 55.7, 37.6, 80, 45)
    ON CONFLICT (vehicle_id, timestamp) DO NOTHING;
    → affected rows = 0
    → запись уже есть, ничего не произошло

  Redis (текущая позиция):
    SET vehicle:truck-42 "{lat:55.7, lon:37.6, speed:80}"
    → перезапись тем же значением = noop

Дубль безопасен. Ни PG ни Redis не пострадали.
```

**t=10...20 сек — Кеш прогревается**

Новые события для ТС из партиций [4,5] начинают заполнять кеш инстанса 1. Через 10 секунд (= TTL) кеш полностью "прогрет" — дедупликация для этих ТС снова работает.

**t=20+ — Полная работоспособность**

```
Инстанс 1: обрабатывает 6 партиций (нагрузка ×1.5 от нормы)
Инстанс 3: обрабатывает 6 партиций (нагрузка ×1.5 от нормы)
→ HPA видит рост CPU/lag → через cooldown поднимет 3-й инстанс
→ Kafka ребалансит обратно на 3 → нагрузка выровнялась
```

**Итого: timeline**

```
t=0       Инстанс 2 упал, кеш потерян
t=0-6     Kafka ждёт heartbeat timeout. Партиции [4-7] не обрабатываются
t=6-10    Ребаланс. Партиции переезжают на инстансы 1 и 3
t=10-12   Перечитывание незакоммиченных сообщений → дубли проходят (~20-50 штук)
t=10-20   Кеш прогревается для новых партиций
t=20+     Дедупликация полностью восстановлена
```

**Критично ли?**

| Вопрос | Ответ |
|---|---|
| Данные потеряны? | **Нет.** Kafka хранит всё. Незакоммиченные — перечитаны |
| Сколько дублей пройдёт? | ~20-50 (незакоммиченное окно). Не тысячи |
| Дубли опасны? | **Нет.** PG: `ON CONFLICT DO NOTHING`. Redis: idempotent SET |
| Диспетчер заметит? | **Нет.** Разрыв 6-10 сек. GPS обновляется каждую секунду — на карте точка "подвисает" на 10 сек, потом догоняет |
| Алерт сработает? | **Да.** `consumer_lag > 1000` через ~2 сек. Но к моменту реакции дежурного (15 мин SLA) — уже всё восстановилось |
| Нужно ли ручное вмешательство? | **Нет.** Kafka ребаланс + HPA — полностью автоматическое восстановление |

**На интервью:** "Потеря in-memory кеша при падении инстанса — by design. Мы осознанно выбрали этот trade-off: окно уязвимости 10-15 секунд, ~20-50 дублей, но downstream идемпотентен и даже не замечает. Взамен убрали Redis как внешнюю зависимость — меньше инфраструктуры, меньше точек отказа, быстрее latency."

### Добавился новый инстанс (scale up) — пошагово

```
Было: 3 инстанса
HPA добавил 4-й (lag > 1000 или CPU > 70%)

t=0     Новый инстанс стартует, пустой кеш
t=0-5   Kafka ребаланс:
          Инстанс 1 ← [0,1,2]
          Инстанс 2 ← [3,4,5]
          Инстанс 3 ← [6,7,8]
          Инстанс 4 ← [9,10,11]   ← новый, кеш пуст

t=5-15  Инстанс 4 читает партиции [9,10,11]
        Кеш пуст → если в этот момент придёт дубль — пропустит
        Новые события заполняют кеш

t=15+   Кеш прогрет (10 сек TTL), дедупликация работает

Последствия: аналогичны падению — окно ~10 сек без дедупликации
для партиций нового инстанса. Downstream идемпотентен → ок
```

### Kafka брокер упал

```
Один брокер из 3 упал:
  - Replication factor = 3 → данные есть на 2 оставшихся
  - min.insync.replicas = 2 → запись продолжается (2 из 3 живы)
  - Leader партиций с упавшего брокера → Kafka автоматически выбирает нового лидера среди реплик
  - Consumer-ы переключаются на нового лидера
  - Простой: секунды (время выбора лидера)

Два брокера из 3 упали:
  - min.insync.replicas = 2, живых = 1 → запись НЕВОЗМОЖНА
  - Адаптеры получают ошибку записи → буферизуют в памяти / ретраят
  - Consumer-ы не могут читать → lag копится
  - Критический инцидент → DevOps поднимает брокеры
  - После восстановления: адаптеры дошлют, consumer-ы догонят

Все 3 брокера упали:
  - Полная недоступность Kafka
  - Push-адаптеры (WS, TCP): копят в памяти, при переполнении — дропают старые (ring buffer)
  - Pull-адаптеры (REST, SOAP): перестают поллить, данные копятся у провайдера
  - После восстановления Kafka: адаптеры дошлют, pull-адаптеры заберут накопленное
  - GPS-данные за период простоя от push-адаптеров могут быть потеряны
```

### In-memory кеш переполнился (утечка памяти)

Может случиться если cleanup горутина зависла или пришёл аномальный burst.

**Три уровня защиты:**

**1. Фоновый cleanup (штатный режим):**
Горутина на каждый шард, раз в 5 сек удаляет просроченные ключи. В нормальном режиме этого достаточно — ключи живут 10 сек, cleanup каждые 5.

**2. Проверка на вставке (аварийная):**
При каждой вставке нового ключа проверяем `len(shard.items) > maxPerShard`. Если шард переполнен — полный flush.

```go
// внутри IsDuplicate, перед вставкой:
if len(sh.items) > maxPerShard {
    sh.items = make(map[string]int64)  // полный flush шарда
    metrics.DedupCacheFlushTotal.Inc()
}
sh.items[key] = now + 10_000
```

Проверка **на вставке, не на чтении** — потому что:
- Чтение (дубль найден) → map не растёт, нечего защищать
- Вставка (новое событие) → map растёт, тут и проверяем
- Проверка на вставке = мгновенная реакция, не ждём cleanup через 5 сек

`maxPerShard = 50 000 / 256 ≈ 200` в норме. Ставим `maxPerShard = 1000` (×5 запас). Если в одном шарде > 1000 ключей — что-то пошло не так.

**3. Мониторинг:**
Метрика `dedup_cache_size` (сумма `len(items)` по всем шардам) → алерт если > 200 000 (4× нормы в 50 000). Метрика `dedup_cache_flush_total` → алерт если > 0 (flush = аномалия, нужно разбираться).

**Принцип: лучше потерять кеш и пропустить дубли чем OOM.** OOM = под убит K8s-ом, ребаланс, простой. Flush кеша = 10 сек без дедупликации, downstream идемпотентен.
