## 1. О компании и проекте

**ЛАНИТ** — крупнейшая российская группа IT-компаний, на рынке с 1989 года. Больше 14 000 сотрудников, десятки дочерних структур: системная интеграция, разработка ПО, дистрибуция, консалтинг. Я работал в одном из внутренних подразделений разработки — делали заказную систему для крупного логистического оператора, название заказчика под NDA, но это федеральная компания с тысячами грузоперевозок в день по всей России.

Проект — **система управления логистикой (TMS)** для трекинга грузоперевозок в реальном времени. До нас у заказчика был зоопарк: часть трекинга через 1С:TMS, часть через Excel и телефонные звонки диспетчерам, телематика от разных провайдеров не агрегировалась — данные терялись, маршруты не оптимизировались, клиенты жаловались на отсутствие прозрачности. Наша задача — собрать единую платформу с нуля: реал-тайм трекинг 10 000+ транспортных средств, унификация данных от пяти внешних провайдеров телематики и маршрутизации, REST API для клиентов заказчика и gRPC для внутренних сервисов.

Бизнес-цель простая: заказчик хотел уйти от ручного диспетчирования и дать своим клиентам (грузоотправителям) личный кабинет с трекингом, ETA, нотификациями — как у СДЭК или Яндекс Доставки, только для FTL-перевозок.

## 3. Процессы и церемонии

### Спринты и планирование

Спринты двухнедельные. Планирование — **понедельник утро**, 10:00, длится час-полтора. Оцениваем в **стори-поинтах**, покер через **Miro** (у Miro есть плагин для Planning Poker). Шкала: 1, 2, 3, 5, 8, 13. Всё что выше 8 — декомпозируем. Типичная задача на бэке — 3-5 SP.

### Дейли

Каждый день в **10:30**, 15 минут максимум. Формат стандартный: что сделал, что буду делать, есть ли блокеры. По вторникам и четвергам — живьём у доски, в остальные дни — Zoom. Если кто-то затягивал — Алексей мягко обрезал: "давайте после дейли обсудим детально".

### Груминг бэклога

Раз в неделю, **среда в 15:00**, час. Участвуют бэкендеры + продакт заказчика. Разбираем задачи на следующий спринт, уточняем acceptance criteria, определяем зависимости между сервисами.

### Ретро

Каждые две недели, **пятница в 16:00**, после завершения спринта. Формат — **Start/Stop/Continue** в Miro. Реальные темы, которые поднимались:

- "Давайте перестанем деплоить в пятницу после 15:00" — после инцидента когда Денис задеплоил в пятницу вечером, а в субботу утром посыпались алерты.
- "Нужны acceptance criteria от заказчика ДО начала спринта, а не в процессе" — продакт заказчика иногда приносил уточнения в середине спринта.
- "Начинаем писать ADR (Architecture Decision Records) для крупных решений" — моя инициатива, чтобы не объяснять по три раза почему выбрали Kafka а не Redis Streams.

### Правила команды

- **Не деплоим в пятницу после 15:00** и в предпраздничные дни.
- **Минимум 2 аппрува** на PR, один обязательно от сеньора (я или Максим).
- PR блокируется если: нет тестов на новую логику, линтер не прошёл, нет описания что и зачем.
- Критичные сервисы (трекинг, интеграции) — обязательно моё или Алексея ревью.

## 4. Инженерные практики

### Код-ревью

Два аппрува обязательно. Для некритичных сервисов — любые два бэкендера. Для трекинга, интеграций, всего что связано с Kafka — обязательно я или Алексей. На что смотрим:

- Правильность обработки ошибок (в Go это критично — не теряем ли ошибку, не логируем ли дважды).
- Конкурентность: правильное использование каналов, мьютексов, нет ли горутин-утечек.
- Контракты: совместимость gRPC/REST-контрактов, обратная совместимость.
- SQL: нет ли N+1, правильные ли индексы используются, корректна ли миграция.

### Тестирование

- **Юнит-тесты:** **testify** (assert + require), моки через **mockery** (генерация из интерфейсов). Покрытие бизнес-логики — 75-80%. На чистых функциях — table-driven tests. Race detector обязателен: `go test -race ./...` в CI.
- **Интеграционные тесты:** **testcontainers-go** — поднимаем PostgreSQL, Redis, Kafka в Docker-контейнерах. Тестируем реальное взаимодействие с БД, проверяем миграции, Kafka consumer/producer. Запускаются отдельным стейджем в CI, дольше юнитов (2-3 минуты), но ловят то что юниты не ловят.
- **QA на стейдже:** Наталья прогоняет функциональные сценарии после деплоя. Smoke-автотесты на Python проверяют основные flows: создание заказа → трекинг → нотификация.

### CI/CD

**GitLab CI**, пайплайн:

1. **lint** — `golangci-lint run` (errcheck, govet, staticcheck, gosec, ineffassign, misspell)
2. **unit tests** — `go test -race -coverprofile=coverage.out ./...`, порог покрытия 70%
3. **integration tests** — testcontainers, отдельный runner с Docker-in-Docker
4. **build** — multi-stage Docker: `golang:1.22-alpine` → `scratch`, `CGO_ENABLED=0`, итоговый образ ~20-25MB
5. **push** — образ в GitLab Container Registry с тегом `$CI_COMMIT_SHA`
6. **deploy staging** — автоматически через `helm upgrade`, Helm-чарт в отдельном репозитории
7. **deploy prod** — ручной триггер (manual approval), только после QA sign-off

**Rollback:** `helm rollback <release> <revision>`. Держим последние 5 ревизий. За два года откатывались раза три — один раз серьёзно (сломали Kafka consumer, подробнее в секции инцидентов).

### Логирование

**Библиотека:** **zap** (uber-go/zap). В hot path (обработка телематических событий) — `Logger` без аллокаций. В менее критичных местах — `SugaredLogger` для удобства. Формат — JSON. Уровни: debug (только локально и стейдж), info, warn, error.

**trace_id** прокидывается через `context.Context`. В каждом gRPC-вызове trace_id приходит из OpenTelemetry middleware и добавляется в каждую строку лога через `zap.String("trace_id", ...)`. Для HTTP — аналогично, middleware извлекает из заголовков W3C Trace Context.

**Инфраструктура:** **ELK** — Fluent Bit как DaemonSet в K8s собирает stdout контейнеров, шлёт в Elasticsearch, визуализация в Kibana. Основные дашборды: error rate по сервисам, поиск по trace_id, логи конкретного пода.

### Мониторинг и метрики

**Prometheus + Grafana**. Библиотека — **prometheus/client_golang**, эндпоинт `/metrics` на каждом сервисе.

Ключевые метрики:

- `grpc_server_handling_seconds` — латенсии gRPC-вызовов (histogram, P50/P95/P99)
- `http_request_duration_seconds` — латенсии REST API
- `http_requests_total` / `grpc_server_handled_total` — RPS, разбивка по status code и методу
- `kafka_consumer_lag` — отставание консьюмеров (кастомная метрика)
- `tracking_events_processed_total` — количество обработанных телематических событий
- `go_goroutines` — количество горутин (для детекта утечек)
- `process_resident_memory_bytes` — потребление памяти

**Дашборды:** общий overview (RPS, латенсии, error rate всех сервисов), отдельные дашборды на трекинг-сервис и Kafka (consumer lag, throughput, partitions).

### Трейсинг

**OpenTelemetry SDK → Jaeger**. Библиотеки: `go.opentelemetry.io/otel` + `otelgrpc` + `otelhttp`. Trace context прокидывается через `context.Context` внутри сервиса и через W3C Trace Context заголовки между сервисами. Для Kafka — trace_id записывается в headers Kafka-сообщения, consumer его извлекает и восстанавливает контекст.

На собесе: "Jaeger очень помог когда дебажили тормоза в цепочке трекинг → маршрутизация → аналитика. Видели в Jaeger что 80% латенсии — это один SQL-запрос в сервисе аналитики, который не попадал в индекс. Без трейсинга искали бы часами."

### Алерты

**Alertmanager (Prometheus) → Telegram** (канал `#tracking-alerts`). Дежурный реагирует в течение SLA.

Пороги:

- Error rate > 5% за 5 мин → **warning**
- Error rate > 15% за 5 мин → **critical**
- P99 латенсия REST API > 2 сек → **warning**
- P99 латенсия gRPC > 500ms → **warning**
- Сервис не отвечает на `/health` 3 мин → **critical**
- `kafka_consumer_lag` > 5000 → **warning**
- `kafka_consumer_lag` > 20000 → **critical**
- `go_goroutines` > 10000 → **warning** (возможная утечка)

## 5. Жизненный цикл задачи

Пример: **"Реализация единого адаптер-слоя для интеграции с 5 внешними провайдерами телематики и маршрутизации"** — одно из ключевых достижений.

### Груминг

На грумминге продакт заказчика объяснил боль: у них пять провайдеров телематики (два — REST API, два — SOAP, один — проприетарный протокол поверх TCP). Каждый возвращает координаты, скорость, статус в своём формате. Диспетчеры вручную смотрели в пяти разных интерфейсах. Нужен единый поток данных.

Я предложил архитектуру: **Adapter Pattern** — по адаптеру на каждого провайдера, общий интерфейс `TelematicsProvider`, и сервис-оркестратор который агрегирует и нормализует данные в единую модель.

### Планирование и оценка

На планировании декомпозировали: общий интерфейс + маппинг моделей (3 SP), REST-адаптеры (5 SP за два), SOAP-адаптеры (8 SP — SOAP в Go это боль), TCP-адаптер (5 SP), оркестратор + retry/circuit breaker (5 SP), интеграционные тесты (3 SP). Итого ~29 SP, растянули на два спринта.

### Декомпозиция

Первый спринт: общий интерфейс, REST-адаптеры, юнит-тесты. Второй: SOAP-адаптеры (здесь я использовал `encoding/xml` и кастомную обёртку, потому что Go-библиотеки для SOAP — боль, **etree** для парсинга XML помог), TCP-адаптер, оркестратор с **go-retryablehttp** (HashiCorp) для exponential backoff к ненадёжным REST-провайдерам.

### Разработка

Начал с определения gRPC-контракта сервиса интеграций — `.proto`-файл с `TelematicsEvent` (vehicle_id, lat, lon, speed, timestamp, provider, raw_payload). Потом общий интерфейс:

```go
type TelematicsProvider interface {
    FetchEvents(ctx context.Context, since time.Time) ([]TelematicsEvent, error)
    Name() string
}
```

Каждый адаптер реализует этот интерфейс. Оркестратор запускает все адаптеры параллельно через `errgroup`, собирает результаты, нормализует и публикует в **Kafka** (топик `tracking.telematic-events`). Для SOAP-провайдеров пришлось писать кастомный маршалинг XML — стандартный `encoding/xml` не справлялся с их WSDL. Потратил на это дня два, но в итоге сделал чистый слой абстракции.

### Тестирование

Юнит-тесты на каждый адаптер: мокаю HTTP-ответы через `httptest.NewServer`, проверяю маппинг в единую модель. Интеграционные тесты — testcontainers с Kafka, проверяю что события доходят до топика с правильной структурой. Покрытие сервиса интеграций — 82%.

### Ревью

PR на ~1200 строк, разбил на три: контракт + интерфейс, адаптеры, оркестратор. Первый PR Алексей одобрил быстро. На втором Максим нашёл потенциальную горутин-утечку: я не закрывал body в одном из REST-адаптеров при ошибочном статусе — классика Go. Исправил, добавил в линтер-конфиг правило `bodyclose`.

### QA

Наталья тестировала на стейдже: отправляла запросы через Postman-коллекцию, проверяла что данные от всех пяти провайдеров агрегируются корректно. Нашла edge case: один провайдер иногда возвращал координаты 0,0 (баг на их стороне) — я добавил валидацию через **go-playground/validator** на уровне маппинга.

### Деплой

Задеплоили на стейдж через GitLab CI автоматом. Два дня на стейдже — Наталья гоняла smoke-тесты, я мониторил метрики. Потом ручной триггер на прод. Раскатывали через **rolling update** в K8s, `maxUnavailable: 0, maxSurge: 1` — ни одного запроса не потеряли.

### Мониторинг

После деплоя на прод следил за: error rate интеграционного сервиса (первые 2 часа — 0.3%, норма), consumer lag Kafka (не рос), латенсии gRPC-вызовов к сервису трекинга (P99 осталась на уровне 45ms). Через неделю перестал активно следить — всё стабильно.

## 6. Реагирование на инциденты

### Дежурства

Дежурим по ротации: бэкендеры по неделе, DevOps-ы параллельно. У дежурного телефон на алертах (Telegram-бот + PagerDuty-подобная интеграция на базе Alertmanager). Дежурство — с 9:00 до 21:00, ночью — только на critical (звонок).

### Градация severity

- **S1 (Critical):** система полностью недоступна или теряются данные. Реакция — 15 минут. Пример: Kafka consumer не обрабатывает сообщения, данные трекинга не обновляются.
- **S2 (Major):** деградация функционала, часть пользователей затронута. Реакция — 30 минут. Пример: один из провайдеров телематики не отвечает, трекинг работает по 4 из 5 источников.
- **S3 (Minor):** некритичная проблема, workaround есть. Реакция — 4 часа. Пример: дашборд аналитики тормозит на больших временных диапазонах.
- **S4 (Low):** косметика, документация. Следующий спринт.

### Алгоритм реакции

1. Алерт приходит в Telegram → дежурный подтверждает что видит (реакция в чате)
2. Смотрим Grafana-дашборд → определяем какой сервис затронут
3. Идём в Kibana → ищем по trace_id первую ошибку
4. Если нужно — Jaeger → смотрим где в цепочке сломалось
5. Если проблема в коде — hotfix PR с ускоренным ревью (один аппрув достаточно для hotfix)
6. Если проблема в инфре — DevOps подключается, рестарт пода или rollback Helm-релиза
7. Post-mortem в течение 48 часов: что случилось, timeline, root cause, action items

### Пример инцидента

**Инцидент: Kafka consumer lag вырос до 50 000, трекинг данные отставали на 8 минут.**

Четверг, ~14:00. Алерт в Telegram: `kafka_consumer_lag > 20000 [CRITICAL]`. Я был дежурным.

**Что произошло:** Накануне Денис задеплоил обновление сервиса телематики — добавил новое поле в обработку событий. Но в обработчике был вызов к Redis для дедупликации, и он случайно убрал `context.WithTimeout` — при проблемах с Redis обработка каждого сообщения зависала на дефолтный таймаут net/http (нет таймаута = ждёт бесконечно).

**Как нашли:** Grafana показала что consumer lag растёт линейно с ~14:00. В Kibana нашёл что сервис перестал логировать обработанные события. В Jaeger увидел спаны длиной 30+ секунд на вызовах к Redis. Проверил Redis — тот был жив, но сервис не ставил таймаут на `Get` операции. Один из Redis нод кратковременно тупил (GC pause), и без таймаута горутины зависали.

**Как починили:** Откатил на предыдущую версию через `helm rollback` (2 минуты). Lag начал уменьшаться, через 15 минут нагнал. Потом Денис добавил `context.WithTimeout(ctx, 100*time.Millisecond)` на все Redis-вызовы, я зааппрувил hotfix, задеплоили.

**Что сделали чтобы не повторилось:**

- Добавили линтер-правило: запретили вызовы `redis.Get`/`Set` без явного таймаута в контексте (кастомный golangci-lint check).
- Добавили интеграционный тест: consumer должен обработать 1000 сообщений за <10 секунд с мокнутым "медленным" Redis.
- Написали ADR: "Все внешние вызовы (Redis, HTTP, gRPC) обязательно с таймаутом через context".

- **Мессенджер:** корпоративный Mattermost (ЛАНИТ не использует Slack из-за санкций). Каналы: `#tracking-dev`, `#tracking-alerts`, `#tracking-deploys`.
- **Звонки:** Zoom для удалённых дней, Google Meet как fallback.

### Взаимодействие с QA

Перед передачей задачи Наталье я:

1. Обновляю **Swagger-документацию** (генерируется через **swaggo/swag**, хостится на стейдже по `/swagger/`)
2. Если API изменился — обновляю **Postman-коллекцию** в общем workspace с описанием сценариев
3. Для gRPC — кладу обновлённые `.proto` файлы в shared-репозиторий, пишу в Mattermost какие методы затронуты
4. Описываю в Jira-тикете acceptance criteria и edge cases которые покрыл тестами

### Взаимодействие с тимлидом

1-на-1 с **Алексеем** — раз в две недели, 30 минут. Обсуждаем: мои текущие задачи, архитектурные решения которые я хочу протолкнуть, фидбэк по менторингу Артёма, карьерные вопросы. Формат неформальный — иногда за кофе в офисе, иногда по Zoom.

По архитектурным вопросам — ad-hoc созвоны. Если я проектирую новый сервис или меняю контракт, который затрагивает другие команды — сначала пишу RFC-документ в Confluence, потом обсуждаем на созвоне с Алексеем и заинтересованными.
### Визуализация архитектуры

- **Miro** — для высокоуровневых архитектурных схем, C4-диаграмм, флоу данных. Используем на грумингах и при обсуждениях с заказчиком.
- **draw.io** — для детальных sequence-диаграмм и ER-диаграмм. Экспортируем в PNG, вставляем в Confluence.
- Диаграммы хранятся в Confluence, привязаны к соответствующим ADR. Раз в квартал проверяем актуальность — обычно на ретро кто-то напоминает что "схема в Confluence устарела".
