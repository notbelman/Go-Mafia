# Go-стек: справочник дефолтов

Этот файл — справочник базовых технологий для генерации легенды. Правило простое: если технология указана в резюме — берём из резюме. Если не указана, но категория нужна для легенды — берём дефолт из этого файла.

При генерации легенды ОБЯЗАТЕЛЬНО указывай конкретные библиотеки и обосновывай выбор (кратко, как на собесе).

---

## Брокер сообщений

**Дефолт:** Kafka (segmentio/kafka-go) **Почему дефолт:** Kafka — стандарт для event-driven микросервисов. segmentio/kafka-go — чистый Go, без CGO, простой деплой в Docker/K8s. **Почему не другие:**

- confluent-kafka-go — требует CGO и librdkafka, усложняет сборку и кросс-компиляцию в Docker multi-stage
- Sarama — устаревающий API, сложнее в использовании
- franz-go — хороший, но менее распространён, меньше примеров
- RabbitMQ — другая модель (очереди vs лог), для event sourcing и стриминга Kafka лучше
- NATS — проще, но менее зрелая экосистема для аналитики и replay

**Если в стеке Redis и нет Kafka/NATS/RabbitMQ:** использовать Kafka

---

## Логирование (библиотека)

**Дефолт:** zap (uber-go/zap) **Почему дефолт:** структурированный JSON, высокая производительность (без рефлексии, sync.Pool), стандарт де-факто в production Go-сервисах. **Почему не другие:**

- slog — стандартная библиотека (Go 1.21+), хороший выбор для новых проектов, но пока менее распространён в production
- zerolog — быстрее zap, но меньше экосистема
- logrus — устаревает, медленнее

**На собесе:** "Использовали zap в режиме Logger (не Sugared) для hot path, SugaredLogger для менее критичных мест. Формат — JSON, уровни: debug/info/warn/error."

---

## Стек логирования (инфраструктура)

**Дефолт:** ELK (Elasticsearch + Fluent Bit + Kibana) **Почему дефолт:** зрелый стек, стандарт в энтерпрайзе. Fluent Bit как DaemonSet в K8s, Elasticsearch для хранения и поиска, Kibana для визуализации. **Альтернатива:** Loki + Grafana — легче, дешевле, но менее мощный поиск. **Правило:** если в стеке уже есть Grafana — можно использовать Loki. Если ничего не указано — ELK.

---

## Мониторинг и метрики

**Дефолт:** Prometheus + Grafana **Библиотека:** prometheus/client_golang, эндпоинт `/metrics` **Почему дефолт:** стандарт для Kubernetes-окружений, pull-модель, PromQL. **Альтернатива:** Datadog, VictoriaMetrics — но Prometheus + Grafana бесплатны и самые распространённые.

**Базовые метрики для любого сервиса:**

- `http_request_duration_seconds` / `grpc_server_handling_seconds` — латенсии (histogram, P50/P95/P99)
- `http_requests_total` / `grpc_server_handled_total` — RPS, разбивка по status code
- `go_goroutines` — количество горутин
- `process_resident_memory_bytes` — потребление памяти

## Трейсинг

**Дефолт:** OpenTelemetry SDK → Jaeger **Почему дефолт:** OTel — vendor-neutral стандарт. Jaeger — самый популярный бэкенд для трейсов в open-source. **Библиотеки:** go.opentelemetry.io/otel + otelgrpc + otelhttp **Альтернатива:** Tempo (Grafana) — если уже есть Grafana-стек.

**На собесе:** "Использовали OpenTelemetry SDK, trace context прокидывали через context.Context внутри сервиса и через W3C Trace Context заголовки между сервисами. Бэкенд — Jaeger."

---

## Web-фреймворк / HTTP

**Дефолт:** chi **Почему дефолт:** легковесный, совместим с net/http (стандартные middleware работают), достаточно для REST API. **Почему не другие:**

- Gin — популярнее, но свой контекст, не совместим с net/http middleware напрямую
- Echo — хороший, но менее распространён
- Fiber — на fasthttp, не совместим с net/http, нет HTTP/2
- net/http (Go 1.22+) — достаточен для простых случаев, но нет middleware-чейнинга из коробки

**Правило:** если в стеке указан Gin — используем Gin. Если указан REST API без конкретного фреймворка — chi.

---

## PostgreSQL драйвер

**Дефолт:** pgx (jackc/pgx/v5) **Почему дефолт:** нативный, быстрее lib/pq, поддержка PostgreSQL-специфичных типов (JSONB, arrays), batch queries. **Почему не lib/pq:** медленнее, менее активная разработка.

---

## SQL: ORM vs query builder

**Дефолт:** sqlx (jmoiron/sqlx) поверх pgx/stdlib **Почему дефолт:** контроль над SQL, без ORM-магии, StructScan удобнее чем ручной Scan. Для сеньора на собесе sqlx — более "взрослый" выбор чем GORM. **Почему не другие:**

- GORM — ORM-магия, хуже контроль над запросами, производительность ниже
- sqlc — генерация кода из SQL, хороший подход, но менее распространён
- чистый pgx — можно, но больше бойлерплейта

**На собесе:** "Использовали sqlx поверх pgx — полный контроль над SQL, никакой магии. Для сложных запросов это критично — знаешь какой точно SQL уходит в базу."

---

## Миграции БД

**Дефолт:** golang-migrate **Почему дефолт:** CLI + библиотека, поддерживает PostgreSQL/MySQL/SQLite/ClickHouse, формат up/down SQL файлов. **Альтернатива:** goose — тоже хороший, миграции на Go или SQL.

---

## Тестирование

**Дефолт:**

- Assertions: testify (assert + require)
- Моки: mockery (генерация из интерфейсов, совместимость с testify/mock)
- Интеграционные: testcontainers-go (PostgreSQL, Redis, Kafka в Docker)
- Race detector: `go test -race ./...`
- Покрытие: 70-80% на бизнес-логике

**Почему не gomock:** больше бойлерплейта, mockery проще для типичных случаев.

---

## Валидация

**Дефолт:** go-playground/validator **Почему:** стандарт де-факто, struct tags, интеграция с Gin из коробки.

---

## Конфигурация

**Дефолт:** viper **Почему:** поддержка env + yaml + флаги, unmarshal в структуру, hot reload. **Альтернатива:** cleanenv, koanf — проще, если не нужен hot reload и множество источников.

---

## HTTP-клиент

**Дефолт:** net/http + go-retryablehttp (HashiCorp) для внешних интеграций **Почему:** стандартный клиент для простых случаев, retryablehttp — exponential backoff для ненадёжных внешних API. **Альтернатива:** resty — fluent API, удобнее для REST-клиентов.

---

## Redis клиент

**Дефолт:** go-redis (redis/go-redis/v9) **Почему:** type-safe API, Cluster/Sentinel, Pub/Sub, Streams, context.Context. **Почему не redigo:** устаревает, нет type-safe команд.

---

## gRPC

**Дефолт:** google.golang.org/grpc **Почему:** единственный реальный вариант. Плюс protoc-gen-go + protoc-gen-go-grpc для кодогенерации. **Interceptors:** обязательно упоминать — логирование, трейсинг, авторизация через unary/stream interceptors.

---

## DI (Dependency Injection)

**Дефолт:** wire (Google) **Почему:** compile-time, нет рефлексии в рантайме, ошибки на этапе компиляции. **Альтернатива:** fx (Uber) — runtime DI, проще для старта, но ошибки в рантайме. **Правило:** если в резюме нет упоминания DI — можно не включать в легенду. Не каждый проект использует DI-фреймворк, многие обходятся ручной инъекцией через конструкторы.

---

## UUID

**Дефолт:** google/uuid (v4 для обычных ID) **Для первичных ключей в БД:** рассмотреть UUID v7 (gofrs/uuid) — сортируемый по времени, меньше фрагментация индекса.

---

## CLI (если релевантно)

**Дефолт:** cobra (+ viper для конфигов) **Почему:** стандарт де-факто, используется в kubectl, docker, hugo.

---

## JWT (если есть авторизация)

**Дефолт:** golang-jwt/jwt **Алгоритм:** RS256 для микросервисов (асимметричный, публичная верификация), HS256 для монолита.

---

## WebSocket (если релевантно)

**Дефолт:** gorilla/websocket **Альтернатива:** nhooyr/websocket — более современный, context-aware, concurrent-safe writes.

---

## CI/CD

**Дефолт:** GitLab CI **Почему:** самый распространённый в российских компаниях, встроенный Container Registry. **Альтернатива:** GitHub Actions — если компания использует GitHub.

**Стандартный пайплайн:**

1. lint (golangci-lint)
2. unit tests (go test -race ./...)
3. integration tests (testcontainers)
4. build (multi-stage Docker)
5. deploy staging (auto)
6. deploy prod (manual approval)

---

## Контейнеризация

**Дефолт:** Docker + Kubernetes + Helm **Docker:** multi-stage build, golang:1.22-alpine → scratch/alpine, CGO_ENABLED=0, ~15-25MB итоговый образ. **K8s:** Helm-чарты, HPA для автоскейлинга, readiness/liveness probes на /health. **Rollback:** helm rollback.

---

## Линтер

**Дефолт:** golangci-lint (без вариантов) **Включённые линтеры:** errcheck, govet, staticcheck, gosec, ineffassign, misspell.

---

## Алерты

**Дефолт:** Alertmanager (Prometheus) → Telegram **Альтернатива:** Grafana Alerting → Telegram/Slack **Базовые пороги:**

- Error rate > 5% за 5 мин → warning
- Error rate > 15% за 5 мин → critical
- P99 латенсия > 2 сек → warning
- Сервис не отвечает на healthcheck 3 мин → critical
- Kafka consumer lag > 5000 → warning

---

## Профилирование

**Дефолт:** pprof (встроенный) **Эндпоинт:** `/debug/pprof/` (отключён на проде или за авторизацией) **Continuous profiling:** Pyroscope (если нужен continuous profiling в production) **На собесе:** "pprof использовали для анализа CPU и memory профилей при оптимизации. Типичный кейс — нашли goroutine leak через /debug/pprof/goroutine, оказалось HTTP-клиент не закрывал body."

**Дефолт:** go-ethereum (geth) — github.com/ethereum/go-ethereum **Когда включать:** только если в стеке или домене есть blockchain, crypto, DeFi, Web3. **Не включать по умолчанию.**
